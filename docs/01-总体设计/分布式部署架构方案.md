## 0. 阶段 0 契约冻结（实现前必须完成）

**本方向已确认可作为架构基线，但实现前必须先冻结以下契约，否则一落地就会与现有代码撞车。**

| # | 冻结项 | 说明 |
|---|--------|------|
| 1 | **UploadBatch / UploadItem schema** | 精确 JSON 结构，逐项 ACK，UploadItem 携带**完整 envelope**（含 device_type/scan_rate/contract_version/qualities）+ **上传会话身份** (upload_session_id, local_seq) |
| 2 | **StreamEnvelope v1/v2 两版本契约表** | v1 七字段（device_code/device_type/group_code/scan_rate/ts/config_version/values）；v2 = v1 + contract_version=2 + qualities；Ingest 透传 v2，Writer 已支持；明确编码/解码/必填字段/非法版本行为 |
| 3 | **Redis Stream / latest 兼容键名与字段** | Stream 复用现有 collector 格式；latest 保持一 var_id 一个 JSON，扩展为 `{"v","t","q","e"}`，**不新增 hash 字段** |
| 4 | **固定 batch_id + 逐项 ACK + 错误码表** | batch_id 在 collector 写 outbox 时生成永不变；rejected 按 terminal/retryable/401-403/429-5xx 分类处理 |
| 5 | **版本双轨：节点级 revision + 组级 config_version** | 节点级 `desired/applied_revision` 用于配置同步；组级 `config_version` 随每条 item/entry 传。删 mapping_version，不删节点级 revision |
| 6 | **存储映射物理坐标（point_storage_mapping）** | 含 point_id/device_code/device_type_code/stable_name/child_table/group_code/td_column_name/var_type，永久不变；唯一约束 (device_code, td_column_name)；点位创建与 mapping 插入同事务；全量回填+校验+**差异非零阻断上线** |
| 7 | **latest 写入规则** | 一 var_id 一 JSON，Lua 用 cjson.decode 比较 t/e，incoming.ts>现值 或 (等值且高 epoch) 才更新 |
| 8 | **幂等去重：严格按序+单批次在途** | 去重身份 `(node_uuid, upload_session_id, local_seq)`；upload_session_id 由边缘生成随机 UUID；中心只记录 high_watermark；严格按序上传（seq==hw+1 接收，seq>hw+1 拒绝）；单批次在途（无并发，无 gap） |
| 9 | **迁移裁决：严格时间窗 + 时钟偏差冻结** | 旧 epoch 只接受 ts<cutover_at，新 epoch 只接受 ts>=cutover_at；不贯通 Stream/Writer/TDengine；**冻结 max_clock_skew 阈值（默认±30s）+ 迁移时序（B 提前启动、A 延后停止）+ 超偏差门禁规则** |
| 10 | **ACK durability 语义** | **"中心已接收"**：Redis XADD 成功即 ACK，不等 Writer/TDengine 落盘；Redis AOF everysec 可能丢失 ~1s 数据（可接受）；outbox 最大离线期参数；含容量公式+内存预算 |
| 11 | **节点认证强度** | mTLS 或对 method/path/timestamp/nonce/body_hash 签名 + 重放校验 |
| 12 | **Uploader 单例围栏** | 每节点只能运行一个 Uploader，**Windows 用 OS mutex**（推荐），跨平台用文件锁 |
| 13 | **容灾策略：放弃+重新开始** | Redis 全丢/队列损坏/积压超限 → 放弃旧数据，生成新 upload_session_id，从最新采集重新开始；**不尝试补传历史**，不停止系统 |
| 14 | **三个固定角色安装包** | 统一代码仓库构建中心式、分布式边缘、分布式中心三个包；删除运行时角色切换及管理页面开关 |
| 15 | **采集调度与读取超时** | 保留现有完成后调度、同设备单请求在途语义；`read_timeout_ms` 可选，中心式按本机配置、分布式按边缘节点配置，未配置沿用驱动默认 |
| 16 | **自适应上传节拍** | 点位 `scan_rate` 保持可配置；本节点 `min(scan_rate)` 决定实时节拍；混合频率共用一条严格有序链路；离线积压连续追赶 |

完成上述冻结后，"中心 Ingest + 边缘 SQLite/Uploader"的总体路线即可开工。**中心 MySQL 做配置真源、边缘 SQLite 只存本机快照、全局业务数据由中心提供，这三项已确认合理。**

**v8 简化协议（删除容灾复杂机制，聚焦分布式主链路）**：

## 1. 背景与目标

现有部署是**单机集中式**：一台机器上 collector 采集 -> Redis Stream -> writer 入库 -> TDengine，配置与权限来自 MySQL，Web/App 经 Backend 读 MySQL + TDengine。

随着现场设备规模增长、地理分布变广，需要把**采集(collector)与数据上传下沉到多台边缘机**，每台边缘只负责一部分设备，数据统一汇聚到中心。目标：

- **横向扩展采集能力**：设备分摊到多台边缘机，单机压力下降。
- **就近采集**：边缘贴近现场设备，网络链路短、稳定。
- **中心统一**：配置、权限、历史数据、可视化仍以中心为唯一真源。
- **零迁移成本**：现有单机用户默认不受影响,不改配置就是原来那套。
- **多管理端**：几台领导电脑都能装 App 做管理，不只中心机一台。
- **轻量边缘**：边缘机不再需要 Redis/MySQL/TDengine，只需 SQLite + 采集/上传组件。

## 2. 总体架构与数据流

### 2.1 三种部署形态下的 Writer 语义统一

| 部署形态 | 数据流 | Writer 职责 |
|---------|--------|------------|
| **单机(现状)** | Collector -> 本地 Redis Stream -> **Writer** -> TDengine | 读 MySQL 映射，写 TDengine |
| **分布式-边缘** | Collector -> SQLite outbox -> **Uploader** -> 中心 Ingest | 边缘无 Writer,用 Uploader 上传 |
| **分布式-中心** | Ingest -> 中心 Redis Stream -> **Writer** -> TDengine | 读 MySQL 映射，写 TDengine |

**关键原则**: Writer 这个名字只留给"读 MySQL 映射、写 TDengine"的组件。边缘的数据转发组件叫 **Uploader**(上传器)，不叫 writer，避免语义混淆。

**Redis 之后完全复用**：中心式 Collector 和分布式 Ingest 虽然进入 Redis 前的路径不同，但从 Redis Stream -> Writer -> TDengine 的消费、映射和入库链路一致，不维护第二套 Writer。

### 2.2 StreamEnvelope v1/v2：共享的 Redis 契约（P0 核心）

**必须复用现有 collector 的 Redis 格式，Ingest 绝不另造一套。** 现有 collector 与 Writer 已支持两版本契约：

#### 契约表（冻结）

| 项 | v1（现状默认） | v2（Q2 质量码） |
|---|---|---|
| **Stream 键** | `rt:stream:{device_type}:{group_code}:{shard_no}`<br/>分片: `shard_no = crc32(device_code) % shard_count` | 同 v1 |
| **Stream 字段** | `device_code, device_type, group_code, scan_rate, ts, config_version, values`<br/>`values` = msgspec.json 编码的 `{var_id: value_str}`，已过滤 STRING/is_storage=0 | v1 全部字段 +<br/>`contract_version: "2"`<br/>`qualities: {var_id: quality_code}` (msgspec.json) |
| **Latest 键** | `rt:latest:{device_code}:{group_code}` | 同 v1 |
| **Latest 字段** | 每个 var_id 一个 JSON: `{"v": value_str, "t": ts_ms, "q": quality_int, "e": epoch}`<br/>**不新增 `var_id:ts` 之类的独立 hash 字段** | 同 v1（`q` 字段 v1 时可为 0 或省略） |
| **UploadItem 必填** | `batch_id, local_seq, assignment_epoch, device_code, device_type, group_code, scan_rate, ts, config_version, values` | v1 全部 +<br/>`contract_version: 2, qualities` |
| **Writer 支持** | `writer/consumer.py:515` 已支持（contract_version 缺省=1） | `writer/consumer.py:552-650` 已支持（=2 时解析 qualities，严格校验键对齐） |
| **Ingest 上传错误** | **Ingest HTTP 响应**：身份/序号合法但业务校验失败 → 200 + rejected_consumed/stale_config_warning，推进 hw | 同 v1 |
| **Writer DLQ** | **Writer 消费 Stream**：遇到非法 entry（未知 contract_version/malformed） → 写入 DLQ，继续消费下一条 | 同 v1 |
| **Ingest 行为** | **透传 v2**：UploadItem 带什么版本就写什么版本到 Stream（不降级） | 同 v1 |
| **编码库** | `msgspec.json.encode` (collector/writer 现状) | 同 v1 |

**阶段 0 行动**：提取一个共享模块 `StreamEnvelope`，封装上述两版本的 stream key 生成、latest key 生成、分片算法、字段编码、latest JSON 编解码。由中心式 Collector 与 Central Ingest **共用同一份代码**，保证格式一字不差。

**关键点**：
- **Latest 不新增 hash 字段**：保持 `ws_push.py:99-106` 的 hgetall 遍历契约，每 var_id 一个 `{"v","t","q","e"}` JSON，否则 `123:ts` 会被当成假点位推给 App
- **Ingest 透传 v2 不降级**：UploadItem 带 contract_version=2 + qualities 时，直接写 v2 到 Stream；Writer 已支持解析
- **Q2 前后兼容**：Q2 未开启时，UploadItem 省略 contract_version/qualities（默认 v1）；Q2 开启后必填 v2

### 2.4 Central Ingest 的职责边界

**Ingest 负责**（顺序执行，逐项处理）：

1. 验证节点 mTLS/签名 + 节点 approved 状态
2. 逐项校验设备归属 + assignment_epoch + **严格时间窗**（见 §7）
3. 校验 config_version、数据格式、时间戳、质量码（envelope 自带，不查库补齐）
4. 逐项 local_seq 幂等判断（节点级 high_watermark 严格按序，Redis Lua 原子，见 §8.2）
5. 用 StreamEnvelope v2 写中心 Redis Stream（复用现有键格式）
6. 更新 rt:latest（一 var_id 一 JSON，逐点时间戳比较，见 §8.2）
7. （阶段3新增）PUBLISH rt:change 触发实时推送
8. 逐项返回 ACK（按错误码表分类，见 §8.1）

**Ingest 不负责**：
- 不直写 TDengine（交给中心 Writer）
- 不做业务查询、不管用户权限、不做长时间数据转换

**部署方式**：
- 第一阶段：与 Backend 同机，独立进程/端口（`:8010`），经反向代理统一入口。
- 后续扩展：多个无状态 Ingest 实例，通过中心 Redis 汇聚。

### 2.5 边缘机组件清单

**需要**：Edge Agent（身份/心跳/配置同步）、Collector（采集）、Uploader（上传）、SQLite（配置缓存 + outbox）、边缘 App（本机运维；全局数据查中心）

**不再需要**：Redis、Writer、MySQL、TDengine、Backend（边缘 App 的本机运维接口由 Edge Agent 提供）

**禁止边缘直连中心 Redis**：Collector 必须先在同一进程内把采集结果持久化到本机 SQLite outbox，Uploader 再通过持久 HTTP 连接调用中心 Ingest。中心 Redis 只对中心组件开放；节点认证、限流、版本校验、session 围栏和逐项 ACK 全部收敛在 Ingest。

### 2.6 采集调度与读取超时（保留现状）

分布式边缘 Collector 复用现有采集任务模型和调度语义，不另造调度器：

- 同一设备、相同 `scan_rate` 的点位合并为一个采集任务，连续地址进一步合并为读取块。
- 不同设备按确定性相位错峰启动，避免同一时刻集中请求。
- 同一设备只允许一个读取请求在途；同设备其他周期任务遇到占用时跳过本周期。
- 执行时间小于采集周期时，等待剩余时间后开始下一轮。
- 执行时间大于等于采集周期时，本轮完成后立即开始下一轮，不切换为固定时间轴补点。
- 不同设备独立执行；单台慢设备不得形成等待全部设备完成的同步屏障。

示例：`scan_rate=100ms`、设备在 130ms 返回时，调度序列为 `0ms 发起 -> 130ms 返回并落 outbox -> 130ms 发起下一轮`。

新增可选采集设置 `read_timeout_ms`（正整数，单位毫秒），与点位 `scan_rate` 分离：

- `scan_rate` 继续按点位配置，表示期望采集频率；架构不冻结统一周期，也不把当前现场的 100ms 当作平台下限。
- `read_timeout_ms` 表示单次设备读取允许等待的最长时间。中心式安装包按本机 Collector 配置；分布式部署按边缘节点配置，同一节点内设备延迟相近，因此第一阶段无需再细分到设备级。
- 不规定统一默认毫秒值。`read_timeout_ms` 未配置时沿用各协议驱动现有默认超时；配置后才作为该 Collector/边缘节点的显式覆盖值。
- 允许 `read_timeout_ms > scan_rate`，两者不设硬性倍数约束；一次读取在途期间，同设备后续周期仍按现有规则跳过，不产生并发读取。
- 设置页面可按 `estimated_skipped_cycles = max(0, ceil(read_timeout_ms / min_scan_rate_ms) - 1)` 展示当前节点可能跳过的周期数，仅作影响提示，不阻止保存、不静默裁剪用户配置。
- 在超时范围内返回的数据正常接收，并保留设备源时间戳；无源时间戳时记录边缘采集时间。
- 超时后本次读取失败，不伪造值，记录超时指标并进入现有设备错误/重连流程。
- 调度层逻辑超时与协议驱动底层 socket/client 超时必须同时生效。阻塞线程中的底层调用实际结束前不得释放同设备在途锁，避免迟到响应与下一请求并发污染连接。

## 3. 三个固定角色安装包

项目保持统一代码仓库，通过构建目标生成三个安装包；安装包在构建时裁定进程、页面与默认配置，安装后不通过运行时开关改变节点角色。

| 安装包 | 包含组件 | 页面边界 |
|--------|----------|----------|
| **中心式安装包** | App、Backend、Collector、Redis、Writer、MySQL、TDengine | 现有中心式业务页面，不包含边缘节点管理和分布式运行模块 |
| **分布式边缘安装包** | 边缘 App、Edge Agent、Collector、SQLite outbox、Uploader | 本机设备/采集状态、配置同步、离线积压和上传状态；不包含中心管理页面 |
| **分布式中心安装包** | 中心 App、Backend、Ingest、Redis、Writer、MySQL、TDengine | 完整中心业务页面，并包含所有边缘节点的注册、分配、状态和告警管理 |

**冻结原则**：

- 三个安装包共享核心代码和前端组件，不维护三套代码分支。
- 安装包角色固定：需要中心式就安装中心式包；需要分布式则分别安装分布式中心包和分布式边缘包。
- 删除运行时 `mode=standalone|center|edge` 角色切换和 `distributed_management_ui_enabled` 页面开关，避免角色误切换及无效配置组合。
- `center_url` 仅是分布式边缘包的连接参数，指向统一反向代理；`/api/*` 转 Backend、`/ingest/*` 转 Ingest。它不承担角色切换语义。

### 3.1 向后兼容

- 现有单机用户升级到中心式安装包后，Collector -> Redis -> Writer -> TDengine 行为保持不变。
- 分布式部署必须安装对应角色包，不通过修改配置把已安装实例变成另一角色。
- 角色变更通过卸载原角色包并安装目标角色包完成，数据迁移按独立运维流程执行。

## 4. 三类 App 页面策略

原则：**页面能力随安装包构建，不提供边缘/中心运行时切换；账号权限继续控制对应安装包内的菜单与操作。**

| App 形态 | 页面范围 | 数据来源 |
|----------|----------|----------|
| **中心式 App** | 现有设备、点位、实时、历史、告警、用户权限页面 | 本机 Backend |
| **分布式边缘 App** | 本机设备与采集状态、配置同步状态、SQLite 积压、Uploader 状态和本机日志 | 本地 Agent；需要全局实时/历史数据时经 `center_url` 查询中心 Backend |
| **分布式中心 App** | 中心式业务页面 + 全部边缘节点管理、注册审批、设备分配、积压/版本/在线状态和告警 | 中心 Backend |

- 三类 App 复用组件和类型定义，但由构建目标裁剪路由、菜单和随包资源。
- 边缘 App 不出现用户权限、全局节点管理及其他中心专属页面。
- 中心式 App 不包含 Edge Agent、Uploader、outbox 等分布式运行页面。
- 分布式中心 App 内的边缘管理页面始终随包存在，再由账号权限决定是否可见和可操作，不再使用独立功能开关。

**边缘 App 本机数据源（冻结）**：

- 边缘 App 不直接打开 SQLite，统一调用 Edge Agent 提供的本地 HTTP API；默认只监听 `127.0.0.1`，并使用随安装生成的本机访问凭据。
- 本机设备列表读取 Edge Agent 对 SQLite 配置快照的只读查询；只展示中心已分配到本节点的设备，配置编辑仍由中心 Backend 完成。
- 采集状态来自 Collector 运行指标/IPC，离线积压来自 SQLite outbox 聚合查询，上传状态来自 Uploader 运行状态，本机日志来自 Agent 日志接口。
- 建议固定本地接口边界：`/local/devices`、`/local/collector`、`/local/outbox`、`/local/uploader`、`/local/logs`。
- 中心断网时，上述本机页面继续可用；全局实时、历史及配置编辑页面明确显示“中心不可达”，不得影响本地采集、落 outbox 和后续补传。

> **重要区分**：边缘 App 的本机运维数据来自本地 Edge Agent，全局业务数据来自中心 Backend；边缘 Collector 只读取本地 SQLite 中分配给本节点的设备配置。三条路径职责分离。

## 6. 心跳与配置推送（拉模式，版本双轨）

**版本双轨制**（修复"组级 config_version 被当节点级修订号"）：

| 概念 | 层级 | 用途 | 来源 |
|------|------|------|------|
| `desired_revision` / `applied_revision` | **节点级** | 配置快照同步：中心期望版本 vs 边缘已应用版本 | 中心为每个节点维护 |
| `config_version` | **组级** | 随每条 UploadItem / Stream entry 传输 | `device_point_group`（现状） |

- **边缘 -> 中心 心跳**（轮询，非 WebSocket）：Edge Agent 固定间隔 POST，携带 `node_uuid / applied_revision / 本地 high_watermark / 边缘本地时间 / 运行状态`。
- **配置推送 = 拉模式**：
  - 中心改某节点配置后 `desired_revision + 1`。
  - 边缘心跳带 `applied_revision`，中心响应告知最新 `desired_revision` + checksum。
  - 版本不一致 -> 边缘拉取属于自己的设备清单（每组各自带组级 config_version），校验 checksum，**原子切换本地 SQLite**（复用现有热重载），成功后回报 `applied_revision`。
- **离线自主**：中心不可达时，已审批且本地有有效配置快照的节点**继续采集缓存**；只有首次注册且 SQLite 为空的节点才进入等待。

## 7. 设备绑定与迁移（所有权围栏 + 严格时间窗）

### 7.1 assignment_epoch 的正确语义

**epoch 不是去重键，而是所有权围栏**，回答"这台设备当前归谁采集"。

- 绑定关系：`device_assignment(device_id, node_id, assignment_epoch, effective_at, cutover_at)`。
- **保留 assignment 历史**：主键至少含 `(device_id, assignment_epoch)`，不覆盖旧记录。

### 7.2 迁移握手流程（严格时间窗，消除重叠）

设备从节点 A 迁到 B，走**四步握手**：

```
1. 中心发新 epoch (assignment_epoch + 1，记录到 device_assignment，预设 cutover_at)
2. 新节点 B 应用配置并确认 (ACK)
3. 中心记录 cutover_at 生效 (以中心时间为准，不信边缘时钟)
4. 旧节点 A 停止采集并确认 (ACK)
```

**裁决规则（严格时间窗，彻底消除重叠）**：
- 旧 epoch 的数据：只接受 `ts < cutover_at`。
- 新 epoch 的数据：只接受 `ts >= cutover_at`。
- cutover 附近旧节点晚到的、`ts >= cutover_at` 的旧 epoch 数据 -> **拒绝并告警**（不进 latest、不进 Stream）。
- **不依赖"高 epoch 胜出"**，因此 Stream/Writer/TDengine **无需引入 epoch 字段**，契约不变（现状 `consumer.py:3-6` 流字段无 epoch，保持不变）。

### 7.3 握手超时与强制切换（旧节点离线无法完成第 4 步）

旧节点 A 离线/失联，无法回报第 4 步 ACK 时：

- **cutover grace**：cutover_at 后设一个宽限窗口 `cutover_grace`（远小于 max_offline_retention_days），允许旧节点补传 `ts < cutover_at` 的积压。
- **强制切换**：宽限期结束仍无 ACK，中心**强制完成迁移**，旧 epoch 此后任何数据一律拒绝。
- **重新上线围栏**：旧节点恢复后，心跳拉到新 `desired_revision` 发现自己已不持有该设备 -> 停采、清本地 assignment、转空闲或接新分配。若旧节点仍持旧 epoch 上传，按上条拒绝。

### 7.4 时钟与冲突裁决（冻结规则）

**时钟偏差阈值（冻结）**：
- **`max_clock_skew`**：默认 **±30 秒**，超出此偏差视为时钟异常。
- **心跳时钟比对**：边缘心跳携带 `edge_local_time_ms`（边缘本地时间戳），中心收到时记录 `center_received_at_ms`（中心时间）。
- **偏差计算**：`clock_skew = edge_local_time_ms - center_received_at_ms - estimated_rtt/2`（粗略，不考虑单程延迟差异）。
- **超偏差门禁**：
  - `|clock_skew| > max_clock_skew` → 节点标记 `clock_anomaly=true`，中心 system_log 告警。
  - **迁移阻断**：时钟异常节点**不可作为迁移目标**（新 assignment 被拒绝），已持有设备的节点可继续采集（数据仍接受，避免全节点停摆）。
  - **全局拒绝（可选，阶段 4）**：超偏差且无法自动校时时，可选择**拒绝该节点所有数据**，直到时钟恢复正常。

**迁移时序（冻结，修复"仍依赖边缘样本时钟"）**：

严格时间窗裁决（§7.2）用**边缘样本时间戳 `ts`** 与**中心生成的 `cutover_at`** 比较，因此必须冻结迁移时序，避免时钟偏差导致数据空洞或误拒：

1. **中心生成 `cutover_at`**（中心时间，不信边缘时钟），预留足够缓冲（建议 ≥ 2 × max_clock_skew）。
2. **新节点 B 提前启动采集**：B 在 `cutover_at - max_clock_skew` 时刻开始采集（若 B 时钟慢 30s，实际采集时间已是 cutover_at）。
3. **旧节点 A 延后停止采集**：A 在 `cutover_at + max_clock_skew` 时刻停止采集（若 A 时钟快 30s，采样时间戳仍 < cutover_at）。
4. **重叠期两节点同时采集**：重叠期 `[cutover_at - skew, cutover_at + skew]` 内，A/B 同时采集同一设备，中心按 `ts < cutover_at` / `ts >= cutover_at` 裁决，**样本级 TDengine 主键去重**兜底（同 ts 后到的覆盖前到的，不重复）。

**Latest 更新（仅 latest 层，不影响历史层）**：
- `incoming.t > 现值` → 更新该点 JSON
- `incoming.t == 现值 且 incoming.e > 现值.e` → 更新（高 epoch 优先）
- 否则 → 不更新

**时钟校时（建议，非强制）**：
- 边缘节点启用 NTP 自动校时，定期与中心时间同步。
- 首次注册时中心检查时钟偏差，超阈值告警并建议校时后重试。

### 7.5 幂等性分层

| 层次 | 机制 | 用途 |
|------|------|------|
| **所有权** | assignment_epoch + cutover + 严格时间窗 | 判断谁有权采、哪个时间窗接受 |
| **批次/序列** | local_seq + high_watermark 严格按序 | 上传重试避免重复写 |
| **样本级** | 点位时间戳 | TDengine 主键去重 |

**系统语义承诺**：
- **正常运行且未放弃 session 时**："至少一次上传 + 幂等处理"
- **发生 session 切换时**：明确允许丢失（SQLite 损坏/积压超限/seq_reject/Redis 全丢）
- **不承诺**：绝对 exactly-once 或"不丢不重"

## 8. 数据上传与幂等方案

### 8.1 上传契约与错误码表

**batch_id 在 collector 写 outbox 时生成，此后永不改变**。每 item 另带**上传会话身份** `upload_session_id`（边缘生成的随机 UUID）和**会话内单调递增的 `local_seq`**（用于中心 high_watermark 去重，见 §8.2）。批量上传用 `request_id + items[]`，**每 item 直接携带完整 envelope**：

```json
POST /ingest
{
  "node_uuid": "...",
  "request_id": "本次HTTP请求ID(可重生)",
  "items": [
    {
      "batch_id": "collector生成,永不变(审计追踪)",
      "upload_session_id": "边缘生成UUID,SQLite重建/积压超限时生成新UUID",
      "local_seq": 12345,
      "assignment_epoch": 5,
      "device_code": "...",
      "device_type": "qc",
      "group_code": "g001",
      "scan_rate": 1000,
      "ts": 1721800000000,
      "config_version": 12,
      "contract_version": 2,
      "values": { "var_id": "value_str" },
      "qualities": { "var_id": "quality_code" }
    }
  ]
}
```

- `upload_session_id` / `local_seq`：去重身份三元组 `(node_uuid, upload_session_id, local_seq)`，必填
- `contract_version` / `qualities`：Q2 质量码开启后必填；未开启可省
- Ingest 用这些字段**直接生成 StreamEnvelope v1/v2**，不再回库拼第二份 envelope

**ACK 语义 = 逐项确认**（不是整批原子），按错误码表分类：

```json
{ "results": [ 
  { "batch_id": "...", "upload_session_id": "...", "local_seq": 12345, "status": "ack|duplicate|seq_reject|rejected_consumed|stale_config_warning|commit_unknown|session_obsolete|bad_request", ... }
] }
```

**ACK 回显三元组**：`batch_id + upload_session_id + local_seq`，边缘用三元组匹配 outbox 行更新状态。

**错误码表（冻结）**：

| HTTP | status | 边缘 outbox 动作 | 中心 hw 推进 | 说明 |
|------|--------|------------------|-------------|------|
| 200 | `ack` | -> sent | **是（hw=seq）** | 首次接收，推进 hw 到该 seq |
| 200 | `duplicate` | -> sent | **否（hw 不变）** | 重复上传（seq<=hw），hw 已经在该 seq 或更高，不回退 |
| 200 | `seq_reject` | -> **放弃整个 session** | 否 | seq > hw+1（乱序），边缘生成新 session_id 重新开始 |
| 200 | `rejected_consumed` | -> **dead**（terminal） | **是（hw=seq）** | 身份/序号合法，但业务校验失败（stale_epoch/out_of_time_window/unknown_device/malformed_envelope），**推进 hw 避免空洞** |
| 200 | `stale_config_warning` | -> sent | **是（hw=seq）** | config_version 旧但可解码，**允许入 Stream**，Writer 用永久 point_storage_mapping 解码，边缘记录告警但继续 |
| 200 | `commit_unknown` | -> **放弃整个 session** | **未知（可能部分执行）** | Redis 脚本执行错误（XADD 成功但后续 HSET/SET 失败），边缘放弃 session 避免状态不一致 |
| 200 | `session_obsolete` | 旧 session 响应→忽略；本地当前 session→暂停上传并对账 | 否 | active_session 已切换；不推进 hw，不写 Stream/latest |
| 400 | `bad_request` | -> **放弃整个 session** | 否 | 请求级错误（连 upload_session_id/local_seq 都无法解析） |
| 401 / 403 | `unauthorized` | 暂停节点 + 触发重新认证（不变状态） | 否 | 认证失败 |
| 429 | `throttled` | -> retry_wait（backoff） | 否 | 限流（执行 Lua 前的限流，**确定未执行**，可保留 session 重试） |
| 5xx | `server_error` | -> retry_wait（backoff） | **未知** | 服务端错误（可能发生在 Lua 执行中或响应失败，hw 状态未知，边缘用原 session 和原三元组重试，由 duplicate 实现收敛） |
| 网络失败 | (无响应) | 保持重试 | **未知** | TCP 超时/连接断开（可能发生在任何阶段，hw 状态未知，边缘用原 session 和原三元组重试，由 duplicate 实现收敛） |

**关键变化**：
- **stale_config 不再拒绝消费**：新增 `stale_config_warning` 状态，config_version 旧但可解码时**允许入 Stream**，Writer 用永久 `point_storage_mapping` 解码（§10 设计目标），边缘记录告警但标记 sent 继续上传
- **区分"旧版本"vs"非法 schema"**：`stale_config_warning` 支持断网期间旧版本采集的数据补传；`rejected_consumed` 只用于真正非法的 schema（unknown_device/malformed_envelope）
- 新增 `commit_unknown` 状态：Redis 脚本执行错误（XADD 成功但后续操作失败），**边缘放弃整个 session**，避免重传造成重复或状态不一致
- **5xx/网络失败 hw 状态未知**：可能发生在 Lua 执行中或响应失败，边缘用原 session 和原三元组重试，由 `duplicate` 实现收敛（不能假设"确定未执行"）
- **429 vs 5xx/网络失败区别**：429 是执行 Lua 前的限流（确定未执行）；5xx/网络失败可能部分执行，hw 状态未知
- 删除 `batch_stopped` 状态（Redis 脚本错误统一用 `commit_unknown` + 放弃 session，不再尝试批次内停止处理）

### 8.2 中心 Ingest 幂等 + latest 防倒退（严格按序，无 gap）

**幂等去重改为严格按序 + 单批次在途，不再维护 gap**（简化 v7 的 watermark+gap 方案）。

**核心原则**：
- **严格按序上传**：Uploader 只能按 local_seq 升序发送，单批次在途（上一批 ACK 后才发下一批）
- **中心只记录 high_watermark**：每个 session 记录最大已接收 seq
- **seq 裁决规则**：
  - `seq <= hw`：重复上传，返回 `duplicate`
  - `seq == hw + 1`：正常接收，推进 `hw = seq`，返回 `ack`
  - `seq > hw + 1`：序号空洞或中心 hw 重置，返回 `seq_reject`，**边缘放弃整个 session**

**Ingest 应用层流程**（按 local_seq 顺序逐项处理）：

```python
# 伪代码：Ingest 应用层批次处理
for item in sorted(items, key=lambda x: x.local_seq):
    # 1. 解析与认证（应用层完成）
    if not parse_and_authenticate(item):
        item.status = "bad_request"
        abandon_session_and_stop_batch()  # 放弃整个 session
        break
    
    # 2. 业务校验（应用层完成，查 MySQL）
    validation_result = validate_business_rules(item)  # stale_epoch/out_of_time_window/unknown_device/malformed_envelope
    config_version_status = check_config_version(item)  # "current" / "stale_but_decodable" / "unknown"
    
    if validation_result in ["stale_epoch", "out_of_time_window", "unknown_device", "malformed_envelope"]:
        action = "consume_reject"  # 真正非法，推进 hw 避免空洞，但不写 Stream
        final_status_override = "rejected_consumed"
    elif config_version_status == "stale_but_decodable":
        action = "accept"  # 旧 config_version 但可解码，允许入 Stream，Writer 用永久 mapping 解码
        final_status_override = "stale_config_warning"
    elif config_version_status == "unknown":
        action = "consume_reject"  # config_version 完全未知，拒绝
        final_status_override = "rejected_consumed"
    else:
        action = "accept"  # 正常接收
        final_status_override = None
    
    # 3. 调用 Lua 原子操作（只负责 seq 裁决 + Redis 操作）
    try:
        lua_result = call_ingest_lua(
            keys=[hw_key, stream_key, latest_key, active_session_key],  # 通过 KEYS[] 传入
            args=[
                item.node_uuid,
                item.upload_session_id,
                item.local_seq,
                action,  # "accept" or "consume_reject"
                item.envelope if action == "accept" else None,
                build_latest_updates(item) if action == "accept" else None,  # {var_id: {v,t,q,e}}
                stream_maxlen
            ]
        )
    except RedisScriptError as e:
        # Redis 脚本执行错误（XADD 成功但后续操作失败，或其他执行错误）
        # 状态未知（可能部分执行），放弃整个 session
        item.status = "commit_unknown"
        abandon_session_and_stop_batch()
        break
    
    # 4. 处理 Lua 返回结果
    if lua_result == "ack":
        item.status = final_status_override if final_status_override else "ack"
    elif lua_result == "duplicate":
        item.status = "duplicate"
    elif lua_result == "seq_reject":
        item.status = "seq_reject"
        # seq_reject 是应用层能识别的确定状态，不放弃 session，由边缘决定是否放弃
    elif lua_result == "rejected_consumed":
        item.status = final_status_override if final_status_override else "rejected_consumed"
    elif lua_result == "session_obsolete":
        item.status = "session_obsolete"

return results
```

**业务校验语义说明**：
- **stale_config_warning**：config_version 旧但在永久 `point_storage_mapping` 中可解码 → action="accept"，允许入 Stream，Writer 用永久 mapping 解码，边缘记录告警
- **rejected_consumed**：真正非法（stale_epoch/out_of_time_window/unknown_device/unknown_config_version） → action="consume_reject"，推进 hw 但不写 Stream，边缘标记 dead
- **支持断网期间旧版本采集的数据补传**：§10 设计的永久 `point_storage_mapping` 正是为此目的

**Lua 原子操作**（缩减为单项 seq 裁决 + Redis 操作，通过 KEYS[] 传入键）：

```lua
-- KEYS[1]: hw_key (hw:{node_uuid}:{upload_session_id})
-- KEYS[2]: stream_key (rt:stream:{device_type}:{group_code}:{shard_no})
-- KEYS[3]: latest_key (rt:latest:{device_code}:{group_code})
-- KEYS[4]: active_session_key (active_session:{node_uuid})
-- ARGV[1]: node_uuid
-- ARGV[2]: upload_session_id
-- ARGV[3]: local_seq
-- ARGV[4]: action ("accept" | "consume_reject")
-- ARGV[5]: envelope_data (JSON object with device_code/device_type/group_code/scan_rate/ts/config_version/values/qualities/contract_version)
-- ARGV[6]: latest_updates (JSON: {var_id -> {v,t,q,e}}, accept 时有效)
-- ARGV[7]: stream_maxlen

local hw_key = KEYS[1]
local stream_key = KEYS[2]
local latest_key = KEYS[3]
local active_session_key = KEYS[4]

local local_seq = tonumber(ARGV[3])
local action = ARGV[4]

-- 1. session 围栏：必须在读取 hw 和序号裁决前执行
local active_session = redis.call("GET", active_session_key)
if active_session == false then
    -- 节点首次上传
    redis.call("SET", active_session_key, ARGV[2])
elseif active_session ~= ARGV[2] then
    -- 已被显式切换替代的旧 session 不再推进 hw，也不写 Stream/latest
    return "session_obsolete"
end

local hw = tonumber(redis.call("GET", hw_key) or "0")

-- 2. 序列裁决
if local_seq < hw then
    return "duplicate"
elseif local_seq == hw then
    return "duplicate"
elseif local_seq > hw + 1 then
    return "seq_reject"
end

-- local_seq == hw + 1：正常处理

if action == "consume_reject" then
    -- 业务校验失败，只推进 hw，不写 Stream/latest
    redis.call("SET", hw_key, local_seq)
    return "rejected_consumed"
end

-- action == "accept"：正常接收

-- 3. 写入 Stream（使用 pcall 捕获错误）
-- Stream 字段格式与现有 Collector 一致：独立字段而非单个 data 字段
local envelope_data = cjson.decode(ARGV[5])  -- 解析 envelope JSON
local stream_maxlen = tonumber(ARGV[7])

-- 构建 XADD 字段（与 collector/storage/redis_writer.py:105 一致）
local xadd_args = {
    stream_key, "MAXLEN", "~", stream_maxlen, "*",
    "device_code", envelope_data.device_code,
    "device_type", envelope_data.device_type,
    "group_code", envelope_data.group_code,
    "scan_rate", tostring(envelope_data.scan_rate),
    "ts", tostring(envelope_data.ts),
    "config_version", tostring(envelope_data.config_version),
    "values", cjson.encode(envelope_data.values)  -- Writer 期望 JSON 字符串
}
if envelope_data.contract_version == 2 then
    table.insert(xadd_args, "contract_version")
    table.insert(xadd_args, "2")
    table.insert(xadd_args, "qualities")
    table.insert(xadd_args, cjson.encode(envelope_data.qualities))  -- Writer 期望 JSON 字符串
end

local reply = redis.pcall("XADD", unpack(xadd_args))
if type(reply) == "table" and reply.err then
    -- Redis OOM / 限流等错误，脚本终止，应用层捕获异常返回 commit_unknown
    return redis.error_reply(reply.err)
end

-- 4. 更新 latest（逐点时间戳比较）
local latest_updates = cjson.decode(ARGV[6])  -- {var_id -> {v,t,q,e}}

for var_id, incoming in pairs(latest_updates) do
    local current = redis.call("HGET", latest_key, var_id)
    if current then
        local cur = cjson.decode(current)
        local cur_e = tonumber(cur.e or 0)  -- 兼容旧 collector 写入的 {v,t,q}（无 e 字段），视为 epoch=0
        -- incoming.t > current.t，或 t 相同且 e 更高
        if incoming.t > cur.t or (incoming.t == cur.t and incoming.e > cur_e) then
            redis.call("HSET", latest_key, var_id, cjson.encode(incoming))
        end
    else
        -- 该 var_id 不存在，直接写入
        redis.call("HSET", latest_key, var_id, cjson.encode(incoming))
    end
end

-- 5. 推进 high_watermark
redis.call("SET", hw_key, local_seq)
return "ack"
```

**Redis 错误处理语义**：
- **执行 Lua 前的限流**（429）：确定未执行；5xx/网络失败的执行状态未知，边缘保留原 session 和原三元组重试
- **Redis 脚本执行错误**（`commit_unknown`）：可能部分执行（XADD 成功但后续 HSET/SET 失败），边缘**放弃整个 session**，避免重传造成重复或状态不一致
- **第一阶段允许 Redis 故障时丢数据**：不在 Lua 中设计完整的 OOM 恢复状态机，简化为"放弃 session"

**状态机测试用例（严格按序）**：

**初始状态**：hw=10（已确认到 seq=10）

| 到达序列 | 预期 hw 轨迹 | 预期响应 | 说明 |
|---------|-------------|---------|------|
| `11` | 10→11 | ack | 正常连续 |
| `11,12,13` | 10→11→12→13 | ack,ack,ack | 顺序场景 |
| `11,11` | 10→11 | ack,duplicate | 重复请求（幂等） |
| `12` | 10 | seq_reject | 乱序（seq>hw+1），边缘放弃 session |
| `9` | 10 | duplicate | 已处理的旧数据 |

**关键点**：
- **Stream 与 latest 分开处理**：Stream 永远追加（历史完整），latest 只反映"最新时间戳的值"
- **Latest 不新增 hash 字段**：保持 `ws_push.py` 的 hgetall 遍历契约，每 var_id 一个 `{"v","t","q","e"}` JSON
- **Latest 逐点更新**：一个 UploadItem 只有一个 device/group，`latest_updates` 直接传 `{var_id: {v,t,q,e}}`，不需要嵌套为 device→group→var
- **Latest 更新判断**：`incoming.t > current.t` 或 `incoming.t == current.t 且 incoming.assignment_epoch > current.e` 时更新
- **严格按序保证 seq 连续**：hw 单调递增，无空洞
- **batch_id 保留作审计追踪**，不是去重主键
- **rejected_consumed 推进 hw**：业务校验失败但序号合法，推进 hw 避免空洞
- **commit_unknown 放弃 session**：Redis 脚本执行错误（可能部分执行），边缘放弃整个 session 避免状态不一致
- **Lua 只负责 seq 裁决 + Redis 操作**：业务校验（归属/epoch/config_version/schema）在 Ingest 应用层完成（查 MySQL）
- **Latest 旧值兼容**：`cur.e or 0` 兼容旧 collector 写入的 `{v,t,q}`（无 e 字段），视为 epoch=0
- **使用 redis.pcall 正确判断错误**：`type(reply) == "table" and reply.err` 判断错误，而非 `not ok`
- **通过 KEYS[] 传入键**：hw_key/stream_key/latest_key/active_session_key 通过 KEYS[] 传入，符合 Redis EVAL 键声明要求；**Redis Cluster 兼容需后续设计**（当前脚本访问的键通常不在同一 hash slot，第一阶段使用单实例 Redis）

### 8.3 容灾策略：放弃旧数据，重新开始

**核心原则**：不尝试补传历史，不停止系统，**放弃旧数据并从最新采集重新开始**。

#### 8.3.1 触发场景

以下场景会导致边缘**放弃当前 upload_session_id**，生成新 UUID 重新开始：

| 场景 | 触发条件 | 边缘动作 |
|------|---------|---------|
| **SQLite 损坏/丢失** | 启动时无法打开 outbox.db | 生成新 upload_session_id，重置 metadata.last_seq=0 |
| **积压超限（FIFO 丢弃）** | outbox 磁盘占用达 95% 水位 | 删除最旧 pending 行，记录丢弃数，生成新 upload_session_id |
| **收到 seq_reject** | 中心返回 seq_reject（seq > hw+1） | 边缘检测到序号空洞或中心 hw 重置，生成新 upload_session_id |
| **收到 commit_unknown** | 中心返回 commit_unknown（Redis 脚本执行错误） | 边缘放弃当前 session，生成新 upload_session_id |
| **Redis 全丢（中心侧）** | 中心 Redis 重启，hw 丢失 | 中心检测到新 session_id，从 hw=0 开始接收 |

#### 8.3.2 边缘放弃流程

```
1. 停止旧 session 的 Uploader 发送，记录 old_session_id
2. 生成新 upload_session_id，并在同一 SQLite 事务中持久化 pending_session_switch_old_id、new_session_id 和 last_seq=0
3. 清空 outbox 所有 pending/retry_wait/inflight 行（保留 sent/dead 供审计）
4. Collector 从最新采集数据开始写新 session outbox；中心 CAS 成功前 Uploader 保持暂停
5. 用固定 old_session_id + new_session_id 重试 /ingest/session_switch，直到 switched/already_switched
6. 清除 pending_session_switch_old_id，恢复新 session 上传
7. 记录切换事件（旧/新 session_id、丢弃行数、原因）
```

#### 8.3.3 中心处理新 session（含 active_session_id 原子切换协议）

- 中心 Ingest 收到新 `upload_session_id` → 创建新 `hw:{node_uuid}:{new_session_id} = 0`
- **active_session_id 围栏是阶段 1 必做项**：上传主 Lua 已在 §8.2 将 `active_session_key` 作为 `KEYS[4]` 传入，并在读取 hw、执行 seq 裁决前检查。非 active session 一律返回 `session_obsolete`，不推进 hw、不写 Stream/latest。
- **边缘切换 session 必须显式通知中心**：`POST /ingest/session_switch` 携带 `old_session_id + new_session_id`，中心使用独立 Lua CAS 原子切换：
  ```lua
  -- KEYS[1]: active_session_key; ARGV[1]: old_session_id; ARGV[2]: new_session_id
  local current = redis.call("GET", KEYS[1])
  if current == false then
      -- Redis 状态首次建立或已丢失
      redis.call("SET", KEYS[1], ARGV[2])
      return "switched"
  elseif current == ARGV[2] then
      -- 上次切换成功但响应丢失
      return "already_switched"
  elseif current == ARGV[1] then
      redis.call("SET", KEYS[1], ARGV[2])
      return "switched"
  else
      -- 禁止未知旧 session 覆盖当前 active session
      return "session_conflict"
  end
  ```
- **CAS 返回语义**：`switched` / `already_switched` 表示成功；`session_conflict` 时暂停上传并告警，不得直接覆盖中心 active session。
- **边缘切换顺序（可崩溃恢复）**：
  1. 停止旧 session 的 Uploader 发送。
  2. 在本地事务中持久化 `pending_session_switch_old_id=old_session_id`，再写入 new_session_id、重置 last_seq、清理旧积压。
  3. Collector 可继续写新 session 的 outbox，但 Uploader 在 CAS 成功前不得发送。
  4. 使用同一 `old_session_id + new_session_id` 重试切换请求，直到返回 `switched` 或 `already_switched`。
  5. 清除 `pending_session_switch_old_id` 并恢复上传；重启发现该键时继续步骤 4。
- **避免随机 UUID 重新激活**：只有显式 CAS 可以覆盖 active session；迟到旧请求只能得到 `session_obsolete`。
- 旧 session 的 watermark 保留（供审计，设置 TTL 如 7 天后过期）
- **不尝试关联新旧 session**，不尝试补全空洞，新 session 从 seq=1 开始独立计数

#### 8.3.4 Redis 全丢处理（中心侧）

- **检测**：中心 Redis 重启后，所有 `hw:{node_uuid}:{session_id}` 丢失
- **行为**：收到任意 session 的 seq=1 → 从 hw=0 开始接收，seq > 1 返回 seq_reject
- **边缘响应**：收到 seq_reject → 放弃当前 session，生成新 session_id（见 §8.3.2）
- **结果**：丢弃 Redis 全丢前所有在途数据，从新 session 重新开始

#### 8.3.5 数据丢失影响评估

| 场景 | 丢失数据范围 | 影响时长 | 可接受性 |
|------|------------|---------|---------|
| SQLite 损坏 | 本地 outbox 积压（最多 max_offline_retention_days） | 一次性 | ✓ 可接受，工业采集场景 |
| 积压超限 FIFO | **当前 session 全部未发送积压**（最多接近 max_offline_retention_days） | 渐进式 | ✓ 可接受，优先保证新数据 |
| seq_reject | **整个离线积压**（session 切换清空所有 pending/retry_wait/inflight，最多接近 max_offline_retention_days） | 一次性 | ✓ 可接受，极少发生（中心状态重置或本地序号异常） |
| commit_unknown | **整个离线积压**（session 切换清空所有 pending/retry_wait/inflight，最多接近 max_offline_retention_days） | 一次性 | ✓ 可接受，极少发生（Redis 脚本执行错误） |
| Redis 全丢 | 所有节点在途数据（积压 + 最近 ~1 分钟） | 一次性 | ✓ 可接受，依靠 AOF 避免 |

**关键承诺**：
- **不停止系统**：Redis 全丢/SQLite 损坏后，系统自动恢复接收新数据
- **不尝试补传**：丢失的历史数据不可恢复，优先保证实时采集
- **明确边界**：ACK 代表"中心已接收"（Redis XADD 成功），不代表 TDengine 永久落盘

### 8.4 容量公式与内存预算（阶段 0 必填）

目标参数：设备数 `D`、每设备扫描频率 `R`(条/秒)、节点数 `N`、保留天数 `P`。

- **high_watermark**：每节点每 session 1 个 string key，活跃 session 数 = N（正常情况），`N × 100B`，可忽略
- **无 gap 集合**：严格按序上传，不需要 gap
- **outbox 积压上限**：单节点 `D_node × R × 86400 × P` 行；按磁盘字节预算（见 §12.4）
- **中心 Redis Stream**：受 `stream_maxlen` 封顶，与现有单机一致
- **对比旧方案**：旧方案 dedupe key 数 = `D × R × 86400 × P`（1000×1×86400×7 ≈ 6.05 亿 key，不可接受）；新方案 dedupe 状态 = N 个 watermark，**与设备数/频率/保留期无关**，内存恒定

### 8.5 ACK durability 语义（明确"中心已接收"）

- **ACK 含义**：**"中心已接收"**，即 Redis XADD 成功，数据已进入中心 Redis Stream
- **不等 TDengine 落盘**：Writer 异步消费 Redis Stream 写 TDengine，ACK 时尚未落盘
- **可能丢失**：Redis AOF `everysec` 模式下，中心掉电可能丢失已 ACK 的 ~1 秒数据
- **可接受性**：工业采集场景，丢失 ~1 秒数据 << 等待 TDengine 落盘的延迟增加
- **依靠 AOF 避免**：Redis 配置 AOF everysec + 定期备份，避免大规模数据丢失
- **不承诺强 ACK**：第一阶段不实现"等待副本/持久化确认"，后续有需求再实现

## 9. 实时监控链路闭环

**现状**：`backend/app/services/ws_push.py` 是每 100ms 轮询 rt:latest，已能约 1 秒更新。

**PUBLISH 是新增能力，不是现有实现**，列入阶段 3：

```
Ingest 接收成功
  ├─ 用 StreamEnvelope v2 写中心 Redis Stream
  ├─ 更新中心 rt:latest (一 var_id 一 JSON, 逐点时间戳比较)
  └─ (阶段3新增) PUBLISH rt:change {device_code, group_code}

Backend WebSocket
  ├─ (阶段3新增) SUBSCRIBE rt:change -> 事件驱动推送
  └─ (现状) 或保持 100ms 轮询兜底
```

**性能指标**：中心收到数据后 1 秒内反映到实时监控页（轮询现状已满足，PUBLISH 可优化到更低延迟）。

**并发**：十几个 App 订阅实时推送，中心 Redis 轻松扛住（单实例上万 QPS，简单 KV 微秒级）。

## 10. 点位映射方案（决策 A：独立 point_storage_mapping，冻结完整物理坐标）

**核心原则：采集配置与入库映射彻底解耦，存储身份 + 物理坐标永久不变。**

### 10.1 独立存储映射表（含完整物理坐标）

TDengine 物理位置由 `device_type -> stable(超级表)` + `device_code -> child_table(子表)` + `td_column_name(列)` 共同决定。三者任一变化都会导致历史解码错位，因此映射表必须**冻结完整坐标**：

```sql
CREATE TABLE point_storage_mapping (
    point_id        BIGINT PRIMARY KEY,         -- = device_variable.id，永久身份
    device_code     VARCHAR(64)  NOT NULL,
    device_type_code VARCHAR(32) NOT NULL,      -- 决定 stable = sd{type_code}，永久不变
    stable_name     VARCHAR(64) NOT NULL,       -- 冗余存储，永久不变
    child_table     VARCHAR(64) NOT NULL,       -- = device_code，冗余存储，永久不变
    group_code      VARCHAR(64) NOT NULL,
    td_column_name  VARCHAR(32) NOT NULL,       -- 永久不变，永不复用
    var_type        VARCHAR(32) NOT NULL,       -- 永久不变
    created_at      DATETIME(3) NOT NULL,
    UNIQUE KEY uk_device_col (device_code, td_column_name)
    -- 注意：无 deleted / enable 过滤，此表只增不改不删
);
```

### 10.2 规则

- **物理坐标永久不变**：point_id、td_column_name、device_type_code、stable_name、child_table、var_type、group_code 一经建立**不可原地修改**。
- **产生历史后不可改的字段**：`device_code`、设备类型（type_id）、`group_code`、`td_column_name`。这些字段在 `catalog.py` 现状允许编辑（如 `update_device:606` 可改 type_id），分布式上线后必须冻结（要变则作废旧 point、建新 point_id，旧行永久保留）。
- 需要改类型或换组 -> **作废旧 point、创建新 point_id**（旧行永久保留供补传解码）。
- **删除点位：只软删采集配置**（`device_variable.deleted=1`），`point_storage_mapping` 行**保留不动**。
- **Writer 的存储映射查询走 `point_storage_mapping`**，不带 `deleted/enable` 过滤，因此软删/禁用/换组后旧数据仍可映射。
- **config_version 不一致只触发重载 + 告警，不拒绝旧点映射**（修复现状 `mysql_mapper.py` 版本不符降级/返回 None 的问题）。
- **不引入 mapping_version**--组级 `config_version` 仍随每条 item/entry 传。

### 10.3 点位创建与回填

- **同事务**：点位创建/编辑时，`device_variable` 写入与 `point_storage_mapping` 插入必须在**同一 MySQL 事务**，避免半写导致映射缺失。
- **全量回填**：上线时对现有 `device_variable` 全量回填 `point_storage_mapping`：
  - 从 `device_variable` JOIN `device_point_group` JOIN `device` JOIN `device_type` 取现有 point_id/device_code/type_code/group_code/td_column_name/var_type；
  - 计算 `stable_name = sd{type_code}`、`child_table = device_code`；
  - **使用 staging 表校验后正式插入**（不用 INSERT IGNORE）：
    1. 先插入 `point_storage_mapping_staging`
    2. 校验：`staging.point_id` 与 `device_variable.id` 一一对应（无缺漏、无孤儿）
    3. 校验：`staging` 内 `(device_code, td_column_name)` 无重复
    4. 校验：`staging` 的 device_code/type_code/td_column_name 与 `device_variable` JOIN 结果一致
    5. 产出差异报告（missing/conflict/orphan）
    6. **差异非零 → 阻断上线**：人工修复差异后重新回填，直到差异报告为空
    7. 差异为空 → `INSERT INTO point_storage_mapping SELECT * FROM point_storage_mapping_staging`
    8. 清空 staging 表
- **回填校验门禁（冻结）**：
  - 差异报告非空 → **阻断分布式上线**，停止分布式中心/边缘安装包的 Ingest、Uploader 启动并进入部署回滚
  - 差异报告示例：`MISSING: point_id=123 (device_code=D001, var_name=温度); CONFLICT: (D002, temp) mapped to point_id=456 and 789; ORPHAN: staging has point_id=999 not in device_variable`
  - 人工修复（补建 device_variable / 删除孤儿 / 解决冲突）后重新回填，循环直到差异为空

### 10.4 与旧方案对比（撤销）

| 旧方案（凭空设计，已撤销） | v5 方案 |
|---|---|
| 新增 `mapping_version` 表 | **删除，不引入** |
| 存储映射只存 device_code/group_code/col/type | **补 device_type_code + stable_name + child_table** |
| 存储映射与采集配置同表(带 deleted/enable 过滤) | 独立表，无过滤 |
| 版本不符拒绝映射 | 版本不符只重载+告警 |
| VARCHAR 无长度（非法 MySQL DDL） | **VARCHAR(64)/VARCHAR(32) 补长度** |
| 无唯一约束 | **UNIQUE (device_code, td_column_name)** |

### 10.5 收益

- 断网补传老数据 / 软删禁用点 / 换组 / Backend 重启缓存清空后，存储映射恒定可查。
- 物理坐标冻结后，TDengine 历史数据不会因设备类型被改而错位。
- 采集侧的启停、禁用、软删完全不影响入库解码。

## 11. 节点身份与安全

### 11.1 节点身份

- **node_uuid**：首次部署生成并持久化（**不用 MAC+hostname 拼接**，避免换网卡/改主机名后身份漂移）。
- 中心侧 `sys_node` 表以 node_uuid 为主键，存公钥/证书指纹。

### 11.2 注册与认证（先生成身份，mTLS/签名证明）

```
1. 边缘首次启动：先生成并持久化 node_uuid + 本地密钥对/证书
2. 引导时输入一次性 enrollment token (中心生成)
3. 用 enrollment token + node_uuid + 公钥/CSR 向中心注册
4. 中心审批后颁发长期 node token + 签发节点证书，绑定到该 node_uuid / 公钥
5. node token 存储：Windows 经 Agent DPAPI 加密 (不落明文 SQLite)
6. 后续通信认证（二选一，阶段0 冻结）：
   a. mTLS：边缘证书 + 中心证书双向校验（推荐，运维需证书分发）
   b. 签名：每次请求对 method/path/timestamp/nonce/body_hash 用私钥签名，
      中心校验签名 + timestamp/nonce 防重放
```

**仅发 Bearer token 不算"绑定公钥"**--必须有 mTLS 或请求签名才能让公钥绑定生效（修复原稿无证明机制的问题）。

### 11.3 令牌吊销与轮换

- 中心可**吊销/轮换** node token / 证书（节点丢失、下线、泄露）。
- 被吊销节点的上传返回 401，边缘停止并告警。
- 与 §7 epoch 围栏配合：吊销令牌 + 收回 assignment。

## 12. 边缘断网缓冲（SQLite outbox）

**边缘不再需要 Redis**--用 SQLite outbox 做断网缓冲。

### 12.1 表结构（含崩溃恢复字段 + upload_session_id + local_seq）

```sql
CREATE TABLE IF NOT EXISTS outbox (
    batch_id       TEXT PRIMARY KEY,          -- collector 生成,永不变(审计)
    upload_session_id TEXT NOT NULL,          -- 边缘生成UUID,SQLite重建/积压超限时生成新UUID
    local_seq      INTEGER NOT NULL,          -- 会话内单调递增,去重身份第3元
    device_code    TEXT NOT NULL,
    group_code     TEXT NOT NULL,
    assignment_epoch INTEGER NOT NULL,
    config_version INTEGER NOT NULL,
    ts             INTEGER NOT NULL,
    payload        BLOB NOT NULL,             -- StreamEnvelope v1/v2 完整 envelope
    state          TEXT NOT NULL DEFAULT 'pending',
    attempt_count  INTEGER NOT NULL DEFAULT 0,
    next_retry_at  INTEGER,
    last_error     TEXT,
    http_status    INTEGER,
    lease_owner    TEXT,                      -- 崩溃恢复：占用该 inflight 的 uploader 实例ID
    inflight_at    INTEGER,
    lease_until    INTEGER,                   -- 租约到期，过期可回收
    acked_at       INTEGER,
    dead_at        INTEGER,
    created_at     INTEGER NOT NULL,
    UNIQUE (upload_session_id, local_seq)    -- 防止重复分配
);
CREATE INDEX IF NOT EXISTS idx_outbox_state_retry ON outbox(state, next_retry_at);
CREATE INDEX IF NOT EXISTS idx_outbox_created ON outbox(created_at);
CREATE INDEX IF NOT EXISTS idx_outbox_lease ON outbox(state, lease_until);
CREATE INDEX IF NOT EXISTS idx_outbox_seq ON outbox(upload_session_id, local_seq);

-- 元数据表：存储 upload_session_id、last_seq 和切换中的 pending_session_switch_old_id
CREATE TABLE IF NOT EXISTS metadata (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
-- INSERT INTO metadata(key, value) VALUES('upload_session_id', '{random_uuid}') ON CONFLICT DO NOTHING;
-- INSERT INTO metadata(key, value) VALUES('last_seq', '0') ON CONFLICT DO NOTHING;
```

**upload_session_id 生成与持久化**：
- **生成时机**：
  - Collector 首次启动
  - SQLite 损坏/丢失
  - 积压超限（FIFO 丢弃后）
  - 收到 seq_reject（中心返回，见 §8.1）
  - 收到 commit_unknown（中心返回，见 §8.1）
- **生成方式**：边缘生成随机 UUID（`uuid.uuid4()`），持久化到 `metadata` 表
- **启动检查**：Collector 启动时从 `metadata` 读取，不存在则生成新 UUID

**local_seq 分配机制（原子，防止分配空洞）**：
```sql
-- 递增 last_seq 与 outbox INSERT 必须在同一事务
-- 先递增再读取，确保首条数据 seq=1
BEGIN;
UPDATE metadata SET value = value + 1 WHERE key = 'last_seq';
SELECT value FROM metadata WHERE key = 'last_seq';  -- 获取新 seq（首次为 1）
INSERT INTO outbox(batch_id, upload_session_id, local_seq, ...) VALUES(?, ?, seq, ...);
COMMIT;
```

**session 切换流程**（触发条件：SQLite 损坏/积压超限/收到 seq_reject/收到 commit_unknown）：
```sql
-- A. 本地准备事务；事务提交后 Collector 可继续采集，但 Uploader 保持暂停
BEGIN;
-- 1. 先持久化旧 session，保证切换请求可在崩溃后重试
INSERT OR REPLACE INTO metadata(key, value)
SELECT 'pending_session_switch_old_id', value FROM metadata WHERE key = 'upload_session_id';
-- 2. 生成并写入新 upload_session_id（随机 UUID）
UPDATE metadata SET value = '{new_uuid}' WHERE key = 'upload_session_id';
-- 3. 重置序号
UPDATE metadata SET value = 0 WHERE key = 'last_seq';
-- 4. 清空旧 session 所有 pending/retry_wait/inflight 行
DELETE FROM outbox WHERE state IN ('pending','retry_wait','inflight');
-- 5. 保留 sent/dead 行供审计
COMMIT;

-- B. 中心 CAS 返回 switched/already_switched 后，清除待切换标记并恢复 Uploader
BEGIN;
DELETE FROM metadata WHERE key = 'pending_session_switch_old_id';
COMMIT;
```

- SQLite 损坏导致旧 `upload_session_id` 无法读取时，边缘先通过已认证的节点状态接口取得中心 `active_session_id`，将其持久化为 `pending_session_switch_old_id` 后再发起 CAS；中心不可达期间只采集入新 outbox，不上传。
- 记录 session 切换事件到边缘日志，包含旧/新 session_id、丢弃行数和触发原因。

### 12.2 状态机（含崩溃恢复 + 错误码分类 + 单例围栏）

```
pending ──领取(占租约,新lease_owner)──> inflight ──ack/duplicate──> sent
                                          │
                                          ├── retryable(429/5xx/网络) ──> retry_wait ──> pending
                                          ├── 401/403 ──> 暂停节点,触发重新认证(不变状态)
                                          ├── rejected_consumed(200业务校验失败) ──> dead
                                          ├── bad_request(400请求级错误) ──> **放弃整个 session**
                                          ├── seq_reject(200乱序) ──> **放弃整个 session**
                                          ├── commit_unknown(Redis脚本执行错误) ──> **放弃整个 session**
                                          ├── session_obsolete ──> 旧响应忽略 / 当前 session 暂停并对账
                                          └── uploader崩溃 ──> (启动回收旧owner或lease过期)──> pending
```

**seq_reject 处理**：
- 中心返回 seq_reject（seq > hw+1，序号空洞或中心 hw 重置） → Uploader 检测到后**立即停止上传**
- 执行 session 切换流程（见 §12.1）：生成新 upload_session_id，清空 pending/retry_wait/inflight

**bad_request 处理**：
- 中心返回 400（连 upload_session_id/local_seq 都无法解析的请求级错误） → Uploader 放弃整个 session

**rejected_consumed 处理**：
- 中心返回 200 + `rejected_consumed` 状态（业务校验失败但序号合法，中心已推进 hw） → 边缘标记 dead，继续发送后续序号

**commit_unknown 处理**：
- 中心 Ingest 捕获 Redis 脚本执行异常（XADD 成功但后续 HSET/SET 失败，或其他执行错误）
- 状态未知（可能部分执行），返回 200 + `commit_unknown` → Uploader **放弃整个 session**，避免重传造成重复或状态不一致

**session_obsolete 处理**：
- 先比较 ACK 回显的 `upload_session_id` 与本地当前 session，不直接修改 outbox。
- 回显属于已切换旧 session：视为迟到响应并忽略。
- 回显等于本地当前 session：暂停 Uploader，读取中心 active_session 并按 §8.3.3 执行受控 CAS 对账；对账成功前不得继续上传。

**Uploader 单例围栏（冻结，防止多实例抢任务）**：

每节点**只能运行一个 Uploader 实例**，用以下机制之一实施围栏：

1. **OS mutex（推荐，Windows）**：
   - 启动时创建全局命名 Mutex（如 `Global\DataWatch_Uploader_{node_uuid}`）
   - 创建失败 → 已有实例运行 → 退出并告警
   - 进程退出时 OS 自动释放 Mutex

2. **文件锁（推荐，跨平台）**：
   - 启动时对 `{data_dir}/uploader.lock` 文件加排他锁（`fcntl.flock` / `msvcrt.locking`）
   - 加锁失败 → 已有实例运行 → 退出并告警
   - 进程退出时 OS 自动释放文件锁

**不推荐 BEGIN EXCLUSIVE 长时间持有**（会阻塞 Collector 写 outbox）。

**崩溃恢复（不依赖墙上时间为主路径）**：
- 每次 Uploader 启动生成新的 `lease_owner`（UUID 或 timestamp）
- 启动时**立即把所有旧 owner 的 inflight 复位为 pending**（主路径，不依赖时间）：
  ```sql
  UPDATE outbox SET state='pending', lease_owner=NULL, lease_until=NULL 
  WHERE state='inflight' AND (lease_owner != '{current_owner}' OR lease_owner IS NULL)
  ```
- `lease_until` 过期作为兜底（时间回拨时也能回收）：
  ```sql
  UPDATE outbox SET state='pending', lease_owner=NULL 
  WHERE state='inflight' AND lease_until < current_timestamp_ms
  ```

**领取原子性**：
- 领取任务用 SQLite 原子事务（`UPDATE ... WHERE state='pending' ... RETURNING`），避免多 Uploader 抢同一行（但单例围栏已阻止多实例）
- **严格按序发送**：Uploader 只能按 local_seq 升序发送，单批次在途（上一批 ACK 后才发下一批）
- **exponential backoff**：attempt_count 驱动 next_retry_at
- 重试始终用同一 batch_id + upload_session_id + local_seq（中心 high_watermark 幂等兜底）

### 12.2.1 自适应实时上传节拍

Uploader 不使用固定周期，也不为不同采集频率创建多条并发上传链路。边缘应用配置后，按本节点全部已启用、已分配点位的最小有效 `scan_rate` 动态计算实时上传节拍：

`upload_interval_ms = min(enabled_assigned_point.scan_rate_ms)`

- 全部点位均为 100ms 时，Uploader 每 100ms 检查一次 outbox；全部点位约为 400ms 时，每 400ms 检查一次；有数据才上传。
- 同时存在 100ms 和 400ms 时，Uploader 每 100ms 检查一次；100ms 数据可进入每个批次，400ms 数据约每四个批次出现一次，完成后并入当时批次。
- `scan_rate` 由点位配置决定。配置修订生效后，Uploader 必须重新计算节拍；不得把某个现场示例周期写死为平台最小值或固定上传周期。
- 单边缘理论请求率约为 `1000 / upload_interval_ms` QPS；中心总设计请求率按所有在线边缘节点的该值求和。空批次不发送，因此实际请求率只会低于该理论值。
- 不等待某个周期或某组设备全部返回。慢设备后续返回的数据进入后续节拍，不阻塞其他设备。
- 每个节拍开始时快照 `target_seq = metadata.last_seq`，只领取已经提交到 outbox 且 `local_seq <= target_seq` 的连续记录。
- 在到达 `target_seq` 前，上一批 ACK 后立即发送下一批；到达该水位后恢复等待下一个自适应节拍。`max_batch_items` / `max_batch_bytes` 只限制单批大小，不把同一水位的剩余数据推迟到下一节拍。
- 始终保持严格按序和单批次在途。若在途请求跨过一个或多个节拍，不并发发送；ACK 后把 `target_seq` 推进到最近已到期节拍对应的 `last_seq`，继续追赶。
- 断网期间保留原 `target_seq` 和原三元组重试；网络恢复后将水位推进到最新已到期节拍并连续发送，直至追平，再恢复正常节拍。重试错误仍遵守 exponential backoff。
- 不发送空批次。配置修订原子应用成功后立即重新计算节拍；没有启用点位时 Uploader 保持休眠，仅 Edge Agent 心跳继续。

因此最快采集周期决定节点可达到的上传实时性，较慢频率数据复用同一有序通道，不额外增加连接和 Uploader 实例。

### 12.3 SQLite 运行参数与磁盘释放

- `journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout`。
- 定期 WAL checkpoint，避免 WAL 无限增长。
- **删行后磁盘释放**：达 95% 水位删除过期 sent/dead 行后，必须执行 `PRAGMA wal_checkpoint(TRUNCATE)` 或 `VACUUM`（或 incremental_vacuum），否则 SQLite 文件未必实际释放磁盘空间给操作系统。

### 12.4 容量、保留与清理

- **统一 `max_offline_retention_days`**：约束 outbox 积压上限 + 中心 watermark 保留（**不含"映射保留"**--映射在 point_storage_mapping 永久保留）。
- **清理规则**：`sent` 记录超过保留期按 `acked_at` 清理；`dead` 记录按 `dead_at` 保留一段供排障后清理；清理后执行 §12.3 的 checkpoint/vacuum。
- **容量按磁盘字节数评估，不按行数**（点位值长度差异大）。
- **水位告警**：磁盘占用 70% / 85% / 95% 三级告警；达上限按 FIFO 丢**当前 session 全部未发送积压**并记录丢弃计数，随后 checkpoint/vacuum 释放空间。
- 承诺明确为"**尽力缓冲 max_offline_retention_days**"，超出即丢弃并告警，不承诺无限缓冲。

## 13. 首次部署引导

首次启动流程由安装包角色固定，不再显示部署模式选择：

```
1. 中心式安装包：沿用现状，初始化/连接本机 MySQL、Redis、TDengine，启动 Collector、Writer、Backend 和 App

   g. 上报心跳，等待中心下发 assignment
   h. 配置生效后按最快有效 scan_rate 计算 Uploader 实时节拍
```

| App | 查本机 Backend | 本机运维查 Edge Agent；全局数据经反向代理查中心 Backend | 查中心 Backend |
| 配置源 | 本机MySQL | 中心MySQL(SQLite只读缓存本机设备) | MySQL权威 |

（Writer 只写 TDengine 不写 MySQL；分布式边缘包无本机 Backend，边缘 App 需要全局数据时经反向代理访问中心。）

## 15. 数据库改动

- **不引入 mapping_version**（决策 A）。
- 中心式 `collector_setting` 增加可空 `read_timeout_ms`；分布式 `sys_node` 增加节点级可空 `read_timeout_ms` 并随节点配置快照同步到边缘 SQLite。未配置时沿用协议驱动默认，配置后同时覆盖调度层与驱动底层超时。
- **新增 `point_storage_mapping`**（point_id 主键、device_code/device_type_code/stable_name/child_table/group_code/td_column_name/var_type，永久保留，无 deleted/enable 过滤，UNIQUE(device_code,td_column_name)，见 §10）。
- 组级 `config_version` 复用现有（device_point_group 已有，Writer/collector 已用）。
- 新增 `sys_node`（node_uuid 主键、公钥/证书指纹、token 状态、**desired_revision/applied_revision**、**current_upload_session_id**、**current_high_watermark**、时钟偏差、心跳时间、水位）。
  - **current_upload_session_id/current_high_watermark 只作监控快照**，运行时裁决状态在 Redis（`hw:{node_uuid}:{session_id}`），避免双真源
  - 中心定期将 Redis watermark 同步到 MySQL 供监控展示，但 Ingest 只读 Redis
- **删除** `sys_node_skipped_seq` 表（无 skip 协议）。
- 新增 `device_assignment(device_id, assignment_epoch, node_id, effective_at, cutover_at, cutover_status)`，保留历史，含 cutover_grace/强制切换状态。
- 采集侧 `device_variable` 保留现有 `deleted/enable`（只影响采集，不影响 point_storage_mapping）。
- **冻结可编辑字段**：`update_device`/`update_point` 产生历史后禁止原地改 device_code/type_id/group_code/td_column_name（要改走作废+新建）。
- **字段以数据库现状为准，不一致改代码不改 schema**。

## 16. MySQL 并发评估

- 中心 writer 单进程消费中心 Redis Stream 入库（读 MySQL/point_storage_mapping 映射，写 TDengine，见 §2.1）。
- MySQL 连接池默认 `pool_size=5 + max_overflow=10 = 15` 并发；TDengine `pool_size=5, max_overflow=0`。
- 实时监控**直接查中心 Redis**，不压 MySQL；十几个 App 并发无压力。
- App 的历史/配置查询走 Backend -> MySQL，属低频，现有连接池足够。
- point_storage_mapping 查询走 Writer 缓存（config_version 命中即用缓存），高频场景不直压 MySQL。

### 16.1 Ingest + Redis 容量门禁

中心容量必须根据实际节点配置计算，不设固定 QPS 上限：

`steady_qps_estimate = sum(1000 / node.upload_interval_ms)`

例如 100 台边缘都配置 100ms 最快周期时，理论稳态上限约为 1000 QPS；若都约为 400ms，则约为 250 QPS。空批次不发送，实际值通常更低。阶段 2 上线前按部署清单计算目标并完成独立压测：

- 持续压测目标不低于 `steady_qps_estimate`，至少 30 分钟；短时突发目标不低于其 2 倍，至少 5 分钟。当前“100 台 × 100ms”示例对应 1000 QPS 稳态、2000 QPS 短时。
- Ingest 响应 P99 应小于该部署的最小上传节拍，服务端错误率 `< 0.1%`。
- Ingest 与 Redis CPU 均不得持续超过 70%，Redis 内存、连接数和 Stream 消费滞后不得持续增长。
- 压测期间不得因容量不足产生 `seq_reject`、`commit_unknown` 或无法收敛的重试积压。
- 未达到上述门禁时，优先增加 Ingest 实例或中心资源，不降低严格按序、单批次在途和 ACK 契约。

## 18. 关键设计决策（汇总）

1. **Writer 语义统一**：中心式安装包与分布式中心安装包的 Writer 同一套--读 MySQL/point_storage_mapping 映射、只写 TDengine；Ingest 不自造格式、不直写 TDengine。
2. **StreamEnvelope v2 复用现有 Redis 契约**：Stream 键 `rt:stream:{device_type}:{group_code}:{shard_no}`（crc32 分片）、latest 键 `rt:latest:{device_code}:{group_code}`；latest 保持一 var_id 一 JSON，扩展为 `{"v","t","q","e"}`，不新增 hash 字段。
3. **反向代理单 center_url**（决策 A）：`/api/*`->Backend:8000，`/ingest/*`->Ingest:8010。
4. **版本双轨**：节点级 `desired/applied_revision` + 组级 `config_version`；删 mapping_version。
5. **独立 point_storage_mapping**（决策 A）：含完整物理坐标（device_type_code/stable_name/child_table），永久不变，无过滤；版本不符只重载+告警；唯一约束+同事务+全量回填。
6. **UploadItem 携带完整 envelope + local_seq**；batch_id 永不变（审计）；逐项 ACK 按错误码表分类。
7. **epoch 严格时间窗裁决**（决策）：旧 ts<cutover、新 ts>=cutover，消除重叠；不贯通 Stream/Writer/TDengine；补握手超时/强制切换/重新上线围栏。
8. **latest 逐点时间戳比较防倒退**（一 var_id 一 JSON），与 high_watermark 幂等同一 Lua 原子。
9. **幂等去重 = upload_session_id + local_seq + high_watermark + 严格按序**，边缘生成 UUID session；单批次在途；seq>hw+1 拒绝；无 gap。
10. **边缘无 Redis/Backend**，用 SQLite outbox + 状态机 + 租约崩溃恢复（新 owner 回收为主、lease 过期兜底）+ checkpoint/vacuum 释放磁盘；边缘 App 本机运维查 Edge Agent，全局数据查中心。
11. **统一 max_offline_retention_days**（不含映射保留）+ outbox 清理规则；容量按磁盘字节 + 三级水位。
12. **ACK = 中心 Redis 接纳成功**，非落盘；明确"已接收"语义。
13. **PUBLISH 是新增能力（阶段 3）**，现状为 100ms 轮询。
14. **首次引导先生成 node_uuid/密钥，再用 enrollment token 注册**；认证用 mTLS 或请求签名+重放校验，token 绑定公钥需有证明机制。
15. **错误码表细化**：terminal->dead，retryable->retry_wait，401/403->重认证，429/5xx->重试，**seq_reject->放弃 session**。
16. **容灾策略：放弃+重新开始**：SQLite 损坏/积压超限/seq_reject/Redis 全丢 → 生成新 upload_session_id，从最新采集开始，不补历史。
17. **三个固定角色安装包**：统一代码仓库分别构建中心式、分布式边缘、分布式中心包；角色与页面随包固定，不设运行时切换开关。
18. **保留现有采集调度**：`scan_rate` 继续按点位配置；相同周期点位批量读取、设备错峰、同设备单请求在途；`read_timeout_ms` 可选且允许大于 `scan_rate`，中心式按本机配置、分布式按边缘节点配置，未配置沿用协议驱动默认。
19. **Uploader 自适应节拍**：本节点最小有效 `scan_rate` 决定节拍；100ms/400ms 混合配置按 100ms 检查，慢频率数据按完成批次并入；离线积压连续追赶；中心容量按各节点节拍求和测算。
