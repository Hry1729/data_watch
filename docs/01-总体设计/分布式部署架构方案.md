## 0. 阶段 0 契约冻结（实现前必须完成）

**本方向已确认可作为架构基线，但实现前必须先冻结以下契约，否则一落地就会与现有代码撞车。**

| # | 冻结项 | 说明 |
|---|--------|------|
| 1 | **UploadBatch / UploadItem schema** | 精确 JSON/MsgPack 结构，逐项 ACK，UploadItem 携带**完整 envelope**（含 device_type/scan_rate/contract_version/qualities） |
| 2 | **StreamEnvelope v1/v2 两版本契约表** | v1 七字段（device_code/device_type/group_code/scan_rate/ts/config_version/values）；v2 = v1 + contract_version=2 + qualities；Ingest 透传 v2，Writer 已支持；明确编码/解码/必填字段/非法版本行为 |
| 3 | **Redis Stream / latest 兼容键名与字段** | Stream 复用现有 collector 格式；latest 保持一 var_id 一个 JSON，扩展为 `{"v","t","q","e"}`，**不新增 hash 字段** |
| 4 | **固定 batch_id + 逐项 ACK + 错误码表** | batch_id 在 collector 写 outbox 时生成永不变；rejected 按 terminal/retryable/401-403/429-5xx 分类处理 |
| 5 | **版本双轨：节点级 revision + 组级 config_version** | 节点级 `desired/applied_revision` 用于配置同步；组级 `config_version` 随每条 item/entry 传。删 mapping_version，不删节点级 revision |
| 6 | **存储映射物理坐标（point_storage_mapping）** | 含 point_id/device_code/device_type_code/stable_name/child_table/group_code/td_column_name/var_type，永久不变；唯一约束 (device_code, td_column_name)；点位创建与 mapping 插入同事务；全量回填+校验+**差异非零阻断上线** |
| 7 | **latest 写入规则** | 一 var_id 一 JSON，Lua 用 cjson.decode 比较 t/e，incoming.ts>现值 或 (等值且高 epoch) 才更新；放进同一 Lua |
| 8 | **幂等去重：incarnation + local_seq + high_watermark + gap** | 去重身份 `(node_uuid, incarnation, local_seq)`；中心 high_watermark + gap；**修正 Lua 算法**（乱序重传去重/空洞连续消费）；补状态机测试用例；**序列重置与跳过协议**（处理 outbox 重建/FIFO 丢弃永久空洞） |
| 9 | **迁移裁决：严格时间窗 + 时钟偏差冻结** | 旧 epoch 只接受 ts<cutover_at，新 epoch 只接受 ts>=cutover_at；不贯通 Stream/Writer/TDengine；**冻结 max_clock_skew 阈值（默认±30s）+ 迁移时序（B 提前启动、A 延后停止）+ 超偏差门禁规则** |
| 10 | **Redis ACK durability + outbox 最大离线期** | "Redis 接纳成功即 ACK"，统一保留期参数；含容量公式+内存预算 |
| 11 | **节点认证强度** | mTLS 或对 method/path/timestamp/nonce/body_hash 签名 + 重放校验；token 绑定 UUID/公钥需有证明机制 |
| 12 | **Uploader 单例围栏** | 每节点只能运行一个 Uploader，用 OS mutex 或 SQLite `BEGIN EXCLUSIVE` leader lock 实施围栏 |

完成上述冻结后，"中心 Ingest + 边缘 SQLite/Uploader"的总体路线即可开工。**中心 MySQL 做配置真源、边缘 SQLite 只存本机快照、Web/App 全部查中心，这三项已确认合理。**

**v6 关闭的阻断问题**：
- **P0-1 (新)**: 修正 high_watermark+gap Lua 算法，乱序重传先检查 gap 避免重复写，空洞连续消费修正 while 逻辑（见 §8.2）
- **P0-2 (新)**: 增加 incarnation + 序列重置与跳过协议，处理 SQLite 重建序号复用、FIFO 丢弃永久空洞（见 §8.3、§12.1）
- **P0-3 (新)**: 明确 StreamEnvelope v1/v2 两版本契约表，冻结字段/编码/非法版本行为（见 §2.2）
- **P1-1**: 冻结时钟偏差阈值（默认±30s）、迁移时序（B 提前启动、A 延后停止）、超偏差门禁规则（见 §7.4）
- **P1-2**: Uploader 单例围栏，用 OS mutex 或 SQLite leader lock（见 §12.2）
- **P1-3**: 回填差异非零阻断上线（见 §10.3）

## 1. 背景与目标

现有部署是**单机集中式**：一台机器上 collector 采集 -> Redis Stream -> writer 入库 -> TDengine，配置与权限来自 MySQL，Web/App 经 Backend 读 MySQL + TDengine。

随着现场设备规模增长、地理分布变广，需要把**采集(collector)与数据上传下沉到多台边缘机**，每台边缘只负责一部分设备，数据统一汇聚到中心。目标：

- **横向扩展采集能力**：设备分摊到多台边缘机，单机压力下降。
- **就近采集**：边缘贴近现场设备，网络链路短、稳定。
- **中心统一**：配置、权限、历史数据、可视化仍以中心为唯一真源。
- **零迁移成本**：现有单机用户默认不受影响,不改配置就是原来那套。
- **多管理端**：几台领导电脑都能装 App 做管理，不只中心机一台。
- **轻量边缘**：边缘机不再需要 Redis/MySQL/TDengine，只需 SQLite + 采集/上传组件。

## 2. 总体架构与数据流

### 2.1 三种部署形态下的 Writer 语义统一

| 部署形态 | 数据流 | Writer 职责 |
|---------|--------|------------|
| **单机(现状)** | Collector -> 本地 Redis Stream -> **Writer** -> TDengine | 读 MySQL 映射，写 TDengine |
| **分布式-边缘** | Collector -> SQLite outbox -> **Uploader** -> 中心 Ingest | 边缘无 Writer,用 Uploader 上传 |
| **分布式-中心** | Ingest -> 中心 Redis Stream -> **Writer** -> TDengine | 读 MySQL 映射，写 TDengine |

**关键原则**: Writer 这个名字只留给"读 MySQL 映射、写 TDengine"的组件。边缘的数据转发组件叫 **Uploader**(上传器)，不叫 writer，避免语义混淆。

### 2.2 StreamEnvelope v1/v2：共享的 Redis 契约（P0 核心）

**必须复用现有 collector 的 Redis 格式，Ingest 绝不另造一套。** 现有 collector 与 Writer 已支持两版本契约：

#### 契约表（冻结）

| 项 | v1（现状默认） | v2（Q2 质量码） |
|---|---|---|
| **Stream 键** | `rt:stream:{device_type}:{group_code}:{shard_no}`<br/>分片: `shard_no = crc32(device_code) % shard_count` | 同 v1 |
| **Stream 字段** | `device_code, device_type, group_code, scan_rate, ts, config_version, values`<br/>`values` = msgspec.json 编码的 `{var_id: value_str}`，已过滤 STRING/is_storage=0 | v1 全部字段 +<br/>`contract_version: "2"`<br/>`qualities: {var_id: quality_code}` (msgspec.json) |
| **Latest 键** | `rt:latest:{device_code}:{group_code}` | 同 v1 |
| **Latest 字段** | 每个 var_id 一个 JSON: `{"v": value_str, "t": ts_ms, "q": quality_int, "e": epoch}`<br/>**不新增 `var_id:ts` 之类的独立 hash 字段** | 同 v1（`q` 字段 v1 时可为 0 或省略） |
| **UploadItem 必填** | `batch_id, local_seq, assignment_epoch, device_code, device_type, group_code, scan_rate, ts, config_version, values` | v1 全部 +<br/>`contract_version: 2, qualities` |
| **Writer 支持** | `writer/consumer.py:515` 已支持（contract_version 缺省=1） | `writer/consumer.py:552-650` 已支持（=2 时解析 qualities，严格校验键对齐） |
| **非法版本** | contract_version 不是 1 或 2 → 422 rejected → DLQ | 同 v1 |
| **Ingest 行为** | **透传 v2**：UploadItem 带什么版本就写什么版本到 Stream（不降级） | 同 v1 |
| **编码库** | `msgspec.json.encode` (collector/writer 现状) | 同 v1 |

**阶段 0 行动**：提取一个共享模块 `StreamEnvelope`，封装上述两版本的 stream key 生成、latest key 生成、分片算法、字段编码、latest JSON 编解码。由 standalone collector 与 Central Ingest **共用同一份代码**，保证格式一字不差。

**关键点**：
- **Latest 不新增 hash 字段**：保持 `ws_push.py:99-106` 的 hgetall 遍历契约，每 var_id 一个 `{"v","t","q","e"}` JSON，否则 `123:ts` 会被当成假点位推给 App
- **Ingest 透传 v2 不降级**：UploadItem 带 contract_version=2 + qualities 时，直接写 v2 到 Stream；Writer 已支持解析
- **Q2 前后兼容**：Q2 未开启时，UploadItem 省略 contract_version/qualities（默认 v1）；Q2 开启后必填 v2


### 2.3 完整链路图

```
━━━━━━━━━━━━━ 边缘机 (mode=edge) ━━━━━━━━━━━━━
  Collector 采集 (读本地 SQLite 配置快照)
    -> SQLite outbox (断网缓冲, batch_id + local_seq)
    -> Uploader (有序/限并发窗口)
    -> POST https://center/ingest  (UploadBatch{request_id, items[]})

  Edge Agent: 心跳 / 配置同步 / 身份令牌

━━━━━━━━━━━━━━━━━ 中心机 (mode=center) ━━━━━━━━━━
  反向代理 https://center
    ├─ /api/*    -> Backend :8000
    └─ /ingest/* -> Ingest  :8010

  Ingest :8010
    -> mTLS/签名校验 -> 校验归属/epoch -> 严格时间窗裁决
    -> 校验 envelope(含质量码)
    -> 节点级 high_watermark + gap 去重 (Redis Lua)
    -> StreamEnvelope v2 写中心 Redis
    -> latest 逐点时间戳比较更新 (同 Lua)
    -> 逐项 ACK

  中心 Redis :6379
    ├─ rt:stream:* -> 中心 Writer -> TDengine (历史持久化)
    └─ rt:latest:* -> Backend WebSocket -> App 实时监控

  Backend :8000 (TurboAPI)
    ├─ 管理接口 (设备/点位/用户/权限) -> MySQL
    ├─ 历史查询 -> TDengine
    └─ 实时推送 -> Redis rt:latest + WebSocket

  MySQL (配置/权限唯一真源)
  TDengine (全量历史数据)

━━━━━━━━━━━━━━━━━━━ 边缘 App (可选) ━━━━━━━━━━━━━
  查询数据 -> https://center/api  (中心 Backend)
  实时监控 -> 中心 Redis (通过 Backend WebSocket)
```

### 2.4 Central Ingest 的职责边界

**Ingest 负责**（顺序执行，逐项处理）：

1. 验证节点 mTLS/签名 + 节点 approved 状态
2. 逐项校验设备归属 + assignment_epoch + **严格时间窗**（见 §7）
3. 校验 config_version、数据格式、时间戳、质量码（envelope 自带，不查库补齐）
4. 逐项 local_seq 幂等判断（节点级 high_watermark + gap，Redis Lua 原子，见 §8.2）
5. 用 StreamEnvelope v2 写中心 Redis Stream（复用现有键格式）
6. 更新 rt:latest（一 var_id 一 JSON，逐点时间戳比较，见 §8.2）
7. （阶段3新增）PUBLISH rt:change 触发实时推送
8. 逐项返回 ACK（按错误码表分类，见 §8.1）

**Ingest 不负责**：
- 不直写 TDengine（交给中心 Writer）
- 不做业务查询、不管用户权限、不做长时间数据转换

**部署方式**：
- 第一阶段：与 Backend 同机，独立进程/端口（`:8010`），经反向代理统一入口。
- 后续扩展：多个无状态 Ingest 实例，通过中心 Redis 汇聚。

### 2.5 边缘机组件清单

**需要**：Edge Agent（身份/心跳/配置同步）、Collector（采集）、Uploader（上传）、SQLite（配置缓存 + outbox）、App（可选，查中心）

**不再需要**：Redis、Writer、MySQL、TDengine、Backend（边缘 App 直连中心 Backend）

## 3. 部署模式开关

分布式能力由**单一配置项**控制，避免多开关组合冲突。

### 3.1 部署模式配置

```toml
[deployment]
mode       = "standalone"          # standalone | center | edge
center_url = ""                    # edge 模式必填，指向反向代理统一入口 https://center
```

| mode 值 | 行为 | 适用场景 |
|---------|------|----------|
| **standalone** | 单机：collector -> 本地 Redis -> writer -> TDengine，读本地 MySQL 配置 | 现有单机部署，默认值，零迁移 |
| **center** | 中心：运行 Backend/Ingest/Writer，接受边缘上传，管理配置/权限 | 中心机 |
| **edge** | 边缘：collector 读本地 SQLite，uploader 上传中心，agent 心跳/配置同步 | 边缘机 |

**统一入口**：`center_url` 指向反向代理（方案 A），`/api/*` 转 Backend、`/ingest/*` 转 Ingest。边缘只配一个地址。若现场无反向代理，才拆成 `control_url` + `ingest_url`。

### 3.2 管理页面显示开关（独立于数据面）

中心侧 MySQL 系统配置 `distributed_management_ui_enabled`：off（默认，页面灰置）/ on（激活，超管可见）。

**关键设计**：此开关**只控制 UI 显示**，不影响数据面。即使管理页关闭，已投产边缘节点仍正常心跳、上传、接收配置。"关管理页" ≠ "停数据面"。

### 3.3 向后兼容

- 默认 `mode=standalone`，现有单机用户不改配置，行为完全不变。
- 切换分布式：中心机改 `mode=center` + 开管理页；边缘机改 `mode=edge` + 填 `center_url`。

## 4. 边缘 App 页面策略

原则：**保留全部页面，可见性纯由账号权限控制，数据查中心看全量。**

- **单代码库**：边缘 App 与中心 App 同一套前端，页面不删不裁。
- **权限区分**：超管看全部页面（含分布式管理、用户权限）；普通用户看不到管理类页面。复用现有导航权限过滤。
- **设备/点位管理**：边缘 App **查中心 Backend**，展示**全量设备/点位**。API base 指向反向代理统一入口。
- **实时监控**：边缘 App 通过中心 Backend WebSocket 订阅 rt:latest，数据源是中心 Redis。中心 Redis 轻松扛十几个并发（单实例上万 QPS）。
- **边缘与中心 App 唯一区别** = 配置的中心地址。

> **重要区分**：边缘 App 查中心看全量（给人看），与边缘 collector 读本地 SQLite 只采本机设备（给采集用）是两条独立数据路径。

## 5. 分布式管理页面（新增页面）

- 默认灰置；`distributed_management_ui_enabled=on` 后激活；仅超管可见。
- 功能：
  - **边缘节点列表**：在线/离线（心跳）、节点编号、node_uuid、最后心跳、当前配置修订号（applied_revision）、当前 high_watermark。
  - **注册审批**：新边缘机注册后审批通过，颁发节点令牌/证书。
  - **设备↔节点绑定**：把设备分配给指定边缘节点。
  - **故障重绑**：节点故障时重绑设备，触发 epoch 握手流程（见 §7）。

## 6. 心跳与配置推送（拉模式，版本双轨）

**版本双轨制**（修复"组级 config_version 被当节点级修订号"）：

| 概念 | 层级 | 用途 | 来源 |
|------|------|------|------|
| `desired_revision` / `applied_revision` | **节点级** | 配置快照同步：中心期望版本 vs 边缘已应用版本 | 中心为每个节点维护 |
| `config_version` | **组级** | 随每条 UploadItem / Stream entry 传输 | `device_point_group`（现状） |

- **边缘 -> 中心 心跳**（轮询，非 WebSocket）：Edge Agent 固定间隔 POST，携带 `node_uuid / applied_revision / 本地 high_watermark / 边缘本地时间 / 运行状态`。
- **配置推送 = 拉模式**：
  - 中心改某节点配置后 `desired_revision + 1`。
  - 边缘心跳带 `applied_revision`，中心响应告知最新 `desired_revision` + checksum。
  - 版本不一致 -> 边缘拉取属于自己的设备清单（每组各自带组级 config_version），校验 checksum，**原子切换本地 SQLite**（复用现有热重载），成功后回报 `applied_revision`。
- **离线自主**：中心不可达时，已审批且本地有有效配置快照的节点**继续采集缓存**；只有首次注册且 SQLite 为空的节点才进入等待。

## 7. 设备绑定与迁移（所有权围栏 + 严格时间窗）

### 7.1 assignment_epoch 的正确语义

**epoch 不是去重键，而是所有权围栏**，回答"这台设备当前归谁采集"。

- 绑定关系：`device_assignment(device_id, node_id, assignment_epoch, effective_at, cutover_at)`。
- **保留 assignment 历史**：主键至少含 `(device_id, assignment_epoch)`，不覆盖旧记录。

### 7.2 迁移握手流程（严格时间窗，消除重叠）

设备从节点 A 迁到 B，走**四步握手**：

```
1. 中心发新 epoch (assignment_epoch + 1，记录到 device_assignment，预设 cutover_at)
2. 新节点 B 应用配置并确认 (ACK)
3. 中心记录 cutover_at 生效 (以中心时间为准，不信边缘时钟)
4. 旧节点 A 停止采集并确认 (ACK)
```

**裁决规则（严格时间窗，彻底消除重叠）**：
- 旧 epoch 的数据：只接受 `ts < cutover_at`。
- 新 epoch 的数据：只接受 `ts >= cutover_at`。
- cutover 附近旧节点晚到的、`ts >= cutover_at` 的旧 epoch 数据 -> **拒绝并告警**（不进 latest、不进 Stream）。
- **不依赖"高 epoch 胜出"**，因此 Stream/Writer/TDengine **无需引入 epoch 字段**，契约不变（现状 `consumer.py:3-6` 流字段无 epoch，保持不变）。

### 7.3 握手超时与强制切换（旧节点离线无法完成第 4 步）

旧节点 A 离线/失联，无法回报第 4 步 ACK 时：

- **cutover grace**：cutover_at 后设一个宽限窗口 `cutover_grace`（远小于 max_offline_retention_days），允许旧节点补传 `ts < cutover_at` 的积压。
- **强制切换**：宽限期结束仍无 ACK，中心**强制完成迁移**，旧 epoch 此后任何数据一律拒绝。
- **重新上线围栏**：旧节点恢复后，心跳拉到新 `desired_revision` 发现自己已不持有该设备 -> 停采、清本地 assignment、转空闲或接新分配。若旧节点仍持旧 epoch 上传，按上条拒绝。

### 7.4 时钟与冲突裁决（冻结规则）

**时钟偏差阈值（冻结）**：
- **`max_clock_skew`**：默认 **±30 秒**，超出此偏差视为时钟异常。
- **心跳时钟比对**：边缘心跳携带 `edge_local_time_ms`（边缘本地时间戳），中心收到时记录 `center_received_at_ms`（中心时间）。
- **偏差计算**：`clock_skew = edge_local_time_ms - center_received_at_ms - estimated_rtt/2`（粗略，不考虑单程延迟差异）。
- **超偏差门禁**：
  - `|clock_skew| > max_clock_skew` → 节点标记 `clock_anomaly=true`，中心 system_log 告警。
  - **迁移阻断**：时钟异常节点**不可作为迁移目标**（新 assignment 被拒绝），已持有设备的节点可继续采集（数据仍接受，避免全节点停摆）。
  - **全局拒绝（可选，阶段 4）**：超偏差且无法自动校时时，可选择**拒绝该节点所有数据**，直到时钟恢复正常。

**迁移时序（冻结，修复"仍依赖边缘样本时钟"）**：

严格时间窗裁决（§7.2）用**边缘样本时间戳 `ts`** 与**中心生成的 `cutover_at`** 比较，因此必须冻结迁移时序，避免时钟偏差导致数据空洞或误拒：

1. **中心生成 `cutover_at`**（中心时间，不信边缘时钟），预留足够缓冲（建议 ≥ 2 × max_clock_skew）。
2. **新节点 B 提前启动采集**：B 在 `cutover_at - max_clock_skew` 时刻开始采集（若 B 时钟慢 30s，实际采集时间已是 cutover_at）。
3. **旧节点 A 延后停止采集**：A 在 `cutover_at + max_clock_skew` 时刻停止采集（若 A 时钟快 30s，采样时间戳仍 < cutover_at）。
4. **重叠期两节点同时采集**：重叠期 `[cutover_at - skew, cutover_at + skew]` 内，A/B 同时采集同一设备，中心按 `ts < cutover_at` / `ts >= cutover_at` 裁决，**样本级 TDengine 主键去重**兜底（同 ts 后到的覆盖前到的，不重复）。

**Latest 更新（仅 latest 层，不影响历史层）**：
- `incoming.t > 现值` → 更新该点 JSON
- `incoming.t == 现值 且 incoming.e > 现值.e` → 更新（高 epoch 优先）
- 否则 → 不更新

**时钟校时（建议，非强制）**：
- 边缘节点启用 NTP 自动校时，定期与中心时间同步。
- 首次注册时中心检查时钟偏差，超阈值告警并建议校时后重试。

### 7.5 幂等性分层

| 层次 | 机制 | 用途 |
|------|------|------|
| **所有权** | assignment_epoch + cutover + 严格时间窗 | 判断谁有权采、哪个时间窗接受 |
| **批次/序列** | local_seq + high_watermark + gap | 上传重试避免重复写 |
| **样本级** | 点位时间戳 | TDengine 主键去重 |

**系统语义承诺**："至少一次上传 + 幂等处理"，而非绝对 exactly-once 或"不丢不重"。

## 8. 数据上传与幂等方案

### 8.1 上传契约与错误码表

**batch_id 在 collector 写 outbox 时生成，此后永不改变**。每 item 另带 collector 节点内**单调递增的 `local_seq`** 和**节点级 `incarnation`**（用于中心 high_watermark 去重，见 §8.2/§8.3）。批量上传用 `request_id + items[]`，**每 item 直接携带完整 envelope**：

```json
POST /ingest
{
  "node_uuid": "...",
  "request_id": "本次HTTP请求ID(可重生)",
  "items": [
    {
      "batch_id": "collector生成,永不变(审计追踪)",
      "incarnation": 0,
      "local_seq": 12345,
      "assignment_epoch": 5,
      "device_code": "...",
      "device_type": "qc",
      "group_code": "g001",
      "scan_rate": 1000,
      "ts": 1721800000000,
      "config_version": 12,
      "contract_version": 2,
      "values": { "var_id": "value_str" },
      "qualities": { "var_id": "quality_code" }
    }
  ]
}
```

- `incarnation` / `local_seq`：去重身份三元组 `(node_uuid, incarnation, local_seq)`，必填
- `contract_version` / `qualities`：Q2 质量码开启后必填；未开启可省
- Ingest 用这些字段**直接生成 StreamEnvelope v1/v2**，不再回库拼第二份 envelope

**ACK 语义 = 逐项确认**（不是整批原子），按错误码表分类：

```json
{ "results": [ 
  { "batch_id": "...", "incarnation": 0, "local_seq": 12345, "status": "ack|duplicate", ... } 
] }
```

**ACK 回显三元组**：`batch_id + incarnation + local_seq`，边缘用三元组匹配 outbox 行更新状态。

**错误码表（冻结）**：

| HTTP | status | 边缘 outbox 动作 |
|------|--------|------------------|
| 200 | `ack` / `duplicate` | -> sent |
| 422 | `rejected` (stale_epoch / out_of_time_window / schema_bad / stale_config) | -> **dead**（terminal） |
| 401 / 403 | `unauthorized` | 暂停节点 + 触发重新认证（不变 dead） |
| 429 | `throttled` | -> retry_wait（backoff） |
| 5xx | `server_error` | -> retry_wait（backoff） |
| 网络失败 | (无响应) | 保持重试 |

（修复原稿"所有 rejected 都转 dead"的粗糙处理。）

### 8.2 中心 Ingest 幂等 + latest 防倒退（同一 Lua 原子）

**幂等去重改为 (node_uuid, incarnation, local_seq) 三元组 + high_watermark + gap，不再一条数据一个 Redis key**（修复 6 亿 key 内存爆炸）。

**修正后的 Lua 算法**（修复 v5 乱序重传重复写 + 空洞消费卡死）：

```lua
-- 逐 item 处理，全部在一个 Lua 内原子
-- 去重身份：(node_uuid, incarnation, local_seq)
local hw_key = "hw:" .. node_uuid .. ":" .. incarnation
local gap_key = "gap:" .. node_uuid .. ":" .. incarnation
local hw = tonumber(redis.call("GET", hw_key) or "0")

-- 1. 序列去重与 gap 管理
if local_seq <= hw then
    return "duplicate"  -- 已处理
end

if local_seq > hw + 1 then
    -- 乱序：先检查 gap 是否已存在（修复重传重复写）
    if redis.call("SISMEMBER", gap_key, local_seq) == 1 then
        return "duplicate"  -- 已在 gap，重传
    end
    -- 首次收到乱序：加入 gap，写 Stream
    redis.call("SADD", gap_key, local_seq)
else
    -- local_seq == hw + 1：连续，先写入再推进
end

-- 2. Stream 始终追加（历史不丢，非 duplicate 必写）
redis.call("XADD", stream_key, ...)  -- StreamEnvelope v1/v2

-- 3. latest 逐点比较：一 var_id 一个 JSON {"v","t","q","e"}
for var_id, val in pairs(values) do
    local cur = redis.call("HGET", latest_key, var_id)
    local cur_t = cur and cjson.decode(cur).t or -1
    local cur_e = cur and cjson.decode(cur).e or -1
    -- incoming.t > 现值，或 等值且高 epoch -> 更新该点 JSON
    if incoming_t > cur_t or (incoming_t == cur_t and incoming_epoch > cur_e) then
        redis.call("HSET", latest_key, var_id, cjson.encode({v=val,t=incoming_t,q=q,e=incoming_epoch}))
    end
end

-- 4. 推进 high_watermark（修复空洞消费逻辑）
if local_seq == hw + 1 then
    hw = local_seq
    -- 连续消费 gap 中的空洞（修复 v5 只检查 hw+1 就退出的 bug）
    while redis.call("SISMEMBER", gap_key, hw + 1) == 1 do
        redis.call("SREM", gap_key, hw + 1)
        hw = hw + 1
    end
    redis.call("SET", hw_key, hw)
end

return "ack"
```

**算法修正说明**：
1. **乱序重传去重**：收到 `seq > hw+1` 时，先检查 `gap` 是否已含该 seq，已含则返回 duplicate，避免重复 XADD。
2. **空洞连续消费**：`local_seq == hw+1` 时，先推进 `hw = local_seq`，**然后** while 循环检查 `gap[hw+1]`，逐个消费连续空洞直到遇到真空洞才停。

**状态机测试用例（阶段 0 必须通过）**：

**初始状态**：hw=10（已确认到 seq=10），gap={}

| 到达序列 | 预期 hw 轨迹 | 预期 gap 轨迹 | 预期 XADD 次数 | 说明 |
|---------|-------------|--------------|---------------|------|
| `12,11` | 10→10→12 | {}→{12}→{} | 2（12,11各1次） | v5 失效场景：修正后 seq=11 推进 hw=11，while 消费 gap[12]→hw=12 |
| `12,12` | 10→10 | {}→{12}→{12} | 1（12首次1次） | 乱序重传：第二个12检查 gap 已含→duplicate，不重复写 |
| `13,12,11` | 10→10→10→13 | {}→{13}→{12,13}→{} | 3 | seq=11 推进 hw=11，while 消费 gap[12]→hw=12，while 消费 gap[13]→hw=13 |
| `14,12,13,11` | 10→10→10→10→14 | {}→{14}→{12,14}→{12,13,14}→{} | 4 | seq=11 推进后连续消费 12,13,14 |
| `11,12,13` | 10→11→12→13 | 始终 {} | 3 | 顺序场景，无 gap |

**关键点**：
- **Stream 与 latest 分开处理**：Stream 永远追加（历史完整），latest 只反映"最新时间戳的值"。
- **Latest 不新增 hash 字段**：保持 `ws_push.py` 的 hgetall 遍历契约，每 var_id 一个 `{"v","t","q","e"}` JSON。
- **gap 集合有界前提**：Uploader 限制每节点有序发送或并发窗口（如 ≤ 64），gap 集合大小被窗口封顶。**但 FIFO 丢弃会产生永久空洞**，需序列跳过协议（见 §8.3）。
- **batch_id 保留作审计追踪**，不再是去重主键。

### 8.3 序列重置与跳过协议（处理 incarnation 切换与永久空洞）

**问题根源**：
1. **SQLite 重建后序号复用**：outbox 清空/损坏/恢复备份后，`local_seq` 从 1 重新开始，中心 hw=1000 会把新数据全当 duplicate。
2. **FIFO 丢弃后永久空洞**：边缘水位达上限，丢弃 pending 序号 101-200，上传 201 → 中心判 `201 > 100+1` 加入 gap，但 101-200 永不到达 → **hw 永久卡在 100，所有后续 seq 全进 gap，gap 无界增长**，违背 §8.2 "gap 有界"前提。
3. **422 terminal 转 dead 也会制造永久空洞**：如 seq=150 因 stale_epoch → dead，永不重传。

**解决方案：中心分配 incarnation + 中心主动跳过 Lua**

#### 8.3.1 incarnation（序列纪元，中心分配）

**中心单调分配 incarnation**（不依赖边缘 SQLite）：

- **初始注册**：边缘首次注册时，中心为该 node_uuid 分配 `incarnation=0`，记录到 `sys_node.current_incarnation`
- **触发条件**：
  - outbox 清空/损坏/恢复旧备份
  - SQLite 重建
  - 手动重置（运维工具）
- **重置流程**：
  1. 边缘检测到需要重置（如 SQLite 丢失/损坏），**停止上传**
  2. 边缘心跳携带 `request_new_incarnation: true` + 原因（sqlite_lost / manual_reset）
  3. **中心分配新 incarnation**：`UPDATE sys_node SET current_incarnation = current_incarnation + 1 WHERE node_uuid = ? RETURNING current_incarnation`
  4. 中心响应心跳：`new_incarnation: 1`（CAS 确认）
  5. 边缘收到新 incarnation 后：
     - 持久化到 Agent DPAPI 状态（与 node_uuid 同级，**不依赖 SQLite**）
     - 镜像到 SQLite metadata 表：`INSERT OR REPLACE INTO metadata(key, value) VALUES('incarnation', '1')`
     - `local_seq` 从 1 重新开始
     - 清空 `skipped_sequences` 表（旧 incarnation 跳过区间作废）
     - 恢复上传
  6. 中心为新 incarnation 创建新的 `hw:{node_uuid}:{incarnation}` 和 `gap:{node_uuid}:{incarnation}` Redis key
- **去重身份**：`(node_uuid, incarnation, local_seq)` 三元组，不同 incarnation 的序列互不干扰
- **边缘启动恢复**：
  - 从 Agent DPAPI 读 incarnation（真源）
  - 对比 SQLite metadata 表的 incarnation 镜像
  - 不一致 → 说明 SQLite 被重建/恢复旧备份 → 请求新 incarnation

#### 8.3.2 序列跳过协议（中心主动 Lua 状态转换，不依赖已丢弃数据到达）

**三种永久空洞来源**：
1. **FIFO 丢弃**：边缘水位达上限，按 FIFO 删除最旧 pending 行
2. **terminal dead**：422 rejected (stale_epoch/out_of_window/schema_bad) → dead，永不重传
3. **序号分配空洞**：next_seq 递增后、outbox INSERT 前崩溃 → 分配的序号永久缺失

**中心主动跳过 Lua**（不依赖已丢弃的 item 到达）：

1. **边缘记录跳过区间**：
   - FIFO 丢弃 pending 行时，记录其 `(incarnation, local_seq)` 到本地 `skipped_sequences` 表
   - terminal dead 时，同样记录到 `skipped_sequences`
   - 聚合连续序号为区间（如 101-200）
   
2. **心跳携带跳过声明**：
   - 心跳 payload 增加 `skip_ranges: [{incarnation, start, end, reason}]`（仅携带尚未确认的区间）
   - 中心收到后先**校验合法性**（start > hw，区间不重叠，reason 合法），然后记录到 `sys_node_skipped_seq(node_uuid, incarnation, seq_start, seq_end, reason, declared_at, confirmed_at)`

3. **中心主动推进 watermark（Lua 状态转换）**：
   
   ```lua
   -- 定期执行（如心跳确认 skip 后立即执行，或每 10s 扫描一次）
   local hw_key = "hw:" .. node_uuid .. ":" .. incarnation
   local gap_key = "gap:" .. node_uuid .. ":" .. incarnation
   local hw = tonumber(redis.call("GET", hw_key) or "0")
   
   -- 从 MySQL sys_node_skipped_seq 读取已确认的 skip ranges（incarnation 匹配）
   local skip_ranges = load_confirmed_skip_ranges(node_uuid, incarnation)
   
   while true do
       local next_seq = hw + 1
       local moved = false
       
       -- 检查 next_seq 是否在某个 skip range 内
       for _, range in ipairs(skip_ranges) do
           if next_seq >= range.start and next_seq <= range.end then
               hw = range.end  -- 跳过整个区间
               moved = true
               break
           end
       end
       
       -- 检查 gap 是否包含 next_seq
       if not moved and redis.call("SISMEMBER", gap_key, next_seq) == 1 then
           redis.call("SREM", gap_key, next_seq)
           hw = next_seq
           moved = true
       end
       
       -- 无法继续推进 → 退出
       if not moved then
           break
       end
   end
   
   redis.call("SET", hw_key, hw)
   return hw
   ```

4. **确认与清理**：
   - 中心响应心跳时携带 `confirmed_skip_ranges: [{incarnation, start, end}]`
   - 边缘收到确认后：
     - 更新本地 `skipped_sequences.confirmed = 1`
     - 定期清理已确认的旧区间（保留最近 7 天供审计）

#### 8.3.3 中心 Redis 恢复（引入 dedupe_generation）

中心 Redis 清空/故障恢复后，`hw:{node_uuid}:{incarnation}` 丢失：

1. **中心维护 dedupe_generation**：
   - MySQL `sys_node` 表增加 `dedupe_generation`（初始=0）
   - Redis 完全恢复/清空后，中心 `UPDATE sys_node SET dedupe_generation = dedupe_generation + 1 FOR ALL`
   - 心跳响应携带当前 `dedupe_generation`

2. **边缘检测 generation 变化**：
   - 边缘缓存上次心跳的 `dedupe_generation`
   - 收到新 generation → **停止上传**，请求 rebase

3. **边缘请求 rebase**：
   - 心跳携带 `request_rebase: true` + `current_outbox_min_seq` / `max_seq` + `pending_count` / `sent_count` / `dead_count`

4. **中心 rebase**：
   - 从 `sys_node_skipped_seq` 重建 skip ranges（incarnation 匹配）
   - 保守设置 `hw:{node_uuid}:{incarnation} = 0`（**不猜测 min_seq-1**，避免 pending 中间夹 sent/dead 的情况）
   - 清空 `gap:{node_uuid}:{incarnation}`
   - 执行一次 skip Lua 推进 hw（跳过已确认的 skip ranges）
   - 响应边缘：`rebase_confirmed: true, new_hw, new_dedupe_generation`

5. **边缘重传**：
   - 缓存新 `dedupe_generation`
   - 从 `state='pending' OR state='retry_wait'` 的所有行开始重传（按 local_seq 升序）
   - 已 sent 的行不重传（已确认入库）
   - dead 的行不重传（terminal rejected）

#### 8.3.4 local_seq 分配原子性与空洞防御

**原子分配**（避免分配空洞）：

```sql
-- next_seq 递增与 outbox INSERT 必须在同一事务
BEGIN;
UPDATE metadata SET value = value + 1 WHERE key = 'next_seq' RETURNING value AS seq;
INSERT INTO outbox(batch_id, incarnation, local_seq, ...) VALUES(?, ?, seq, ...);
COMMIT;
```

**唯一约束**（防止重复分配）：
```sql
UNIQUE (incarnation, local_seq)
```

**分配空洞兜底**（崩溃后检测）：
- Collector 启动时检查：last_inserted_seq 与 metadata.next_seq 是否连续
- 不连续 → 记录空洞区间到 `skipped_sequences`（reason='alloc_gap'），心跳声明跳过

#### 8.3.5 容量修正

- **watermark**：每节点每 incarnation 1 个 string key，`N × I` 个（I 为平均 incarnation 数，正常 ≤ 5），`N × I × 100B`，可忽略。
- **gap 集合**：每节点每 incarnation ≤ 并发窗口（如 64，**窗口锚定 hw+1，禁止滑过空洞**），`N × I` 个 set，内存 = `N × I × 64 × ~16B`，正常 < 100KB。
- **skipped_sequences 表**：边缘本地 SQLite，每节点 < 200 行（聚合为区间，含 FIFO/terminal/alloc_gap 三类），可忽略。
- **sys_node_skipped_seq**：中心 MySQL，每节点 < 200 行，可忽略。

**对比旧方案**：旧方案无 incarnation，SQLite 重建后序号复用导致全部 duplicate；无跳过协议，FIFO 丢弃后 gap 无界增长（6.05 亿 key）。新方案 incarnation 由中心分配（不依赖 SQLite），skip 由中心主动推进（不依赖已丢弃数据到达）。

目标参数：设备数 `D`、每设备扫描频率 `R`(条/秒)、节点数 `N`、保留天数 `P`。

- **high_watermark**：每节点 1 个 string key，N 个，可忽略。
- **gap 集合**：每节点 ≤ 并发窗口大小（如 64），N 个 set，内存 = N × 64 × ~16B，可忽略。
- **outbox 积压上限**：单节点 `D_node × R × 86400 × P` 行；按磁盘字节预算（见 §12.4）。
- **中心 Redis Stream**：受 `stream_maxlen` 封顶，与现有单机一致。
- **对比旧方案**：旧方案 dedupe key 数 = `D × R × 86400 × P`（1000×1×86400×7 ≈ 6.05 亿 key，不可接受）；新方案 dedupe 状态 = N 个 watermark + N 个有界 gap，**与设备数/频率/保留期无关**，内存恒定。

### 8.4 容量公式与内存预算（阶段 0 必填）

目标参数：设备数 `D`、每设备扫描频率 `R`(条/秒)、节点数 `N`、保留天数 `P`、平均 incarnation 数 `I`（正常 ≤ 5）。

- **high_watermark**：每节点每 incarnation 1 个 string key，`N × I` 个，`N × I × 100B`，可忽略。
- **gap 集合**：每节点每 incarnation ≤ 并发窗口（如 64，**窗口锚定 hw+1，禁止滑过空洞**），`N × I` 个 set，内存 = `N × I × 64 × ~16B`，正常 < 100KB。
- **skipped_sequences 表**：边缘本地 SQLite，每节点 < 200 行（聚合为区间，含 FIFO/terminal/alloc_gap 三类），可忽略。
- **sys_node_skipped_seq**：中心 MySQL，每节点 < 200 行，可忽略。
- **outbox 积压上限**：单节点 `D_node × R × 86400 × P` 行；按磁盘字节预算（见 §12.4）。
- **中心 Redis Stream**：受 `stream_maxlen` 封顶，与现有单机一致。
- **对比旧方案**：旧方案 dedupe key 数 = `D × R × 86400 × P`（1000×1×86400×7 ≈ 6.05 亿 key，不可接受）；新方案 dedupe 状态 = `N × I` 个 watermark + `N × I` 个有界 gap，**与设备数/频率/保留期无关**，内存恒定。

### 8.5 ACK durability 语义

- 承诺明确为：**"中心 Redis 接纳成功即 ACK"**，而非"已落盘"。
- AOF `everysec` 下中心掉电仍可能丢失已 ACK 的一小段数据。
- 阶段 0 需**冻结 Redis AOF / fsync / 备份 / 恢复策略**。若要求强 ACK，需额外等待副本/持久化确认（第一阶段不做）。

**现状**：`backend/app/services/ws_push.py` 是每 100ms 轮询 rt:latest，已能约 1 秒更新。

**性能指标**：中心收到数据后 1 秒内反映到实时监控页（轮询现状已满足，PUBLISH 可优化到更低延迟）。

## 10. 点位映射方案（决策 A：独立 point_storage_mapping，冻结完整物理坐标）

**核心原则：采集配置与入库映射彻底解耦，存储身份 + 物理坐标永久不变。**

### 10.1 独立存储映射表（含完整物理坐标）

TDengine 物理位置由 `device_type -> stable(超级表)` + `device_code -> child_table(子表)` + `td_column_name(列)` 共同决定。三者任一变化都会导致历史解码错位，因此映射表必须**冻结完整坐标**：

```sql
CREATE TABLE point_storage_mapping (
    point_id        BIGINT PRIMARY KEY,         -- = device_variable.id，永久身份
    device_code     VARCHAR(64)  NOT NULL,
    device_type_code VARCHAR(32) NOT NULL,      -- 决定 stable = sd{type_code}，永久不变
    stable_name     VARCHAR(64) NOT NULL,       -- 冗余存储，永久不变
    child_table     VARCHAR(64) NOT NULL,       -- = device_code，冗余存储，永久不变
    group_code      VARCHAR(64) NOT NULL,
    td_column_name  VARCHAR(32) NOT NULL,       -- 永久不变，永不复用
    var_type        VARCHAR(32) NOT NULL,       -- 永久不变
    created_at      DATETIME(3) NOT NULL,
    UNIQUE KEY uk_device_col (device_code, td_column_name)
    -- 注意：无 deleted / enable 过滤，此表只增不改不删
);
```

### 10.2 规则

- **物理坐标永久不变**：point_id、td_column_name、device_type_code、stable_name、child_table、var_type、group_code 一经建立**不可原地修改**。
- **产生历史后不可改的字段**：`device_code`、设备类型（type_id）、`group_code`、`td_column_name`。这些字段在 `catalog.py` 现状允许编辑（如 `update_device:606` 可改 type_id），分布式上线后必须冻结（要变则作废旧 point、建新 point_id，旧行永久保留）。
- 需要改类型或换组 -> **作废旧 point、创建新 point_id**（旧行永久保留供补传解码）。
- **删除点位：只软删采集配置**（`device_variable.deleted=1`），`point_storage_mapping` 行**保留不动**。
- **Writer 的存储映射查询走 `point_storage_mapping`**，不带 `deleted/enable` 过滤，因此软删/禁用/换组后旧数据仍可映射。
- **config_version 不一致只触发重载 + 告警，不拒绝旧点映射**（修复现状 `mysql_mapper.py` 版本不符降级/返回 None 的问题）。
- **不引入 mapping_version**--组级 `config_version` 仍随每条 item/entry 传。

### 10.3 点位创建与回填

- **同事务**：点位创建/编辑时，`device_variable` 写入与 `point_storage_mapping` 插入必须在**同一 MySQL 事务**，避免半写导致映射缺失。
- **全量回填**：上线时对现有 `device_variable` 全量回填 `point_storage_mapping`：
  - 从 `device_variable` JOIN `device_point_group` JOIN `device` JOIN `device_type` 取现有 point_id/device_code/type_code/group_code/td_column_name/var_type；
  - 计算 `stable_name = sd{type_code}`、`child_table = device_code`；
  - **使用 staging 表校验后正式插入**（不用 INSERT IGNORE）：
    1. 先插入 `point_storage_mapping_staging`
    2. 校验：`staging.point_id` 与 `device_variable.id` 一一对应（无缺漏、无孤儿）
    3. 校验：`staging` 内 `(device_code, td_column_name)` 无重复
    4. 校验：`staging` 的 device_code/type_code/td_column_name 与 `device_variable` JOIN 结果一致
    5. 产出差异报告（missing/conflict/orphan）
    6. **差异非零 → 阻断上线**：人工修复差异后重新回填，直到差异报告为空
    7. 差异为空 → `INSERT INTO point_storage_mapping SELECT * FROM point_storage_mapping_staging`
    8. 清空 staging 表
- **回填校验门禁（冻结）**：
  - 差异报告非空 → **阻断分布式上线**，回滚 `mode=center/edge` 配置，停止 Ingest/Uploader 启动
  - 差异报告示例：`MISSING: point_id=123 (device_code=D001, var_name=温度); CONFLICT: (D002, temp) mapped to point_id=456 and 789; ORPHAN: staging has point_id=999 not in device_variable`
  - 人工修复（补建 device_variable / 删除孤儿 / 解决冲突）后重新回填，循环直到差异为空

### 10.4 与旧方案对比（撤销）

| 旧方案（凭空设计，已撤销） | v5 方案 |
|---|---|
| 新增 `mapping_version` 表 | **删除，不引入** |
| 存储映射只存 device_code/group_code/col/type | **补 device_type_code + stable_name + child_table** |
| 存储映射与采集配置同表(带 deleted/enable 过滤) | 独立表，无过滤 |
| 版本不符拒绝映射 | 版本不符只重载+告警 |
| VARCHAR 无长度（非法 MySQL DDL） | **VARCHAR(64)/VARCHAR(32) 补长度** |
| 无唯一约束 | **UNIQUE (device_code, td_column_name)** |

### 10.5 收益

- 断网补传老数据 / 软删禁用点 / 换组 / Backend 重启缓存清空后，存储映射恒定可查。
- 物理坐标冻结后，TDengine 历史数据不会因设备类型被改而错位。
- 采集侧的启停、禁用、软删完全不影响入库解码。

## 11. 节点身份与安全

### 11.1 节点身份

- **node_uuid**：首次部署生成并持久化（**不用 MAC+hostname 拼接**，避免换网卡/改主机名后身份漂移）。
- 中心侧 `sys_node` 表以 node_uuid 为主键，存公钥/证书指纹。

### 11.2 注册与认证（先生成身份，mTLS/签名证明）

```
1. 边缘首次启动：先生成并持久化 node_uuid + 本地密钥对/证书
2. 引导时输入一次性 enrollment token (中心生成)
3. 用 enrollment token + node_uuid + 公钥/CSR 向中心注册
4. 中心审批后颁发长期 node token + 签发节点证书，绑定到该 node_uuid / 公钥
5. node token 存储：Windows 经 Agent DPAPI 加密 (不落明文 SQLite)
6. 后续通信认证（二选一，阶段0 冻结）：
   a. mTLS：边缘证书 + 中心证书双向校验（推荐，运维需证书分发）
   b. 签名：每次请求对 method/path/timestamp/nonce/body_hash 用私钥签名，
      中心校验签名 + timestamp/nonce 防重放
```

**仅发 Bearer token 不算"绑定公钥"**--必须有 mTLS 或请求签名才能让公钥绑定生效（修复原稿无证明机制的问题）。

### 11.3 令牌吊销与轮换

- 中心可**吊销/轮换** node token / 证书（节点丢失、下线、泄露）。
- 被吊销节点的上传返回 401，边缘停止并告警。
- 与 §7 epoch 围栏配合：吊销令牌 + 收回 assignment。

## 12. 边缘断网缓冲（SQLite outbox）

**边缘不再需要 Redis**--用 SQLite outbox 做断网缓冲。

### 12.1 表结构（含崩溃恢复字段 + incarnation + local_seq）

```sql
CREATE TABLE IF NOT EXISTS outbox (
    batch_id       TEXT PRIMARY KEY,          -- collector 生成,永不变(审计)
    incarnation    INTEGER NOT NULL,          -- 序列纪元,中心分配(去重身份第2元)
    local_seq      INTEGER NOT NULL,          -- 节点内单调递增,去重身份第3元
    device_code    TEXT NOT NULL,
    group_code     TEXT NOT NULL,
    assignment_epoch INTEGER NOT NULL,
    config_version INTEGER NOT NULL,
    ts             INTEGER NOT NULL,
    payload        BLOB NOT NULL,             -- StreamEnvelope v1/v2 完整 envelope
    state          TEXT NOT NULL DEFAULT 'pending',
    attempt_count  INTEGER NOT NULL DEFAULT 0,
    next_retry_at  INTEGER,
    last_error     TEXT,
    http_status    INTEGER,
    lease_owner    TEXT,                      -- 崩溃恢复：占用该 inflight 的 uploader 实例ID
    inflight_at    INTEGER,
    lease_until    INTEGER,                   -- 租约到期，过期可回收
    acked_at       INTEGER,
    dead_at        INTEGER,
    created_at     INTEGER NOT NULL,
    UNIQUE (incarnation, local_seq)           -- 防止重复分配
);
CREATE INDEX IF NOT EXISTS idx_outbox_state_retry ON outbox(state, next_retry_at);
CREATE INDEX IF NOT EXISTS idx_outbox_created ON outbox(created_at);
CREATE INDEX IF NOT EXISTS idx_outbox_lease ON outbox(state, lease_until);
CREATE INDEX IF NOT EXISTS idx_outbox_seq ON outbox(incarnation, local_seq);

-- 元数据表：存储 incarnation 镜像（真源在 Agent DPAPI）
CREATE TABLE IF NOT EXISTS metadata (
    key   TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
-- INSERT INTO metadata(key, value) VALUES('incarnation', '0') ON CONFLICT DO NOTHING;
-- INSERT INTO metadata(key, value) VALUES('next_seq', '1') ON CONFLICT DO NOTHING;

-- 跳过序列表：记录 FIFO 丢弃/terminal dead/序号分配空洞
CREATE TABLE IF NOT EXISTS skipped_sequences (
    incarnation INTEGER NOT NULL,
    seq_start   INTEGER NOT NULL,
    seq_end     INTEGER NOT NULL,
    reason      TEXT NOT NULL,                -- 'fifo_discard' / 'terminal_dead' / 'alloc_gap'
    discarded_at INTEGER NOT NULL,
    confirmed   INTEGER NOT NULL DEFAULT 0,  -- 0=未确认, 1=中心已确认
    PRIMARY KEY (incarnation, seq_start)
);
```

**incarnation 分配与持久化**（中心分配，不依赖 SQLite）：
- **真源**：中心 MySQL `sys_node.current_incarnation`
- **边缘持久化层级**：
  1. **Agent DPAPI 状态**（与 node_uuid 同级，真源，SQLite 丢失后可恢复）
  2. **SQLite metadata 表镜像**（快速读取）
- **初始注册**：边缘首次注册时，中心分配 `incarnation=0`
- **请求新 incarnation**：边缘检测到 SQLite 丢失/损坏 → 心跳 `request_new_incarnation: true` → 中心分配新值 → 边缘持久化到 DPAPI + SQLite
- **启动恢复**：从 DPAPI 读 incarnation，对比 SQLite 镜像，不一致 → 请求新 incarnation

**local_seq 分配机制（原子，防止分配空洞）**：
```sql
-- next_seq 递增与 outbox INSERT 必须在同一事务
BEGIN;
UPDATE metadata SET value = value + 1 WHERE key = 'next_seq' RETURNING value AS seq;
INSERT INTO outbox(batch_id, incarnation, local_seq, ...) VALUES(?, ?, seq, ...);
COMMIT;
```

**分配空洞检测**（崩溃后启动检查）：
- Collector 启动时检查：`SELECT MAX(local_seq) FROM outbox WHERE incarnation = ?` 与 `metadata.next_seq` 是否连续
- 不连续 → 记录空洞区间到 `skipped_sequences`（reason='alloc_gap'），心跳声明跳过

### 12.2 状态机（含崩溃恢复 + 错误码分类 + 单例围栏）

```
pending ──领取(占租约,新lease_owner)──> inflight ──ack/duplicate──> sent
                                          │
                                          ├── retryable(429/5xx/网络) ──> retry_wait ──> pending
                                          ├── 401/403 ──> 暂停节点,触发重新认证(不变状态)
                                          ├── terminal(422 stale_epoch/out_of_window/schema) ──> dead (记录到 skipped_sequences)
                                          └── uploader崩溃 ──> (启动回收旧owner或lease过期)──> pending
```

**terminal dead 处理**：
- 422 rejected (stale_epoch/out_of_window/schema_bad) → `state='dead'`，同时记录到 `skipped_sequences`（reason='terminal_dead'）
- 心跳携带跳过声明，中心确认后推进 watermark（见 §8.3.2）

**Uploader 单例围栏（冻结，防止多实例抢任务）**：

每节点**只能运行一个 Uploader 实例**，用以下机制之一实施围栏：

1. **OS mutex（推荐，Windows）**：
   - 启动时创建全局命名 Mutex（如 `Global\DataWatch_Uploader_{node_uuid}`）
   - 创建失败 → 已有实例运行 → 退出并告警
   - 进程退出时 OS 自动释放 Mutex

2. **文件锁（推荐，跨平台）**：
   - 启动时对 `{data_dir}/uploader.lock` 文件加排他锁（`fcntl.flock` / `msvcrt.locking`）
   - 加锁失败 → 已有实例运行 → 退出并告警
   - 进程退出时 OS 自动释放文件锁

3. **短事务 generation（备选，复杂）**：
   - `metadata` 表增加 `uploader_generation`（初始=0）
   - 启动时 `UPDATE metadata SET value = value + 1 WHERE key='uploader_generation' RETURNING value`
   - 领取任务时 `UPDATE outbox SET lease_owner='{gen}' WHERE ...`，检查返回的 `lease_owner` 是否等于当前 gen
   - 旧实例发现自己 gen 过期 → 主动退出

**不推荐 BEGIN EXCLUSIVE 长时间持有**（会阻塞 Collector 写 outbox）。

**崩溃恢复（不依赖墙上时间为主路径）**：
- 每次 Uploader 启动生成新的 `lease_owner`（UUID 或 timestamp）
- 启动时**立即把所有旧 owner 的 inflight 复位为 pending**（主路径，不依赖时间）：
  ```sql
  UPDATE outbox SET state='pending', lease_owner=NULL, lease_until=NULL 
  WHERE state='inflight' AND (lease_owner != '{current_owner}' OR lease_owner IS NULL)
  ```
- `lease_until` 过期作为兜底（时间回拨时也能回收）：
  ```sql
  UPDATE outbox SET state='pending', lease_owner=NULL 
  WHERE state='inflight' AND lease_until < current_timestamp_ms
  ```

**领取原子性**：
- 领取任务用 SQLite 原子事务（`UPDATE ... WHERE state='pending' ... RETURNING`），避免多 Uploader 抢同一行（但单例围栏已阻止多实例）
- **exponential backoff**：attempt_count 驱动 next_retry_at
- 重试始终用同一 batch_id + incarnation + local_seq（中心 high_watermark 幂等兜底）

### 12.3 SQLite 运行参数与磁盘释放

- `journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout`。
- 定期 WAL checkpoint，避免 WAL 无限增长。
- **删行后磁盘释放**：达 95% 水位删除过期 sent/dead 行后，必须执行 `PRAGMA wal_checkpoint(TRUNCATE)` 或 `VACUUM`（或 incremental_vacuum），否则 SQLite 文件未必实际释放磁盘空间给操作系统。

### 12.4 容量、保留与清理

- **统一 `max_offline_retention_days`**：约束 outbox 积压上限 + 中心 gap/watermark 保留（**不含"映射保留"**--映射在 point_storage_mapping 永久保留）。
- **清理规则**：`sent` 记录超过保留期按 `acked_at` 清理；`dead` 记录按 `dead_at` 保留一段供排障后清理；清理后执行 §12.3 的 checkpoint/vacuum。
- **容量按磁盘字节数评估，不按行数**（点位值长度差异大）。
- **水位告警**：磁盘占用 70% / 85% / 95% 三级告警；达上限按 FIFO 丢最旧 pending 并记录丢弃计数，随后 checkpoint/vacuum 释放空间。
- 承诺明确为"**尽力缓冲 max_offline_retention_days**"，超出即丢最旧并告警，不承诺无限缓冲。

| Ingest | - | - | 接收上传+high_watermark去重+写中心Redis |

| App | 查本机 | **直连中心Backend(经反向代理)** | 查本机 |
| 配置源 | 本机MySQL | 中心MySQL(SQLite只读缓存本机设备) | MySQL权威 |

（Writer 只写 TDengine 不写 MySQL；edge 无本机 Backend，App 直连中心。）

## 15. 数据库改动

- **不引入 mapping_version**（决策 A）。
- **新增 `point_storage_mapping`**（point_id 主键、device_code/device_type_code/stable_name/child_table/group_code/td_column_name/var_type，永久保留，无 deleted/enable 过滤，UNIQUE(device_code,td_column_name)，见 §10）。
- 组级 `config_version` 复用现有（device_point_group 已有，Writer/collector 已用）。
- 新增 `sys_node`（node_uuid 主键、公钥/证书指纹、token 状态、**desired_revision/applied_revision**、**current_incarnation**、**dedupe_generation**、**当前 high_watermark**、时钟偏差、心跳时间、水位）。
- 新增 `sys_node_skipped_seq`（node_uuid/incarnation/seq_start/seq_end/reason/declared_at/confirmed_at，记录节点 FIFO 丢弃/terminal dead/序号分配空洞的序列区间）。
- 新增 `device_assignment(device_id, assignment_epoch, node_id, effective_at, cutover_at, cutover_status)`，保留历史，含 cutover_grace/强制切换状态。
- 采集侧 `device_variable` 保留现有 `deleted/enable`（只影响采集，不影响 point_storage_mapping）。
- **冻结可编辑字段**：`update_device`/`update_point` 产生历史后禁止原地改 device_code/type_id/group_code/td_column_name（要改走作废+新建）。
- **字段以数据库现状为准，不一致改代码不改 schema**。

## 16. MySQL 并发评估

- 中心 writer 单进程消费中心 Redis Stream 入库（读 MySQL/point_storage_mapping 映射，写 TDengine，见 §2.1）。
- MySQL 连接池默认 `pool_size=5 + max_overflow=10 = 15` 并发；TDengine `pool_size=5, max_overflow=0`。
- 实时监控**直接查中心 Redis**，不压 MySQL；十几个 App 并发无压力。
- App 的历史/配置查询走 Backend -> MySQL，属低频，现有连接池足够。
- point_storage_mapping 查询走 Writer 缓存（config_version 命中即用缓存），高频场景不直压 MySQL。

## 18. 关键设计决策（汇总）

1. **Writer 语义统一**：standalone 与 center 的 Writer 同一套--读 MySQL/point_storage_mapping 映射、只写 TDengine；Ingest 不自造格式、不直写 TDengine。
2. **StreamEnvelope v2 复用现有 Redis 契约**：Stream 键 `rt:stream:{device_type}:{group_code}:{shard_no}`（crc32 分片）、latest 键 `rt:latest:{device_code}:{group_code}`；latest 保持一 var_id 一 JSON，扩展为 `{"v","t","q","e"}`，不新增 hash 字段。
3. **反向代理单 center_url**（决策 A）：`/api/*`->Backend:8000，`/ingest/*`->Ingest:8010。
4. **版本双轨**：节点级 `desired/applied_revision` + 组级 `config_version`；删 mapping_version。
5. **独立 point_storage_mapping**（决策 A）：含完整物理坐标（device_type_code/stable_name/child_table），永久不变，无过滤；版本不符只重载+告警；唯一约束+同事务+全量回填。
6. **UploadItem 携带完整 envelope + local_seq**；batch_id 永不变（审计）；逐项 ACK 按错误码表分类。
7. **epoch 严格时间窗裁决**（决策）：旧 ts<cutover、新 ts>=cutover，消除重叠；不贯通 Stream/Writer/TDengine；补握手超时/强制切换/重新上线围栏。
8. **latest 逐点时间戳比较防倒退**（一 var_id 一 JSON），与 high_watermark 幂等同一 Lua 原子。
9. **幂等去重 = 节点级 local_seq + high_watermark + 有界 gap**，不再一条一 Redis key（修复 6 亿 key）；batch_id 保留作审计。
10. **边缘无 Redis/Backend**，用 SQLite outbox + 状态机 + 租约崩溃恢复（新 owner 回收为主、lease 过期兜底）+ checkpoint/vacuum 释放磁盘；App 直连中心。
11. **统一 max_offline_retention_days**（不含映射保留）+ outbox 清理规则；容量按磁盘字节 + 三级水位；阶段 0 补容量公式+内存预算。
12. **ACK = 中心 Redis 接纳成功**，非落盘；阶段 0 冻结持久化策略。
13. **PUBLISH 是新增能力（阶段 3）**，现状为 100ms 轮询。
14. **首次引导先生成 node_uuid/密钥，再用 enrollment token 注册**；认证用 mTLS 或请求签名+重放校验，token 绑定公钥需有证明机制。
15. **错误码表细化**：terminal->dead，retryable->retry_wait，401/403->重认证，429/5xx->重试。
