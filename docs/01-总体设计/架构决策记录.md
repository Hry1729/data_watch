## ADR-0001 采集与入库经 Redis 解耦

- **状态**：Accepted
- **背景**：自动化码头采集链路存在数百设备、百毫秒级扫描的容量语境。采集进程如果直接写 TDengine，一旦时序库抖动、网络慢、批写失败，会直接反压 PLC 采集，造成实时数据断续和线程堆积。
- **决策**：collector 只写 Redis：`latest` 供实时读，`window` 供短窗口，`stream` 供 writer 消费。writer 独立从 Redis Stream 入库。两者无代码级调用关系。
- **放弃方案**：collector 直接写 TDengine；backend 接收 collector 推送后再入库；采集和入库合并为单进程。
- **后果**：采集与入库故障域隔离，TDengine 故障时 collector 仍可继续写 Redis；代价是多一跳缓冲，需要维护 Stream、PEL、DLQ 和 Redis 容量。
- **验证依据**：代码中 collector 写出集中在 RedisWriter，writer 从 StreamConsumer 消费；模块间没有直接函数调用。
- **相关**：[采集-collector](../02-模块设计/collector/README.md)、[入库-writer](../02-模块设计/writer/README.md)、[Redis流与点位分组](../03-数据与契约/数据库/Redis结构与字段.md)。

## ADR-0002 Redis latest/window/stream/dlq 四结构

- **状态**：Accepted
- **背景**：实时页面、短历史回看、可靠入库、坏数据排查是四种不同需求，不能用单一 key 或单一队列承载全部语义。
- **决策**：Redis 中定义四类结构：
  - `rt:latest:{device}:{group}`：当前实时态；
  - `rt:window:{device}:{group}:{scan_rate}`：最近 10 帧短窗口；
  - `rt:stream:{device_type}:{group}:{shard}`：入库队列；
  - `rt:dlq:{device_type}:{group}`：死信队列。
- **放弃方案**：只写 latest；只写 Stream 由 backend 读 Stream；以 TDengine 作为实时页数据源。
- **后果**：读写语义清晰，前端实时读不会压 TDengine，writer 有可靠消费语义；代价是 Redis key 类型变多，需要文档化不变式。
- **关键不变式**：collector 必须先写 window/stream，最后写 latest。latest 是“本批实时态已完整写入 Redis”的信号。
- **相关**：[Redis流与点位分组](../03-数据与契约/数据库/Redis结构与字段.md)。

## ADR-0003 collector 采用自由线程 Python 3.14t

- **状态**：Accepted
- **背景**：collector 面对大量阻塞型 PLC/OPC 读请求。传统 GIL 会限制多线程阻塞 I/O 与解析阶段并发空间；同时项目压测显示热点更集中在 I/O 调度、读块合并和解析算法。当前部署目标是保持 collector 主体为单 OS 进程，避免先引入多进程设备分片的运维复杂度。
- **决策**：collector 主体保持单进程部署，运行于 free-threaded Python 3.14t；通过 asyncio 调度和显式有界线程池承载 PLC 读、解析、Redis 写等阶段。依赖版本固定到兼容自由线程的组合；序列化使用 msgspec；S7 解析使用块级缓存消除 O(N²) 热点。
- **放弃方案**：切换 Go/Rust 重写采集器；继续使用普通 CPython；直接依赖 orjson；在当前阶段把设备分片到多个 collector 进程。
- **后果**：保留 Python 生态与开发效率，同时在单进程部署内提升多设备阻塞读和解析阶段吞吐；代价是依赖兼容性要求更高，打包环境必须统一。free-threaded 并不意味着 event loop 自动并行，所有多核收益都必须来自明确的 executor/线程池边界。
- **验证依据**：collector `.venv-pack`、打包脚本和性能记忆均指向 3.14t；orjson 因自由线程兼容性不作为当前序列化方案。
- **相关**：[采集-collector](../02-模块设计/collector/README.md)、[运维部署](../05-运维部署/README.md)。

## ADR-0004 TDengine 多表批写 + 二分降级

- **状态**：Accepted
- **背景**：数百设备子表逐表写入会产生大量网络往返；但把所有行合成一条大 SQL 又会遇到 TDengine 单语句大小限制和坏数据拖垮整批的问题。
- **决策**：writer 使用跨子表多表 `INSERT`，按约 3MB SQL 字节预算分块；写失败时根据错误分类处理：连接/未知错整块 RETRY，白名单数据错误才二分隔离坏行，坏行入 DLQ，好行照常落库。
- **放弃方案**：逐设备串行 INSERT；失败整批丢弃；用英文错误关键词粗略判断坏数据。
- **后果**：吞吐高，坏数据隔离精细，不轻易丢数据；代价是写入器复杂度更高，需要维护错误码白名单和 ACK 补偿。
- **相关**：[入库-writer](../02-模块设计/writer/README.md)、[writer可靠入库与TDengine写入](../02-模块设计/writer/可靠入库与TDengine写入.md)。

## ADR-0005 TDengine 宽表模型 + 列只增不减

- **状态**：Accepted
- **背景**：点位数量大、类型多、配置会演进。如果按每点位子表或频繁删改列，历史查询和 schema 迁移成本会很高。
- **决策**：TDengine 使用设备类型超级表 `sd{device_type}` + 设备子表 `device_code` + 点位列 `device_variable.td_column_name` 的宽表模型；所有数据列统一 `DOUBLE`；点位软删除不回收列，schema 只增不减。
- **放弃方案**：每点位一张子表；按 `var_seq` 动态生成物理列；TDengine 保存 quality 字段。
- **后果**：writer 映射缓存可安全降级使用旧版本，历史列不会因配置变更消失；代价是非数值语义要依赖 MySQL 元数据解释，列会随历史点位增长。
- **相关**：[数据库设计](../03-数据与契约/数据库/MySQL结构与字段.md)。

## ADR-0006 OPC DA 使用 x86 sidecar/proxy 隔离

- **状态**：Accepted
- **背景**：OPC DA 依赖 Windows COM/DCOM，现场常见 32 位组件，直接让 64 位 Python collector 加载 COM 风险高、部署复杂、故障域不清。
- **决策**：OPC DA 访问放入 C# .NET Framework 4.8 x86 sidecar/proxy；agent 负责启动、认领、端口映射与健康闸门；collector 通过本机端口或 HTTP ingest 接收数据。
- **放弃方案**：collector 直接访问 COM；手动启动 proxy；把 OPC DA 采集放入 Docker。
- **后果**：COM 位数和权限问题被隔离在 proxy/agent 层，collector 主链路保持 Python 纯采集逻辑；代价是目标机必须验收 DCOM 服务账户权限。
- **相关**：[agent边缘进程编排与凭据](../02-模块设计/agent/边缘进程编排与凭据.md)、[collector调用链与协议设计](../02-模块设计/collector/调用链与协议设计.md)。

## ADR-0007 边缘双根路径契约 + DPAPI 凭据单一来源

- **状态**：Accepted
- **背景**：Windows 的 Program Files 通常只读，ProgramData 才适合写配置、日志和运行状态；数据库密码不能明文散落在 collector/writer/backend/app 多处配置中。
- **决策**：agent 区分 `DATAWATCH_INSTALL_ROOT`（只读安装根）和 `DATAWATCH_DATA_ROOT`（可写数据根）；DB 口令以 DPAPI `password_enc` 保存到 agent `config.toml`；启动 collector/writer 时解密并通过 `DATAWATCH_<DB>_<FIELD>` 注入。
- **放弃方案**：每个模块各自保存密码；安装目录内直接写运行日志；在安装包中固化目标机连接信息。
- **后果**：一包多机，凭据不漂移，不落多处明文；代价是 DPAPI 密文不可跨机/跨账户复制，迁移需重新配置。
- **相关**：[边缘代理-agent](../02-模块设计/agent/README.md)、[运维部署](../05-运维部署/README.md)。

## ADR-0008 双前端分工（Vue Web / Tauri 桌面）

- **状态**：Accepted
- **背景**：业务用户需要设备、点位、实时、历史、日志、系统管理等完整 Web 控制台；现场运维需要本机首装、进程启停、状态指标和日志 tail。两类入口的权限、交互、部署位置不同。
- **决策**：frontend（Vue3 Web）面向业务控制台；app（Tauri + React）面向边缘运维。app 经 Rust HTTP proxy 同时对接本机 agent 与中心 backend。
- **放弃方案**：只做 Web 前端；让 Web 直接管理本机进程；让桌面端承载所有业务功能。
- **后果**：职责清晰、部署边界清楚；代价是两套前端和两套 client 契约需要维护。
- **相关**：[Web前端-frontend](../02-模块设计/frontend/README.md)、[桌面端-app](../02-模块设计/app/README.md)。

## ADR-0009 backend 自定义 TurboAPI ASGI + JWT/RBAC

- **状态**：Accepted
- **背景**：backend 需要同时处理 REST、WebSocket、lifespan、CORS、统一异常、参数绑定和权限校验，并希望保持依赖轻量和行为可控。
- **决策**：backend 使用 TurboAPI，并通过 `EnhancedASGITurboAPI` 实现 ASGI 增强；鉴权采用自实现 JWT(HS256)、PBKDF2 口令哈希和基于权限码的 RBAC。
- **放弃方案**：迁移标准 FastAPI；引入重型认证框架；前端只做权限隐藏。
- **后果**：定制能力强，权限链路可控；代价是增强层维护成本高，`AUTH_SECRET_KEY` 必须由运维保证强随机。
- **相关**：[后端-backend](../02-模块设计/backend/README.md)、[API契约](../03-数据与契约/契约/API契约.md)。

## ADR-0010 实时 diff 推送 + 历史 Perspective 快照

- **状态**：Accepted
- **背景**：实时看板需要低延迟、小包增量；历史大表/趋势需要一次查询后的大结果展示、恢复和版本保护。两类需求不同。
- **决策**：实时走 ws_push：订阅 `(device_code, group_code)`，轮询 Redis latest，首帧 snapshot 后续 diff；历史走 Perspective 会话快照：REST 查询 TDengine，结果经 WebSocket snapshot 推送给前端 runtime。
- **放弃方案**：所有实时数据都用 REST 轮询；所有历史查询都一次性 HTTP 返回并由普通表格渲染；实时与历史共用一个 WS 协议。
- **后果**：两条通道各自优化；代价是前端需维护两套状态机和协议兼容。
- **相关**：[WebSocket协议](../03-数据与契约/契约/WebSocket协议.md)、[frontend页面权限与实时历史设计](../02-模块设计/frontend/页面权限与实时历史设计.md)。

## ADR-0011 中心支持镜像部署，边缘使用 Windows 一体安装包

- **状态**：Accepted
- **背景**：中心服务（backend/frontend/Redis/TDengine）适合容器化部署、升级和离线镜像交付；边缘采集涉及 Windows、OPC DA、DCOM、PLC 网络和桌面 app，不适合放入 Docker。
- **决策**：中心侧提供 `backend/Dockerfile`、`frontend/Dockerfile`、`deploy/docker-compose.yml`、`deploy/nginx.conf`、离线镜像 tar/zip；边缘侧提供 Inno 一体安装包，安装 app/agent/collector/writer/OPC DA proxy，agent 由 NSSM 注册为 Windows 服务。
- **放弃方案**：全量 Docker 化；全量手工服务部署；把 collector/writer 放入中心容器。
- **后果**：中心升级可通过镜像替换，边缘部署贴合 Windows/OPC DA 现实；代价是发版分为镜像包与 Windows 安装包两条轨道。
- **相关**：[运维部署](../05-运维部署/README.md)。

## ADR-0012 接口契约先行，旧文档仅作素材

- **状态**：Accepted
- **背景**：归档文档中存在历史口径，例如 PostgreSQL 备用、旧 TDengine 模型、旧 WS 事件、writer 固定配置等。直接照搬会污染当前实现。
- **决策**：当前代码、数据库现状和新版 `docs/03-数据与契约` 是现行事实源。接口、WebSocket、数据库、Redis 结构发生变化时，先更新契约文档，再改实现和前端。
- **放弃方案**：旧文档覆盖当前实现；前端 mock 先行定义契约；只在代码里隐式变更接口。
- **后果**：文档可作为协作门禁，减少前后端错配；代价是每次结构性变更都要同步维护文档。
- **相关**：[API契约](../03-数据与契约/契约/API契约.md)、[数据库设计](../03-数据与契约/数据库/MySQL结构与字段.md)。
