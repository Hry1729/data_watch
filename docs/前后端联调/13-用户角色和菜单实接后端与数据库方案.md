# `/system` 用户、角色、菜单实接后端与数据库方案

## 现状结论

当前不是从零开始。后端已经有 `sys_user`、`sys_role`、`sys_menu`、`sys_permission`、`sys_role_menu`、`sys_role_permission`、`sys_user_role` 等表模型，也已经有用户、角色、菜单、角色授权、菜单权限接口。

真正的问题在前端和若干后端细节：

- 用户管理：列表已接 `/api/user/list`，但新增、编辑、删除、重置密码、角色选项仍是假操作或 mock。
- 角色管理：列表已接 `/api/role/list`，但新增、编辑、删除、授权保存仍是假操作。
- 菜单管理：读取的是当前用户菜单 `/api/v3/system/menus`，不是管理员全量菜单；新增、编辑、删除、按钮权限都是 TODO。
- 前端当前 `.env` 是 `VITE_ACCESS_MODE=frontend`，运行时菜单仍主要走前端路由，不算真正数据库菜单控制。
- 启动种子逻辑会重置内置用户密码、角色菜单、角色权限，这会覆盖页面里对内置角色的修改，必须先改成非破坏式初始化。

## 总体目标

把数据库作为系统管理的真实数据源：

- 用户管理能真实增删改查、分配角色、禁用启用、重置密码。
- 角色管理能真实增删改查、启用禁用、分配菜单和按钮权限。
- 菜单管理能真实维护菜单树、菜单按钮权限，并驱动前端后端模式下的左侧菜单。
- 后端仍作为最终权限边界，前端按钮隐藏只是体验层，不作为安全边界。

## 分阶段实施

### Phase 0：先修初始化和权限模式，避免后续改完被覆盖

置信度：90%

1. 调整认证初始化逻辑：
   - `bootstrap_auth_schema()` 继续负责建表和补齐缺失种子。
   - 不再每次启动重置内置用户密码。
   - 不再每次启动删除并重建 `R_SUPER`、`R_ADMIN`、`R_USER` 的菜单和权限授权。
   - 只在记录不存在时插入默认角色、默认用户、默认菜单、默认权限、默认授权。
   - 后续如需升级内置权限，用单独迁移脚本或版本化 seed，不在每次启动时强制覆盖。

2. 前端切换到后端权限模式：
   - 开发和生产环境显式配置 `VITE_ACCESS_MODE=backend`。
   - 保留本地路由文件作为组件路径映射基础，但菜单可见性、按钮权限以数据库返回为准。

3. 后端布尔解析统一：
   - `RolePayload`、`RoleStatusPayload`、`MenuPayload`、`PermissionPayload` 不再用 `bool(value)` 直接转换。
   - 统一使用已有 `_coerce_bool()`，避免 `"false"` 被解析成 `True`。

### Phase 1：补齐前端 API 层和类型契约

置信度：88%

在 `frontend/src/api/system-manage.ts` 补齐这些接口包装：

- 用户：
  - `GET /api/user/list`

  - `POST /api/user`

  - `PATCH /api/user/{id}/password/reset`
  - `DELETE /api/user/{id}`
- 角色：
  - `GET /api/role/list`
  - `GET /api/role/options`
  - `GET /api/role/{id}`
  - `POST /api/role`
  - `PUT /api/role/{id}`
  - `PATCH /api/role/{id}/status`
  - `DELETE /api/role/{id}`
  - `GET /api/role/{id}/grant`
  - `PUT /api/role/{id}/grant`
- 菜单：
  - `GET /api/v3/system/menus`
  - `GET /api/v3/system/menus/admin`
  - `POST /api/v3/system/menu`
  - `PUT /api/v3/system/menu/{id}`
  - `DELETE /api/v3/system/menu/{id}`
  - `GET /api/v3/system/menu/{id}/permissions`
  - `POST /api/v3/system/menu/{id}/permissions`
  - `PUT /api/v3/system/menu/{id}/permissions/{permissionId}`
  - `DELETE /api/v3/system/menu/{id}/permissions/{permissionId}`

同时补齐 `Api.SystemManage` 类型：

- `UserPayload`
- `RolePayload`
- `RoleOption`
- `RoleGrant`
- `SystemMenuTreeItem`
- `MenuPayload`
- `PermissionPayload`
- `PermissionItem`

### Phase 2：用户管理页面实接

置信度：85%

1. 列表保留 `useTable + /api/user/list`。
2. 删除当前头像 mock 覆盖逻辑，接口返回什么就展示什么；没有头像时用默认头像或占位。
3. 用户状态文案改为账号状态，不再显示“在线/离线”：
   - `1`：启用
   - `2`：禁用或已注销
4. `UserDialog` 改为真实表单：
   - 用户名 `userName`
   - 昵称 `nickName`
   - 手机号 `userPhone`
   - 邮箱 `userEmail`
   - 性别 `userGender`
   - 状态 `status`
   - 角色 `userRoles`
   - 新增时可填初始密码；不填则后端默认 `123456`
5. 打开弹窗时调用 `/api/role/options` 获取角色选项，不再使用 mock。
6. 新增调用 `POST /api/user`。
7. 编辑调用 `PUT /api/user/{id}`。
8. 删除调用 `DELETE /api/user/{id}`，后端目前是软删除。
9. 增加重置密码动作，调用 `PATCH /api/user/{id}/password/reset`。
10. 建议后端补保护：
   - 不能删除当前登录用户。
   - 不能禁用当前登录用户。
   - 至少保留一个可用的 `R_SUPER` 用户。

### Phase 3：角色管理页面实接

置信度：82%

1. 列表保留 `GET /api/role/list`。
2. `RoleEditDialog` 提交真实接口：
   - 新增：`POST /api/role`
   - 编辑：`PUT /api/role/{roleId}`
3. 删除角色调用 `DELETE /api/role/{roleId}`。
   - 后端已阻止删除仍被用户占用的角色。
4. 启用禁用调用 `PATCH /api/role/{roleId}/status`。
5. 建议保护内置角色：
   - `R_SUPER` 不允许删除。
   - `R_SUPER` 不允许禁用。
   - `R_ADMIN`、`R_USER` 可编辑名称描述，但删除/禁用建议二次确认。
6. 修复 role search：
   - `enabled` 必须传布尔或后端能稳定识别字符串布尔。
   - 日期范围继续传 `startTime/endTime`。

### Phase 4：角色授权实接菜单和按钮权限

置信度：76%

1. 打开角色授权弹窗时并发加载：
   - `/api/v3/system/menus/admin`
   - `/api/role/{roleId}/grant`
2. 授权树节点必须使用稳定 key：
   - 菜单节点：`menu:{menuId}`
   - 按钮权限节点：`permission:{permissionId}`
3. 后端 `authList` 已返回权限 `id/title/authMark`，前端需要保留 `id`。
4. 回显：
   - `grant.menuIds` 转成 `menu:{id}`
   - `grant.permissionIds` 转成 `permission:{id}`
5. 保存：
   - 从 checked keys 拆出 `menuIds` 和 `permissionIds`。
   - 菜单半选节点也要纳入 `menuIds`，避免只选按钮权限时父菜单没保存。
   - 调用 `PUT /api/role/{roleId}/grant`。
6. 后端已有 `_expand_menu_ids()`，会补齐父级菜单；前端仍建议传半选父菜单，数据更直观。

### Phase 5：菜单管理页面实接

置信度：70%

这是三页里风险最高的一块，因为当前菜单页更多是模板 UI。

1. 菜单管理列表改用管理员接口：
   - 从 `/api/v3/system/menus` 改为 `/api/v3/system/menus/admin`。
2. 后端 admin 菜单树需要调整：
   - 管理页必须返回所有菜单，包括禁用菜单。
   - 运行时 `/api/v3/system/menus` 仍只返回当前用户可见且启用菜单。
   - admin 树节点需要带上 `id`、`parentId`、`menuType`、`sort`、`enabled`。
3. 菜单表单补齐父级菜单：
   - 顶部“添加菜单”：`parentId = null`
   - 行内“新增子菜单”：`parentId = 当前菜单 id`
   - 行内“新增权限”：走权限接口，不走菜单接口。
4. 菜单新增：
   - 调用 `POST /api/v3/system/menu`
   - payload 包含 `name/path/component/titleKey/icon/parentId/menuType/sort/enabled/meta` 等字段。
5. 菜单编辑：
   - 调用 `PUT /api/v3/system/menu/{id}`
6. 菜单删除：
   - 调用 `DELETE /api/v3/system/menu/{id}`
   - 后端需补规则：有子菜单时不允许直接删，或要求显式级联。
   - 删除菜单时必须同步删除该菜单下权限和角色权限关联，避免 `sys_permission.menu_id = null` 留孤儿权限。
7. 按钮权限新增/编辑：
   - 新增：`POST /api/v3/system/menu/{menuId}/permissions`
   - 编辑：`PUT /api/v3/system/menu/{menuId}/permissions/{permissionId}`
   - 删除：`DELETE /api/v3/system/menu/{menuId}/permissions/{permissionId}`
8. 权限字段建议：
   - `permissionName`：按钮名称，如“新增”
   - `authMark`：前端 `v-auth` 使用值，如 `add/edit/delete` 或完整权限码
   - `permissionCode`：唯一权限编码，建议默认自动生成，但允许编辑
9. 菜单管理页本身的按钮权限：
   - 继续用 `v-auth="'add'"`、`v-auth="'edit'"`、`v-auth="'delete'"`。
   - 用户管理和角色管理建议用完整权限码，例如 `v-auth="'system:user:create'"`。

### Phase 6：让菜单真正驱动前端路由

置信度：78%

1. 后端菜单 `component` 必须和前端组件路径一致。
   - 例如 `/system/user`、`/system/role`、`/system/menu`。
2. 切到 `VITE_ACCESS_MODE=backend` 后，`MenuProcessor` 会调用 `/api/v3/system/menus`。
3. 登录后：
   - `/api/user/info` 返回用户角色和按钮权限。
   - `/api/v3/system/menus` 返回当前角色可见菜单和当前菜单下按钮权限。
4. 前端路由权限：
   - 菜单可见性由后端返回菜单树控制。
   - 按钮可见性由当前路由 `meta.authList` + `v-auth` 控制。
5. 变更角色授权后：
   - 当前用户需要重新登录或刷新菜单缓存，才能看到最新菜单权限。
   - 可以在保存授权后提示“权限已更新，相关用户重新登录后生效”。

## 数据库与后端约束

置信度：86%

- 当前表结构基本够用，不需要新增核心表。
- 必须修正初始化覆盖问题，否则后台修改内置角色权限会被下次启动还原。
- 菜单删除逻辑必须补强，避免孤儿权限。
- 内置账号和内置角色要加保护，避免误删后无法管理系统。
- 后端接口已有角色校验：
  - 用户管理：`R_SUPER/R_ADMIN`
  - 角色管理：`R_SUPER`
  - 菜单管理：`R_SUPER`
- 这个权限边界建议保持不变。

## 验收测试

1. 用户管理：
   - 超级管理员登录，新增用户，分配 `R_USER`，新用户可登录。
   - 编辑手机号、邮箱、角色后刷新列表，数据仍存在。
   - 禁用用户后该用户无法登录。
   - 重置密码后用新密码可登录。
   - 删除用户后列表不再显示，数据库为软删除。
2. 角色管理：
   - 新增角色，分配给用户，用户重新登录后角色生效。
   - 禁用角色后，该角色用户权限失效。
   - 删除未绑定用户的角色成功。
   - 删除已绑定用户的角色失败并提示。
3. 角色授权：
   - 给角色勾选某个菜单，用户重新登录后看到该菜单。
   - 取消菜单授权，用户重新登录后看不到该菜单。
   - 勾选按钮权限后，对应按钮显示；取消后按钮隐藏。
4. 菜单管理：
   - 新增菜单后刷新仍存在。
   - 编辑菜单名称、图标、排序后刷新仍正确。
   - 禁用菜单后普通运行菜单不显示，管理员菜单页仍能看到。
   - 删除菜单后角色授权中同步消失。
   - 新增按钮权限后角色授权树能看到该权限。
5. 启动持久化：
   - 修改角色授权后重启后端。
   - 再次登录，授权结果不能被 bootstrap 重置。
6. 权限边界：
   - `R_ADMIN` 可以进用户管理，但不能进角色管理和菜单管理。
   - `R_USER` 不能进 `/system`。
   - 未授权 API 直接请求返回 403。

## 默认取舍

- 本轮按“数据库菜单是真实菜单源”实施，不再只做页面 CRUD。
- 保持现有权限边界：用户管理 `R_SUPER/R_ADMIN`，角色和菜单管理仅 `R_SUPER`。
- 初始化逻辑只补缺失数据，不覆盖数据库中已被管理员修改的数据。
- 菜单删除默认不做隐式级联删除子菜单；有子菜单时提示先删除子菜单，更安全。
