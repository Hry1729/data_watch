## 一、目标

本清单用于把 `STEP-003` 的设计结果细化成可执行的落库准备清单，目标是尽快支撑以下能力联调：

1. `GET /api/device-monitor/monitor/device-tree`
2. `GET /api/device-monitor/monitor/realtime-init`
3. `WS /api/device-monitor/ws/realtime`
4. `/device-monitor/realtime` 页面首轮联调

## 二、测试数据总体策略

### 2.1 数据分工

- **MySQL**：负责设备、分组、协议、点位等主数据
- **TDengine**：负责实时最新值与历史时序样本
- **Redis**：当前暂不使用

### 2.2 测试 ID 约定

为避免污染现有真实数据，首批联调数据建议使用独立测试 ID 段：

| 类型 | 建议 ID 范围 |
|------|--------------|
| `comm_protocol` | `9901+` |
| `device_group` | `9910+` |
| `device_type` | `9920+` |
| `variable_group` | `9930+` |
| `device` | `991001+` |
| `device_variable` | `992001+` |

建议测试设备直接采用真实命名规则中的代表编号：

- `qc100`
- `asc7011`
- `agv801`

### 2.3 当前联调链路主键映射

为避免把 MySQL 主键、前端订阅 ID、TDengine 子表名混为一谈，首批联调统一按以下映射执行：

| 语义 | 当前基线 |
|------|----------|
| 前端/后端接口 `deviceId` | MySQL `device.id`（数值型） |
| TDengine 超级表名 | 与 MySQL `device.device_code` 一致 |
| TDengine 子表名 | `{device_code}_{变量编号主体}`，如 `qc100_1` |
| TDengine TAG `device_id` | MySQL `device.id` |
| TDengine TAG `variable_id` | MySQL `device_variable.id` |

结论：

- 接口层设备主键和 TDengine 子表命名键当前不是同一字段。
- 首批测试数据必须同时保证 `device.id`、`device.device_code`、`device_variable.id` 三套键值都可追溯。

### 2.4 首轮状态覆盖分配

为避免把“离线/过期”和“实时告警”压在同一设备上导致状态冲突，首轮联调改为 3 台设备分工覆盖：

| 设备 | 状态职责 | 说明 |
|------|----------|------|
| `qc100` | 在线 + update | 用于首屏正常态、增量更新态 |
| `asc7011` | stale / offline | 仅保留旧样本，用于过期/离线态 |
| `agv801` | 在线 + alarm | 保留最近样本，并让关键点位超阈值 |

补充说明：

- `snapshot / update / alarm / stale` 可通过 DB seed 覆盖。
- `error / pong / reconnect` 不属于落库数据本身，应由后端 WebSocket 运行时行为覆盖。

### 3.4 当前 DDL 下每表最少必填列

以下字段来自当前 collector 的 MySQL DDL / ORM 读取逻辑，正式生成执行 SQL 时至少需要填齐：

| 表 | 当前最少必填列 |
|----|----------------|

补充说明：

- 当前 collector 启动时至少会读取 `device.device_code`、`device.comm_type`、`device.protocol_id`、`device.type_id`、`device.endpoint`、`device.rack`、`device.slot`、`device.scan_cycle`。

### 3.5 当前已识别风险

- `collector/device_watch.sql` 中存在可疑的反向外键表达（`device.id -> device_variable.device_id`），真实库若保留该约束，测试数据插入顺序可能受影响。
- 首轮 seed 默认按“真实库已修正为正常外键方向”准备；执行前应先用真实库结构核验。

## 四、首批 TDengine 落库清单

### 4.1 目标

至少支持以下状态覆盖：

1. 在线正常
2. 在线更新
3. 离线 / 过期
4. 在线告警

### 4.2 推荐样本结构

当前 TDengine 命名与行结构统一为：

- 数据库：按设备类型小写划分，例如 `qc`、`asc`、`agv`
- 超级表：与 `device.device_code` 一致，例如 `qc100`、`asc7011`
- 子表：按 `{device_code}_{变量编号主体}` 生成，例如 `qc100_1`、`asc7011_85`
- 当前行结构：`ts`、`value`
- 当前 TAG：`device_id`、`variable_id`

建议为以下三个设备写入时序数据：

| MySQL 设备ID | device_code | 数据库示例 | 超级表示例 | 目标状态 |
|-------------|-------------|------------|------------|----------|
| `991001` | `qc100` | `qc` | `qc100` | 在线 + update |
| `991002` | `asc7011` | `asc` | `asc7011` | stale / offline |
| `991003` | `agv801` | `agv` | `agv801` | 在线 + alarm |

### 4.3 每个点位最小样本数

推荐按设备状态分组准备样本：

1. `qc100`：每个点位至少 3 条近实时样本（`now - 5m`、`now - 30s`、`now - 10s`）
2. `asc7011`：每个点位仅保留旧样本（例如 `now - 20m`、`now - 12m`、`now - 8m`）
3. `agv801`：每个点位至少 3 条样本，其中 `992006` 的最新值应超阈值

### 4.4 推荐状态样本

| MySQL device_id | variable_id | 期望表现 | 样本要求 |
|-----------------|-------------|----------|----------|
| `991001` | `992001` | 在线正常 | 最近 10 秒有正常值 |
| `991001` | `992002` | 在线更新 | 最近 30 秒与最近 10 秒数值不同 |
| `991002` | `992003` | stale / offline | 最新样本明显早于在线阈值 |
| `991002` | `992004` | stale / offline | 最新样本明显早于在线阈值 |
| `991003` | `992005` | 在线正常 | 最近 10 秒有正常值 |
| `991003` | `992006` | 在线告警 | 最新样本超阈值 |

### 4.5 实时事件覆盖映射

| 事件类型 | 覆盖来源 |
|----------|----------|
| `snapshot` | 后端启动订阅时基于 MySQL 主数据 + TDengine 最新值组装 |
| `update` | 对 `qc100` 连续补写近实时样本 |
| `alarm` | `agv801 / 992006` 最新值超阈值 |
| `stale` / `offline` | `asc7011` 仅保留旧样本 |
| `error` | 后端或 WS 运行时异常，不能单靠 seed 数据生成 |
| `pong` | WS 心跳响应，不能单靠 seed 数据生成 |
| `reconnect` | WS 断线重连逻辑，不能单靠 seed 数据生成 |

### 4.6 当前真实 TDengine 已探测结果

当前应按新模型检查以下对象层级：

- 数据库：`device_data`
- 超级表：`qc`、`asc`、`agv`
- 子表：如 `qc100`、`asc7011`、`agv801`
- 已确认目标列结构为：`ts` + 点位值宽列
- 已确认目标 TAG 为：`device_code`

说明：

- 新增首轮联调数据时，应按 `device_data -> 设备类型超级表 -> 设备子表 -> 点位值宽列` 创建。
- 若本机已有旧模型测试对象，建议保留到运行时代码切换完成后再统一清理，避免影响当前验证链路。

## 五、落库顺序

推荐严格按以下顺序执行：

1. 先写 `comm_protocol`
2. 再写 `device_type`
3. 再写 `device_group`
4. 再写 `variable_group`
5. 再写 `device`
6. 再写 `device_variable`
7. 再初始化 TDengine 超级表 / 子表
8. 先写 `qc100` 在线样本
9. 再写 `asc7011` stale 样本
10. 最后写 `agv801` 告警样本

原因：

- 前端可以最早开始联调 `device-tree`
- 后端可以最早验证 `realtime-init`
- 再逐步补齐 `update / alarm / stale` 状态覆盖

## 六、接口校验点

### 6.1 `GET /monitor/device-tree`

依赖：

- MySQL 的 `device_group + device + device_type + comm_protocol`

校验：

- 能返回至少 3 个设备节点
- 节点 `key/name/status/deviceId/deviceCode/deviceName/children` 齐全

### 6.2 `GET /monitor/realtime-init`

依赖：

- MySQL 主数据
- TDengine 最新值

校验：

- `deviceId/deviceCode/deviceName/driverName/connectStatus/lastCollectTime` 齐全
- `data[]` 至少返回 2 个点位
- `991001` 呈现在线更新态
- `991002` 呈现 stale / offline 态
- `991003` 呈现在线告警态

### 6.3 `WS /ws/realtime`

依赖：

- 后端基于 TDengine 最新值变化统一生成事件

校验：

- 首次订阅可收到 `snapshot`
- 新写入 `qc100` 样本后可收到 `update`
- `agv801` 异常值样本可触发 `alarm`
- `asc7011` 可在初始化或快照中体现 stale / offline
- 断连重连后有 `error / pong`，该部分需由后端运行时补测

---

## 七、前端联调顺序

建议前端按以下顺序开始：

1. 先接 `device-tree`
2. 再接 `realtime-init`
3. 再接 `snapshot`
4. 再接 `update`
5. 再接 `alarm`
6. 最后补 `error / pong / reconnect`

这样可以尽早看到页面结构，避免一开始就卡在完整实时事件流上。
