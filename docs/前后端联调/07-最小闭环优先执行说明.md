# 最小闭环优先执行说明

> 更新时间：2026-04-13
> 作用：明确联调阶段的执行顺序，避免前后端、采集、测试在过大范围内并行铺开而失控

---

## 一、目标

本说明对应治理方案 7：

**先完成最小闭环，再扩展其他模块。**

它解决的问题是：

1. 前后端同时铺开过多页面和接口，导致契约漂移
2. 真实设备、TDengine、WebSocket、Fake Data 尚未稳定时就开始铺量开发
3. 看起来“做了很多页面和接口”，但系统仍然没有形成可联调、可验收的主链路

---

## 二、最小闭环定义

当前项目的最小闭环统一定义为：

1. 设备树
2. 设备列表
3. 实时初始化接口
4. WebSocket 实时推送
5. 前端实时监控页

对应能力如下：

| 能力 | 主要责任方 | 说明 |
|------|------------|------|
| 设备树 | `@backend` + `@frontend` | 用于导航、初始化订阅目标 |
| 设备列表 | `@backend` + `@frontend` | 用于设备管理和状态总览 |
| 实时初始化 | `@backend` | 通过 MySQL + TDengine 提供首屏稳定结构化数据 |
| WebSocket 推送 | `@backend` + `@collector` | 提供实时事件与更新通道 |
| 实时监控页 | `@frontend` | 消费初始化与 WS 推送，展示在线状态和点位值 |

---

## 三、为什么先做这一条链路

相比先做历史查询、日志、Dashboard、导入导出，最小闭环优先有以下优势：

1. 它最先暴露接口结构是否稳定
2. 它最先暴露 TDengine / Fake Data / WebSocket 是否可用
3. 它最先暴露前端状态管理和错误处理是否成熟
4. 它能最快回答“这个系统是否已经能跑起来并联调”

---

## 四、执行顺序

### Phase A：准备阶段

进入最小闭环前，必须先满足以下条件：

- `docs/后端/API接口文档.md` 已作为唯一契约事实源
- `docs/前后端联调/02-前端契约映射清单.md` 已可指导页面字段消费
- `docs/前后端联调/05-Redis实时态与告警态语义说明.md` 已明确“Redis 暂不使用，实时与历史统一由 TDengine 提供”
- `docs/前后端联调/06-联调环境矩阵与验收口径.md` 已明确 Fake Data 与验收标准

### Phase A-1：闭环分层策略

当前默认采用以下策略：

- **M2-A 联调可验收**：允许用 MySQL Seed + 写入真实 TDengine 的测试假数据 + 后端统一 WS 推送完成首轮闭环，但禁止 mock API / mock WebSocket / 前端本地 mock 数据
- **M2-B 环境增强验收**：在 M2-A 之后，再补真实 PLC、长稳运行与现场级联调

结论：

真实 PLC 未就绪，不阻塞最小闭环首轮验证；但 TDengine 是当前闭环基础依赖。

### Phase B：闭环执行顺序

建议严格按以下顺序推进：

1. 后端确认设备树 / 设备列表 / 实时初始化 / WS 事件结构
2. 前端确认 `/device-monitor/realtime` 的路由、菜单、页面、字段映射
3. 数据与测试确认通过真实 MySQL / TDengine 写入测试假数据可支持联调
4. 完成首轮实时监控页联调
5. 完成最小闭环 smoke 验收

补充规则：

- collector 或 Fake Data 可以作为上游事件来源
- 但对前端的 WebSocket 事件结构必须由后端统一归一化后再推送
- TDengine 在 M2-A 首轮中同时承担实时与历史时序数据存储职责

### Phase C：闭环完成后的扩展顺序

只有在最小闭环完成后，才建议继续推进：

1. 历史查询
2. 工作台 Dashboard
3. 系统日志
4. 导入导出
5. 报警增强能力

---

## 五、当前不建议优先铺开的内容

在最小闭环完成前，不建议优先投入大量实现精力到以下内容：

- 历史查询结构优化
- Dashboard 的高级统计
- 大范围导入导出
- 多协议真实设备全量联调
- 非阻塞性的样式细节优化

说明：

这些内容都重要，但不应先于“系统是否能跑通最小闭环”。

---

## 六、完成标准

最小闭环完成，必须同时满足：

1. 能正常进入 `/device-monitor/realtime`
2. 能看到设备树
3. 能获取首屏初始化数据
4. 能接收 WebSocket 更新事件
5. 断连或异常时页面不崩溃，有明确提示
6. 至少具备一组可复用的 Fake Data / Smoke 验证流程，且测试数据写入真实服务链路

对于 M2-A，还应补充理解为：

- 允许基于写入真实服务的 Fake Data 完成
- 允许在真实 PLC 未就绪时先完成联调层闭环
- 不允许用 mock API / mock WebSocket 绕过后端与真实服务链路

---

## 七、协调规则

若执行过程中出现以下情况，必须暂停扩展范围，并回到最小闭环：

- WebSocket 事件结构仍不稳定
- Realtime 页字段仍存在文档与实现冲突
- TDengine 最新值查询口径与后端消费语义不一致
- 设备树 / 实时初始化还不能稳定返回

结论：

**最小闭环不是“一个建议顺序”，而是当前联调阶段的默认执行门槛。**
