# 真实数据登录与权限联调说明

> 更新时间：2026-04-19
> 适用范围：`frontend` 登录、角色权限、动态菜单、系统管理页联调
> 目标：固化 auth / permission 已完成的真实联调结论，并作为后续页面数据接口联调的前置基线

---

## 一、背景与目标

当前前端已经从 mock / 演示态逐步切到真实后端与真实数据库链路。本轮 auth 联调的原始目标是恢复“真实数据登录 + 权限可用”的最小闭环，避免出现以下问题：

1. 前端切到真实数据后，登录无法稳定进入系统
2. `roles / buttons / menus` 三条权限数据链路没有统一事实源
3. `frontend` 模式和 `backend` 模式的切换顺序不清，容易造成菜单空白或路由无权限
4. 用户管理、角色管理、菜单管理页面缺少真实数据库与接口支撑

截至 2026-04-19，这一轮最小闭环已经基本恢复，当前主阻塞已从 auth 登录链路转移到 device-monitor 业务页数据缺口。


## 五、数据库与种子数据基线

### 5.1 权限域表结构

当前 auth / permission 真实数据链路依赖以下 8 张表：

- `sys_user`
- `sys_role`
- `sys_user_role`
- `sys_menu`
- `sys_permission`
- `sys_role_menu`
- `sys_role_permission`
- `sys_data_permission`

作用划分：

- `sys_user / sys_role / sys_user_role`：登录主体与角色归属
- `sys_menu / sys_role_menu`：backend 模式菜单树
- `sys_permission / sys_role_permission`：页面权限码、按钮权限码、后续 API 权限码
- `sys_data_permission`：后续数据范围过滤占位，本轮只建骨架

### 5.2 内置账号与角色

本地联调阶段固定预置：

| 用户名 | 角色 | 用途 |
|---|---|---|
| `Super` | `R_SUPER` | 超级管理员，全量权限联调 |
| `Admin` | `R_ADMIN` | 业务管理员，设备监控 + 用户管理 |
| `User` | `R_USER` | 监控用户，只读查看能力 |

默认密码统一为：

```text
123456
```

### 5.3 默认授权矩阵

- `R_SUPER`
  - 设备监控 7 页全部可见
  - `system/user`、`system/role`、`system/menu` 全部可见
  - 全量页面权限、按钮权限
- `R_ADMIN`
  - 设备监控 7 页全部可见
  - `system/user` 可见
  - 无 `system/role`、`system/menu`
- `R_USER`
  - 只保留：
    - 工作台
    - 实时监控
    - 历史数据
    - 系统日志
  - 不可见：
    - 驱动管理
    - 设备管理
    - 点位管理
    - 系统管理

## 六、当前后端接口基线

### 6.1 认证接口

- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/user/info`

说明：

- 登录入参固定为 `{ userName, password }`
- 登录返回 `{ token, refreshToken }`
- 当前 token 可直接写入前端 `Authorization`

### 6.2 动态菜单与系统管理接口

- `GET /api/v3/system/menus`
- `GET /api/v3/system/menus/admin`
- `GET /api/user/list`
- `GET /api/user/{id}`
- `POST /api/user`
- `PUT /api/user/{id}`
- `PATCH /api/user/{id}/status`
- `PATCH /api/user/{id}/password/reset`
- `DELETE /api/user/{id}`
- `GET /api/role/list`
- `GET /api/role/options`
- `GET /api/role/{id}`
- `POST /api/role`
- `PUT /api/role/{id}`
- `PATCH /api/role/{id}/status`
- `DELETE /api/role/{id}`
- `GET /api/role/{id}/grant`
- `PUT /api/role/{id}/grant`
- `POST /api/v3/system/menu`
- `PUT /api/v3/system/menu/{id}`
- `DELETE /api/v3/system/menu/{id}`
- `GET /api/v3/system/menu/{id}/permissions`
- `POST /api/v3/system/menu/{id}/permissions`
- `PUT /api/v3/system/menu/{id}/permissions/{permissionId}`
- `DELETE /api/v3/system/menu/{id}/permissions/{permissionId}`

### 6.3 返回口径要求

必须保持以下行为不变：

- `GET /api/user/info.buttons` 返回前端直接消费的 `auth_mark[]`
- `GET /api/v3/system/menus[].meta.authList` 返回按钮权限清单
- `user/list`、`role/list` 继续兼容前端当前 `records/current/size/total`
- 无权限统一返回 403
- 空菜单树允许返回 `[]`

## 七、前端联调规则

### 7.1 当前模式要求

在以下条件全部满足前，前端仍保持：

```env
VITE_ACCESS_MODE=frontend
```

原因：

- 当前虽然 auth 已闭环，但页面业务数据缺口仍较大
- 若提前切到 `backend` 模式，容易把页面空白再次误判为权限问题
- 应先完成 `docs/前后端联调/11-真实数据页面缺口与接口联调TODO.md` 中的高优先级项

### 7.2 `frontend` 模式下的角色约束

为保证 `R_USER` 能在真实数据下进入只读页面，设备监控模块前端静态路由需要满足：

- 父级 `device-monitor` 允许 `R_SUPER / R_ADMIN / R_USER`
- 只读开放：
  - `dashboard`
  - `realtime`
  - `history`
  - `log`
- 管理页仅保留：
  - `driver`
  - `device`
  - `point`
  只允许 `R_SUPER / R_ADMIN`

### 7.3 切换 `backend` 模式前的核对项

必须确认：

1. `/api/v3/system/menus` 返回的组件路径与前端页面目录一致
2. 菜单树中 `name / path / component / meta.title / meta.icon / meta.authList` 完整
3. 首页落点、隐藏菜单、固定标签页等元数据没有丢失
4. `User` 账号不会因为菜单树为空而 500
5. device-monitor 七页在真实数据下不再大面积空白
