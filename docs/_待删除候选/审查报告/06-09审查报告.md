## 一、双方一致（最高置信，优先修）

### 1. 多段 Redis 写入非原子 → 实时有值但入库丢批次 ✅
- **A 方**：`monitor/ingest_server.py:253-276`（`write_latest/window/stream` 三段**完全无 try/except**，半写后异常冒泡返 500，客户端误判全失败重推）。
- **Codex C6**：`collector/executor.py:178→193→202`（latest→window→stream 三段，中间失败前段已落、后段丢，最后 `raise`）。
- **结论**：**同一类缺陷出现在两个不同文件**。前端实时值（latest）已刷新，但 stream/TDengine 丢数据。两处都需处理：要么整组写入具备失败回压/补偿，要么至少让“已接受/已写入”计数反映真实落库结果。

### 2. SystemLogWriter 停机可能被满队列卡住 ✅
- **A 方**：`core/system_log.py:57`（`stop()` 用 `await self._queue.put(None)` 入哨兵；队列满且 worker 卡在 DB 写时，`put` 先于 worker timeout，会挂起）。
- **Codex P3-C11**：同一问题（timeout 覆盖不到入队动作）。
- **结论**：一致。停机路径，影响有限，但确属真实阻塞点。

## 三、Codex 独有 —— 跨模块/打包侧已深核（2026-06-09 复核结论）

> 这三项原标“待确认”，已分别用 writer 源码 / 打包脚本 / run.bat 复核完毕。

### C2 ✅ 属实（P1，已用 writer 代码坐实）
- **collector 侧** `collector/executor.py:204`：写 Redis Stream 的 `config_version = device.config_version`，而 `device.config_version` 来自 **`device.variable_config_version`**（设备表，`config.py:59` / `config_db.py:310`）。
- **writer 侧** `writer/mysql_mapper.py:25-31`：映射缓存 SQL `SELECT dpg.config_version ... JOIN device_point_group dpg ...`，`config_version` 取自 **`device_point_group.config_version`**（点位组表）；`get()` 用 `mapping.config_version == stream_config_version` 比对（`mysql_mapper.py:55-85`），并有专门的 `[mapper] config_version mismatch` 告警 + 回退缓存分支。
- **根因**：两侧曾 key 在**两个不同的数据库列**（collector 用 `device.variable_config_version`，writer 用 `device_point_group.config_version`），正确性一度依赖「两列恒等」这一未文档化的隐性约束。
- **后果（修复前）**：① 版本不等但仍能 `load` 到映射 → 刷屏告警 + 配置变更窗口期可能用旧缓存映射写错版本；② `load` 返回 None（该组无变量）→ entry 留 PEL → DLQ，不落 TDengine。
- **修复（已采纳「collector 改用点位组版本」路径，不再要求后端保证两列恒等）**：
  - **executor 轮询路径** → `035a532`：stream `config_version` 改用 `var.group_config_version`（即 `device_point_group.config_version`），逐组对齐 writer。
  - **ingest_server 路径**（OPC DA sidecar / HTTP push）→ **本次补漏**：`ingest_server.py` 写 stream 的 `config_version` 由 `device.config_version` 改为 `var.group_config_version`，与 executor 同源。
  - 至此 collector **两条**写 stream 路径均使用 `device_point_group.config_version`，与 writer 对账列同源，**不再依赖两列恒等的隐性约束；后端无需保证这两列同步**（继续要求恒等反而是维持一个不该存在的隐性契约）。

### C8 ❌ 不成立 —— 双方一致，已从缺陷清单移除
A 方与 Codex(B方) 复核后均确认 C8 **不是缺陷**，从缺陷清单移除（Codex：“之前列成缺陷偏保守了”）。核到的事实：

- `drivers/opcua_driver.py:1` **顶层不导入 asyncua**；asyncua 仅在 `connect()` 内**惰性导入**（`opcua_driver.py:31`）。
- 缺依赖时捕获 `ImportError` 并抛出明确的 `DeviceConnectionError`（`opcua_driver.py:33`），不崩溃、不静默。
- `DeviceManager` 创建 `OPCUADriver()`（`device/manager.py:656`）本身**不触发** asyncua 导入。
- `requirements.txt:12` 已明确把 asyncua 标为 **optional**；`data-watch-collector.spec:6` 的 hidden-import `drivers.opcua_driver` 正常打包（本次构建确实成功）。

所以“打包缺 asyncua → collector 打包/启动失败”**不成立**。真实行为：若库里配置了 OPC UA 设备，运行到连接阶段会**干净失败并提示安装 asyncua**——属“未启用/未开发协议的优雅降级”，非 bug。

> **产品/部署声明（备注，非缺陷）**：OPC UA 协议**当前为 optional、尚未正式支持**（前端显示“开发中”，asyncua 未纳入打包依赖）。**现场不要配置 OPC UA 设备**；待 OPC UA 正式开发时再把 asyncua 纳入打包依赖并补集成测试。

### C12 ✅ 属实但仅开发模式（P3，低优先）
- `collector/run.bat:51` 跑 `check_protocols.py -o batch` **不带 `--config`**，而 `:91` `main.py %*` 透传用户参数；dev 下 `run.bat --config 自定义.toml` 会让协议预检用默认配置、主进程用自定义配置。
- **生产 Agent 路径不受影响**（Agent 直接调 exe 并显式传 `--config`，不经 run.bat）。优先级低，确认即可。
