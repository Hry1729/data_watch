# 系统接入测试计划

更新时间：2026-05-15

> 2026-05-19 更新：TDengine 验收口径已从“每变量一个子表”调整为 `device_data` 单库、`qc/asc/agv` 三个设备类型超级表、每设备一个子表、点位值宽列；实时态由 Redis 最新值/短窗口承接，历史入库由独立入库模块从 Redis Stream 批量写 TDengine。

## 1. 测试目标

本计划用于指导采集系统第一次接入真实设备。首轮目标不是追求全量上线，而是用一台设备验证完整链路：

```text
MySQL 配置库
  -> Collector 加载设备与点位
  -> 按设备和 scan_rate 构建采集任务
  -> 协议驱动读取 PLC / OPC 数据
  -> DataBuffer
  -> DataAggregator
  -> Redis 实时缓存 / Stream
  -> 入库模块
  -> TDengine 宽表批量写入
```

核心验收目标：

- 配置能从 MySQL 正确加载。
- 设备能连接。
- 地址解析和点位合并结果符合预期。
- TDengine 能按 `device_data -> qc/asc/agv -> 设备子表 -> 点位值宽列` 建表。
- 每台设备对应一个 TDengine 子表。
- 点位列能根据 MySQL `device_variable.var_seq` 动态补齐；历史表不保存 `quality`。
- 实时采集值与 HMI / PLC 在线值一致。
- 采集运行期间无持续丢点、无持续写库失败、无异常重连风暴。

## 6. TDengine 表结构确认

当前 TDengine 写入模型：

```text
device_data
  -> qc / asc / agv 设备类型超级表
  -> 每台设备一个子表
  -> 每行字段: ts + 点位值宽列
```

也就是说：**一台设备一个 TDengine 子表，变量作为列写入**。

| 步骤 | 检查项 | 预期结果 | 置信度 |
| --- | --- | --- | --- |
| 6.1 | 检查测试库是否可清理 | 如有旧结构表，允许清理或换新库 | 0.84 |
| 6.2 | 检查超级表结构 | 包含 `ts` 和 MySQL `device_variable.var_seq` 对应的点位值列 | 0.9 |
| 6.3 | 检查设备子表数量 | 子表数量等于接入设备数量 | 0.88 |
| 6.4 | 检查子表 TAG | 保留 TDengine 必需的设备标识 TAG，如 `device_code` | 0.82 |
| 6.5 | 检查旧表兼容性 | 旧点位子表/quality 模型应迁移或换新库验证 | 0.9 |

建议首轮使用测试库或可清理库，避免旧表结构影响验证。
