## Slide 1｜封面：Data Watch——设备数据采集与监控平台

- 完整标题：Data Watch：设备数据采集与监控平台
- 核心主张：让分散的设备数据完整、持续、可信地流动
- 汇报人：胡若愚｜尚东分公司工程技术部
- 页面角色：封面 / 项目定位
- 视觉构想：以“DATA FLOW”为主视觉，将离散节点汇聚为一条有序数据流；大留白、冷灰蓝细线网格
- 对应原稿：标题、问候与讲者信息

## Slide 2｜吞吐量增长正在抬高设备稳定性要求

- 洋山四期集装箱吞吐量持续增长，设备稳定性要求同步提高
- 传统运维需要向更主动、更智能的方式升级
- 智能运维的底座不是单点工具，而是完整、连续、可靠的数据
- 本页结论：先建可信数据底座，才有智能运维
- 页面角色：背景 / 必要性
- 视觉构想：左侧用不标具体年份和数值的加速上升曲线与逐级增高的集装箱堆叠表达吞吐量持续增长；中部用“设备稳定性要求同步提升”的因果箭头连接右侧“传统运维 → 主动运维 → 智能运维”升级阶梯；底部只保留一句结论
- 对应原稿：项目背景与智能运维基础

## Slide 3｜现状痛点：多协议、多系统、多口径，让一次故障分析变得低效

- 设备种类多，S7、GE SRTP、OPC UA、OPC DA 等通信协议并存
- 数据分散在不同系统中，结构与呈现方式不统一
- 技术人员需要在多个系统之间反复切换，故障分析链路长
- 本页结论：问题不在“没有数据”，而在“数据无法统一流动”
- 页面角色：问题定义 / 痛点分析
- 视觉构想：左侧碎片化协议与系统，右侧漫长排障路径；以“断裂链路”为唯一隐喻
- 对应原稿：设备、协议与数据孤岛问题

## Slide 4｜解决方案：Data Watch 建立统一的数据流动与存储入口

- 面向不同来源的设备数据，提供统一采集、传输、监控和存储能力
- 将现场数据转换为上层应用可直接使用的标准化数据流
- 以平台化方式替代多个系统间的人工拼接
- 本页结论：Data Watch 是工业设备数据的统一入口与可靠通道
- 页面角色：解决方案 / 项目诞生
- 视觉构想：多个输入汇入单一“数据通道”，再分发至实时、历史与应用端
- 对应原稿：Data Watch 诞生与建设目标

## Slide 5｜总体架构：两条部署路径，共用一套数据契约

- 中心式：PLC / OPC → Collector → Redis → Writer → TDengine
- 分布式：PLC / OPC → Collector → Edge Storage / SQLite outbox → Uploader → Ingest → Redis
- Backend 通过 Redis、TDengine、MySQL 提供实时、历史与控制能力
- Web、桌面 App 与 CLI 面向业务用户、现场运维、脚本与 AI Agent
- 本页结论：部署方式可变，数据契约与质量语义不变
- 页面角色：系统架构 / 数据流
- 视觉构想：上下双路径在中心汇聚，使用一条贯穿全页的契约主轴
- 对应原稿：完整数据链路与 Redis、TDengine、MySQL 分工（两段合并）

## Slide 6｜创新一：统一数据契约，屏蔽底层设备与协议差异

- S7、GE SRTP、OPC 等来源进入平台后统一为同一种数据结构
- 关键字段覆盖设备、点位、数值、时间与数据质量
- Good / Uncertain / Bad 质量语义贯穿采集、实时、入库、查询与展示链路
- 上层应用不再逐一适配 PLC 型号和通信协议
- 本页结论：统一契约把“协议复杂性”留在平台内部
- 页面角色：创新点 / 核心能力
- 视觉构想：不同形态输入穿过“CONTRACT”边界后变为同构数据单元
- 对应原稿：创新总起与第一项创新（合并）

## Slide 7｜创新二：模块化与可插拔驱动，把故障控制在局部

- Collector、Storage、Uploader、Ingest、Writer、Backend 等模块职责独立
- 单模块异常不应扩散为整条数据链路失效
- 驱动接口、能力与运行过程统一管理，支持新协议扩展
- OPC DA 通过独立 sidecar / proxy 隔离 COM 与 DCOM 依赖
- 本页结论：低耦合模块 + 可插拔驱动，兼顾稳定性与扩展性
- 页面角色：创新点 / 模块化机制
- 视觉构想：模块化架构骨架，故障被限制在单一隔离舱
- 对应原稿：第二项创新

## Slide 8｜创新三：集中式与分布式部署，适配不同现场条件

- 设备较少、网络条件较好时，采用中心式链路简化部署
- 设备多、跨区域或网络不稳定时，采用分布式边缘部署
- 边缘侧以 SQLite outbox 持久化交接，网络恢复后可靠上传中心
- 两种部署共享统一格式、质量标识与处理规则
- 本页结论：部署形态随现场变化，数据可信性不打折
- 页面角色：创新点 / 部署比较
- 视觉构想：一张左右对照的“双路径选择矩阵”，以网络条件与规模作为坐标
- 对应原稿：第三项创新

## Slide 9｜创新四：同一受控接口，让人和 AI 在权限边界内协同

- Web 端服务业务用户，桌面 App 服务现场运维，CLI 服务人工、脚本和 AI Agent
- 三类入口共享 Backend 的身份认证、权限与数据访问规则
- CLI 只访问 Backend API，不直连 PLC 或数据库
- AI 无法绕过平台权限边界，可在授权范围内查询与分析数据
- 本页结论：先统一身份与权限，再释放人机协同价值
- 页面角色：创新点 / 人机协同
- 视觉构想：人与 AI 位于同一权限“防线”外，通过单一受控网关进入数据系统
- 对应原稿：第四项创新

## Slide 10｜应用成效：单机承载 126 台设备与 4 万+点位持续采集

- 已在一台国产信创电脑上持续采集与监控 126 台设备
- 覆盖 4 万多个核心 PLC 点位
- 采集链路延迟保持在 50–400 ms
- 支持实时监控、历史查询、趋势绘制与数据导出分析
- 本页结论：平台已从架构设计走向真实生产规模验证
- 页面角色：成果 / 数据证据
- 视觉构想：以“126 / 40,000+ / 50–400 ms”三组核心数字建立证据主轴，辅以精简趋势线
- 对应原稿：当前应用成效

## Slide 11｜下一步：从“连接更多数据”走向“释放更多应用价值”

- 扩展更多工业通信协议，接入更多类型设备
- 增加受控数据库连接能力，逐步关联 TOS、ECS、RCMS 等数据
- 基于可信点位数据拓展异常报警与分析应用
- 建议推进顺序：协议覆盖 → 数据关联 → 场景应用
- 本页结论：先扩覆盖面，再扩数据关系，最终扩智能应用
- 页面角色：路线图 / 下一步计划
- 视觉构想：三阶段递进路线图，终点为“智能应用”而非单纯接入量
- 对应原稿：持续拓展方向

## Slide 12｜结语：让数据先流动起来，智能运维才会真正发生

- Data Watch 先解决智能运维最基础、最关键的一步
- 让分散数据汇聚起来，完整、持续、可信地流动
- 在可信数据底座上，人和 AI 才能真正协同
- 收束主张：DATA FIRST · TRUST BY DESIGN · HUMAN + AI
- 页面角色：总结 / 结束页
- 视觉构想：从多个离散节点汇聚为一条稳定数据流，并延伸至“Human + AI”终点
- 对应原稿：结语
