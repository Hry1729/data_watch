## 本轮实现

- **C01**：SQLite 成组提交、事件唤醒、独立 latest 快车道之外，增加 EVALSHA 缓存和单 owner 的有界确认窗口；整个窗口在同一连接末尾执行一次 WAITAOF。NOSCRIPT 或确认失败保留 SQLite 并按原身份重放。宽帧提交与窗口上限经过实测调整：SQLite 每次最多 50 帧/1 MiB、单帧上限 1 MiB；历史窗口最多 4096 帧/32 MiB 原始数据、64 MiB 保守线缆字节。新旧历史 Lua 都改成最多 256 字段一批的 HMGET，逐点时间戳保护不变。同一 outbox 路径增加 OS 级独占锁；第二进程明确失败，进程强杀后可重新打开。
- **C02**：新帧写入独立 v2 表，启动生成不可复用 session，seq 与帧在同一事务持久化。Redis 每 session 一个无 TTL 水位 hash，包含连续高水位和最多 1024 个乱序间隙。旧 UUID 帧保持旧回执协议。v2 积压期间，SQLite 触发器拒绝旧版本向旧表新增帧。
- **R01**：按同组连接选中点并集 HMGET，旧整组订阅使用 HGETALL；连接池上限 256。订阅版本变化时丢弃正在进行的旧范围读取，避免覆盖新快照或假离线。保持初始快照、撤权、慢发送关闭与五秒兜底。
- **后端运行时**：SQLAlchemy 限定 `>=2.0.54,<2.1`，Docker 构建导入完整应用后断言 GIL 仍关闭，并补回归测试。依据：[SQLAlchemy 2.0.54 官方发行记录](https://github.com/sqlalchemy/sqlalchemy/releases/tag/rel_2_0_54)。
- **W03/W06**：PEL、溢出回收、ACK/XDEL 重试按条数、时间和流轮转处理；待确认/待删除身份纳入容量背压，已写入但待 ACK 的帧不会因 PEL 回领重复写入。动态流每轮有界接入。
- **W04**：在线程执行单元按批次解码 JSON，缓冲、映射和 ACK 仍由原消费协程拥有；每八帧让出调度。实际原始字节预算在解码前执行，避免越过预算膨胀。
- **W06 指标**：持续输出每 worker 和总量；区分完整逻辑帧、SQL 元组尝试/成功确认、SQL 字节分布和速率。lag/PEL 有任何未知时总量为 null，另给已知小计；Redis 入流年龄与原始采样年龄分开。SQL 元组成功确认不是底层磁盘写次数，也不推断报错语句内部的部分执行量。

| 输入结束后排空 | 约 58 秒 | 约 1.6 秒 |
| 最终值/质量行 | 60000 / 600000 | 60000 / 600000 |

修复后短测来源到 TD 完整确认最大 1343.4ms，P99 直方图上界 1500ms；最终 outbox、lag、PEL 为零。30 分钟持续测试完成：180 万帧、180 万值行、1800 万质量行全部正确，最终 outbox/PEL/lag 清零；约 1000 帧/秒，来源至 TD 确认平均 647.772ms、最大 1560.749ms，P95/P99 直方图上界 1500ms，事件循环延迟 P99 15.505ms。峰值 RSS 190468096 字节包含基准保留的样本，不能用作生产内存泄漏结论。该长测加载较早的 EVALSHA/单次 WAITAOF 窗口代码，尚不含后续 owner 锁、HMGET 和 Writer 最后修改；期间部分短测共享基础设施。[完整版本边界及摘要](../outputs/performance-20260924/pipeline-soak-summary.json)。最终代码另做 60 秒全链路复测：60000 帧、60000 值行、600000 质量行全部正确，队列排空，最大确认延迟 1363.059ms，稳态检查通过。[最终代码原始结果](../outputs/performance-20260924/pipeline-final-60s.json)。

**千点宽帧尚有容量缺口**：独立无 GIL Collector 在 2 CPU 下，100 设备 × 1000 点 × 100ms、10 秒实际接收 9900 帧（983.96 帧/秒），生产结束积压 9020 帧，之后 39.895 秒排空。历史回放总速率约 198.17 帧/秒，后段约 226.1 帧/秒；4 CPU 的三秒短测也只有约 210/250 帧/秒。两次完整数据核对通过，容量未达输入速率，不能称此档稳态达标。[独立测试证据](../outputs/performance-20260924/collector-ft-validation-notes.md)。同连接拆分测量显示 Lua/Redis 工作与 AOF 确认等待各占约一半窗口时间；WAITAOF 命令 CPU 统计不包含阻塞等待。历史 Lua 批量 HMGET 微基准约 1.948→1.749ms/帧，不能将这个局部改善等同于总体容量达标。[瓶颈归因](../outputs/performance-20260924/collector-ft-profile-attribution.md)。

最终 HMGET 后独立三秒宽帧复测：3000 帧接收约 997.85 帧/秒，生产结束 outbox 2978 帧，之后 9.408 秒排空；总体历史回放 241.64 帧/秒，停采后段 316.53 帧/秒，历史无重复且 latest 正确。相比之前测试存在运行负载差异，不能把全部速率变化归因于 HMGET；这一结果仍明确不满足约 1000 帧/秒持续输入。[最终宽帧证据](../outputs/performance-20260924/collector-ft-profile-final-hmget-3s.json)。

## 剩余验收与明确不作完成声明的项目

- **千点满速容量仍未达标**：100 台 × 每台 1000 点 × 100ms 的输入约 1000 帧/秒，本机单 Redis 的可靠历史回放明显低于这一速率。HMGET 的局部提速不足以解决缺口；需要结合目标机 CPU、内存、磁盘及实际分组点数确定后续容量方案。没有通过放松 AOF 确认、丢样、拒收或改质量语义伪造通过。
- 本轮证明百设备每台 10 点负载能持续运行 30 分钟；尚未证明至少 30% 的持续吞吐余量，更高档负载也未完成 30–60 分钟稳态验证。最终所有补丁只做了专项回归和一分钟全链路复测，不能当作最终版本完整长测。
- W02 已量化每点每周期质量写放大；未实施“仅质量变化写入”，因为它需要历史查询兼容、回填与可回滚迁移设计。W04 已降低同步解析造成的事件循环阻塞，未盲目扩展成多进程架构。
- 现场运行版本指纹、实际 PLC、浏览器应用/绘图延迟、安装包首次启动/旧配置迁移和硬件断电仍需目标环境验收。Docker 强杀与恢复不能替代硬件断电测试。

## 运维约束

- 降级前停止新采集，用新版本排空 v2；旧二进制不会消费 v2 表。新旧二进制不得同时运行同一队列；旧二进制不了解新 OS 锁。
- 新 session 水位不能仅凭当前队列为空就清理。清理期限必须覆盖所有可恢复 SQLite 备份及旧介质；Redis/SQLite 从不一致时间点恢复仍需明确运维恢复契约。
- 现场安装包构建指纹、真实 PLC、浏览器绘图、硬件断电与目标机容量尚未验证。本地 Docker 结果不是现场验收。
- 所有原始 JSON 和测试日志位于 `outputs/performance-20260924`（本轮根目录 JSON、Markdown 和测试日志已显式纳入提交；依赖缓存仍被忽略）；复现脚本在 `scripts/` 及 `backend/scripts/`。已有用户改动均保留。
