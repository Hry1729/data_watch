# DW-01 确认语义、持久化边界与故障恢复规范

本文档定义 Data Watch 采集端、边缘端与中心端在当前实现下的确认保证、允许的数据损失边界、故障假设以及与下游 Writer 的入库水位对账契约。

---

## 1. 核心确认保证 (Confirmation Guarantee)

1. **边缘上传 ACK 语义**：
   - 边缘端收到中心 Ingest 返回的 `status: "ack"` 或 `status: "duplicate"` 时，**仅表示数据已成功进入中心 Redis 实例的内存 Stream 及最新值 Hash，并受 Redis AOF 机制保护**。
   - ACK **不表示**数据已最终写入 TDengine 历史时序库（写入过程由中心 Writer 消费者异步分批完成）。
   - 为避免在中心 Writer 尚未消费且 Redis 异常时导致数据永久丢失，边缘 Outbox 将已确认记录保留时长从原先的 60 秒延长至 **24 小时**（`SENT_RETENTION_MS = 86_400_000`）。在此期间，中心若发现水位缺口，边缘仍持有原始 Payload 可支持重放。

2. **集中式采集重试保证**：
   - 当 PLC 采集成功但 Redis 发生瞬时写故障时，集中式 Collector 通过本地 SQLite `collector_retry_outbox` 进行持久化缓冲。
   - 保留原始采样值与采样时间戳（毫秒精度），在 Redis 恢复后按原时间戳执行重放，遵循 **At-least-once（至少一次）** 投递原则。

3. **中心 Redis 持久化保证**：
   - `deploy/redis.conf` 启用 AOF（`appendonly yes`），刷盘策略为 `appendfsync everysec`。
   - 保证常规进程重启、崩溃时数据完全从 AOF 恢复；但在极端整机掉电或操作系统崩溃场景下，理论上存在最多 **1 秒** 的 fsync 刷新残留窗口。

---

## 2. 允许的数据损失边界与故障假设 (Fault Assumptions & Loss Boundaries)

| 故障场景 | 预期数据损失边界 | 恢复机制 |
|---|---|---|
| 边缘网络中断 / 边缘断电 | 零丢失 | 边缘 Outbox 本地 WAL 事务持久化，网络恢复后按顺序断点续传 |
| 中心 Redis 进程正常退出 / 崩溃重启 | 零丢失 | 重新加载 AOF 日志完全恢复 |
| 中心整机断电 / OS 瞬间宕机 | 最多丢失最近 1 秒内的数据（AOF fsync 窗口） | 依赖边缘 24 小时保留记录重传补漏 |
| 中心 Writer 消费者短暂停摆 | 零丢失 | 数据在 Redis Stream 中堆积，Writer 恢复后通过消费组消费 |
| 集中式 Collector 遇到 Redis 不可用 | 零丢失（在 50,000 条有界缓冲内） | 写入本地 retry_outbox，Redis 恢复后自动重放 |
| 集中式 Collector 本地重试队列饱和（> 50,000条） | 淘汰最老 10% 记录以保护磁盘 | 记录明确告警，优先保留最新鲜状态 |

---

## 3. 下游 Writer 水位契约提案（交由另一智能体负责协调）

由于 Writer 负责将 Redis Stream 批量落库至 TDengine，为彻底闭环“最终入库零丢失”，需要中心 Writer 暴露最终入库水位契约供 Ingest / Edge 对账：

1. **落库确认水位键规范**：
   - 键名：`rt:watermark:{device_type}:{group_code}:{shard}`
   - 类型：Hash
   - 字段：`last_committed_ts`（已成功落库的最大时间戳）、`last_committed_entry_id`（Stream entry ID）。
   - 更新时机：Writer 在执行 `tdengine.write_multi_table()` 成功并 `XACK` 之后更新该 Hash。

2. **边缘清理与对账查询接口**：
   - 中心 Ingest 暴露 `GET /ingest/watermark/{device_code}/{group_code}` 接口。
   - 边缘端只有在确认记录时间戳 `<= last_committed_ts`，或记录已超过安全对账保留窗口（24小时）后，才执行物理删除。
