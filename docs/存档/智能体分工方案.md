# 智能体分工方案

> 版本：2026-04-13 联调治理更新版
> 目的：在当前仓库基线之上，为工业设备数据采集与监控平台提供可执行、可并行、低冲突的多智能体协作方案。

---

## 一、方案目标

本方案解决三个核心问题：

1. **职责边界清晰**：避免多个智能体同时修改同一类事实源。
2. **并行开发可控**：不是所有智能体长期满负荷并行，而是按阶段激活。
3. **联调风险前置**：接口、数据库、测试和模拟环境尽早落地，避免后期集中爆雷。

当前仓库基线判断：

- `collector/` 已有较多核心代码，适合继续增量完善。
- `frontend/src/views/device_monitor/` 已有 7 个核心页面代码与 API 适配层，适合联调式推进。
- `backend/` 目录当前作为预留目录，后端服务需要正式起盘。
- 测试目前主要集中在 `collector/tests/`，还缺少契约测试、联调测试、CI 质量门禁和本地模拟环境。

## 二、技术栈总览

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| 前端 | ArtDesignPro（Vue 3 + TypeScript） | 设备监控页面、数据可视化、交互工作台 |
| 后端 | TurboAPI | REST API、WebSocket、业务编排 |
| 关系数据库 | MySQL 8.0+ | 主业务库 |
| 时序数据库 | TDengine 3.0+ | 实时 + 历史时序数据 |
| 缓存 | Redis | 核心实时缓存层与待入库队列，负责 100ms 实时最新值、短窗口缓存与 Stream 队列 |

| 测试 | pytest / httpx / locust | 单测、契约测试、集成测试、压测 |

## 三、并行开发总原则

### 3.1 单一事实源（Single Source of Truth）

任何跨智能体共享事实都必须只有一个主文档或主文件，其他文件只能派生，不允许双向漂移。

| 主题 | 唯一事实源 | Owner | 消费方 | 规则 |
|------|------------|-------|--------|------|
| 数据库结构 | `docs/设计方案/数据库结构v3.md` | `@database` | `@backend`, `@collector`, `@test` | 数据表、索引、字段语义以此为准 |
| 采集架构 | `docs/采集模块/采集模块整体结构设计.md` | `@collector` | `@database`, `@test`, `@doc` | 采集模块边界和流程以此为准 |
| API / WebSocket 契约 | `docs/后端/API接口文档.md` | `@backend` | `@frontend`, `@test`, `@doc` | 前端类型和后端实现都从这里落地 |
| 联调治理套件 | `docs/前后端联调/` | `@coordinator` | `@backend`, `@frontend`, `@database`, `@test` | 存放联调门禁、映射、矩阵和验收文档 |
| 前端类型适配层 | `frontend/src/types/api/device-monitor.d.ts` | `@frontend` | `@frontend`, `@test` | 只能根据 API 契约更新，不得反向定义接口事实 |
| 前端 API 调用层 | `frontend/src/api/device-monitor.ts` | `@frontend` | `@frontend`, `@test` | 作为前端调用适配层，不单独发明字段 |
| 项目执行板 | `docs/项目TODO文档.md` | `@coordinator` | 所有智能体 | 项目状态、优先级、依赖关系以此为准 |

### 3.2 三段式责任模型

跨模块任务统一采用三段式责任模型：

- **Design Owner**：定义结构、契约、字段、边界。
- **Implementation Owner**：在所属代码目录中完成实现。
- **Reviewer**：重点审核兼容性、依赖影响和验收结果。

示例：

- TDengine 超级表命名规则：`@database` 设计，`@collector` 实现，`@test` 验证。
- 设备监控 REST/WS 契约：`@backend` 设计，`@backend` 与 `@frontend` 各自实现，`@test` 做契约验证。
- 页面交互流程与 API 对接：`@frontend` 实现，`@backend` 复核字段和分页语义。

### 3.3 阶段化并行，而非全时全量并行

不建议 7 个智能体在所有阶段同时拉满并行。默认采用“阶段激活 + WIP 限制”模式：

- 同一时刻**最多 4 条主动开发泳道**。
- 每个智能体**最多 2 个进行中任务**。
- 接口契约、数据库结构、WebSocket 载荷变更，必须先更新事实源，再改代码。
- 若后端尚未落地，前端只能完成页面骨架和适配层，不得自行扩展业务字段。

### 3.4 测试左移

测试不是 `@test` 单独兜底，而是模块责任的一部分：

- 模块 Owner 改代码时必须同步补对应单元测试。
- `@test` 主要负责：契约测试、跨模块集成测试、压测、模拟环境、CI 门禁。
- 没有模拟环境的协议/外设功能，不允许直接宣称“已完成上线级能力”。

### 3.5 交付包最小要求

每次跨智能体交接必须至少包含：

1. 任务 ID 与背景说明。
2. 已更新的事实源文件路径。
3. 受影响代码路径。
4. 新增/更新测试说明。
5. 测试假数据脚本或示例载荷。
6. 兼容性说明与回退方式。

## 四、智能体详细分工

### 1. 项目协调智能体（Coordinator Agent）

**代号**：`@coordinator`

**主责范围**：

- 维护 `docs/项目TODO文档.md` 与阶段目标。
- 控制并行泳道数量、依赖顺序和风险升级路径。
- 裁决跨智能体边界冲突与优先级冲突。
- 组织里程碑验收，明确“代码已写”与“可联调验收”的区别。

**不负责**：

- 不直接成为业务模块默认实现者。
- 不替代模块 Owner 写模块内细节代码。

**核心输出物**：

- 阶段计划
- 风险清单
- 验收结论
- 版本里程碑说明

### 2. 数据采集智能体（Collector Agent）

**代号**：`@collector`

**代码 Owner 目录**：

- `collector/core/`
- `collector/drivers/`
- `collector/device/`
- `collector/collector/`
- `collector/data_queue/`
- `collector/storage/`
- `collector/monitor/`
- `collector/utils/`
- `collector/main.py`

**主责范围**：

- PLC 驱动与协议接入（S7、GE-SRTP、OPC UA）。
- 设备注册、连接、重连、熔断和健康管理。
- 调度器、执行器、缓冲队列、聚合器、批量写入器。
- TDengine 写入实现、监控 API、外部采集接口。

**边界约束**：

- 不负责 MySQL DDL 设计和迁移脚本制定。
- 不负责前端字段命名与接口契约定义。
- 当前重新引入 Redis 运行依赖；实时最新值/短窗口/待入库 Stream 写入 Redis，TDengine 历史数据由独立入库模块批量写入。

**开始任务前必读**：

1. `docs/采集模块/采集模块整体结构设计.md`
2. `docs/采集模块/采集模块代码设计逻辑.md`
3. `docs/设计方案/采集模块设计.md`
4. `collector/main.py`
5. `collector/drivers/base.py`

### 3. 后端服务智能体（Backend Agent）

**代号**：`@backend`

**代码 Owner 目录**：

- `backend/`
- `docs/后端/API接口文档.md`

**主责范围**：

- TurboAPI 项目骨架、依赖注入、中间件、统一响应和错误处理。
- API / WebSocket 契约定义与实现。
- MySQL/TDengine 业务访问层。
- 设备、点位、实时监控、历史数据、日志、工作台接口。

**边界约束**：

- 不直接修改前端页面逻辑。
- 不直接成为数据库结构事实源 Owner。
- 若需变更接口字段，必须先更新 `docs/后端/API接口文档.md`，再通知 `@frontend` 和 `@test`。

**开始任务前必读**：

1. `docs/后端/API接口文档.md`
2. `docs/设计方案/标准后端架构.md`
3. `docs/设计方案/数据库结构v3.md`

**当前特别说明**：

- `backend/` 当前是预留目录，后端智能体的第一优先级不是“继续追加接口细节”，而是先建立可运行骨架。

- 前端 API 调用适配、页面状态管理、WS 客户端处理。

**边界约束**：

- TDengine 最新值查询、连续聚合与实时快照口径设计。
- Demo / seed / fixture 所需的数据库侧结构支撑。

**边界约束**：

- 不负责 Python 运行时业务逻辑实现。
- 不负责 Vue 页面代码。
- 不替代后端编写 ORM 和 Service，只提供事实源与 SQL 基线。

**开始任务前必读**：

### 6. 测试与基础设施智能体（Test / Infra Agent）

**代号**：`@test`

**边界约束**：

- 不替代模块 Owner 编写所有单元测试。
- 模块 Owner 改动模块代码时，必须同步补本模块单测。
- `@test` 重点做“跨边界质量保证”，而不是“模块内部兜底开发”。

**开始任务前必读**：

1. `collector/tests/conftest.py`

3. `docs/后端/API接口文档.md`

**主责范围**：

- 文档结构治理、目录规范、发布说明、部署手册、运维手册。
- 对已有事实源做标准化整理和可读性增强。
- 维护交接记录、验收清单、上线手册。

**边界约束**：

- 不默认成为 API / 数据库事实源 Owner。
- 当事实源由其他智能体维护时，`@doc` 负责润色、整理和发布，而不是擅自改语义。

## 六、阶段化激活策略

### Phase 0：基线治理（立即执行）

**激活智能体**：`@coordinator`、`@doc`、`@backend`、`@frontend`、`@collector`

**目标**：

- 校准 TODO 与仓库现状。
- 固定唯一事实源路径。
- 冻结 v1 API / WS 契约基线。
- 明确第一条闭环链路的范围。

### Phase 1：最小闭环（优先）

**激活智能体**：`@collector`、`@backend`、`@frontend`、`@test`

**建议闭环**：

- 设备树 / 设备列表
- 实时初始化接口
- WebSocket 实时推送
- 前端实时监控页

**原因**：

- 这是最能暴露接口、TDengine 最新值查询、状态同步和联调问题的一条主链路。

### Phase 2：扩展能力

**激活智能体**：`@collector`、`@backend`、`@frontend`、`@database`、`@test`

**目标**：

- 历史查询
- 工作台统计
- 日志能力
- TDengine 查询与聚合优化

### Phase 3：质量与交付

**激活智能体**：`@test`、`@doc`、`@coordinator`，按需拉上模块 Owner

**目标**：

- 集成测试
- 压测
- CI 门禁
- 部署文档
- 验收清单

## 七、沟通与升级机制

### 7.1 日常沟通格式

统一使用以下最小模板：

- 任务 ID
- 当前状态（`✅ / 🔄 / 📋 / ⏸️`）
- 依赖项
- 输出文件路径
- 风险或阻塞说明

### 7.2 需要强制升级到 `@coordinator` 的场景

- 两个以上智能体要同时修改同一事实源。
- API 契约与前端页面实现发生字段级冲突。
- 数据库结构调整会影响采集与后端已有实现。
- 里程碑关键路径超过 2 个工作日未推进。

### 7.3 必须发起评审的变更

以下变更必须至少经过一个 Reviewer：

- 数据库字段新增、重命名、删除
- TDengine 最新值查询口径或聚合策略修改
- WebSocket 事件结构调整
- 历史查询返回结构修改
- 批量导入导出字段修改

## 八、当前风险与控制措施

| 风险 | 等级 | 控制措施 | Owner |
|------|------|----------|-------|
| 前后端契约再次漂移 | 高 | 锁定 `docs/后端/API接口文档.md` 为唯一契约源 | `@backend` |
| TODO 与仓库状态再次失真 | 高 | 只允许 `@coordinator` 更新执行板，周内做一次校准 | `@coordinator` |
| 后端代码缺位导致前端空转 | 高 | 第一阶段先起 TurboAPI 骨架和最小闭环接口 | `@backend` |
| 缺少 PLC / TDengine / MySQL 联调环境 | 高 | 提前建设 fixture、fake data、smoke script | `@test` |
| 采集链路可运行但不可验收 | 中 | 强制补单测、契约测试、集成测试 | `@collector`, `@test` |
| 文档多人维护再次出现双事实源 | 中 | 文档 Owner 与事实源 Owner 分离 | `@doc`, `@coordinator` |
