### CRITICAL 严重问题

---

#### C-1：Redis Stream 写入脚本与采集器实际写入格式完全不兼容

**文件**：`scripts/redis_to_tdengine_writer.py`  
**对应写入方**：`storage/redis_writer.py`

`redis_to_tdengine_writer.py` 设计读取的 Stream 格式（来自 `redis_mock_writer.py`）：

| 字段 | mock 格式 |
|------|-----------|
| Stream Key | `rt:stream`（单个 key） |
| `type` | 设备类型如 `"qc"` |
| `ts` | ISO 时间字符串如 `"2026-05-19T13:00:00.100"` |
| `payload` | JSON 对象 `{"qc1": 1.23, "qc2": 4.56}` |

而实际采集器 `storage/redis_writer.py` 写入的格式：

| 字段 | 实际格式 |
|------|----------|
| Stream Key | `rt:stream:{device_type}:{group_code}:{shard_no}`（分片多 key） |
| `device_type` | 设备类型（字段名不同） |
| `ts` | 毫秒时间戳整数字符串 |
| `values` | JSON 字符串 `{var_id: value_str}` |

**差异点**：
1. Stream Key 完全不同（单 key vs 分片 key）
2. 字段名不同：`type` vs `device_type`，`payload` vs `values`
3. 时间戳格式不同：ISO 字符串 vs 毫秒整数
4. 数据内容不同：wide-table 列名 vs variable_id

**后果**：`redis_to_tdengine_writer.py` 无法读取真实采集器写入的任何 Stream 数据，Redis → TDengine 宽表写入链路实际处于**不可用状态**。

**建议**：`redis_to_tdengine_writer.py` 需要重写以匹配 `redis_writer.py` 实际写入的 key 和字段格式，或统一明确其中一个 Stream 格式作为标准。

---

#### C-2：采集器仍有直接写 TDengine 的链路，与设计文档目标状态不符

**文件**：`main.py`（全文），`storage/batch_writer.py`，`storage/tdengine.py`

设计文档（`采集模块整体结构设计.md` 头部）明确：
> 当前目标状态：采集模块**只写 Redis** 最新值、短窗口和待入库 Stream。历史态由**独立 TDengine 入库模块**从 Redis Stream 批量消费后写入宽表。

但实际代码在 `main.py` 中：
```python
self.tdengine = TDengineConnection(config.tdengine)
self.batch_writer = BatchWriter(self.tdengine, ...)
self.aggregator.set_output_callback(self.batch_writer.write_sync)  # → TDengine
# ...
await self.tdengine.connect()
await self.tdengine.init_storage_topology(...)
```

**两条写入链路并存**：
1. `executor → DataBuffer → DataAggregator → BatchWriter → TDengine`（旧窄表模型，collector 直写）
2. `executor → RedisWriter → Redis Stream → redis_to_tdengine_writer.py → TDengine`（新宽表模型，设计目标）

**后果**：
- 如果两个写入进程同时运行，同一数据写入两套 TDengine schema（窄表 + 宽表），数据双写。
- 因为 C-1 问题，链路 2 实际不工作，当前只有链路 1 有效；但如果修复 C-1 后，双写问题将出现。
- `tdengine.py` 的 `init_storage_topology` 创建的是**每变量一个子表**的窄表模型，与 docs 描述的宽表模型不符。

**建议**：明确架构方向（旧窄表模型还是新宽表模型），选定后清理多余路径。如果迁移到宽表模型，则应将 `TDengineConnection`、`BatchWriter` 从 collector 中移除，改为独立 writer 进程消费 Redis Stream。

#### H-2：`aggregator.py` 的 `_restore_batch_to_cache` 中时间戳判断逻辑永远为 False

**文件**：`data_queue/aggregator.py`，第 190 行

```python
self._pending_time[point.variable_id] = (
    point.timestamp / 1000.0
    if isinstance(point.timestamp, (int, float))
    else time.time()
)
```

`DataPoint.timestamp` 在 `data_queue/buffer.py` 中定义为 `datetime` 类型（`field(default_factory=datetime.now)`），其类型永远是 `datetime`，绝不会是 `int` 或 `float`。

**后果**：条件分支 `isinstance(point.timestamp, (int, float))` 恒为 False，每次写入失败后恢复 batch 时，所有点的 `_pending_time` 都被更新为 `time.time()`（当前时间），而非原始时间。这导致**刚写入失败的 batch 的去重时间窗口被错误地刷新**，在下次重试时会继续正常入缓存（问题不大），但原始语义被破坏了。

**建议**：修正为：
```python
self._pending_time[point.variable_id] = (
    point.timestamp.timestamp()
    if isinstance(point.timestamp, datetime)
    else time.time()
)
```

### MEDIUM 中优先级问题

---

#### M-1：两处 `asyncio.get_event_loop()` 在异步上下文中使用了被废弃 API

**文件**：`main.py` 第 554 行，`collector/executor.py` 第 125 行

Python 3.10+ 废弃了在已有运行循环的异步上下文中调用 `asyncio.get_event_loop()`，在 Python 3.14 中会触发 DeprecationWarning（项目使用 Python 3.14 free-threading）。

```python
# main.py:554
loop = asyncio.get_event_loop()
for sig in (signal.SIGINT, signal.SIGTERM):
    loop.add_signal_handler(sig, app.stop)

# executor.py:125（在 async def execute 中）
loop = asyncio.get_event_loop()
loop.run_in_executor(None, self._write_to_redis, ...)
```

**建议**：在异步函数内改用 `asyncio.get_running_loop()`：
```python
# executor.py:125
loop = asyncio.get_running_loop()
loop.run_in_executor(None, self._write_to_redis, device, scan_task, points)
```
`main.py:554` 发生在 `async def main()` 内，应使用 `asyncio.get_event_loop()` → `asyncio.get_running_loop()`（注意：信号注册必须在事件循环启动后，此处逻辑已正确，只需换 API）。

#### M-2：`ingest_server.py` 的 `log_message` 存在竞态条件

**文件**：`monitor/ingest_server.py`，第 437-440 行

```python
def log_message(self, fmt, *args):
    if not hasattr(self.server, '_log_counter'):   # ← 非原子检查
        self.server._log_counter = 0               # ← 非原子初始化
        self.server._log_last_time = time.time()
        self.server._log_last_fmt = ""
```

`ThreadingHTTPServer` 使用多线程处理请求，多个线程可能同时通过 `hasattr` 检查并执行初始化，导致计数器被重置。

**建议**：使用 `threading.Lock()` 保护初始化，或在 `_IngestHTTPServer.__init__` 中提前初始化这些属性：
```python
class _IngestHTTPServer(ThreadingHTTPServer):
    def __init__(self, ...):
        super().__init__(...)
        ...
        self._log_counter = 0
        self._log_last_time = time.time()
        self._log_lock = threading.Lock()
```

#### M-4：`tdengine.py` 的 `_stable_exists` 与 `_table_exists` 依赖 `USE db` 后执行，存在并发隐患

**文件**：`storage/tdengine.py`，第 307-334 行

`_stable_exists` 调用 `await self.execute(f"USE \`{db_name}\`")`（持有 `_execute_lock`），然后调用 `_fetch_all(f"SHOW STABLES LIKE ...")`（不持有 `_execute_lock`）。在 `init_storage_topology` 的循环中虽然是顺序执行，但如果未来并发调用，两步之间可能被其他 `execute` 插入而切换数据库上下文。

**建议**：使用绝对路径 `SHOW STABLES IN \`{db_name}\`` 代替 `USE + SHOW`，或在 `_fetch_all` 前也加锁。

### HIGH 高优先级问题

#### H-1：`_flush` 写入失败后仍清空内存缓冲区，失败行丢失直到重启

**文件**：`writer/consumer.py`，第 352-382 行

```python
async def _flush(self) -> None:
    ...
    for child_table, buffered_rows in by_table.items():
        ok = await self._writer.write_batch(rows)
        if ok:
            self._ack_rows(buffered_rows)
        else:
            logger.error("... not acking, will retry")  # 未 ACK

    self._buffer.clear()   # ← 无论成败，全部清空
    self._last_flush = time.monotonic()
```

当某个 `child_table` 写入失败时：
1. 这批行**未被 XACK**，保留在 Redis Stream 的 pending 状态 ✓
2. 但 `self._buffer.clear()` 立刻将内存中的行**全部清除** ✗

失败行只有在下次进程重启时（`drain_pending` 在 `run_loop` 开始时执行一次）才会被重新处理。在运行期间不会自动重试。

**建议**：仅对成功写入的 table 对应行调用 clear，保留失败行以便当次周期重试：
```python
failed_rows = []
for child_table, buffered_rows in by_table.items():
    ok = await self._writer.write_batch(...)
    if ok:
        self._ack_rows(buffered_rows)
    else:
        failed_rows.extend(buffered_rows)

self._buffer = failed_rows   # 保留失败行，下次 flush 重试
self._last_flush = time.monotonic()
```

#### H-2：MySQL 查询直接在 asyncio 事件循环线程中同步执行

**文件**：`writer/consumer.py`，第 307 行；`writer/mysql_mapper.py`，第 77-127 行

```python
# consumer.py _handle_entry 中（无 await，无 executor）：
mapping = self._mapper.get_or_load(device_code, group_code, config_version)
```

`get_or_load` 调用 `load` 执行 `cur.execute(_SQL, ...)` —— 这是 pymysql 的同步 I/O，直接阻塞事件循环线程。`_handle_entry` 在每个 Stream 消息处理时都可能触发，批量消费时（`batch_count=200`）缓存冷启动后会有大量同步 MySQL 查询堆积，阻塞所有 asyncio 协程。

**建议**：将 `load` 方法包装在 `await asyncio.get_running_loop().run_in_executor(None, ...)` 中执行，或改用 `aiomysql` 异步客户端。

#### H-3：pending 消息仅在启动时回收一次，运行期间无定期重声明

**文件**：`writer/consumer.py`，第 88-94 行

```python
async def run_loop(self, stream_keys):
    self._ensure_consumer_groups(stream_keys)
    for sk in stream_keys:
        await self.drain_pending(sk, self._consumer_name)  # ← 仅启动时执行一次
    ...
    while True:
        # 主循环中无任何 pending reclaim
```

如果进程在 XACK 之前因 TDengine 写入失败而崩溃，未 ACK 的消息将永久留在 pending 中，直到下次重启。在长时间运行的场景下，**一次 TDengine 抖动导致的失败消息只有重启才能恢复**。

**建议**：在主循环中加入周期性 `drain_pending` 调用，例如每 5 分钟执行一次对各 stream key 的 pending 回收。

#### M-6：无 SIGTERM 信号处理，停止时 buffer 不刷新

**文件**：`writer/main.py`

Python 3 中 `SIGTERM` 默认不触发 `KeyboardInterrupt`。Docker/systemd 发送 `SIGTERM` 时进程直接终止，内存中的 `_buffer` 中的行不会被 XACK，这些 pending 消息需要等下次重启的 `drain_pending` 恢复。

**建议**：注册 SIGTERM 处理器取消主 task 并执行最终 `_flush`：
```python
loop = asyncio.get_running_loop()
loop.add_signal_handler(signal.SIGTERM, consumer_task.cancel)
```

#### M-7：`config_version` 不匹配时 entry 永久 pending，引发持续 MySQL 查询

**文件**：`writer/consumer.py`，第 307-314 行；`writer/mysql_mapper.py`，第 62-74 行

**建议**：对版本不匹配的 entry 增加超时 DLQ 策略（如超过 `pending_max_retry` 次进 DLQ），或在 `get_or_load` 中对 "MySQL 最新版也不匹配" 的情况（而非 "缓存过期" 的情况）直接放行/丢弃。

#### B-H1：`_push_loop` 将 Redis 不可用误报为设备离线，且所有错误完全静默

**文件**：`backend/app/services/ws_push.py`，第 49-89 行

链路中存在两层静默吞噬：

```python
# _read_latest（第 61-62 行）
async def _read_latest(...) -> dict:
    try:
        ...
        raw = await r.hgetall(...)
        ...
    except Exception:
        return {}   # ← Redis 连接失败，静默返回空字典

# _push_loop（第 71-73 行）
if not latest:
    await self._broadcast(key, {"type": "offline", ...})
    continue
```

Redis 连接超时、认证失败、网络抖动均会使 `_read_latest` 返回 `{}`，进而向**所有当前连接的 WebSocket 客户端**广播 `{"type": "offline"}`，将设备状态显示为离线。整个过程没有任何 `logger.warning`/`logger.error` 输出，Redis 故障在服务端完全不可见。

**后果**：Redis 发生短暂抖动时，所有监控终端将出现设备离线告警，而服务器日志中毫无记录，排查时难以定位根因是 Redis 问题还是设备真的断连。

**建议**：
1. `_read_latest` 内的 `except` 应区分"key 不存在（正常情况）"与"连接失败（需告警）"，连接失败时记录一条 `logger.warning`；
2. `_push_loop` 对"空字典"状态应标记来源（`redis_error` 还是 `no_data`），避免两种情况映射到同一条 `offline` 消息；
3. `_push_loop` 第 88-89 行的 `except Exception: pass` 至少应 `logger.warning("ws_push loop error: %s", exc)` 记录一次，防止未知异常完全湮灭。

#### B-M1：`TDengineClient` 每次查询都新建连接，无连接池

**文件**：`backend/app/db/tdengine.py`，第 71-83 行

```python
async def fetch_all(self, sql: str, ...) -> list[tuple]:
    return await asyncio.to_thread(self._fetch_all_sync, sql, database)

def _fetch_all_sync(self, sql: str, ...) -> list[tuple]:
    conn = self.connect(database=database)   # ← 每次查询建一个新连接
    cursor = conn.cursor()
    try:
        cursor.execute(sql)
        return list(cursor.fetchall() or [])
    finally:
        cursor.close()
        conn.close()
```

`history.py` 中的多点位历史查询通过 `asyncio.gather` 并发执行（例如 20 个点位），会同时发起 20 个 `asyncio.to_thread` 调用，每个线程各建一次 TDengine 连接（WS 或 REST 握手）。高频 Perspective 数据流场景下，连接建立/销毁的开销会成为瓶颈。

**建议**：使用连接池（如 `taosws` 内置连接池选项，或通过 `asyncio.Semaphore` 限制并发连接数），或将 `TDengineClient` 升级为持久连接单例并在连接断开时自动重连。

#### B-M2：`_calculate_auto_interval` 中存在永不可达的分支

**文件**：`backend/app/services/history.py`，第 636-656 行

```python
def _calculate_auto_interval(self, start_dt, end_dt, target_points=2000) -> str:
    total_seconds = (end_dt - start_dt).total_seconds()
    if total_seconds <= 0:
        return "5s"
    interval_sec = max(1, int(total_seconds / target_points))   # ← 最小值保证 >= 1
    if interval_sec < 1:
        return "500ms"   # ← 永远不可达
    if interval_sec < 5:
        return "5s"
    ...
```

`interval_sec = max(1, ...)` 保证结果 `>= 1`，因此 `if interval_sec < 1` 恒为 False，`return "500ms"` 是死代码。短时间范围（< 2 秒总时长）时，目标粒度 500ms 无法被选择，只能退回到 "5s"，实际采样点数会远少于 `target_points=2000`。

**建议**：将 `max(1, ...)` 改为 `max(0, ...)`，并在 `interval_sec < 1` 时使用 `"500ms"`；或直接添加对时间窗口 `< 2s` 的前置判断。
