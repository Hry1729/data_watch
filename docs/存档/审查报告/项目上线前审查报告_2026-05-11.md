## 三、上线阻断与高风险问题

### P0-1：点位编辑会重置 `scanRate` / `isStorage`

涉及文件：

- `frontend/src/views/device_monitor/point/modules/point-dialog.vue`
- `frontend/src/types/api/device-monitor.d.ts`
- `backend/app/services/catalog.py`

现象：

- 后端点位列表序列化已经返回 `scanRate` 和 `isStorage`。
- `PointForm` 类型也定义了 `scanRate?: number` 和 `isStorage?: boolean`。
- 但是 `PointListItem` 没声明这两个字段。
- 点位编辑弹窗没有把 `scanRate` 和 `isStorage` 放入 `formData`。
- 后端 `update_point()` 在 payload 缺失字段时默认写入：
  - `scanRate = 1000`
  - `isStorage = true`

风险：

- 用户只编辑点位名称、描述、地址等字段，也可能把原本的采集周期和是否存储配置改掉。
- 对采集模块来说，这是配置破坏风险。

置信度：95%

建议修复：

1. `PointListItem` 补充 `scanRate?: number`、`isStorage?: boolean`。
2. 点位编辑弹窗 `formData` 恢复并提交这两个字段。
3. 后端 `update_point()` 对缺失字段不要使用固定默认值，而应保留数据库原值，或要求前端明确传入。
4. 新增测试：编辑点位名称后，`scan_rate` 和 `is_storage` 不变。

### P0-2：采集模块当前不是真正 100ms 采集

涉及文件：

- `collector/core/config_db.py`
- `collector/core/config.py`
- `collector/collector/scheduler.py`

现象：

`collector/core/config_db.py` 中 `_normalize_scan_rate()` 逻辑：

- `scan_rate >= 100` 被视为毫秒。
- 但最终使用 `math.ceil(v / 1000)` 转成秒。
- 因此 `100ms` 会变成 `1s`。
- `500ms` 也会变成 `1s`。

风险：

- 如果现场要求 100ms 采集，当前采集模块实际达不到。
- 历史数据中有 100ms 写入，不代表当前采集调度一定按 100ms 执行，可能来自模拟或其他写入链路。

置信度：95%

建议修复方向：

方案 A：正式支持亚秒采集。

- `scan_rate` 内部统一用秒，但允许 float，例如 `0.1`、`0.5`、`1.0`。
- `config.py` 中类型从 `int` 调整为 `float`。
- `_normalize_scan_rate()` 中 `100` 转成 `0.1`，`500` 转成 `0.5`。
- `scheduler.py` 当前 `asyncio.sleep(interval)` 可支持 float，改动面可控。
- 测试覆盖 `100ms -> 0.1s`、`500ms -> 0.5s`、`1000ms -> 1s`。

方案 B：不支持亚秒采集。

- 明确限制最小采集周期为 `1000ms`。
- 前端和后端点位配置禁止保存小于 1000ms 的周期。
- 文档写明采集模块最小周期 1s。

建议选择：如果桥吊/轨道吊确实依赖 100ms I/O 状态变化，选方案 A。

### P0-3：S7 地址和数据类型缺少统一入口校验

涉及文件：

- `backend/app/services/catalog.py`
- `collector/core/config_validator.py`
- `collector/drivers/s7_driver.py`

现状：

- S7 驱动运行时会严格校验地址和数据类型。
- 例如：
  - `%I100.0` 必须是 `BOOL`
  - `%IB100` 对应 1 字节类型
  - `%IW100` 对应 2 字节类型
  - `%ID100` 对应 4 字节类型
  - `DBX` 必须是 `BOOL`
  - `DBW` 不能配 `REAL`
  - `DBD` 不能配 `INT`
- 但点位新增、编辑、导入入口只校验地址文本和数据类型枚举，没有校验二者是否匹配。

风险：

- 错误点位可以进入数据库。
- 采集启动后才在驱动层报错。
- 大量 I/Q/M 点时，一个配置错误可能造成采集日志刷屏或任务异常。

置信度：90%

建议修复：

1. 新增共享校验函数，例如 `validate_s7_address_data_type(address, data_type)`。
2. 后端点位新增、编辑、导入都调用。
3. 采集模块 `config_validator.py` 也调用同一套规则或保持规则一致。
4. 错误应在点位保存/导入阶段返回明确提示。

建议允许的组合示例：

- `%I100.0` / `%Q100.1` / `%M100.2` + `BOOL`
- `%IB100` / `%QB100` / `%MB100` + `BYTE`
- `%IW100` / `%QW100` / `%MW100` + `INT` 或 `WORD`
- `%ID100` / `%QD100` / `%MD100` + `DINT`、`DWORD` 或 `REAL`
- `DB1.DBX0.0` + `BOOL`
- `DB1.DBB0` + `BYTE`
- `DB1.DBW0` + `INT` 或 `WORD`
- `DB1.DBD0` + `DINT`、`DWORD` 或 `REAL`

### P1-1：I/Q/M 大量点位没有合并读取

涉及文件：

- `collector/device/device.py`
- `collector/drivers/s7_driver.py`

现象：

`collector/device/device.py` 中 `_build_read_blocks()` 注释写的是“连续地址合并读取”，但实际实现是每个变量创建一个 `ReadBlock`。

风险：

- 桥吊、轨道吊存在大量 I/O 点。
- 当前设计可能导致一个周期内对 PLC 发起大量小读请求。
- 对 DB 连续块读取通常还能接受，但 I/Q/M 点尤其多时，性能和 PLC 负载风险更高。

置信度：95%

建议：

1. 短期先做现场压测，确认当前点位数量下每周期读耗时。
2. 如果 100ms 周期下读耗时接近或超过周期，必须实现合并读取。
3. 合并策略按协议和区域分组：
   - DB：按 DB 号分组。
   - I/Q/M：按 area 分组。
   - 对连续或相近 byte offset 合并为较大 read_area/db_read。
   - 回填时按每个变量 offset/bit/type 解析。

建议优先合并 I/Q/M，DB 可后置。

### P1-2：聚合器去重逻辑与测试预期不一致

涉及文件：

- `collector/data_queue/aggregator.py`
- `collector/tests/test_data_aggregator.py`

测试失败：

```text
test_aggregator_dedupes_unchanged_values
assert 3 == 2
```

现象：

- 聚合器 `should_store()` 只看已确认写入的 `_confirmed_values`。
- flush 成功前，同一变量相同值重复进入缓存。
- 测试期望是同一批次内不重复缓存相同值。

风险：

- 短时间内相同值会重复写入，增加 TDengine 写入量。
- 如果采集频率提高到 100ms，重复写入压力更明显。

置信度：90%

建议：

- `should_store()` 同时参考 pending 状态。
- 对同一变量，缓存中已经有相同 pending 值且未超时，应跳过。
- 写入失败回滚时要保证 pending 状态恢复合理。

### P1-3：缓存默认 TTL 未生效

涉及文件：

- `collector/core/cache.py`
- `collector/tests/test_cache.py`

测试失败：

```text
test_ttl_expiry
test_cleanup_task
```

现象：

- `CacheManager(default_ttl=1)` 后调用 `set("key", "value")`。
- 当前 `set()` 只有显式传 `ttl` 才设置过期时间。
- 未传 `ttl` 时没有使用 `default_ttl`。

风险：

- 默认 TTL 配置无效。
- 缓存可能长期不失效。

置信度：98%

建议：

- `set()` 和 `set_sync()` 中使用 `effective_ttl = ttl if ttl is not None else self.default_ttl`。
- 对 `ttl <= 0` 的语义需要明确：是不过期，还是立即过期。

### P1-4：TDengine 存储测试桩未跟上实现

涉及文件：

- `collector/storage/tdengine.py`
- `collector/tests/test_tdengine_storage.py`

测试失败：

```text
test_init_storage_topology_builds_variable_targets
test_batch_writer_groups_by_variable_subtable_without_variable_id_column
test_batch_writer_raises_on_partial_subtable_failure
```

现象：

- 当前 `init_storage_topology()` 会调用 `_stable_exists()` 和 `_table_exists()`。
- 这些方法内部会走 `_fetch_all()`。
- 测试只 mock 了 `execute()`，没有 mock `_fetch_all()` 或 `_conn.query()`。
- 因此测试中报 `Not connected to TDengine`。

判断：

- 这更像测试桩问题，不一定是生产逻辑 bug。
- 但上线前测试套件红灯必须处理。

置信度：85%

建议：

- 在单元测试中 mock `_stable_exists()`、`_table_exists()`，或 mock `_fetch_all()` 返回空列表。
- 保持测试不依赖真实 TDengine 连接。

## 五、建议修复顺序

### 第一批：先修最小且高确定性问题

1. 点位编辑保留 `scanRate` / `isStorage`。
2. 缓存默认 TTL 生效。
3. 聚合器同批 pending 值去重。
4. TDengine 存储测试桩修复，让采集模块 pytest 恢复全绿。

原因：

- 改动小。
- 风险可控。
- 能快速恢复测试信心。

### 第二批：修采集配置正确性

1. S7 地址和数据类型统一校验。
2. 点位新增、编辑、导入全部接入校验。
3. 采集模块配置校验同步规则。

原因：

- 直接影响桥吊/轨道吊 I/Q/M 点是否能可靠采集。
- 能把错误挡在配置入口，而不是运行时爆错。

### 第三批：决定 100ms 采集策略

需要先确认业务要求：

- 如果必须 100ms：将 `scan_rate` 内部改为 float 秒。
- 如果不必须：前后端限制最小 1000ms，并写入文档。

### 第四批：I/Q/M 合并读取和性能压测

1. 统计单设备点位数量、I/Q/M 点数量、每周期读取耗时。
2. 如果 100ms 周期下压力高，优先实现 I/Q/M 合并读取。
3. 压测桥吊、轨道吊典型点表。

## 六、上线建议

当前状态不建议直接上线到正式采集现场。

理由：

- 采集模块完整测试仍有 6 个失败。
- 点位编辑存在采集配置被重置风险。
- 100ms 采集语义和当前实现不一致。
- I/Q/M 大量点位读取没有合并策略，现场性能风险未验证。

建议上线前达成以下最低条件：

1. 后端测试通过。
2. 前端类型检查通过。
3. 采集模块 pytest 全绿。
4. 点位编辑不再重置采集周期和是否存储。
5. S7 地址和数据类型错误配置无法保存或导入。
6. 明确 100ms 是否支持。
7. 至少完成一次桥吊/轨道吊典型 I/Q/M 点表采集压测。
