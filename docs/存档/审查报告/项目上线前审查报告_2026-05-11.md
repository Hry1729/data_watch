## 三、上线阻断与高风险问题（已全部修复）

### P0-1 ✅ 已修复：点位编辑会重置 `scanRate` / `isStorage`

涉及文件：

- `frontend/src/views/device_monitor/point/modules/point-dialog.vue`
- `frontend/src/types/api/device-monitor.d.ts`
- `backend/app/services/catalog.py`

现象：

- 后端点位列表序列化已经返回 `scanRate` 和 `isStorage`。
- `PointForm` 类型也定义了 `scanRate?: number` 和 `isStorage?: boolean`。
- 但是 `PointListItem` 没声明这两个字段。
- 点位编辑弹窗没有把 `scanRate` 和 `isStorage` 放入 `formData`。
- 后端 `update_point()` 在 payload 缺失字段时默认写入：
  - `scanRate = 1000`
  - `isStorage = true`

风险：

- 用户只编辑点位名称、描述、地址等字段，也可能把原本的采集周期和是否存储配置改掉。
- 对采集模块来说，这是配置破坏风险。

置信度：95%

修复内容：

1. `PointListItem` 已补充 `scanRate?: number`、`isStorage?: boolean` 字段声明。
2. 点位编辑弹窗 `formData` 已恢复并提交这两个字段。
3. 后端 `update_point()` 对缺失字段改为保留数据库原值，不再强写默认值。
4. 已补充回归测试：编辑点位名称后验证 `scan_rate` 和 `is_storage` 不变。

### P0-2 ✅ 已修复：采集模块当前不是真正 100ms 采集

涉及文件：

- `collector/core/config_db.py`
- `collector/core/config.py`
- `collector/collector/scheduler.py`

现象：

`collector/core/config_db.py` 中 `_normalize_scan_rate()` 逻辑：

- `scan_rate >= 100` 被视为毫秒。
- 但最终使用 `math.ceil(v / 1000)` 转成秒。
- 因此 `100ms` 会变成 `1s`。
- `500ms` 也会变成 `1s`。

风险：

- 如果现场要求 100ms 采集，当前采集模块实际达不到。
- 历史数据中有 100ms 写入，不代表当前采集调度一定按 100ms 执行，可能来自模拟或其他写入链路。

置信度：95%

修复内容（采用方案 A）：

- `scan_rate` 内部已改为 float 秒，支持亚秒采集。
- `_normalize_scan_rate()` 已修正：`100ms → 0.1s`、`500ms → 0.5s`、`1000ms → 1.0s`。
- `config.py` 中 `scan_rate` 类型已从 `int` 改为 `float`。
- `scheduler.py` 的 `asyncio.sleep(interval)` 本身支持 float，无需改动。
- 已新增测试覆盖 `100ms → 0.1s`、`500ms → 0.5s`、`1000ms → 1.0s` 三种场景。

### P0-3 ✅ 已修复：S7 地址和数据类型缺少统一入口校验

涉及文件：

- `backend/app/services/catalog.py`
- `collector/core/config_validator.py`
- `collector/drivers/s7_driver.py`

现状：

- S7 驱动运行时会严格校验地址和数据类型。
- 例如：
  - `%I100.0` 必须是 `BOOL`
  - `%IB100` 对应 1 字节类型
  - `%IW100` 对应 2 字节类型
  - `%ID100` 对应 4 字节类型
  - `DBX` 必须是 `BOOL`
  - `DBW` 不能配 `REAL`
  - `DBD` 不能配 `INT`
- 但点位新增、编辑、导入入口只校验地址文本和数据类型枚举，没有校验二者是否匹配。

风险：

- 错误点位可以进入数据库。
- 采集启动后才在驱动层报错。
- 大量 I/Q/M 点时，一个配置错误可能造成采集日志刷屏或任务异常。

置信度：90%

修复内容：

1. 已新增共享校验函数 `validate_s7_address_data_type(address, data_type)`。
2. 后端点位新增、编辑、导入接口已全部接入该校验，错误在保存阶段返回明确提示。
3. 采集模块 `config_validator.py` 已同步同一套规则，前后端校验逻辑一致。

### P1-1 ✅ 已修复：I/Q/M 大量点位没有合并读取

涉及文件：

- `collector/device/device.py`
- `collector/drivers/s7_driver.py`

现象：

`collector/device/device.py` 中 `_build_read_blocks()` 注释写的是“连续地址合并读取”，但实际实现是每个变量创建一个 `ReadBlock`。

风险：

- 桥吊、轨道吊存在大量 I/O 点。
- 当前设计可能导致一个周期内对 PLC 发起大量小读请求。
- 对 DB 连续块读取通常还能接受，但 I/Q/M 点尤其多时，性能和 PLC 负载风险更高。

置信度：95%

建议：

修复内容：

- `_build_read_blocks()` 已实现真正的连续地址合并：按协议和区域分组，对连续或相近 byte offset 合并为较大 read_area/db_read，回填时按每个变量的 offset/bit/type 单点还原。
- I/Q/M 区域合并已优先实现，DB 合并已同步完成。
