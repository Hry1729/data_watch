# 审查报告 20260521

## 问题背景

writer 模块启动后写入 TDengine 时报错：

```
[0x2603] Internal error: Table does not exist
```

追查后发现多个关联问题，本次统一修复。

---

## 问题一：writer 子表/超级表名称错误

**文件**：`writer/mysql_mapper.py`

**原因**：`MysqlMapper.load()` 生成的 `child_table` 和 `stable` 与 TDengine 实际结构不匹配。

| 字段 | 修复前 | 修复后 |
|------|--------|--------|
| `child_table` | `t_{device_code}_{group_code}`（如 `t_qc100_g001`） | `device_code`（如 `qc100`） |
| `stable` | `st_{device_type}_{group_code}`（如 `st_qc_g001`） | `sd{device_type}`（如 `sdqc`） |

---

## 问题二：writer 未使用 USING 语法，子表不存在时写入失败

**文件**：`writer/tdengine_writer.py`

**原因**：`_write_table_rows` 原本使用普通 `INSERT INTO child (cols) VALUES (...)` 语法，要求子表预先存在。

**修复**：改为 `INSERT INTO child USING stable TAGS('tag') (cols) VALUES (...)` 语法，TDengine 会在子表不存在时自动创建。同时在 `_BufferedRow` 和 row dict 中补充了 `device_code` 字段（作为 TAG 值）。

---

## 问题三：`asc` 是 TDengine 保留关键字

**影响**：超级表名 `asc` 在 SQL 中使用时若未加反引号会报语法错误，长期存在隐患。

**决策**：将三张超级表统一重命名，同时加 `sd` 前缀以降低与关键字冲突的风险：

| 旧名 | 新名 |
|------|------|
| `qc` | `sdqc` |
| `asc` | `sdasc` |
| `agv` | `sdagv` |

**迁移方式**：历史子表数据不保留（测试数据），直接 DROP 旧超级表，CREATE 新超级表，writer 通过 USING 语法按需自动重建子表。

**迁移脚本**：`scripts/migrate_tdengine_rename.py`

---

## 问题四：`catalog.py` 生成的 `td_column_name` 格式错误

**文件**：`backend/app/services/catalog.py`

**原因**：`_allocate_point_slot_for_update` 生成的列名为 `v{index:04d}`（如 `v0001`），不符合实际命名规则。

**命名规则**：
- qc 类设备 → `qc1`, `qc2`, ...
- asc 类设备 → `asc1`, `asc2`, ...
- agv 类设备 → `agv1`, `agv2`, ...

**修复**：
1. `create_point` 中的 `device_row` 查询增加 `LEFT JOIN device_type` 获取 `type_code`。
2. `_allocate_point_slot_for_update` 新增 `type_code: str = ""` 参数。
3. `td_column_name` 生成逻辑改为：
   ```python
   f"{type_code}{next_column_index}" if type_code else f"v{next_column_index:04d}"
   ```

---

## 问题五：TDengine 超级表缺列导致新增点位写入失败

**文件**：`writer/tdengine_writer.py`、`writer/config/settings.toml`

**原因**：MySQL 新增点位后，TDengine 超级表缺少对应列，writer INSERT 时报列不存在错误。原 writer 没有任何 DDL 管理能力。

**限制发现**：TDengine 不允许创建仅含 `ts TIMESTAMP` 的超级表（无数据列时报 `Illegal number of columns`），因此不能在启动时预建空表。

**修复**：在 `TDengineWriter` 内新增动态 Schema 管理能力，分三层：

**层一：启动时（`connect()` 后）**
- `_ensure_database()`：`CREATE DATABASE IF NOT EXISTS device_data`
- `_preload_stables()`：对 `settings.toml` 中 `stable_names` 列表逐一执行 `DESCRIBE`，将现有列加载进内存缓存 `_col_cache: dict[stable, set[col]]`

**层二：写入前（`_write_table_rows()` 开头）**
- `_ensure_stable()`：stable 不在缓存时，用第一个真实业务列创建超级表（`ts TIMESTAMP, first_col DOUBLE`），再 DESCRIBE 填充缓存
- `_ensure_columns()`：diff 出当前 batch 中缺失的列，逐列执行 `ALTER STABLE ADD COLUMN <col> DOUBLE`

**层三：ALTER 容错**
- ALTER 成功 → 更新缓存
- ALTER 失败且错误含 `already exist` / `duplicated` → DESCRIBE 刷新缓存，非 fatal
- 其他 ALTER 失败 → log error，写入继续（INSERT 失败后走 consumer retry 流程）

**列类型决策**：新增列统一 `DOUBLE`，与现场 live schema（全 DOUBLE）和 writer `float(raw)` 序列化保持一致。`var_type` 精细映射留后续优化。

**settings.toml 新增**：
```toml
[writer]
stable_names = ["sdqc", "sdasc", "sdagv"]
```

**已验证**：
- TDengine 连接成功
- 启动缓存预热：`{'sdqc': 1000, 'sdasc': 1000, 'sdagv': 1000}`
- 对已有列执行 `_ensure_columns` 无 DDL 变更（diff 正确）

**已知限制**：
- 首次写入某 stable 大量新列时（如 1000 列），ALTER 串行执行约 10-30 秒，期间 `_lock` 被持有，其他设备写入阻塞。属于一次性开销，日常新增 1-2 列不受影响。

**后续小修（代码审查后）**：
- `connect()` 失败分支先 `close()` 已创建的连接再置空，避免启动失败时连接泄漏
- 删除未使用的 `table_exists()` 死代码
- "DESCRIBE 返回空集不写缓存"行为**保持不变**：TDengine 不允许只含 `ts + TAG` 的超级表，空集不缓存才能让首次真实写入时用第一列触发 `CREATE STABLE`，是正确行为
