# 采集模块审查与改造计划

> 状态：方案已实施并归档
> 更新日期：2026-08-12
> 范围：采集链路只读安全、稳定性与性能、GE SRTP 专项优化、内置/外置驱动统一插件化

---

## 1. 结论摘要

本轮审查形成以下结论：

1. 当前生产采集主链路没有调用 PLC 写入接口，S7、GE SRTP、OPC UA、OPC DA 和 Modbus TCP 驱动的 `write()` 也会拒绝写入；但基础接口、驱动清单和部分底层协议库仍保留写能力表达，因此还不能把“所有可安装代码绝对无法写 PLC”作为系统级安全保证。
2. 采集性能下降并非单一原因。已确认的重点包括：GE Block 串行读取、异常被过度吞并、线程池背压信号丢失、超时后的连接可能继续复用、相同设备不同扫描周期的任务不能合并，以及读、解析、Redis 写入共用同设备 in-flight 生命周期。
3. 当前 GE SRTP 单个 Block 最大为 250 bytes。现场单次请求往返约 33ms 时，12 个串行 Block 的理论耗时约为 `12 × 33ms ≈ 396ms`，与观测到的约 400ms 基本吻合。
4. GE 响应长度目前只解析了低 8 位。250 bytes 未触发问题，是因为响应长度未超过 255；若直接放大到 500～1024 bytes，可能出现截断、报文错位或后续请求解析失败。**16 位 payload 长度与异常断连属于必须完成的协议正确性修复。**
5. 1024 bytes 是基于工业驱动资料和 GE 文档得到的候选上限，不应未经实机验证直接作为所有设备的默认值。建议先保持 250 bytes，再按 `500 → 1000 → 1024` 分档验证。
6. 驱动插件化建议采用统一注册表管理两类来源：安装包自带的 `bundled` 驱动，以及运行时安装的 `installed` 驱动。原有驱动仍随安装包提供，但在同一“驱动管理”入口中展示和管理；Modbus TCP 作为第一个由外置样板转为内置随包分发的驱动。

## 2. 目标与边界

### 2.1 目标

- 证明并强化生产采集路径只读，避免配置、接口或 UI 对能力产生误导。
- 修复会造成采集失步、错误重连、吞吐下降或状态误判的真实问题。
- 在不牺牲稳定性的前提下降低 GE SRTP 的请求次数和批次延时。
- 统一内置与外置驱动的发现、状态、能力和版本管理方式。
- 保留安装包开箱即用，不要求用户额外安装现有驱动。

### 2.2 非目标

- 不在采集服务中增加 PLC 控制或写点功能。
- 不一次性重构整个 collector。
- 不在未完成实机兼容性测试前把 GE 最大 payload 强制改为 1024 bytes。
- 不同时实施多个高风险改动；严格遵循“一次修复一个最小问题、单独测试、可单独回退”。

## 3. 已确认问题与根因

### 3.1 只读边界

当前生产路径是只读的：调度器只调用驱动 `read()`，现有内置驱动以及 Modbus TCP 样板驱动的 `write()` 均拒绝执行。

仍需处理的边界问题：

- `BaseDriver` 仍定义通用 `write()` 抽象接口和写点数据结构。
- 驱动清单允许声明 `write` / `读写`，Agent 校验逻辑也接受这类能力。
- Backend 协议目录对部分实际只读驱动显示为“读写”，与运行时行为不一致。
- GE、Modbus 等底层库中存在写命令常量或第三方写函数；虽然生产主链路没有调用，但静态存在不等于不可触达。
- 外置 Python 驱动运行在 collector 进程内，可以自行创建 Socket；仅依靠 manifest 无法形成硬安全边界。

因此只读保证需要分为两层：

1. **应用层保证**：生产接口、驱动能力声明、Backend 展示和安装校验统一为只读。
2. **基础设施硬边界**：对 PLC 账号、网络 ACL、交换机/防火墙或独立读代理进行限制。对于不受信任的第三方 Python 插件，只有进程隔离或网络策略才能形成真正的强边界。

### 3.2 通用稳定性与性能问题

| 问题 | 根因 | 可能影响 | 优先级 |
|------|------|----------|--------|
| GE 线程池背压被吞掉 | GE 驱动使用宽泛的 `except Exception`，把 `ExecutorSaturatedError` 当普通读失败处理 | 上层无法正确降载，出现空结果、重连或持续过载 | P0 |
| 超时后的连接继续复用 | 半包/超时/序列错误后连接仍可能保持 `connected` | 遗留字节污染下一响应，形成级联报文错误 | P0 |
| 部分 Block 失败仍显示在线 | 只有所有 Block 失败才进入设备错误处理 | 局部点位长期无值但设备仍为 ONLINE | P1 |
| 超时不是严格的墙钟上限 | 执行器会等待底层 I/O 结束并回收任务 | 配置的读取超时不能限制整批实际耗时 | P1 |
| 同设备任务重复和碰撞 | 点位按精确扫描周期分别规划，同一时刻到期也分别执行 | 重复读取相同或相邻 Block，增加 PLC 往返 | P1 |
| in-flight 覆盖链路过长 | 设备占用状态覆盖读取、解析和 Redis 写入 | Redis 变慢也可能导致下一采集周期被跳过 | P2 |

### 3.3 GE SRTP 当前瓶颈

当前 GE 驱动对规划后的 Block 逐个串行发送请求。单次请求的固定往返延时远大于多传输几百字节的时间，因此请求次数是主要变量：

```text
整批 GE 读取耗时 ≈ Block 数 × 单次 SRTP RTT + 少量解析开销
```

以现场约 33ms RTT 为例：

| 串行 Block 数 | 理论通信耗时 |
|---------------:|-------------:|
| 12 | 约 396ms |
| 6 | 约 198ms |
| 3 | 约 99ms |

但 Block 数不能简单按“全部点位总字节数 ÷ 最大 payload”计算。以下边界仍会导致拆包：

- `%R`、`%AI`、`%AQ`、`%I`、`%Q` 等不同存储区需要分别请求。
- 不同扫描周期目前生成不同任务。
- 同一存储区的地址跨度超过最大 payload 时必须拆分。
- 点位过于离散时，是否读取中间空洞取决于合并阈值和 PLC 负载权衡。
- 不同 PLC 型号、固件和以太网模块可能具有不同的实际可接受长度。

## 4. 两个 GE 开源项目调研结论

### 4.1 `TheMadHatt3r/ge-ethernet-SRTP`

项目地址：[TheMadHatt3r/ge-ethernet-SRTP](https://github.com/TheMadHatt3r/ge-ethernet-SRTP)

该项目适合作为协议考古资料，不适合直接替换当前实现：

- 主要是面向 GE 90-30 / 90-70 的概念验证代码。
- 初始化、序列号、邮箱等处理较固定。
- 一次 `send()` 后直接 `recv(1024)`，没有严格处理 TCP 半包和完整帧边界。
- 主分支未实现写入；其写入相关 PR 不应引入本项目。
- 多寄存器读取 PR 的返回值解码方式也不适合作为生产实现。

### 4.2 `jobeastwood/gesrtp-py`

项目地址：[jobeastwood/gesrtp-py](https://github.com/jobeastwood/gesrtp-py)

这是当前项目内嵌 GE 协议库的主要来源。相比前者，它提供了：

- 多种 GE 内存区读取。
- 可配置槽位邮箱。
- 请求序列号递增和响应序列校验。
- 对 RX3i 等设备更完整的报文结构处理。
- 面向读取的公开 API。

当前项目已经在上游基础上补充过：

- `TCP_NODELAY`。
- TCP 半包的 `recv_exact` 读取。
- 避免无条件构造大段十六进制日志。
- 更准确的 NACK 状态字节解析。

因此不建议整体替换或覆盖本地协议库。应保留现有补丁，只针对已确认问题继续做最小修复。

### 4.3 可借鉴但需要验证的结论

- 工业驱动 D2000 的 GE SRTP 配置允许 1～1024 bytes 的 Maximum Payload，并按连续地址合并请求。
- PACSystems 以太网手册中部分读通道命令支持最多 1024 bytes / 512 words。
- 这些资料说明 1024 bytes 是合理的测试目标，但不能直接证明当前逆向实现的 HMI 内存读取请求在所有 PLC 上都支持同一上限。
- 其他开源实现也普遍采用“按存储区读取连续范围”，而不是逐个寄存器请求；不同存储区通常仍需分别读取。

参考资料：

- [D2000 General Electric SRTP protocol](https://d2.doc.ipesoft.com/wiki/spaces/D2DOCV25EN/pages/26348029/General+Electric+SRTP+protocol)
- [PACSystems RX7i/RX3i Ethernet Communications Manual, GFK-2224M](https://www.astor.com.pl/wsparcie/dokumentacja-techniczna/pobierz/GE/Kontrolery%20PAC/PACSystems%20RX7i/Podr%C4%99czniki/GFK2224M-PACS-Ethernet-Manual.pdf)
- [Leveraging the SRTP Protocol for Over-the-Network Memory Acquisition](https://dfrws.org/wp-content/uploads/2019/06/paper_leveraging_the_srtp_protocol_for_over-the-network_memory_acquisition_of_a_ge_fanuc_series_90-30.pdf)
- [uGESRTP](https://github.com/kkuba91/uGESRTP)

## 5. GE SRTP 必须实施项与实验项

### 5.1 必须实施：协议正确性和故障恢复

以下工作即使最终继续使用 250 bytes，也必须完成：

1. **修复线程池背压传播**
   `ExecutorSaturatedError` 必须原样交给上层处理，不能转换为普通 Block 失败。

2. **传输或协议致命错误后使连接失效**
   收包超时、半包、连接关闭、序列号不匹配、非法帧等错误发生后，应关闭 Socket、标记断开，并终止本批剩余 Block。不能在字节流边界已经不可信时继续复用连接。

3. **按 16 位解析响应 payload 长度**
   当前逻辑只读取 `header[4]`，应按小端长度读取：

   ```text
   payload_length = header[4] + header[5] × 256
   ```

   修改后仍先保留 250 bytes 默认上限，用测试验证兼容性。

4. **降低正常 Block 日志开销**
   单次读取的高频 INFO 日志降为 DEBUG；批次总结、异常和慢请求保留合适级别。

5. **补充可观测性**
   增加计划 Block 数、各存储区 Block 数、请求字节数、单 Block RTT、批次总耗时、NACK/超时/协议错误/线程池饱和分类指标。

### 5.2 建议实施：可配置大 Block

新增 GE 专用配置，例如：

```text
ge_max_payload_bytes = 250
```

约束建议：

- 可配置范围：8～1024 bytes。
- 默认值第一阶段保持 250 bytes。
- 字寄存器最大数量由 `max_payload_bytes // 2` 推导，不再固定为 125 words。
- 配置值必须进入运行日志和性能快照，方便定位现场差异。
- 发现 NACK、超时率升高或长度不兼容时，可只回退该设备配置，无需回退整个版本。

### 5.3 现场递进验证

在同一台 PLC、同一组点位和相同网络条件下依次测试：

```text
250 → 500 → 1000 → 1024 bytes
```

每档至少记录：

- 规划 Block 总数及每个存储区的 Block 数。
- 单次 RTT 的 P50 / P95 / 最大值。
- 整批采集耗时的 P50 / P95 / 最大值。
- 超时、NACK、重连、序列错误和数据长度错误次数。
- PLC CPU/通信负载和其他上位机连接是否受影响。
- 结果值与 250 bytes 基线是否逐点一致。

可能结果：

- 如果当前 12 个 Block 主要由 250-byte 上限造成，放大后可能降为 3～6 个请求，通信时间有机会降到约 100～200ms。
- 如果 Block 主要由多个存储区、扫描周期或离散地址造成，放大 payload 的收益会有限，但协议修复仍然必要。

### 5.4 后续性能手段

仅在完成前述正确性修复和实测后评估：

1. **同设备到期任务合并**：同一调度时刻到期的多个扫描周期任务先合并读取，再按各自周期分发结果，减少重复 Block。
2. **优化跨空洞合并阈值**：以“多读取少量无用字节”换取减少一次固定 RTT，并对不同内存区分别设置规则。
3. **可选双连接读取**：增加 `ge_parallel_channels`，默认 1，试验上限先设为 2；每个通道必须使用独立连接和序列空间。需评估 PLC 最大客户端数、CPU 负载和数据快照时间偏差，不作为首选方案。
4. **整批 deadline 与局部质量码**：整批超限时结束本轮，并将失败 Block 对应点位标记为明确的 Bad/Timeout，而不是静默缺值。

## 6. 驱动插件化目标方案

### 6.1 统一注册表

collector 只通过一个驱动注册表解析协议，不再由各层分别维护内置协议常量和硬编码工厂。

注册表同时扫描两个来源：

```text
驱动注册表
├─ bundled   安装包默认自带、受保护、随产品升级
│  ├─ s7
│  ├─ ge_srtp
│  ├─ opcua
│  ├─ opcda_center
│  └─ modbus_tcp
└─ installed 用户安装、可升级/卸载
   └─ <第三方驱动包>
```

统一返回至少包含：

- `id`、`protocol`、别名和版本。
- `source = bundled | installed`。
- `protected = true | false`。
- `capabilities`、`read_write`、加载状态和错误信息。
- 工厂入口、规划器入口和解析入口。

冲突规则：

- `bundled` 驱动默认受保护，不能在 UI 中卸载。
- 外置包不能覆盖受保护协议及其别名。
- 是否允许官方更新包覆盖 bundled 驱动，应通过签名和独立升级机制实现，不通过普通第三方安装入口实现。

### 6.2 Modbus TCP 内置化

现有 `packages/modbus_tcp` 保留驱动包结构，但构建安装包时作为 bundled 驱动一起分发：

- 用户安装产品后即可直接使用 Modbus TCP。
- 驱动管理页面能查看它的版本、能力和状态。
- 它与外置驱动使用同一份 manifest 和加载契约。
- 产品卸载时随产品移除；普通“卸载驱动”操作不可删除它。

### 6.3 分阶段迁移

1. 先让统一注册表支持 `bundled` / `installed` 两个来源，不搬动现有驱动代码。
2. 把 Modbus TCP 作为第一个 bundled 包接入，验证构建、安装、发现和管理闭环。
3. 用薄适配器把 S7、GE SRTP、OPC UA、OPC DA 注册到同一注册表，保持原导入路径和运行行为。
4. 再逐个迁移协议专属规划/解析钩子，消除 `Device`、`TaskExecutor` 和 Backend 中的协议硬编码。
5. 每迁移一个驱动单独回归；不得一次性移动全部驱动。

## 7. 分阶段实施计划

每个阶段只处理一个最小问题，通过验收后再进入下一阶段。

| 阶段 | 改动主题 | 主要范围 | 验收方式 |
|------|----------|----------|----------|
| 1 | GE 背压传播 | `ge_srtp_driver.py` 及对应测试 | 线程池饱和异常能到达 TaskExecutor，不被转换为空结果 |
| 2 | GE 异常连接失效 | GE connection/driver 及测试 | 模拟半包、超时、序列错误后 Socket 被关闭，本批停止，下一轮重新连接 |
| 3 | 16 位 payload 长度 | GE connection/packet 测试 | 256、500、1000、1024 bytes 的分段响应可完整读取；默认仍为 250 |
| 4 | GE 指标与基准 | GE 驱动、性能指标/基准工具 | 能输出 Block 规划、RTT、批次耗时和分类错误，建立 250-byte 基线 |
| 5 | 可配置最大 payload | GE 配置、规划器、驱动及测试 | 默认 250 行为不变；非法值拒绝；分档实机验证并可单设备回退 |
| 6 | 同设备到期任务合并 | 调度/任务规划及测试 | 同一时刻的重叠 Block 只读取一次，不改变各周期点位输出语义 |
| 7 | 可选双连接实验 | GE 驱动及配置 | 默认关闭；启用时连接、序列号完全隔离，现场验证无 PLC 负载异常 |
| 8 | 批次 deadline 与局部质量 | TaskExecutor/质量码测试 | 部分失败不再静默，失败点位有明确质量，成功点位仍可输出 |
| 9 | 强化只读契约 | BaseDriver、manifest、Agent、Backend 目录与测试 | 所有生产驱动统一显示只读；安装包拒绝写能力；无生产写调用 |
| 10 | 统一驱动注册表 | collector/agent/backend 注册与发现逻辑 | bundled/installed 使用同一查询结果，协议别名只维护一处 |
| 11 | Modbus TCP bundled | 构建、安装包、驱动注册与验收 | 全新安装可直接使用、可查看版本状态、不可普通卸载 |
| 12 | 现有驱动逐个插件化 | S7 → GE → OPC UA → OPC DA | 每次只迁移一个驱动，行为、性能和安装包默认可用性不变 |

### 7.1 第一阶段拟修改范围

第一阶段只实施“GE 背压传播”：

- `collector/drivers/ge_srtp_driver.py`：对 `ExecutorSaturatedError` 单独放行，其他 Block 读取错误继续按现有策略处理。
- 现有 GE 驱动测试文件：新增一个回归用例，证明饱和异常不会被宽泛异常捕获。

第一阶段不修改协议长度、Block 上限、连接逻辑、调度器或插件系统。

## 8. 验收标准

### 8.1 只读安全

- 生产代码中不存在对驱动 `write()` 的调用路径。
- 所有 bundled 驱动 manifest 均声明 `read` / `只读`，不声明 `write`。
- Backend、Agent、collector 对同一驱动显示相同能力。
- 第三方包声明写能力时安装失败，并给出明确错误。
- 部署文档明确说明：不受信任 Python 插件需要进程/网络隔离，manifest 不是安全沙箱。

### 8.2 GE 正确性

- TCP 响应无论分成多少次到达，都能按完整长度收取。
- 超过 255 bytes 的响应长度解析正确。
- 超时、半包、序列错误之后不复用失步连接。
- 对同一组点位，扩大 payload 前后的值、字节序和质量码逐点一致。

### 8.3 GE 性能

- 测试报告必须同时给出 Block 数和批次 P50/P95，不只给单次最佳值。
- payload 增大后请求数应符合规划结果；若请求数未下降，应能从存储区、扫描周期或地址离散度解释原因。
- 不以固定“必须低于 100ms”作为所有现场的统一标准；以相同点位、相同网络下相对 250-byte 基线的改善及稳定性为准。
- 任一档位出现错误率、PLC 负载或其他客户端影响明显上升时，回退到上一稳定档位。

### 8.4 插件化

- 安装包默认携带 S7、GE SRTP、OPC UA、OPC DA、Modbus TCP。
- bundled 与 installed 驱动在同一管理页面可查看状态、版本和能力。
- bundled 驱动受保护，普通用户不能卸载或被第三方覆盖。
- 外置驱动的安装、升级、禁用、卸载流程保持可用。
- 单个驱动加载失败不影响其他驱动和 collector 主进程启动。

## 9. 风险与回退

| 风险 | 控制措施 | 回退方式 |
|------|----------|----------|
| PLC 不支持大 payload | 分档实机测试，默认保持 250 | 单设备配置恢复 250 |
| 大块读取提高 PLC 负载 | 监控 PLC CPU、通信状态和其他客户端 | 降低 payload 或调整空洞合并阈值 |
| 双连接超过 PLC 连接能力 | 默认关闭，仅少量设备试点 | 恢复单连接 |
| 异常分类变化导致重连增多 | 用故障注入测试区分 NACK 与字节流失步 | 单独回退异常断连阶段 |
| 插件迁移影响安装包 | 先注册适配、不搬源码，Modbus 单驱动试点 | 保留原硬编码工厂作为阶段性回退 |
| 第三方插件绕过只读声明 | 只加载可信/签名包并配合网络 ACL | 禁用外置插件或使用隔离进程 |

## 10. 推荐执行顺序

近期优先完成阶段 1～5：先消除 GE 正确性和故障恢复风险，再通过指标与实机数据决定 1024 bytes 是否成为某些设备的推荐配置。

### 11.2 新增 GE 配置

- ge_max_payload_bytes：允许 250～1024，默认 250；支持全局值和单设备覆盖。
- ge_parallel_channels：只允许 1 或 2，默认 1。
- ge_batch_deadline_ms：可选正整数；未配置时不启用批次截止时间。
- 对应环境变量：DATAWATCH_GE_MAX_PAYLOAD_BYTES、DATAWATCH_GE_PARALLEL_CHANNELS、DATAWATCH_GE_BATCH_DEADLINE_MS。

1024 bytes 是软件允许的实验上限，不代表所有 GE PLC 型号、固件和网络环境都支持。上线时仍按 250 → 500 → 768 → 1024 分档验证。

### 11.3 插件与安装包装配

- 开发环境：内置 Modbus TCP 从 packages/modbus_tcp 加载。
- PyInstaller 环境：该目录打包到 _internal/bundled_drivers/modbus_tcp，运行时从 sys._MEIPASS 定位。
- Inno Setup 的各安装角色继续递归携带同一 collector onedir，因此无需复制第二份 Modbus 源码。
- 外置插件仍安装到 DATAWATCH_DATA_ROOT/drivers，由同一注册表发现；内置别名和协议名保留，外置包不得覆盖。
- 内置驱动在管理 API 和桌面端返回 source=bundled、protected=true、readWriteType=只读。

### 11.4 只读验收结果

生产驱动目录和 Modbus TCP 包的写入/删除 API 静态扫描仅命中 BaseDriver.write。该方法固定抛出只读错误；S7、GE SRTP、OPC UA、OPC DA Center 和 Modbus TCP 均未实现 PLC 写入覆盖。驱动清单、Agent ZIP 校验、collector 注册表和中心注册流程也都拒绝 write capability 或非“只读”声明。

网络侧仍建议使用 PLC 账户权限、只读通信账户（协议支持时）和 ACL 作为第二道边界；代码只读不能替代网络与设备权限控制。

### 11.6 现场验收清单

1. 使用正式 cp314t 构建安装包，确认 _internal/bundled_drivers/modbus_tcp/driver.toml、代码和 vendor 目录存在。
2. 对每类 PLC 做只读抓包，确认只出现读请求、握手、心跳和断连，不出现写功能码。
3. GE 先保持单连接和 250 bytes，记录请求数、块数、P50/P95/P99、超时和重连。
4. 逐档提高 payload；每档同时观察 PLC CPU、其他客户端、错误率和采集周期。
5. 单连接仍不能满足周期时，再对少量设备启用双连接；确认 PLC 连接资源允许并验证自动降级。
6. 最后按业务周期设置批次截止时间，验证部分坏质量不会污染历史值。
7. 比较改造前后相同点表、相同扫描周期和相同网络条件下的数据，再决定设备级推荐配置。
