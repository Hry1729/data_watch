# 安全边界

本文档明确 Data Watch 的安全信任边界和已知限制。

---

## 外置驱动安全边界

### **信任边界**

外置驱动安装机制假设：

1. **文件系统信任**：`DATAWATCH_DATA_ROOT` 目录（默认 `C:\ProgramData\DataWatch`）只有 **Agent 服务账户** 和 **管理员** 可写。
2. **本地权限信任**：本地管理员可以上传和安装驱动 ZIP 包。
3. **ZIP 包校验**：安装器会校验 ZIP 结构、路径穿越、符号链接、文件数量和总大小。
4. **驱动包签名（可选签名，签名即强制校验）**：
   - 包内**没有** `signature.json` ⇒ 接受安装，但记录为**未获批准来源**（`signature_verified=False`）。
   - 包内**有** `signature.json` ⇒ **必须**通过 Ed25519 校验，否则**拒绝安装**（HTTP 409）。校验项：算法必须为 `ed25519`；`driver.toml` 必须声明发布者；发布者公钥必须来自驱动目录 `catalog.json` 的 `trusted_publishers`，且 `key_id` 与公钥 sha256 前 16 位一致；签名清单覆盖的文件摘要必须与包内容逐项一致；签名本身必须有效。
   - **目录不可读按失败处理**：读不到 `catalog.json` 时 `trusted_publishers` 取不到，带签名的包会被拒；不会因为读不到目录而放宽。
   - 实现位置：`data_watch_driver_signatures.verify_package_signature()`；调用点 `agent/app/services/driver_zip.py`（签名校验失败 → `DriverZipError(status_code=409)`）。
5. **三种"签名"互不相同，不要混用**：
   - **驱动包签名**：上一条的 Ed25519，针对**包内容**，表达"来源可信 + 内容完整"。
   - **上传请求签名**：Uploader ↔ Ingest 之间的请求签名，与驱动包无关。
   - **Windows EXE 代码签名（Authenticode）**：本机制**不**验证也不依赖它；可执行文件是否带 Authenticode 签名不由本流程保证。

### **已知限制**

#### **TOCTOU 窗口（Time-Of-Check to Time-Of-Use）**

**问题描述**：
- Agent 在解压 ZIP 文件时，会先检查目标路径是否包含符号链接。
- 检查通过后，打开文件写入数据。
- 在"检查"和"打开文件"之间存在短暂的时间窗口（通常 < 1ms）。
- 理论上，拥有 `DATAWATCH_DATA_ROOT/drivers/` 写权限的本地攻击者可能在这个窗口内将文件替换为符号链接，从而将数据写入到攻击者控制的目标位置。

**风险评估**：
- **攻击前提**：攻击者必须已经获得本地 `DATAWATCH_DATA_ROOT/drivers/` 目录的写权限。
- **实际影响**：在上述 ACL 信任前提成立时，风险处于可接受范围；但重解析点仍可能借用 Agent 服务权限把写入引向数据根目录之外，不能视为完全没有额外攻击面。

**缓解措施**：
1. **权限配置**（推荐）：
   - 确保 `C:\ProgramData\DataWatch` 及其子目录只有 **Agent 服务账户** 和 **管理员组** 有写权限。
   - 移除其他用户的写权限。

   ```powershell
   # 检查权限
   Get-Acl "C:\ProgramData\DataWatch" | Format-List

   # 如果需要修复权限
   icacls "C:\ProgramData\DataWatch" /inheritance:r
   icacls "C:\ProgramData\DataWatch" /grant:r "BUILTIN\Administrators:(OI)(CI)F"
   icacls "C:\ProgramData\DataWatch" /grant:r "NT AUTHORITY\SYSTEM:(OI)(CI)F"
   ```

2. **定期审计**：
   - 监控 `DATAWATCH_DATA_ROOT/drivers/` 目录的文件修改事件。
   - 记录所有驱动安装/卸载操作的审计日志（已实现）。

**为什么不修复**：
- 彻底修复需要使用 Windows 底层 API（CreateFile + FILE_FLAG_OPEN_REPARSE_POINT）或 `O_NOFOLLOW` 标志。
- 当前的权限配置已经能够有效缓解风险（攻击者需要先获得本地管理员权限）。
- 修复成本（重写文件 I/O 逻辑 + 测试覆盖）与实际风险不匹配。
- 第一期聚焦核心功能，该限制列入已知限制清单，在后续版本中根据实际需求评估是否修复。

## 审计日志

### **Best-Effort 机制**

操作审计日志采用 **best-effort** 机制：

- 审计日志写入失败**不会影响业务操作的成功**。
- 例如：卸载驱动成功，但审计日志因数据库连接失败而未写入，App 仍然显示"卸载成功"。
- 审计失败会记录到应用日志（Backend 日志），但不会向用户报错。

**原因**：
- 审计是辅助功能，不应阻断核心业务。
- 如果审计失败导致业务失败，可能造成用户困惑（例如驱动已删除但显示"删除失败"）。

**缓解措施**：
- 定期检查 Backend 日志中的审计失败警告。
- 确保 MySQL 连接稳定，减少审计失败概率。
