# 全流程性能诊断

用于“没有报错，但采集或入库越来越慢”的现场问题。中心式路径为 PLC → Collector 读取/解析 → Redis Stream → Writer 解析/构建 SQL → TDengine → Redis 确认。

脚本观察真实运行负载，不造测试数据，不领取或确认消息，不清理 Redis，不改配置，也不重启进程。只在所选输出目录写诊断文件。目标机需要 Windows PowerShell 5.1 或 PowerShell 7、可用的 Docker 命令和正在运行的 Backend 容器；无需另装 Python。使用当前部署的数据库凭据，凭据只在容器内使用。

## 在中心机上运行

将 `diagnose_pipeline.ps1` 和 `pipeline_diagnostics.py` 放在同一文件夹。在真实积压增长、Collector 与 Writer 都运行时，打开 PowerShell，进入该文件夹执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\diagnose_pipeline.ps1
```

默认观察 180 秒，约每 10 秒采样。Collector 每 60 秒、Writer 每 30 秒输出内部性能快照，3 分钟通常能拿到足够的增量记录。采样命令有超时限制，实际间隔可能长于 10 秒；速率按真实采样时间计算。显示“Captured sample”说明仍在工作。

默认查找以下运行日志目录：

- `C:\ProgramData\DataWatch\runtime\logs`（中心式）；
- `C:\ProgramData\DataWatch Distributed Center\runtime\logs`（分布式中心）；
- `C:\ProgramData\DataWatch Edge\runtime\logs`（边缘）。

同机安装多个角色，或自定义了运行目录时，显式指定 **runtime 目录**：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\diagnose_pipeline.ps1 -RuntimeRoot "C:\ProgramData\DataWatch\runtime" -DurationSeconds 300 -OutputRoot "D:\DataWatch诊断"
```

容器使用其他名称时：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\diagnose_pipeline.ps1 -BackendContainer "实际Backend容器名" -RedisContainer "实际Redis容器名" -TdengineContainer "实际TDengine容器名"
```

Redis 数据库、地址和密码来自 Backend 容器的环境变量。Writer 组名默认使用 `WRITER_REDIS_GROUP_NAME`，未设置时为 `writer_cg`；实际组名不同时用 `-RedisConsumerGroup "实际组名"`。必须确认 Backend 与 Collector/Writer 连接同一个 Redis 数据库，脚本不会替你变更连接配置。Redis/TDengine 使用外部实例时，实际连接仍会被探测；相应 Docker 容器负载会显示不可用。

脚本不需要管理员权限；如果进程 CPU 或日志访问被拒绝，报告会保留缺失项，可用管理员 PowerShell 补跑。不要为了诊断关闭业务或删除积压。

## 结果在哪里

运行结束后显示输出目录，默认位于脚本旁的 `pipeline-diagnostics\时间戳-随机后缀`。

- `report.md`：先看这个中文报告，包含候选慢环节、同口径帧速度、积压净变化、各阶段增量耗时、CPU/内存/磁盘负载、失败原因抽样及证据缺口；
- `summary.json`：结构化分析，包括每个流、每个进程的具体数值；
- `samples.jsonl`：逐次采样，便于进一步核对趋势。

把整个输出目录打包用于进一步分析。报告保留进程名、日志路径、Stream 名和少量失败记录 ID；不导出容器环境、认证信息、原始点位值、SQL 内容或完整日志。日志尾部最多读取 4 MB，只保留性能指标和警告类别；每个 DLQ 最多抽样最近 3 条，仅输出错误类别、错误代码和记录 ID。警告计数是有限尾部样本，不是完整审计总数。

退出码 0 表示报告生成成功，**不表示性能合格**；退出码 2 表示分析程序不可用，已采样内容仍在 `samples.jsonl` 中。Docker 或 Backend 不可用时，脚本会先给出启动失败原因。

## 怎么判断

| 报告现象 | 优先排查 |
| --- | --- |
| PLC 读取耗时高、采集任务迟到/跳周期增加 | PLC、协议驱动、网络、设备扫描周期 |
| 采集存储阶段慢，但 Redis 命令通信并不慢 | Collector 线程排队、同设备并发、存储路径 |
| Redis 命令通信慢，同时 Redis CPU 或延迟 fsync 增长 | Redis 请求量、磁盘、容器资源及网络 |
| 进入 Stream 比 Writer 新领取更快，未领取 + 未确认持续增长 | Writer 吞吐缺口，继续看其内部阶段 |
| SQL 构建或构建线程排队用时高 | Writer 编码/拼接、线程资源、每批大小 |
| TDengine 执行写入用时高 | TDengine、磁盘、SQL 次数/大小、连接和服务日志 |
| Redis 确认/删除用时高 | ACK/XDEL 请求量、Redis 或网络 |
| 新增重试或 DLQ 净增长 | 先定位失败原因；扩大缓存不能修复坏数据或连接错误 |

每行同时列出操作次数、平均耗时、累计用时。不同阶段的操作粒度不同，且可能并行，不能只比较单次平均值，或把所有累计耗时相加当成整个流程耗时。耗时来自累计直方图的增量，平均值有少量舍入误差；重启导致计数下降时跳过该区间，不伪造速率。

`进入 Redis` 和 `Writer 新领取` 都以 Stream 帧计数；一次采样可能包含多个点位，不能与点位/秒混算。新领取不包含 PEL 重试，不等于成功入库。`committed_value_rows` 是 Writer 确认完整入库的帧，来自内部快照；老版本缺失时明确无法判断。

Redis 的 PING 从 Backend 容器发起，只代表这条连接的延迟。TDengine 只读探测执行 `SELECT SERVER_VERSION()`，只能说明连接/简单查询是否慢。`td_execute_ms` 是客户端观察到的整段调用耗时，包含线程等待和事件循环恢复，不能当作服务端纯执行时间。新版报告另外列出排队、同步调用、恢复及线程 CPU 时间。健康接口正常并不能证明性能正常。

新版 Writer 的 `stages_ms`、`executor_ms` 按各 Worker 的累计计数分别求窗口增量，再汇总。循环直属的回收 own 阶段扣除内部刷新；outer 阶段仅作辅助观察。完整调用和超时/取消的未完成调用分开统计，Worker 重启导致的下降区间不作为有效均值。执行器里的 `redis_*` 是 ACK/重试线程内的子命令，不能与外层 `ack` 相加。目标机更新与三组参数对照见 [Writer目标机验证](Writer目标机验证.md)。

## 指标缺失与分布式边界

旧日志、时间无法解析、快照不足或消费组 lag 为未知时，报告显示“无法判断”，不会当作零积压或正常。没有新鲜快照时，确认实际运行版本及日志路径，必要时延长到 300 秒；无需为了增加日志改变采样频率。默认最多分析 64 个 Stream，超过时明确标记部分观测，可用 `-MaxStreams 128` 增大范围。扫描也设有时间/页数上限，避免诊断本身长时间占用 Redis。

分布式中心机只能直接证明 Redis → Writer → TDengine 这一段。脚本会收集本机 Storage/Uploader/Ingest 的警告类别，但这些模块当前没有与中心 Collector/Writer 同样的逐段耗时快照；远端 PLC、边缘落盘和上传耗时仍会列为证据缺口，不能据此宣布“全流程正常”。如需定位跨主机上传问题，还应提供边缘机同一时段的 Collector/Storage/Uploader 日志和本地队列状态。边缘机没有 Backend 容器时，不要在边缘机运行这个入口。
