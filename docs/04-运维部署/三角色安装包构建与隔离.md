# 三角色安装包构建与隔离

> 对应《分布式部署架构方案》v14。本文记录统一代码仓库的角色构建入口、组件边界、Docker 发布边界和并存隔离约束。

## 1. 构建入口

在仓库根目录执行：

```powershell
# 一次生成三个安装包
pwsh -File installer\build.ps1

# 只生成一个角色包
pwsh -File installer\build.ps1 -Role centralized
pwsh -File installer\build.ps1 -Role edge
pwsh -File installer\build.ps1 -Role distributed-center
```

构建入口只生成 Windows 安装包，不调用 Docker，也不读取或复制 `deploy\images`。Backend/Frontend 与数据库容器按《运维部署》第 4、5 节独立发布。

构建产物：

- `DataWatch-Centralized-Setup-0.1.0.exe`
- `DataWatch-Edge-Setup-0.1.0.exe`
- `DataWatch-Distributed-Center-Setup-0.1.0.exe`

构建脚本自动生成 `installer/Output/SHA256SUMS.txt` 与 `release-manifest.json`；清单记录实际安装包哈希、源码提交，以及各角色 App/Agent 二进制哈希。构建要求 Windows 打包输入的受跟踪源码无未提交修改，并在结束时重新检查输入源码和安装包；独立 Docker 现场配置不属于 Windows 包输入。正式交付以本次构建清单为准。

2026-10-15 的工作区修复批次由 `installer/.build/rebuild-working-tree-installers.ps1` 构建。该入口用于保留未提交修改的本机构建，不改变上面正式入口的 clean-tree 要求，也不自动提交 Git。交付时必须连同本批 `release-manifest.json`、`SHA256SUMS.txt` 一起检查：来源应明确为工作区，包含基础提交和构建输入内容哈希，并记录实际打包组件。不得将带未提交修改的产物标记为纯基础提交构建。本次 App 与 Agent 必须重编，Backend 也需同步更新；不运行安装器就不会升级现有 Windows 服务。

## 2. 组件裁剪

| 角色 | Windows 安装包内容 | 外部依赖（不入 EXE） |
|---|---|---|
| centralized | App、Agent、Collector、Writer、OPC DA sidecar | Docker Backend/Frontend；Docker 或外部 MySQL/Redis/TDengine |
| edge | Edge App、Edge Agent、Storage、Edge Collector、Uploader、OPC DA sidecar | 分布式中心统一入口 |
| distributed-center | Center App、Agent、Ingest、Writer | Docker Backend/Frontend；Docker 或外部 MySQL/Redis/TDengine |

Storage、Edge Collector 与 Uploader 使用独立 PyInstaller 入口；edge 包不复制 Writer、Ingest 或中心容器资源。中心式包不复制 Storage/Uploader；分布式中心包不复制 Storage/Collector/Uploader。三个包都不复制 Compose、`backend.env` 或 Docker tar。

## 3. 并存隔离

| 角色 | Agent 端口 | Windows 服务 | ProgramData | 安装目录 |
|---|---:|---|---|---|
| centralized | 7070 | DataWatchCentralizedAgent | `DataWatch` | `DataWatch Centralized` |
| edge | 7071（Agent）/7073（Storage） | DataWatchEdgeAgent | `DataWatch Edge` | `DataWatch Edge` |
| distributed-center | 7072 | DataWatchDistributedCenterAgent | `DataWatch Distributed Center` | `DataWatch Distributed Center` |

三个入口还使用不同 AppId 和 Tauri identifier。升级或卸载只停止本角色服务；共享安装器不按通用进程名结束其他角色进程。

角色由安装器注入的服务环境变量 `DATAWATCH_ROLE` 决定：`installer/DataWatchRole.iss` 注册 NSSM 服务时显式写入 `DATAWATCH_ROLE`、`DATAWATCH_AGENT_PORT`、`DATAWATCH_AGENT_SERVICE_TOKEN` 与双根路径。安装包内容固定不等于角色是不可变边界——`agent/service/install_service.py` 这个通用脚本不注入该变量，缺失时 agent 回退为中心式，只能用于开发辅助，正式部署必须使用三角色安装包。

## 4. 中心访问路径

Docker Frontend/nginx 将 `/api/*` 代理到 Backend，将 `/ingest/*` 代理到宿主机 8010 端口的 Ingest。分布式边缘的 `center_url` 指向该统一入口，例如 `http://center-host:8080`。

Vite 开发服务 5173 目前只代理 `/api`，不能替代 8080 的完整数据入口。现场和端到端测试必须保持 nginx 容器运行；否则 Edge Agent 心跳与 Uploader 会同时显示中心不可达。

中心安装目录不包含 `center\deploy` 或 `center\docker-images`。Docker 发布目录独立配置 `backend.env` 并启动 Compose。Backend 需要调用中心本机 Agent 时，从对应 ProgramData 的 `agent_service_token.txt` 复制 token，并按角色配置宿主机端口 7070 或 7072。

## 5. 当前边界

三个 Windows 包均不包含 Docker 镜像、Compose 或数据库密码。安装器只生成本角色 Agent 服务令牌；Docker Desktop、Backend/Frontend 和 MySQL/Redis/TDengine 由独立部署流程负责。Inno Setup 6 是生成 EXE 的必要构建依赖。

Uploader 上传节拍与安装包构建无关。采集频率继续取点位可配置的 `scan_rate`，不引入固定 200ms 默认值。
