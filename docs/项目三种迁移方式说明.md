# 项目三种迁移方式说明

## 一、总体说明

本文说明项目迁移到其他电脑或现场主机时的三种方式。为避免路径绑定，文档中的路径统一使用占位符：

```text
<项目根目录>        项目所在目录，例如 D:\python\device_alarm\data_watch
<后端Python3.14t>   Python 3.14 free-threading 解释器路径
<采集Python3.14>    普通 Python 3.14 解释器路径
```

本项目主要包含：

```text
data_watch/
├─ frontend     前端模块
├─ backend      后端模块
├─ collector    采集模块
└─ docs         项目文档
```

外部依赖服务主要包括：

```text
MySQL
TDengine
OPC DA / DCOM
Snap7 / S7 PLC
GE SRTP
现场设备网络
```

采集模块涉及 OPC DA、DCOM、PLC 网络通信和现场驱动环境，因此不建议优先容器化。正式部署时，采集模块更适合继续运行在 Windows 主机环境中。

迁移时需要区分三类内容：

```text
程序代码：frontend / backend / collector 源码
运行环境：Node、pnpm、Python、pip 依赖、Docker 镜像
运行数据：MySQL 数据、TDengine 数据、配置文件、日志、上传文件
```

不要把以下目录作为正式迁移内容：

```text
frontend/node_modules/
frontend/dist/
backend/.py314t-site/
backend/.venv-314t/
collector/.venv/
__pycache__/
.pytest_cache/
.mypy_cache/
.ruff_cache/
.coverage
htmlcov/
logs/
.tmp_*
```

这些内容应在目标设备上重新安装或重新生成。

## 二、配置文件迁移原则

不要只笼统迁移一个 `.env`，应按模块确认：

```text
frontend/.env
frontend/.env.development
frontend/.env.production
backend/.env 或由 backend/.env.example 复制生成
collector/config/ 下的采集配置
Docker 部署用 .env（如果后续补充 docker-compose）
```

迁移后必须检查：

```text
MySQL 地址、端口、账号、库名
TDengine 地址、端口、账号、库名
后端 API 地址
前端代理地址
采集模块连接 MySQL / TDengine 的配置
OPC DA / PLC 网络地址
```

## 三、方案一：仅 TDengine 容器化，前端、后端、采集模块本机运行

### 1. 适用场景

适合开发阶段、现场调试阶段和需要快速排查问题的场景。

结构：

```text
Windows 主机
├─ frontend    本机 pnpm dev 启动
├─ backend     本机 Python / uvicorn 启动
├─ collector   本机 .venv / run.bat 启动
└─ Docker
   └─ TDengine
```

### 2. 目标设备需要安装

```text
Docker / Docker Compose
Node.js
pnpm
Python 3.14 free-threading（后端）
Python 3.14（采集模块）
pip
```

### 3. 迁移内容

建议迁移：

```text
frontend/
backend/
collector/
docs/
必要配置文件
MySQL 数据备份
TDengine 数据备份或挂载目录
```

不建议迁移：

```text
frontend/node_modules/
frontend/dist/
backend/.py314t-site/
backend/.venv-314t/
collector/.venv/
__pycache__/
.pytest_cache/
logs/
.tmp_*
```

### 4. 迁移步骤

#### 4.1 迁移数据库

MySQL 和 TDengine 都需要单独备份和恢复。

TDengine 如果使用 Docker volume 或宿主机挂载目录，需要备份对应数据目录。Docker 镜像不等于数据库数据，镜像只包含程序，数据通常在 volume 或挂载目录中。

#### 4.2 迁移前端

```powershell
cd <项目根目录>\frontend

pnpm install
pnpm dev
```

访问：

```text
http://127.0.0.1:3006
```

#### 4.3 迁移后端

推荐在目标设备重新创建后端虚拟环境：

```powershell
cd <项目根目录>\backend

& "<后端Python3.14t>" -m venv .venv-314t
.\.venv-314t\Scripts\python.exe -m pip install -r requirements.txt
.\.venv-314t\Scripts\python.exe -m pip install pytest pytest-asyncio
```

启动后端：

```powershell
cd <项目根目录>\backend

.\.venv-314t\Scripts\python.exe -m uvicorn main:app --host 127.0.0.1 --port 8000 --reload
```

说明：

- 不建议把当前电脑的 `backend/.py314t-site` 直接复制到目标设备。
- 不建议在通用迁移步骤中依赖 `C:\Users\<用户名>\...` 这类用户目录路径。

#### 4.4 迁移采集模块

```powershell
cd <项目根目录>\collector

& "<采集Python3.14>" -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

优先使用脚本启动：

```cmd
cd /d <项目根目录>\collector

run.bat
```

也可以直接启动主进程：

```powershell
cd <项目根目录>\collector

.\.venv\Scripts\python.exe main.py
```

直接启动 `main.py` 会跳过 `run.bat` 中的 OPC DA 自动检测和辅助服务启动。

### 5. 方案特点

优点：

```text
结构直观
调试方便
代码改动即时生效
采集模块兼容性最好
```

缺点：

```text
目标设备需要安装 Node / pnpm / Python
不同设备环境一致性较差
迁移步骤较多
```

## 四、方案二：前端、后端、TDengine 使用镜像迁移，采集模块本机运行

### 1. 当前状态说明

该方案是推荐的正式交付方向，但当前项目根目录尚未看到可直接执行的：

```text
docker-compose.yml
frontend/Dockerfile
backend/Dockerfile
```

因此本方案目前属于部署规划。执行前需要先补齐 Dockerfile、docker-compose 配置和镜像构建流程。

### 2. 适用场景

适合正式部署、内网部署、离线交付。

结构：

```text
Windows 主机
├─ collector   本机 .venv / run.bat 启动
└─ Docker
   ├─ frontend
   ├─ backend
   └─ TDengine
```

### 3. 目标设备需要安装

```text
Docker / Docker Compose
Python 3.14（用于采集模块）
```

不需要单独安装：

```text
Node.js
pnpm
前端 node_modules
后端 Python 运行环境
后端 pip 依赖
backend/.py314t-site
```

这些应封装在前端、后端镜像中。

### 4. 需要迁移

```text
frontend 镜像
backend 镜像
TDengine 镜像
docker-compose.yml
Docker 部署用 .env
MySQL 数据备份
TDengine 数据 volume 或挂载目录
collector 源码
collector requirements.txt
采集模块相关配置
```

### 5. 镜像导出与导入

旧设备导出镜像：

```powershell
docker save -o frontend.tar data-watch-frontend:latest
docker save -o backend.tar data-watch-backend:latest
docker save -o tdengine.tar tdengine/tdengine:latest
```

新设备导入镜像：

```powershell
docker load -i frontend.tar
docker load -i backend.tar
docker load -i tdengine.tar
```

实际镜像名称以项目构建结果为准。

### 6. 启动容器

```powershell
cd <项目根目录>

docker compose up -d
docker compose ps
docker compose logs -f
```

### 7. 迁移采集模块

采集模块仍然按方案一中的方式在 Windows 主机创建 `.venv` 并运行 `run.bat`。

需要确认容器端口映射到宿主机：

```text
backend    127.0.0.1:8000
TDengine   127.0.0.1:6041 / 6030
MySQL      127.0.0.1:3306
```

具体端口以实际配置为准。

### 8. 方案特点

优点：

```text
前端和后端环境封装
目标设备不需要安装 Node / pnpm / 后端 Python 依赖
部署速度快
适合离线迁移
环境一致性好
```

缺点：

```text
需要先补齐 Dockerfile 和 docker-compose
需要管理 Docker 镜像 tar 包
镜像体积可能较大
代码修改后需要重新构建镜像
数据库数据仍需单独备份和恢复
采集模块仍需单独配置 Python 环境
```

## 五、方案三：前端、后端、TDengine 在目标设备重新构建镜像，采集模块本机运行

### 1. 当前状态说明

该方案同样依赖 Dockerfile 和 docker-compose。当前项目如果还没有这些文件，需要先补齐后才能执行。

### 2. 适用场景

适合可联网测试环境、持续迭代环境、目标设备可以访问依赖源的场景。

结构：

```text
Windows 主机
├─ collector   本机 .venv / run.bat 启动
└─ Docker
   ├─ frontend  目标设备重新 build
   ├─ backend   目标设备重新 build
   └─ TDengine  pull 或 load 镜像
```

### 3. 目标设备需要安装

```text
Docker / Docker Compose
Python 3.14（用于采集模块）
```

目标设备需要能够访问：

```text
Docker 基础镜像源
npm / pnpm 依赖源
pip 依赖源
```

完全离线环境不建议使用该方案，优先使用方案二。

### 4. 需要迁移

```text
frontend 源码
backend 源码
frontend/Dockerfile
backend/Dockerfile
docker-compose.yml
Docker 部署用 .env
MySQL 数据备份
TDengine 数据 volume 或挂载目录
collector 源码
collector requirements.txt
采集模块相关配置
```

### 5. 重新构建并启动

```powershell
cd <项目根目录>

docker compose build
docker compose up -d
```

强制重新构建：

```powershell
docker compose build --no-cache
docker compose up -d
```

查看状态：

```powershell
docker compose ps
docker compose logs -f
```

### 6. 方案特点

优点：

```text
源码迁移轻量
方便重新构建
目标设备不需要安装 Node / pnpm / 后端 Python 依赖
适合频繁更新
```

缺点：

```text
依赖网络环境
目标设备构建时间较长
离线环境不稳定
需要先补齐 Dockerfile 和 docker-compose
数据库数据仍需单独备份和恢复
采集模块仍需单独配置 Python 环境
```

## 六、三种方案对比

| 对比项 | 方案一：仅 TDengine 容器化 | 方案二：镜像迁移 | 方案三：重新构建镜像 |
|---|---|---|---|
| 前端 | 本机运行 | 容器运行 | 容器运行 |
| 后端 | 本机运行 | 容器运行 | 容器运行 |
| TDengine | 容器运行 | 容器运行 | 容器运行 |
| 采集模块 | 本机运行 | 本机运行 | 本机运行 |
| 是否需要安装 Node / pnpm | 需要 | 不需要 | 不需要 |
| 是否需要安装后端 Python 依赖 | 需要 | 不需要 | 不需要 |
| 是否需要安装采集模块 Python 环境 | 需要 | 需要 | 需要 |
| 是否需要传输镜像 | 不需要 | 需要 | 不需要 |
| 是否需要重新 build | 不需要 | 不需要 | 需要 |
| 是否依赖网络下载依赖 | 前后端依赖需要 | 基本不需要 | 需要 |
| 当前可执行程度 | 可执行 | 需先补 Docker 文件 | 需先补 Docker 文件 |
| 适合场景 | 开发调试 | 正式部署 / 离线迁移 | 可联网测试 / 持续迭代 |

## 七、推荐选择

开发调试阶段：

```text
方案一：仅 TDengine 容器化，前端、后端、采集模块本机运行
```

正式部署或现场交付：

```text
方案二：前端、后端、TDengine 使用容器镜像迁移，采集模块本机运行
```

前提是先补齐 Dockerfile、docker-compose 和镜像构建流程。

可联网测试环境：

```text
方案三：目标设备重新构建镜像，采集模块本机运行
```

最终建议：

```text
开发阶段：方案一
现场部署 / 正式交付：方案二
持续迭代 / 可联网测试：方案三
```

采集模块暂时不建议容器化，继续在 Windows 主机运行更稳妥。
