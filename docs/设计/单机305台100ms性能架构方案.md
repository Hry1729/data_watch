> - **磁盘容量与保留策略**按用户要求**不展开**（默认全量写、磁盘另行扩容）。

## 1. 目标与基线

**硬目标**：单台边缘机稳定支撑

- 设备数：**305 台**
- 单设备点位：**1000 点**
- 采集周期：**全部 100ms（10Hz）**
- 写入语义：**全量写**（每周期每设备所有可存点都进 Redis stream → TDengine，不做变化过滤）

由此得到容量基线：

| 指标 | 数值 |
|---|---|
| 点位总数 | 305 × 1000 = **30.5 万点** |
| 采样速率 | 30.5 万 × 10Hz = **305 万点/秒** |
| 设备读取频率 | 305 次/100ms = **3050 次读/秒** |
| 设备写 Redis 频率 | **3050 设备写/秒**（每次含 latest/window/stream） |
| writer 入库行 | **3050 行/秒**，每行最多 1000 列 |

**判据**：每个采集实例的 `deadline_lag_ms` 同时满足 p99/p99.9、miss 比例与最大连续 miss 上限，30 分钟压测无采样丢失；Redis stream 不持续积压、writer pending 趋零（指标定义见 §9）。

## 2. 逐级吞吐账（为什么需要新架构）

### 2.1 PLC 读取并发（是否为瓶颈待实测）
- 当前安装的 `python-snap7 3.0.0` 是**纯 Python ISOTCP/socket 实现**：阻塞 `socket.recv` 等待期间通常可释放 GIL，但 PDU 构造、协议解析、结果转换仍执行 Python 代码，不能按“原生 `libsnap7` 全程并行”估算。
- 单次读耗时 **T** 同时包含 PLC/网络往返与 Python 协议处理。现场观察的 **10~30ms** 只能作为初始假设，必须用 §9 的 `read_ms` 分位数在 30/60/120/200/305 台逐级校准。
- S7 并发槽粗算仍可用 `设备数 × T / 周期` 作为起点，但线程池容量、CPU 占用和 deadline 是否达标必须联合观测，不能仅凭平均 T 判定“读不是瓶颈”。
- 155 台 AGV 的读负担也不能预先按“每 OPC server 一次”扣除；现有 proxy 每次请求临时建组并 `AddItems`，合并前必须先完成持久 Group、server handle 缓存与分块实测（§7.7）。
- 因此 v3 不预判读或写谁必然是唯一瓶颈；以 `read_ms`、parse CPU、`json_ms`、`redis_ms` 和 deadline 指标共同定性。

### 2.2 JSON 序列化 CPU（隐藏主瓶颈，v1 曾严重低估约 300 倍）
- `write_latest`（`redis_writer.py:25`）对 latest Hash 的**每个点单独 `json.dumps`**：1000 点 = **1000 次** dumps；window、stream 各再 1 次大 dumps。
- 即**每设备每周期 ≈ 1000（小）+ 2（大）次** dumps。305 台 × 10Hz：
  - 小 dumps（latest 单点 `{"v","t","q"}`）：**≈ 305 万次/秒**
  - 大 dumps（window/stream 的 ~1000 键 values）：**≈ 6100 次/秒**
- 粗估 CPU（**须实测校准**）：小 dumps ~1.5µs × 305万 ≈ **~4.6 核**；大 dumps ~200µs × 6100 ≈ **~1.2 核** → **合计约 5~6 核纯花在序列化**。
- 结论：序列化是已知的大块 CPU 成本，但“最先撞墙”仍需与 `read_ms`、parse 和 Redis 实测对照。优化 `write_latest`（§7.4）是公共前置项；需要并行时，A 由多进程摊核，C 则必须把 parse/编组/编码显式提交到 CPU executor，不能只切换解释器。

### 2.3 Redis（命令数不是瓶颈，但带宽 / AOF / 落盘是）
- **命令/往返**：latest 单独写 → 每设备每周期 **2 次往返**（window+stream 合 1 个 pipeline + latest 1 次）→ **≈ 6100 次往返/秒**（非 v1 的 3050）。通用基准中的 Redis 命令吞吐不能直接证明本负载足够；本项目还包含大 payload、分配、AOF 与 Docker 开销。
- **写带宽**：latest + window + stream 各携 ~1000 点 payload ≈ 3 × ~25KB × 3050 ≈ **~228 MB/秒**。loopback 可承受；**过网必须 10GbE**（§5 分布式）。
- **真正要盯且 v1 漏算的三项**：① ~228MB/s 的内存分配与拷贝；② **AOF 持久化**——`appendonly` 在 228MB/s 逻辑写下是**磁盘写风暴 + rewrite 放大**（§7.5 配置决策、§10 磁盘 I/O）；③ **Windows / Docker Desktop** 额外开销（边缘机是 Windows）。
- 所以"Redis 不是瓶颈"**只对命令数成立**；带宽、AOF、Docker 层**必须实测**，不能默认无忧。

> pipeline 只减少往返次数，**不减少 JSON CPU、也不减少字节量**——§2.2 的核数和 §2.3 的带宽与是否 pipeline 无关。

### 2.4 writer → TDengine
- 305 万值/秒。当前 writer **单循环、单连接、单锁、按设备串行 INSERT**（一轮最多 305 次串行落库）是明确瓶颈。
- 先验证：**多表批量 INSERT + 失败/ACK 语义**；若单 writer 仍不达标，再启用多进程分片与独立 TDengine 连接。

## 3. 当前架构与限制

```
[单 collector 进程]                         [单 writer 进程]
 1 event loop                                1 run_loop 消费所有 stream key
 共享默认线程池(≤32) ← 读+写+ping 挤一起     单 TDengine 连接 + 单锁
 单 RedisWriter(BlockingPool max=64)         _flush 按子表串行 write_batch
 latest 逐点 json.dumps + 2 次往返/设备      4 个 shard 只是 key，不是 4 路并行
```

限制小结：
1. **GIL**：单进程 CPU 密集只用满 1 核，而序列化就要 ~5~6 核（§2.2），单进程必然先在序列化卡死，用不满 12 核。
2. **共享线程池**：S7 阻塞读、Redis 写、ping 抢同一 ≤32 线程池；Redis 写阻塞会占住线程拖慢读（§7.3 要拆开）。
3. **writer 串行**：单连接单锁，按子表逐条 `write_batch`，一轮最多 305 次串行落库。
4. **Redis 写未优化**：`write_latest` 逐点 `json.dumps`（§2.2），且每设备 2 次往返、未跨设备 pipeline。

> 已完成的相关改动（基础，不在本方案重复）：DB 连续合并（单设备读从 ~800 次降到 ~1 次）、S7 read/ping/disconnect 共用 `threading.Lock`（消除 WinError 10035 与断连竞态）、Redis 改 `BlockingConnectionPool(max=64, timeout=2)`。

## 4. 目标架构

```
                    MySQL (配置)            Redis (单实例, maxmemory+noeviction)
                       │                         │  rt:stream:{type}:{group}:{shard 0..S-1}
        ┌──────────────┼───────────────┐         │
   collector worker_0 ... worker_{N-1}                     ← C：线程任务；A：进程分片
   每 worker 容量由压测定  各自: 有界 executor + Redis 写路径
   每设备每周期: pipeline(window+stream) → latest(最后)
                       │ XADD                    │ XREADGROUP
                       ▼                         ▼
                               writer worker_0 ... worker_{M-1} ← 单/多进程由压测定
                               多进程时各自独立 TDengine 连接
                              多表批量 INSERT (一条 SQL 写多个子表)
                              按 stream 聚合 XACK
                                        │
                                        ▼
                                   TDengine
```

图中 `worker` 是逻辑并行单元，最终采用 C 的线程任务还是 A 的进程分片由 §7.8 gate 决定。涉及分片时，两套分片**互相独立、都以 device_code 为键**：
- **collector 进程分片**：决定哪台设备由哪个 collector 进程采集。
- **Redis stream 分片**：决定某设备数据进哪个 stream（`crc32(device_code) % stream_shard_count`，已有）。
- writer 按 **stream 分片**消费，与 collector 进程分片无关。

## 5. 部署拓扑决策（首选分布式，单机为备选）

> v1 默认"单机满血"。v2 把**分布式（远端库 + 多采集机）升级为首选拓扑**：单纯序列化就要 ~5~6 核（§2.2），叠加 ~228MB/s 写带宽、AOF/落盘（§2.3、§10）、以及边缘机是 **Windows + Docker Desktop** 的额外开销，单台 12 核"刚好够"的余量非常薄，任何一项实测偏高就翻车。横向加采集机比纵向堆单机更稳、更可预期。

### 拓扑 A — 分布式（首选）

```
   采集机1 (Windows, 近 PLC)        采集机2 ...        采集机k
   collector_0..a  ──┐             collector ...       collector ...
   各自 event loop    │ XADD over 10GbE
   显式读/parse/写 executor │
                      ▼
            ┌──────────────────────────────────────────┐
            │   服务器侧 (Linux, 无 Docker Desktop 开销)  │
            │   Redis(单/分实例)  ← 带宽汇聚 ~228MB/s     │
            │   writer_0..m  →  TDengine 集群             │
            │   MySQL(配置)   backend/frontend            │
            └──────────────────────────────────────────┘
```

- **采集机**：每台只跑一部分设备的 collector 进程，靠近 PLC，本地只做 read+parse+序列化+XADD。
- **服务器侧**：Redis、writer、TDengine、MySQL、backend 集中部署在 **Linux**，避开 Windows/Docker Desktop 损耗；TDengine 可走集群分担落盘带宽（§10）。
- **网络**：collector→Redis 跨网，**228MB/s 必须 10GbE**（千兆会成为硬瓶颈）；Redis 与 writer 尽量同机/同交换机降延迟。
- **扩缩**：设备增长时**加采集机 / 加 writer 进程**即可，单机核数不再是天花板。

### 拓扑 B — 单机满血（备选）

- 全部组件（collector_0..N、writer_0..M、Redis、TDengine、backend）压在**一台 12+ 核**机器上，全 loopback、无跨网带宽问题。
- 适用：**设备规模偏小 / 现场只有一台机 / 不具备 10GbE 组网**；或作为分布式的单点回退。
- 风险：序列化+落盘+AOF 全挤一台，12 核余量薄；Windows/Docker Desktop 开销直接计入预算（§6、§10）。**必须实测确认达标**，不能默认可行。

### 两拓扑的共性

A、B 共用指标、序列化优化、Redis/TDengine 验证与 writer 批写设计；collector 的并行方式则由 §7.8 gate 决定：C 通过时采用单进程自由线程 + 显式 executor，C 不通过才启用 A 的多进程分片。拓扑只决定**进程跑在哪、是否跨网**，不能替代运行时和容量验证。

### 当前执行决策与分布式前置改动（暂缓，最后处理）

> **当前先验证单机（拓扑 B）**。分布式（A）虽为长期首选，但落地前需补一处代码改动，**暂缓到单机验证完成后再处理**。

**数据面已就绪（仅配置）**：collector→中心 Redis、writer 经 consumer group、配置读中心 MySQL，host 均为配置项，多机指向同一套中心服务无需改代码。

**缺失的前置项（多采集机必须先有，否则多机重复采集）**：
- **collector 无"按实例分片加载设备"能力**：`config_db.py` 加载设备仅 `where(DBDevice.enable == 1)`（约 293 行），每个 collector 都加载全部启用设备；也没有实例/分片标识环境变量。直接多机部署会**各采全部 305 台（重复采集）**。
- **需补的小改（有界，非框架重写）**：设备加载加分片过滤 `crc32(device_code) % N == my_index`（crc32 逻辑 `redis_writer.py:58` 已现成），N/index 经环境变量注入，热更新循环同样遵守；writer 把写死的 `consumer_name="writer-1"` 改为按实例注入。因一机一 collector，§7.1 的多进程共存坑（8090/flag/proxy/ProcessManager）不会触发。
- **与运行时优化正交**：分布式只摊负载到多机，不改变单机单进程受 GIL 限制；§7.4 序列化、§7.6 writer 批写、§7.9 并发契约、§9 指标无论单机/分布式都要做。

## 6. 资源规划（两拓扑核预算）

> 所有数字为**实测前的粗预算**，须用 §9 指标（尤其 `json_ms`/`read_ms`/`write_batch_ms`）校准。CPU 密集项以"满载核当量"计，I/O 阻塞项以"进程数"计（多为等待，可超配核数）。

### 6.1 CPU 密集刚性下限（两拓扑都绕不开）

| 项 | 量 | 单价（须实测） | 核当量 |
|---|---|---|---|
| latest 小 dumps | ~305 万次/秒 | ~1.5µs | **~4.6** |
| window/stream 大 dumps | ~6100 次/秒 | ~200µs | **~1.2** |
| parse / 编排 / Redis 客户端开销 | — | — | ~1~2 |
| **序列化+采集侧 CPU 合计** | | | **≈ 6~8 核** |

- 这 6~8 核是**优化前的采集侧粗预算**，不是刚性下限；其中 parse 与编码的真实单价须用可复现 benchmark 和整包压测校准。
- GIL 版 CPython 需要多进程摊核；自由线程 3.14t 只有在 parse/编组/编码显式并行且线程安全 gate 通过后，才可能单进程用满多核（§7.8）。
- **§7.4 的 `write_latest` 序列化优化可显著降低小对象编码成本**，但 2.74M/s 仍低于目标 3.05M/s，不能按“一核足够”入账。

### 6.2 拓扑 A（分布式）核预算

| 侧 | 组件 | 形态 | 核预算 |
|---|---|---|---|
| 采集机（合计 k 台） | collector worker（C 线程/A 进程） | I/O+parse+序列化 | 每机承载 §6.1 的一部分；k 台均摊优化前 CPU 预算 |
| 服务器(Linux) | Redis | 单线程命令+持久化 | 1~2（命令）+ AOF 落盘 I/O（§10） |
| 服务器(Linux) | writer 多进程 | 批写 | 2~3 |
| 服务器(Linux) | TDengine | 集群/单机 | 2~4（入库）+ 落盘带宽（§10） |
| 服务器(Linux) | MySQL/backend/frontend | — | 轻 |

- 采集侧把 6~8 核序列化**分散到 k 台**，每台压力小、余量大；服务器侧专注 Redis/writer/TDengine，**Linux 无 Docker Desktop 损耗**。这是首选 A 的核心理由。

### 6.3 拓扑 B（单机满血）核预算（12 核）

| 组件 | 形态 | 核预算 |
|---|---|---|
| collector | C：1 进程+显式 worker；A：8~10 进程 | 优化前粗估 **~6~8**（§6.1，全压这台） |
| writer | 4~8 进程 | ~2~3 |
| Redis | 容器/单线程 | 1~2 + AOF I/O |
| TDengine | 容器 | 2~4 |
| Windows + Docker Desktop | 系统/虚拟化开销 | **不可忽略，计入** |
| backend/frontend | 容器 | 轻 |

- 把刚性 6~8 核序列化、2~3 writer、1~2 Redis、2~4 TDengine 全叠一台：**裸和已逼近甚至超过 12 核**，再加 Windows/Docker Desktop 开销，**余量极薄**。
- 结论：B 是否可行**完全取决于实测**——尤其 §7.4 序列化优化能砍多少、`read_ms` 实际多大。**不优化序列化的前提下，单机 12 核大概率不达标。**

## 7. 关键设计

> §7.1/§7.2 仅用于多进程回退 A；其余为 A/C 共用优化与验证项。任何“足够”“低风险”结论均以 §8/§9 gate 为准。

### 7.1 collector 多进程共存契约（最重 P1：现状起不来）

> **适用条件**：本节**仅当走多进程方案（§7.8 的 A，或一机多 collector）时需要**。若自由线程候选 C 通过完整 gate，本节不实施。

**问题**：当前代码处处假设"只有一个 collector"。直接起 N 份会有四处硬冲突，必须先立契约：

| # | 现状冲突 | 锚点 | 契约 |
|---|---|---|---|
| 1 | **ingest 端口 8090 冲突**：每个 collector 内置 ingest server 默认绑 `8090`，第二个进程直接端口占用失败。 | `collector/monitor/ingest_server.py:603` | 每分片**独立端口 `8090 + shard_index`**（或关闭各分片内置 ingest，改由一个聚合 ingest/Agent 主动拉取）。health/监控端点按分片注册。拓扑 A 同机多 collector 同样适用。 |
| 2 | **shutdown_flag 共用**：所有进程读同一个停机 flag，停一个会停全部。 | `collector/main.py`、`collector/tests/test_shutdown_flag.py` | 每分片**独立 flag 文件 + PID + 日志目录**（按 `shard_index` 命名），启停互不波及。 |
| 3 | **OPC proxy 整组生命周期**：当前停 collector 会停掉**全部** OPC DA proxy sidecar，其它分片会断线。 | `agent/app/services/sidecar_manager.py:315 on_collector_stop` | proxy 改**引用计数 / 按分片归属**：仅当某 proxy 不再被任何存活分片引用时才停；停单分片**不得**断开其它分片仍在用的 proxy。 |
| 4 | **ProcessManager/Admin/UI 只认一个 collector**：注册、状态、启停都是单实例视角。 | `agent/app/services/process_manager.py:50`、`agent/app/routers/admin.py` | 扩展为管理 **`collector_0 … collector_{N-1}` 进程组**：注册表多实例、状态聚合、启停支持"按组 / 按分片"两种粒度。 |

**编排契约（每分片注入）**：
- `DATAWATCH_COLLECTOR_SHARD_COUNT = N`、`DATAWATCH_COLLECTOR_SHARD_INDEX = i`。
- 独立 NSSM 服务，或一个 supervisor 拉起 N 个子进程；独立端口 / flag / PID / 日志目录。
- 注：collector/writer 为**单进程 exe、无应用子进程**，proxy sidecar 由 Agent 管理——上述生命周期契约都落在 **Agent/sidecar_manager 侧**，不是 collector 内部。

**仍沿用的分片基础**：
- **进程数 N**：单机（拓扑 B）初始 **8~10**（留核给 writer/redis/tdengine）；分布式（拓扑 A）按每台采集机核数定。collector 多为 I/O 等待，可适度超配核数；升级/加机后线性加 N。
- **分片规则**：见 **§7.2 哈希策略**（固定 N 停启 vs Rendezvous）。进程启动时按分片过滤 MySQL 设备表，只加载/采集自己分片的设备。
- **每进程独立**：自己的 event loop、`DeviceManager`/`scheduler`、`RedisWriter` 及连接池；**读/parse/写线程池隔离见 §7.3**。
- **配置热更新**：每进程 `_config_reload_loop` 只处理自己分片的设备；设备"改了分片归属"的迁移由 Agent 编排路由到正确分片进程（依赖已修复的 read/ping/disconnect 锁，避免热更新 socket 竞态）。

### 7.2 collector 分片哈希策略（P2：crc32 % N 不可平滑扩缩）

> **适用条件**：同 §7.1，**仅多进程方案（A）需要**；自由线程单进程（C）无需把设备分片到多进程，本节不适用（Redis stream 分片是另一回事，仍在）。

> **澄清两套分片别混**：①**collector 进程分片**（哪台设备归哪个采集进程，本节）；②**Redis stream 分片**（数据进哪个 stream，`crc32(device_code) % stream_shard_count`，`redis_writer.py:58`，改动走 v0.6 §12.5 迁移，不在本节）。本节只谈 ①。

**问题**：`shard_index = crc32(device_code) % N` 在 **N 固定时重启稳定**，但 **N 一变（如 8→9）大量设备会重新落到不同进程**——扩缩容会引发大面积重分配，期间易**重复采集或漏采**。给两种方案，按运维方式二选一：

**方案一：固定 N + 整体停启（默认推荐，简单）**
- 规则：`shard_index = crc32(device_code) % N`，N 写死在编排配置。
- 扩缩流程：**先全停所有 collector 分片 → 改 N → 全启**。全停期间无人采集（短暂 gap，可接受），重启后各设备稳定归位，**不会出现新旧进程同时采同一设备**。
- 适用：现场设备规模相对稳定、可接受扩容时的秒级全停。**满足当前需求即用这个。**

**方案二：Rendezvous / HRW（最高随机权重）哈希（需在线扩缩才上）**
- 规则：对每台设备，在所有存活进程里取 `argmax_i hash(device_code, node_i)` 作为归属。**增删一个节点时，只有原本指向该节点的设备会迁移**，其余不动。
- 在线扩缩流程（避免重复/漏采）：用**成员版本号（epoch）**做交接——某设备从进程 A 迁到 B 时，**A 先停止采集该设备并确认最后一批已 flush，B 再开始**（先停后起，避免双写）；交接窗口尽量短以减少漏采，并用 §9 的 `deadline_miss_count` 监控迁移期影响。
- 代价：实现与编排更复杂（需成员发现 + epoch 协调）。**只有"不停机加采集机"是硬需求时才值得。**

**结论**：除非明确要在线扩缩，**默认方案一（固定 N + 停启）**。Redis stream 分片仍按 `stream_shard_count` 走既有迁移流程，与本节进程分片解耦。

### 7.3 读 / parse / 写 executor 隔离（P1：线程池只调大、未隔离竞争）

**问题**：S7 阻塞读、Redis 写、ping 当前**共享同一个默认线程池**（`collector/collector/executor.py` / loop 默认 executor）。Redis 写阻塞时（`BlockingConnectionPool(timeout=2)` 满了要等 ~2s）会**占住线程**，连带拖慢 PLC 读——只把池调大并不能消除这种相互占用。

**契约**：collector 显式建相互隔离的 executor，按任务类型分派，互不共享：

| executor | 专做 | 大小 |
|---|---|---|
| `plc_read_executor` | snap7 阻塞读（read/connect/ping/disconnect，已共用 device `threading.Lock` 串行化） | `K_read ≈ 进程设备数 × T_ms/100 + 余量`（如 35 台 ×20ms ≈ 7 → 取 12~16） |
| `cpu_parse_executor` | 原始块解析、按组编排、JSON/msgspec 编码 | 按可用物理核与实测扩展曲线定；必须有界，禁止无界堆积 |
| `redis_write_executor` | Redis 写（XADD/pipeline/HSET） | 独立设定，Redis 端阻塞不再占读线程 |

- 调用处对三类任务显式指定 executor，不再吃默认 ≤32 池。当前 `executor.py` 在 event loop 内同步执行 `_parse_result`，切换到自由线程运行时**不会自动并行**；C 路线必须把 parse+编组+编码整体搬入 `cpu_parse_executor`，并审计传入/返回对象的线程共享边界。
- **ping/health 不与读抢核**：并入 `plc_read_executor` 走已有 device 锁串行，不另开抢核的池。
- 可选进一步：Redis 写改**异步 redis 客户端 + 有界写队列**，背压时丢最旧 window / 告警，而非阻塞读路径。

### 7.4 write_latest 序列化优化（P1 降本：直击 ~4.6 核）

**现状**：`collector/storage/redis_writer.py:25` 对 latest Hash 的**每个点单独 `json.dumps`**，1000 点=1000 次 → **~305 万次/秒 ≈ ~4.6 核**（§6.1）。这是整个 CPU 预算里最大的单块。

**优化**：latest 单点 value 形状固定 `{"v","t","q"}`，但 `v` 仍可能是字符串、`None` 或特殊浮点，编码必须保持合法 JSON：
- **首选：msgspec**（`msgspec.json.encode`）——已有自由线程 import/encode 初测，通用且避免手写转义；仍需整包并发压测确认线程安全与吞吐。
- **备选：手写拼串**——初测单线程 **~2.74 M/s（比 `json.dumps` 快 ~13×）**，但低于目标 **3.05 M/s**。只有通过与标准 JSON 编码器逐字节/语义等价的属性测试（引号、反斜杠、控制字符、Unicode、`None`、NaN/Inf、整数/浮点）后才可采用，并且至少需要约 `3.05/2.74≈1.11` 个满载核，不是“一核远超目标”。
- **orjson 仅限多进程 CPython（A）**：它快，但**不支持自由线程（实测构建失败）**，走 C 路线用不了。
- window/stream 的大对象优先用 msgspec；不得在没有等价性测试时扩大手写拼串范围。

**预期（实测校准）**：2.74 M/s 对应 latest 理论下限约 **1.11 核**，尚未计入对象构造、线程调度和 Redis 客户端开销。该优化收益高，但不是“单线程已达标”；以可复现 benchmark、属性测试和 §9 `json_ms` 现场复测共同验收。

### 7.5 Redis 写路径与实例配置（含 AOF 决策）

**写路径**：
- **pipeline 合并**：把每设备每周期的 `window + stream` 合并进**一个 pipeline（1 次往返）**，`latest` **仍单独、且只在前两步成功后写**（保住"latest 最后、仅在 window/stream 成功后刷新"的不变式，见 v0.6 §13）。每设备往返从 3 降到 2。
- 可选进一步：一个进程一轮 flush 内**跨设备合并 pipeline**，再降往返。
- 注：pipeline 只省往返，**不省 §7.4 的序列化 CPU、也不省字节量**（§2 已述）。

**实例配置候选**（单实例能否承载须压测，全 collector 进程 + writer + backend 共用）：
- `maxmemory <按机器定>`、`maxmemory-policy noeviction`（满了让 XADD 报错、绝不 evict stream）。
- 固定镜像版本（勿用 `latest`）、容器 `mem_limit` 兜底。
- `stream_maxlen` 按实测重算（全量 batch entry 较大，50万 偏高）。

**AOF 决策（P1 关联，必须实测定夺，别默认 `appendonly yes`）**：~228MB/s 逻辑写下，AOF 是**磁盘写风暴 + rewrite 放大**（§10）。三选一：

| 方案 | 收益 | 代价/风险 |
|---|---|---|
| `appendonly yes` + `everysec`（默认） | 宕机最多丢 1s | rewrite 期 I/O 尖峰可能拖累延迟，须 §10 盯盘带宽 |
| 关 AOF、仅 RDB | 盘压最小 | 宕机丢未落盘窗口数据——**实时缓冲层能否接受须评估**（数据已落 TDengine 的部分不丢） |
| AOF + 独立高速盘 + 调 `auto-aof-rewrite-percentage` | 兼顾持久化与盘压 | 需独立 NVMe、参数调优 |

- **拓扑 A（分布式）下 Redis 在 Linux 服务器**，盘与参数更可控，是优先选 A 的又一理由。
- 单 Redis 只作为第一轮候选，**不能从命令数推导“吞吐足够”**。必须测命令 CPU、网络/内存复制、AOF 实际字节率与 rewrite 期间 p99 延迟；不达标时再评估关闭 AOF、独立实例或分片。

### 7.6 writer 多表批写 + 身份契约 + 失败隔离 + 缓存快路径

**多表批量 INSERT（高收益候选，须先做原子性与边界实验）**：TDengine 支持一条 SQL 写多个子表
```sql
INSERT INTO `db`.`qc100` USING `db`.`sdqc` TAGS('qc100') (ts,...) VALUES(...)(...)
            `db`.`qc101` USING `db`.`sdqc` TAGS('qc101') (ts,...) VALUES(...)(...)
```
一轮 flush 可尝试把多个子表合成 1~few 条 SQL，理论上显著减少往返；实际收益和可用批大小由 SQL 字节上限、TDengine 版本、单语句耗时及失败语义决定。

**失败隔离（P1，必须；一个坏设备不能拖垮整批 305）**：
- **分块**：按 **SQL 字节数 / 子表数 / 行数**上限切块，避免超长 SQL / 单次超时（阈值按实测定）。
- **TDengine 多表语句语义**：先确认其是否"全有或全无"（一个子表坏数据是否导致整条 SQL 失败）→ 据此设计降级。
- **二分降级**：整块失败时**二分重试**定位坏子表——坏的进 **DLQ**、好的照常入库；不让坏数据阻塞整批。
- **XACK 边界**：**只 XACK 已确认成功落库的 entry**；失败 / 降级中的 entry **不 ACK**，留给 pending / 重试（保 at-least-once）。

**多进程身份契约（P2，当前配置写死 `writer-1` 起不了多份）**：起 **M 个 writer 进程（4~8）**，每进程必须：
- 共用**同一个 consumer group**；
- **唯一 `consumer_name`**——当前 `writer/config/settings.toml` 写死 `consumer_name = "writer-1"`，须按 worker 注入 `writer-{id}`（参考 `docs/运维/测试脚本/redis_to_tdengine_writer.py:295` 的 `f"writer-{worker_id}"`）；
- **显式声明只消费哪些 stream shard**，各自独立 TDengine 连接；
- 独立 **shutdown flag / PID / log**；
- **只 reclaim / XAUTOCLAIM 自己负责的 stream**，不抢其它 worker 的 pending。
- 若需比 `stream_shard_count=4` 更高并行度，调大 shard **需走迁移流程**（v0.6 §12.5 双消费，勿直接改配置）。

**缓存快路径（P2，省每消息线程切换）**：`writer/consumer.py:442` 即使 mapper **缓存命中**也 `run_in_executor` 切线程，3050 条/秒持续浪费。改为：**缓存命中在事件循环内同步取，仅 miss 才进线程池查 MySQL**。

**保留**：聚合 ACK（按 stream 统一 `XACK` 替代每设备单独 ACK）、现有 pending/DLQ/重启 drain 语义（v0.6 §16.3/16.8）。

### 7.7 OPC 同源设备合并读（先改 proxy 持久组，再评估调度合并）

> 实施顺序可后置：先用 S7/可重复仿真负载完成 collector、Redis、writer 与运行时定型，再实施本节；但最终“305 台混合协议达标”验收必须包含真实 OPC DA/DCOM 负载。

**现状**：每台 AGV 是独立 `device`，调度按设备各起一个读任务（`scheduler.py:61` 每 task 一个 loop、`executor.py:94` 每设备一次 `driver.read`）。但 10~15 台 AGV **共用同一个 OPC server**（同 `proxy + opc_server + vm_host`，连接经 `OpcDaIpcClientPool` 共享）。结果是**每周期 155 次 `read_items` 请求**，而物理连接只有 ~10 条——读请求被设备粒度放大了。

**当前硬约束**：proxy 的 `OpcConnectionManager.ReadItems` 每次请求都会创建临时 OPC Group、对全部 item 执行 `AddItems`，读取后再删组。若把 10~15 台 ×1000 点直接合成一个 10k~15k item 请求，将在 100ms 周期反复 Add/Remove，约等于 **155 万 item AddItems 操作/秒**，可能比 155 个小请求更差。

**正确的前置顺序**：
1. proxy 先实现按 OPC server 复用的**持久 Group + item server handle 缓存**，配置变化时做增量 add/remove，而不是每周期重建；明确断线重连后 handle 失效与重建语义。
2. 按 OPC server 实测单次可承载 item 数、请求/响应字节数、DCOM 超时和 64MB IPC 帧上限，设置有界 chunk（每块多少 item 由实验决定，不能预写 10k/15k）。
3. 持久组正确性与容量实验通过后，再把同源设备在调度层归并，并按 item_id 的显式归属映射扇出；不得依赖容易冲突的字符串前缀猜设备。
4. 对单点错误、坏质量、超时、断线和部分 chunk 失败定义隔离语义，避免一个坏 item/块拖垮整组设备。

- **预期而非承诺**：最终请求数可能从 155 降到“每 server 若干 chunk”，不预先写死为 ~10；以 proxy `AddItems/read/remove` 耗时、chunk p99 和 deadline 指标验收。
- **数据库结构与数据面保持不变**：每台 AGV 仍是独立设备、独立 TDengine 子表、独立 Redis latest/window/stream 键；但 proxy、driver/IPC 与 scheduler 都可能需要改动，不能描述为“只改调度”。
- **不影响序列化/写入负载**（§2.2 仍按设备数算）——本优化只省"读"，不省"写/序列化"，两根轴别混。
- 适用范围：仅 OPC DA 同源设备；S7 各自独立 PLC 连接，不适用。

### 7.8 collector 运行时选型（用满多核的三条路：A 多进程 / B Rust·Go 重写 / C 自由线程 3.14t）

> 本节 A/B/C 是**运行时路线编号**，与 §5 的“拓扑 A/B”不是同一维度。

**问题定性**：当前 collector 的 Python CPU 工作（parse、编组、编码）主要在单 event loop 线程串行执行；GIL 版 CPython 无法靠普通线程并行这些工作。S7 又是纯 Python ISOTCP 实现，读路径也含 Python 协议处理。"用满多核"有三条路，但任何路线都必须先完成指标和整包压测：

| 维度 | A. 多进程 CPython | B. Rust/Go 重写 | C. 自由线程 Python 3.14t |
|---|---|---|---|
| 用满核方式 | N 进程 × 各 1 核 | 无 GIL，1 进程多线程 | 无 GIL，1 进程多线程 |
| 复用现有代码 | ✅ 高 | ❌ 全部重写 | ✅ 高，但须调整并行边界 |
| §7.1 多进程共存坑 | ❌ 必须做 | ✅ 天然无 | ✅ 单进程天然无；少量多进程隔离变体需精简处理 |
| 内存效率 | 差（N 份解释器+连接池） | 最好 | 好（单进程共享） |
| 落地工作量 | 中（增量改造） | 很大（从零重造） | 中（运行时、executor、线程安全、打包与依赖） |
| 风险 | 低（复用已调好代码） | 高（已修复的竞态/DB合并/latest不变式全要重来） | 中（自由线程较新，依赖兼容待验） |
| 技术栈 | 单一 Python | 多语言（后端/writer/agent 仍 Python） | 单一 Python |
| 团队已有经验 | 有 | 无 | **有（后端已跑 3.14t）** |

**逐项判断**：
- **B（Rust/Go 重写）**：能解决 CPU 并行与内存密度，但要把 S7/OPC IPC/调度/热更新/配置/Redis 三写不变式/打包/测试从零再造。它不能消除 PLC/DCOM 的外部延迟，且迁移风险最高；仅作长期储备。
- **A（多进程 CPython）**：复用全部已测代码、工作量有界、单栈；唯一痛点是 §7.1 共存契约——而该痛点**在分布式拓扑（每机一进程）下自然消失**（§5）。是稳妥保底。
- **C（自由线程 3.14t）**：避免解释器 GIL，但不会让 event loop 中同步 `_parse_result` 自动并行。必须把 parse+编组+编码显式移入有界 CPU executor，审计 scheduler、Device、变量快照、RedisWriter 与热更新共享态，并完成依赖、PyInstaller、断连/热更和真负载整包 gate。隔离 import 与 microbench 只是前置证据，不足以批准生产。

**选型结论：C（自由线程 3.14t）为优先验证候选，A（多进程）为明确回退，B（Rust/Go）为长期储备。** 在完整 gate 通过前，不把 C 写成生产首选，也不提前放弃 §7.1/§7.2 的估算与回退准备。

**推荐路线**：
1. 先做与运行时无关的核心工作：§9 指标与可复现 benchmark、§7.4 安全序列化、§7.6 TDengine 多表原子性/边界实验、§7.9 并发状态契约；§7.7 OPC 持久 Group 按用户决策后置。
2. **验证 C**：显式 parse executor、依赖锁定、完整 frozen collector，在 30→305 台负载下覆盖 Redis、热更、断连、停机与 30 分钟零丢样 gate。通过才正式选择 C。
3. **回退 A**：C 任一生产 gate 不通过即进入 §7.1/§7.2 多进程路线，不以“能启动/能 import”代替容量验收。
4. **B 留作长期战略储备**：单机密度/内存成硬指标且接受多语言栈时再上。

> 一句话：先证明公共优化和真实瓶颈，再让 C 与 A 通过同一套生产 gate；“可 import、可打包、microbench 扩展”不等于“305 台整包可运行”。

#### 7.8.1 3.14t 前置 spike（2026-06-19，尚未达到生产 gate）

已有 `python3.14t`（`Py_GIL_DISABLED=1`）隔离 import、microbench 与最小打包实验，说明 C 值得继续验证；但实验脚本、原始输出、机器信息和精确依赖锁尚未固化进仓库，且不是完整 collector 压测，因此不能据此判定“依赖关与打包关已通过”。

**① 依赖自由线程兼容矩阵**（隔离 import，看 GIL 是否被偷偷重开）：

- 若最终改裸 aiomysql/PyMySQL，按完整配置数据库适配层迁移估算，逐项覆盖读取、热更新版本、状态更新、事务和错误语义，不能按小改处理。

**切 C 前的 gate**：固化 benchmark 与依赖锁；解决 SQLAlchemy frozen 根因；完成 parse executor 与线程共享态审计；打完整 collector；在真实负载下覆盖 30→305 台、Redis、OPC/S7、热更新、断连、优雅停机和 30 分钟零丢样。缺一项都不能批准 C 上生产。

### 7.9 并发状态契约（自由线程与多进程公共正确性基础）

> 目标不是“给所有对象加锁”，而是让每个采集结果都能证明自己仍属于当前设备配置，并让同一设备的 I/O 与写入保持有序。该契约在普通 CPython 下也有价值，在自由线程 C 路线中是生产前置条件。

**1. 不可变配置快照 + generation**

- 每个设备维护单调递增的 `generation`（进程内代次号）。热更新、设备删除、驱动重建或重连切换成功时递增。
- 热更新先在旁路完整构建新的变量、点位组和 scan task 快照；全部成功后一次性替换引用并递增 generation，禁止对正在使用的列表/dict 原地增删。
- 每个采集 job 在创建时固定携带 `device_id + generation + config_version + immutable variables/groups snapshot`。parse worker 只读该快照，不直接读取或修改实时 `Device` 对象。

**2. 迟到结果拒绝**

- `task.cancel()` 只能取消协程等待，不能保证已经进入线程池的 read/parse 立即停止；因此不能把“已 cancel”当作线程已退出。
- read/parse 完成后、进入 Redis 写队列前再次比较当前设备的 `generation/config_version/active`。任一不匹配即丢弃整批，并递增 `stale_result_drop_count`；旧配置结果不得写入新配置的 key/stream。
- 设备删除后保留短生命周期的 tombstone/generation 信息，确保晚到线程可以识别“设备已失效”，而不是因注册表已删除而误写。

**3. 每设备 I/O 与生命周期串行**

- 同一设备的 `read/connect/ping/disconnect` 共用线程级 I/O 锁；任何阻塞等待都在线程池内发生，禁止在 event loop 直接等待 `threading.Lock`。
- 同一设备最多允许一个 in-flight 采集周期。上一周期未完成时，本周期记 deadline miss 并跳过，**不排队补跑**，否则延迟会无限累积并形成旧样本洪峰。
- 热更新/删除先停止产生新 job；需要断连时等待当前 I/O 临界区结束，再切换 generation 和驱动。parse 可以晚结束，但其结果会被 generation gate 丢弃。

**4. Redis 顺序与背压**

- 按 `device_code` 稳定分片到有界写队列；同一设备始终落入同一写 worker，保证其批次顺序，不使用一把全局锁串行全部 305 台。
- 单批严格保持 `window + stream` 成功后才更新 `latest`。失败批次不得越过重试中的旧批次更新 latest。
- 所有 executor、队列和 semaphore 必须有上限；达到上限时按明确策略拒绝新周期并告警，不允许创建无界 future。全量写语义下不得静默丢弃，拒绝数必须进入样本对账并判定压测失败。

**5. 关闭与故障恢复**

- 优雅停机顺序：停止调度新 job → 等待/超时终止 I/O → drain 有界写队列 → 关闭 Redis/驱动连接。超时退出必须记录未完成 job 数。
- 网络恢复或服务重启时，设备重连采用指数退避 + 稳定随机 jitter，并设置全局 `reconnect_semaphore`；禁止 305 台在同一秒同时 connect/ping，避免 PLC、线程池和网络被恢复风暴再次打挂。

**6. 必测并发场景**

- 用 `threading.Event` 精确覆盖：read 中热更新、parse 中删除、cancel 后工作线程迟到、disconnect 等待 I/O、Redis 批次失败、关闭时队列未清空。
- 对每个场景断言：无旧 generation 写入、无同设备乱序、无 event loop 阻塞、无无界队列增长，且计划/成功/拒绝/落库样本数可对账。

### 7.10 资源边界与故障半径

- **对象分配/GC**：305 万点/秒可能产生大量短命 dict/list/string，即使编码器变快也可能卡在分配器、GC 与 RSS。优先复用不可变元数据、避免每点临时 dict、采用 tuple/紧凑批结构；压测记录 allocation rate、GC pause、峰值 RSS，不以 CPU 使用率单独判断。
- **单进程故障半径**：C 单进程一旦崩溃会同时中断全部 305 台。必须由 Agent/watchdog 快速拉起并测量恢复时间；若可用性 gate 不通过，可采用少量（如 2~4 个）自由线程进程做故障域隔离，而不是在“单进程 C”和“大量进程 A”之间二选一。该变体仍需落实 §7.1 的精简共存处理（独立端口、runtime/shutdown flag、进程身份与生命周期），不能沿用“单进程 C 天然无共存问题”的结论。
- **连接总预算**：按最终 worker 数核算 Redis、MySQL、TDengine、OPC 与 PLC 的总连接数，配置全局上限和各池上限；进程数翻倍不能让数据库连接数无控制地同步翻倍。
- **TDengine 边界**：在精确生产版本上预检 1000 列宽表、单行/单 SQL 字节上限、多表语句最大表数、超时与部分失败语义；由实验结果决定 batch/chunk，不把理论支持当作现场可用。
- **日志与指标反压**：100ms 热路径禁止逐点 INFO/WARNING。坏质量、deadline miss、队列拒绝等使用聚合计数 + 限速摘要；同时保留首个样本定位字段，避免“为观测性能而制造性能问题”。
- **时间语义**：调度间隔只用 monotonic clock；业务时间戳使用受监控的 wall clock/PLC 时间源。监控 NTP 偏差与时间回拨，避免调度正确但跨设备时间轴不可比较。

## 8. 压测计划

在**真实目标机硬件**上分级压测（核数直接决定可起进程数）；**拓扑 A、B 各跑一遍**，用数据选定拓扑（§5）：

```
30 台 → 60 台 → 120 台 → 200 台 → 305 台
```

每级：
1. 全 100ms 全量跑 ≥30 分钟。
2. 看 §9 指标：`deadline_lag_ms` p99/p99.9、miss 比例/最大连续 miss、`json_ms`、`read_ms`、parse CPU、stream `XLEN` 趋势、writer pending、各组件 CPU、**磁盘写带宽（§10）**。
3. 找拐点：哪个实例先 `deadline_miss` / 哪个 stream 先积压 → 定位该级瓶颈（读并发？parse？序列化？writer？落盘？）→ 调运行时、executor、批大小或编码方案，再压。
4. 记录每级配置与指标，形成容量曲线。
5. benchmark 与压测必须固化：脚本、随机种子/数据集、机器 CPU/内存/磁盘/网络、Python/依赖精确版本与 hash、命令行、原始输出和 commit id 一并保存；没有这些材料的数字只作线索，不作选型证据。
6. 在 120 台和 305 台档加入故障注入：Redis 短暂停顿/AOF rewrite、PLC 网络中断后恢复、热更新/删除设备、collector 重启和写入批次失败；验证队列始终有界、无旧 generation 写入、无重连风暴，恢复后样本可对账。

## 9. 可观测性（达标的唯一硬依据）

> v1 把"一轮执行耗时"误称为 `scheduler_lag`。**执行耗时 ≠ 调度迟到**——必须拆成四件套，并对 305 个 100ms 任务做**相位错开**，否则它们卡同一 tick 同时触发会形成周期性尖峰。

**collector 实例 — scheduler 指标四件套（P1）**：

| 指标 | 含义 | 用途 |
|---|---|---|
| `execution_ms` | 一轮 `read + parse + Redis 写` 的纯执行耗时 | 看单轮重不重（拆 `read_ms` / `json_ms` / `redis_ms`） |
| `start_to_start_ms` | 相邻两次启动的间隔 = **真实采样周期**（应 ≈ 100ms） | 看实际采样频率有没有掉 |
| `deadline_lag_ms` | 实际启动时刻 − 计划时刻 = **迟到量** | **核心判据** |
| `deadline_miss_count` | `deadline_lag_ms` 超阈值的次数 | go/no-go 计数 |

- **相位错开**：用稳定键计算初始相位，例如 `crc32(device_code) % period_us`；不得使用会随增删/排序变化的 `device_index`，避免拓扑变化导致所有设备相位整体漂移。
- 细分项：`read_ms`（PLC 读）、`parse_ms`/CPU（解析与编组）、`json_ms`（序列化，**§7.4 优化前后对比**）、`redis_ms`（写 Redis）。
- 并发/背压：`inflight_jobs`、各 executor/队列深度、队列拒绝数、`stale_result_drop_count`、当前/峰值重连并发、停机未 drain job 数（§7.9）。
- 运行时：进程/线程 CPU、RSS、对象分配速率、GC pause/次数；自由线程与多进程必须用同口径比较（§7.10）。

**writer 每进程**：`write_batch_ms`、`rows_per_flush`、每 stream `XLEN`/pending、消费滞后、降级/DLQ 计数。

**Redis**：内存用量、`XLEN`、Consumer Group pending、最早未 ACK 时间、**AOF rewrite 状态、磁盘写带宽（§10）**。

**达标定义**（阈值须在压测前写死，禁止看结果后调整）：
- 所有实例 `deadline_lag_ms` 的 p99 与 p99.9 均低于约定阈值；
- deadline miss 比例低于约定上限，最大连续 miss 不超过约定次数；
- 30 分钟全量压测中，计划样本数、成功采样数、Redis 入流数与 TDengine 确认落库数可对账，**零无解释丢样**；
- stream `XLEN` 不持续增长、writer pending 可回落，AOF rewrite/磁盘尖峰期间仍满足上述指标。

## 10. 磁盘 I/O 带宽（性能因子，纳入；容量/保留单列见 §13）

> **区分两件事**：磁盘**容量与保留策略**按用户要求不展开（§13 单列）；但磁盘 **I/O 带宽与延迟**是真实性能约束，**必须纳入**——v1 把磁盘整体排除在性能外是错的。

**三处盘压**：
1. **TDengine 落盘**：305 万值/秒持续写，WAL + 落盘带宽是入库延迟的下游约束；多表批写（§7.6）减少 SQL 数但**不减少落盘字节量**。
2. **Redis AOF fsync + rewrite**（§7.5）：~228MB/s 逻辑写下 AOF 是磁盘写风暴，rewrite 期有 I/O 尖峰。
3. **同盘竞争**：若 Redis AOF、TDengine 数据、应用日志落**同一物理盘**，三者互抢 IOPS/带宽，延迟劣化。

**措施**：
- **Redis AOF 与 TDengine 数据分物理盘 / NVMe**，避免同盘竞争；日志再单独一盘或限速。
- 把**盘写带宽、fsync/flush 延迟**纳入 §9 观测项与 §8 压测判据，不能假设盘无限快。
- **拓扑 A（Linux 服务器）盘与文件系统更可控**，是优先 A 的又一理由；拓扑 B（Windows + Docker Desktop）盘 I/O 经虚拟化层，须重点实测。

**结论**：磁盘 I/O 带宽是 305 全量写能否稳的硬约束之一，与序列化、读并发并列进压测，不可省略。

## 12. 风险与未决项

1. **JSON/CPU 预算未实测校准**：§6.1 的 ~6~8 核为粗估；`json.dumps` 单价、§7.4 优化后实际值都须用 `json_ms` 实测，预算才作数。
2. **snap7 纯 Python读路径未实测**：阻塞 socket 等待可释放 GIL，但协议构造/解析仍耗 Python CPU；T、parse CPU 与线程扩展曲线共同决定读池和运行时选择。
3. **拓扑 A vs B 未定**：A（分布式，首选）需 10GbE + Linux 服务器；B（单机）余量薄、依赖序列化优化。**最终以 §8 两拓扑压测数据决定**（§5）。
4. **Redis AOF / 磁盘 I/O 未定夺**：§7.5 三方案、§10 三处盘压，须实测选 AOF 策略与盘布局。
5. **多进程共存改造量大**：仅在 C gate 失败、选 A 时实施 §7.1/§7.2；仍需提前保留估算和回退设计。
6. **stream_shard_count 调整需迁移**：加 shard 按 v0.6 §12.5 双消费迁移，不能直接改配置。
7. **跨 N 进程配置热更新**：每进程只管自己分片；设备"改了分片归属"由 Agent 路由到正确进程。
8. **Redis 单实例未获证明**：共享 SPOF + 带宽汇聚（~228MB/s）；须在 AOF rewrite 与磁盘压力下验证，未达标时当期就要调整持久化或分实例，不能只留作未来事项。
9. **多进程内存**：每进程独立常驻 + 连接池，N 进程内存线性增加；是否构成约束须在 A 路线容量测试中测 RSS，不能预先排除。
10. **SQLAlchemy frozen 崩溃根因未定**：禁用 C 扩展仍崩；先做可复现 spike。若迁移裸 aiomysql，按完整 663 行配置数据库适配层工作量估算。
11. **OPC DA 持久组风险**：需验证 handle 生命周期、断线重建、配置热更、chunk 上限和部分失败隔离；未通过前不得采用“大组每周期读取”。
12. **线程任务迟到与配置串代**：协程取消不等于线程停止；必须落实 §7.9 的不可变快照、generation gate 与 tombstone，否则热更新/删除后仍可能写入旧结果。
13. **无界背压与恢复风暴**：executor future、Redis 队列或重连任务无上限会在下游变慢时放大故障；采用单设备单 in-flight、有界队列、拒绝计数、退避+jitter和全局重连 semaphore。
14. **对象分配/GC 未入容量账**：305 万点/秒下，短命对象可能先于编码 CPU 成为瓶颈；按 §7.10 测 allocation/GC/RSS，并优化批结构和元数据复用。
15. **C 单进程故障半径**：单进程崩溃影响全部设备；验证 Agent 拉起与恢复时间，必要时使用少量自由线程进程隔离故障域。
16. **连接总预算**：collector/writer worker 增加会放大 Redis/MySQL/TDengine/PLC 连接；须设置系统级总预算与池上限，避免局部参数都合法但总量压垮服务。
17. **TDengine 宽表/批 SQL 边界未验证**：在精确生产版本上验证 1000 列、SQL 字节/表数/行数上限和部分失败语义，再确定 writer batch。
18. **日志和时钟可能扰动热路径**：逐点日志需聚合限速；调度用 monotonic，业务时间戳监控 wall clock/NTP 偏差。

## 13. 磁盘容量与保留（单列，本方案不展开）

按用户要求，磁盘**容量/保留策略**不在本方案讨论，仅记录约束以免被遗忘：
- 全量写 305×1000×100ms ≈ **2.1TB/天原始**（TDengine 压缩后数百 GB/天，须实测压缩比）。
- 需**另行扩容 + 定保留策略**，否则磁盘会**先于性能**爆。
- 与 §10 区分：§10 谈磁盘 **I/O 带宽（性能）**，本节谈**容量（存量）**，两者都真实存在、分开处理。

## 14. 结论（待实测验证，非文档可单独断言）

305×1000×100ms 全量的**验证方向成立**：指标与可复现 benchmark 先行，安全序列化优化，读/parse/写 executor 隔离与 generation 并发契约，writer 多表原子性实验，OPC 持久 Group/chunk 实验，Redis/AOF/磁盘/GC/连接预算 gate，以及 C/A 运行时的同口径分级压测。

但**能否达标不是文档能断言的**，必须满足：
1. **拓扑首选分布式（A）**：远端库 + 多采集机，把 ~6~8 核序列化摊到多台、服务器侧用 Linux 避开 Windows/Docker 损耗；228MB/s 跨网须 10GbE。**单机（B）为备选**，且**不做 §7.4 序列化优化大概率不达标**。
2. **公共核心项先行，再选运行时**：完成 §9 指标/对账、§7.4 安全序列化、§7.6 writer 实验与 §7.9 并发契约；C 通过核心 gate 才采用自由线程，否则执行 A 的多进程共存契约。OPC 持久组后置，但最终混合协议验收不可省略。
3. **以真机实测定论**：序列化（`json_ms`）、PLC 读与解析（`read_ms`/parse CPU）、Redis（命令 CPU、带宽、AOF）、writer/TDengine 原子性与落盘四项，配合 §8 分级压测的 p99/p99.9、miss 比例、最大连续 miss 与 30 分钟样本对账——**达标判据以此为准，任何“单实例足够”“C 已可生产”“155→10”结论在 gate 前均不成立**。
