# 入库模块日志入库方案（writer → system_log）

> 状态：**阶段 1 / 2 / 3 全部已实现并通过真实环境验收（2026-05-31）**；并顺带修复了 Agent 实时日志链路（见第一节、第六节）。本文档记录 writer（入库模块）运行日志进入“系统日志中心”的设计、约束、分阶段计划与最终落地结果。
> 适用读者：后续接手实现的工程师 / Codex 审查。
> 相关文档：`docs/设计/系统日志总体设计方案.md`、`docs/入库模块/入库模块代码设计逻辑.md`。

## 一、背景：为什么走 DB 中心日志，而不是 Agent 文件 tail

平台存在**两条互不相干**的日志链路，必须分清：

1. **DB 中心日志（本方案采用）**
   ```
   collector(core/system_log.py) ┐
   backend(core/log_writer.py)   ├─→ MySQL system_log 表 ─→ backend GET /api/device-monitor/log/list ─→ Vue 日志监控页 / Tauri app
   frontend-vue(POST /log/client)┘
   ```
   - collector 已通过 `SystemLogWriter` 在关键事件落库，所以“日志监控页”能看到采集模块日志。
   - **writer 目前只有 `logging.basicConfig` 控制台输出，从未写过 `system_log` 表**，所以页面上看不到 writer。

2. **Agent 文件 tail（实时日志，已于本轮修复）**
   - Agent 的 WS `/viewer/logs/{name}/tail` 读子进程控制台输出文件。**原先该文件无人写入**：Agent 的 `ProcessManager.start()` 用 `subprocess.Popen` 拉起 writer/collector 时**未重定向 stdout/stderr**，而 writer 只有 `logging.basicConfig` 控制台输出、collector 写的是另一路径，导致 tail 文件长期为空 —— app 实时面板「暂无日志」。
   - **修复（2026-05-31）**：`ProcessManager` 把子进程 stdout/stderr 重定向到 `{runtime_dir}/logs/{name}/current.log`（`stdout=文件, stderr=STDOUT, env PYTHONUNBUFFERED=1`，启动前截断，stop 时关句柄）；`LogManager.attach()` 改读同一路径（`ProcessManager.log_file()` 作唯一来源）。改动文件：`agent/app/services/process_manager.py`、`log_manager.py`、`routers/admin.py`。一处修复同时覆盖 writer 与 collector。

**结论**：最终形成**两条互补链路**——**实时日志** = Agent stdout/stderr tail → app「实时」Tab（全量控制台流，前端只保留最近 50 行省内存）；**历史日志** = writer/collector `system_log` → Backend `GET /api/device-monitor/log/list` → app「历史」Tab（结构化稀疏事件，可历史查询）。Vue 日志监控页零改动即可看 writer 历史日志。

## 二、后端接口契约（已核实，来源 `backend/app/services/log.py` / `api/routes/log.py`）

查询接口：`GET /api/device-monitor/log/list`，过滤参数为 **camelCase query 参数**：

| 参数 | 匹配方式 | 对 writer 的约束 |
| --- | --- | --- |
| `serviceName` | `system_log.service_name == ` **精确相等** | **writer 落库的 `service_name` 必须恰好为 `"writer"`**；模块细分不要放这里 |
| `type` | `system_log.log_type ==` 精确 | 用 **`storage`**（在合法集合 `{system,auth,operation,collect,storage,frontend,security,alarm}` 内，对应“存储”分类） |
| `kind` | `all` / `system` / `operation` | 查 system_log 时传 `system` 或 `all`，**不要传 `operation`** |
| `source` | `LIKE %...%` 模糊 | 放模块细分，如 `writer.main` / `writer.consumer` / `writer.tdengine` / `writer.dlq` |
| `level` | 精确 | `DEBUG/INFO/WARN/ERROR/CRITICAL` |
| `deviceCode` / `traceId` / `keyword` | 模糊 / 精确 | writer 通常 `device_code` 留空 |
| `startTime` / `endTime` | 区间 | **不传默认只查最近 24 小时**；app 拉历史需显式带时间范围 |

要点：
- 参数名是 **`serviceName`（驼峰），不是 `service_name`**。
- **DEBUG 仅在写入侧过滤**（`services/log.py` 注释明确：查询侧允许查看历史 DEBUG）。因此 DEBUG 落库门控必须由 writer 写入侧实现。

## 三、`system_log` 字段映射（writer 侧取值）

参照 `backend/app/models/log.py` 的 `SystemLog` 与 collector `config_db.write_system_log` 的口径：

| 列 | writer 取值 | 长度上限 |
| --- | --- | --- |
| `log_time` | 事件发生时间（本地时区） | datetime |
| `level` | 规范化后：`WARNING→WARN`，非法→`INFO`，合法集 `{DEBUG,INFO,WARN,ERROR,CRITICAL}` | 16 |
| `log_type` | 固定 `"storage"` | 32 |
| `source` | `writer.main` / `writer.consumer` / `writer.tdengine` / `writer.dlq` / `writer.mysql_mapper` | 64 |
| `service_name` | 固定 `"writer"` | 64 |
| `device_id` | `NULL` | — |
| `device_code` | 通常 `""`（如确有设备维度可填） | 64 |
| `point_id` | `NULL` | — |
| `host_name` | `socket.gethostname()` | 64 |
| `content` | 事件文本（**裁剪到 500**） | 500 |
| `detail_json` | 结构化详情或 `NULL` | JSON |
| `trace_id` | 通常 `""` | 64 |
| `exception_stack` | 异常堆栈或 `NULL` | TEXT(≤65535) |
| `elapsed_ms` | 耗时或 `NULL` | int |
| `create_time` | 写入时间 | datetime |

## 四、`SystemLogWriter` 设计（writer 专用，**不照抄 collector 的 asyncio 版**）

### 4.1 为什么不复用 writer 主流程的 MySQL 连接
- writer 进程是 asyncio（`asyncio.run(main())`），但 MySQL 用的是**同步 pymysql 单连接**，且在 executor 线程里被 consumer 使用（`main.py`）。
- pymysql 连接**非线程安全**；日志落库与 consumer 并发使用同一连接会撑坏协议。
- 因此日志写入器必须使用**独立的专属 pymysql 连接**。

### 4.2 结构：独立后台线程 + `queue.Queue` + 专属连接
- `emit()` 可从任意上下文（事件循环线程 / executor 线程）调用，`queue.Queue.put_nowait` 线程安全。
- 落库在独立 daemon 线程，不阻塞消费主回路。
- best-effort：队列满则丢弃；DB 异常吞掉并惰性重连；**任何情况下不得影响 writer 主流程**。

### 4.3 接口草案
- `__init__(mysql_config: dict, queue_max_size=1000)`：仅保存配置，不立即连库。
- `start()`：建立专属连接（`charset=utf8mb4, autocommit=True`）并启动后台线程；**连接失败不抛出致命错误，进入惰性重连**。
- `emit(*, level, log_type, source, content, detail_json=None, device_code="", service_name="writer", trace_id="", exception_stack=None, elapsed_ms=None) -> bool`：仅 `put_nowait`；队列满 → 节流（≥60s 一次）`logger.warning` 后丢弃。
- 后台线程循环：`q.get()` → 规范化 level → （阶段 2 起）DEBUG 门控 → 字段裁剪 → 参数化 INSERT → 异常吞掉、失败惰性重连。
- `stop(timeout)`：**投哨兵 `None` 前不得清空/丢弃队列**；后台线程需先处理完哨兵之前已入队的事件（含 `writer stopped`）再退出；`join(timeout)` 超时才放弃，最后关连接（见约束 3）。

## 五、执行约束（评审确定，实现时强制遵守）

1. `start()` 可建连接，但**连接失败必须允许惰性重连**，绝不能因日志库连接失败影响 writer 主流程。
2. `emit()` 内**禁止任何阻塞**，只能 `put_nowait`；队列满即丢，最多本地 `logger.warning` 限流提示。
3. `stop()` **投哨兵前不能直接丢弃队列**；后台线程应处理完哨兵之前已入队的事件（含 `writer stopped`）后再退出，`join` 超时才放弃；不能因 daemon 线程被直接回收而频繁丢失 `writer stopped`。
4. `content` / `detail_json` / `exception_stack` 中**明确禁止出现密码、token、连接串明文**。
5. **阶段 1 只写三类事件**：`writer started` / `writer stopped` / `startup fatal error`；**不要一开始就插 consumer / tdengine 批量事件**。
6. **DEBUG 门控阶段 1 暂不实现**（阶段 1 不产生 DEBUG）；待阶段 2 出现 DEBUG 事件时再补（读 `log_retention_policy.debug_db_enabled` / `debug_enabled_until`，带短 TTL 缓存）。

## 六、分阶段计划与落地结果

- **阶段 1（最小可见）✅ 已完成并验收**：新建 `writer/system_log.py`（独立线程 + `queue.Queue` + 专属 pymysql 连接）+ `writer/main.py` 接入，仅 emit `writer started` / `writer stopped` / `startup fatal error`。
  - `startup fatal error` 仅覆盖 **`SystemLogWriter.start()` 成功之后**的致命错误；MySQL 主连接建立之前的失败仍无法落库（详见第七节）。
  - 验收：启停 writer + 运行中杀 TDengine，`system_log` 出现 `service_name='writer'` 行，Vue 日志页 `serviceName=writer` 可查到。
- **阶段 2（关键事件插桩）✅ 已完成并验收**：在 `consumer.py` / `tdengine_writer.py` 最小插桩 6 个事件，全部**防刷库**（状态转换或 60s 节流）：
  - `writer.consumer` flush 退化(WARN，连续失败首次) / flush 恢复(INFO)；
  - `writer.dlq` 条目进 DLQ(ERROR，60s 节流) / DLQ 写入失败(ERROR，60s 节流)，由 consumer 侧 emit、不改 `dlq.py`；
  - `writer.tdengine` 重连成功(WARN，60s 节流) / 重连失败(ERROR，60s 节流)。
  - `mysql_mapper.py` 的 MySQL 失败事件**缓做**（逐条触发刷库风险，需状态化后再加）；**DEBUG 写入侧门控延后**（本阶段不产生 DEBUG 事件，按约束 6「出现 DEBUG 再补」）。
  - 验收：运行中杀/恢复 TDengine，`system_log` 出现 `degraded→recovered`、`reconnect failed→succeeded` 各一次（节流生效，无刷库）。
- **阶段 3（Tauri app 历史视图）✅ 已完成并验收**：app `WriterPage` / `CollectorPage` 右侧日志面板改为 **Tab 切换（实时 / 历史，默认实时）**。
  - 「历史」= `useModuleDbLogs(serviceName, logType?)` 调 backend `GET /log/list?serviceName=<模块>&kind=system[&type=storage]`（writer 锁 `type=storage`；collector 不锁 type）；展示组件 `ModuleDbLogPanel`（挂载拉一次 + 手动刷新）。
  - 鉴权：`Authorization: Bearer <backendToken>`；后端登录返回的 token **已带 `Bearer ` 前缀**，`backendFetch` 做规范化避免 `Bearer Bearer`（2026-05-31 修复）。401 → `logout()`。
  - 新增/改动文件：`app/src/lib/backend-client.ts`、`hooks/useModuleDbLogs.ts`、`components/ModuleDbLogPanel.tsx`、`pages/WriterPage.tsx`、`pages/CollectorPage.tsx`、`types/index.ts`；实时行数上限 `useWebSocketLog.ts` 由 5000 改 50。
- **附加：Agent 实时日志链路修复** —— 见第一节第 2 点（让「实时」Tab 真正有数据）。

### 已知后续项（本轮未做，下次再补）
- **历史视图分页**：当前固定 `pageSize=200` 一次性渲染，行数多时占内存；应改为分页/虚拟滚动（属阶段3 当初延后的「过滤 + 分页」）。
- **历史默认时间窗**：沿用后端默认**最近 24h**（不传 `startTime/endTime`）。故 writer 长时间平稳运行（无状态事件）时历史不增长属正常，非刷新 bug；collector 因事件更频繁而显得持续更新。
- `mysql_mapper.py` 失败事件插桩、DEBUG 写入侧门控。

## 七、已知缺口与启动顺序

- **MySQL 连接失败本身不可落库**：日志目标就是 MySQL，连不上时只能退化到控制台 / Agent，无法进 DB。可接受。
- **启动顺序建议**：MySQL 主连接建立成功后，**尽早 `SystemLogWriter.start()`**（在 TDengine 连接、stream scope 探测之前），使这些环节的致命错误能落库为 `startup fatal error`。
- 失败重连、MySQL 重启自愈需在实现时专门测一次。
