# 工业级设备监控系统数据库结构（v3，2026-05-23 live schema 校准）

---

## 一、数据库架构

系统当前采用 MySQL + Redis + TDengine 的分层数据架构：

| 类型 | 技术 | 用途 |
| :--- | :--- | :--- |
| 关系数据库 | MySQL 8.0+（主）/ PostgreSQL（备用） | 配置、主数据、业务规则 |
| 实时缓存 / 队列 | Redis | 最新快照、最近 N 行短窗口、待入库 Stream、WebSocket 实时推送数据源 |
| 时序数据库 | TDengine 3.0+ | 历史值、历史查询、聚合统计 |

当前统一口径：

- MySQL 负责设备、协议、点位等主数据配置
- Redis 负责 100ms 实时监控所需的最新快照、短窗口缓存，以及待入库 Stream
- TDengine 负责 500ms/1s 批量历史落库与历史查询

## 五、TDengine 当前口径

当前 TDengine 统一采用宽表历史落库模型：

```text
device_data 数据库 -> 设备类型超级表 -> 设备子表 -> 点位列
```

命名规则：

- 数据库名：固定为 `device_data`
- 超级表名：`sd{device_type}`，如 `sdqc`、`sdasc`、`sdagv`
- 子表名：与 MySQL `device.device_code` 保持一致，如 `qc100`、`asc7011`、`agv801`
- 点位列名：使用 MySQL `device_variable.td_column_name`，如 `qc1`、`asc85`、`agv100`
- TAG：当前使用 `device_code VARCHAR(32)`

当前目标 schema 示例：

```sql
CREATE DATABASE IF NOT EXISTS device_data;

CREATE STABLE IF NOT EXISTS device_data.sdqc (
    ts TIMESTAMP,
    qc1 DOUBLE,
    qc2 DOUBLE
) TAGS (
    device_code VARCHAR(32)
);

CREATE TABLE IF NOT EXISTS device_data.qc100
USING device_data.sdqc TAGS ('qc100');
```

动态点位列策略：

- writer 写入 TDengine 前以 MySQL `device_variable.td_column_name` 为事实源；
- 对每个设备类型维护一个 `sd{device_type}` 超级表；
- 首次创建超级表时尽量一次性带上当前批次全部列；
- 若超级表缺少对应点位列，则执行 `ALTER STABLE ... ADD COLUMN <td_column_name> DOUBLE`；
- 点位删除或停用不立即删除 TDengine 列，避免破坏历史查询；
- TDengine 历史宽表只保存点位数值，不再保存 `quality`。

live schema 校验（2026-05-23）：

- `SHOW device_data.STABLES`：`sdqc`、`sdasc`、`sdagv`
- `SHOW device_data.TABLES`：当前至少包含 `qc100`、`qc128`、`asc7011`、`asc7611`、`agv801`
- 旧口径 `st_qc_g001` / `st_asc_g001` / `st_agv_g001` 不存在；旧窄表口径 `qc100_30` 不再使用

当前读取口径：

- 设备树、设备列表、点位配置：读取 MySQL；
- 实时页、WebSocket：优先读取 Redis 最新快照与最近 N 行短窗口；
- 历史页、Dashboard 历史趋势：读取 TDengine 时间范围数据。

### 6.2 报警系统

为恢复 Dashboard 告警侧真实数据，本轮已将报警域从“仅保留表名规划”升级为“正式结构设计 + SQL 基线已确定”。当前设计原则：

- `alarm_record` 固定为告警历史主事实表
- `alarm_active` 固定为当前活动告警快照表
- 规则 / 字典表保留严格关联
- 事实表保留设备、点位、等级、类型等快照字段，保证历史可读性

### 6.3 用户权限

为恢复真实数据登录、角色菜单和按钮权限闭环，权限域不再只保留“表名清单”，当前已在 `backend/app/models/auth.py` 与启动 bootstrap 中固化字段、索引、约束与种子数据。当前实施口径如下：

#### 6.3.1 `sys_user`

- 主字段：`id`、`user_name`、`password_hash`、`nick_name`、`email`、`phone`、`gender`、`avatar`、`status`
- 登录态字段：`last_login_time`、`last_login_ip`
- 审计字段：`create_by`、`create_time`、`update_by`、`update_time`、`deleted`
- 约束说明：
  - `user_name` 全局唯一
  - `status` 继续兼容前端当前口径，默认使用 `1=可用`、`2=停用`
  - `deleted` 采用软删，避免影响历史授权和操作审计
- 当前首版联调实现：
  - 启动 bootstrap 时内置 `Super`、`Admin`、`User` 三个账号
  - 默认密码统一为 `123456`
  - 当前口令哈希实现为标准库 `PBKDF2-SHA256`，后续如需接入 `bcrypt` 可平滑迁移

#### 6.3.2 `sys_role`

- 主字段：`id`、`role_code`、`role_name`、`description`、`enabled`、`sort`、`create_time`、`update_time`
- 约束说明：
  - `role_code` 全局唯一
  - `enabled` 控制角色是否继续参与菜单与权限聚合
- 当前种子角色：
  - `R_SUPER`：超级管理员，拥有全部权限
  - `R_ADMIN`：业务管理员，拥有设备监控全量和用户管理权限
  - `R_USER`：监控用户，仅保留工作台 / 实时 / 历史 / 日志查看能力

#### 6.3.3 `sys_user_role`

- 作用：补齐“用户-角色”多对多关系，对齐前端 `userRoles: string[]`
- 主字段：`id`、`user_id`、`role_id`
- 约束说明：
  - 复合唯一键：`(user_id, role_id)`
  - 索引：`user_id`、`role_id`
  - 外键：分别关联 `sys_user.id` 与 `sys_role.id`

#### 6.3.4 `sys_menu`

- 主字段：`id`、`parent_id`、`name`、`path`、`component`、`title_key`、`icon`
- 菜单控制字段：`menu_type`、`link`、`is_iframe`、`keep_alive`、`is_hide`、`is_hide_tab`、`fixed_tab`、`active_path`、`is_full_page`、`sort`、`enabled`
- 约束说明：
  - `name` 全局唯一，作为后端与前端路由节点的稳定标识
  - `parent_id` 支持树结构
  - 索引：`parent_id`、`sort`
- 当前种子菜单至少覆盖：
  - 设备监控 7 页：`dashboard / driver / device / point / realtime / history / log`
  - 系统管理 3 页：`system/user`、`system/role`、`system/menu`

#### 6.3.5 `sys_permission`

- 主字段：`id`、`permission_code`、`permission_name`、`permission_type`、`menu_id`、`auth_mark`、`description`、`sort`、`enabled`
- 权限类型：
  - `page`：页面访问权限
  - `action`：按钮或操作权限
  - 预留 `api`、`data`，后续可扩展
- 约束说明：
  - `permission_code` 全局唯一
  - `menu_id` 允许为空，便于后续扩展纯 API 权限
  - 索引：`menu_id`、`permission_type`
- 当前口径：
  - `permission_code` 作为后端真实权限码，例如 `device_monitor:device:create`
  - `auth_mark` 作为前端 `v-auth / hasAuth` 直接消费的权限字符串
  - 设备监控模块默认保持 `permission_code == auth_mark`
  - 旧系统菜单示例页允许继续使用 `add / edit / delete` 这类短 `auth_mark`

#### 6.3.6 `sys_role_menu`

- 作用：控制 backend 模式下每个角色可见的菜单树
- 主字段：`id`、`role_id`、`menu_id`
- 约束说明：
  - 复合唯一键：`(role_id, menu_id)`
  - 索引：`role_id`、`menu_id`
  - 外键：分别关联 `sys_role.id` 与 `sys_menu.id`

#### 6.3.7 `sys_role_permission`

- 作用：控制角色拥有哪些页面权限、按钮权限与后续 API 权限
- 主字段：`id`、`role_id`、`permission_id`
- 约束说明：
  - 复合唯一键：`(role_id, permission_id)`
  - 索引：`role_id`、`permission_id`
  - 外键：分别关联 `sys_role.id` 与 `sys_permission.id`

#### 6.3.8 `sys_data_permission`

- 当前仅落最小骨架，不立即接入设备 / 点位 / 历史过滤
- 主字段：`id`、`role_id`、`scope_type`、`scope_value`、`enabled`
- 当前 `scope_type` 规划：
  - `all`
  - `device_group`
  - `device_type`
  - `device`
- 约束说明：
  - 索引：`role_id`、`(scope_type, scope_value)`
  - 当前首版默认三类内置角色都先写入 `all/*` 占位数据，后续再接真实业务过滤

#### 6.3.9 当前种子与启动规则

- 当 `backend` 启动且 `AUTH_AUTO_BOOTSTRAP=true` 时：
  1. 自动建表
  2. 自动写入内置角色、账号、菜单、权限
  3. 自动写入角色菜单、角色权限和数据权限占位授权
- 当前后端真实登录与权限闭环依赖这套 bootstrap 口径，不再需要单独维护 mock 登录数据
- 当前正式 SQL 基线位于：
  - `docs/数据库/sql/auth_schema_2026_04_19.sql`
  - `docs/数据库/sql/auth_seed_2026_04_19.sql`
  - `docs/数据库/sql/auth_verify_2026_04_19.sql`
  - `docs/数据库/sql/auth_migration_2026_04_19.sql`

### 6.4 日志系统

为恢复 `log/list` 真实分页查询，当前日志域固定采用“操作审计 + 系统运行”物理分表方案：

#### 6.4.1 `operation_log`

- 作用：记录“谁在什么时间做了什么”的操作审计事实
- 核心字段：
  - `id`
  - `log_time`
  - `operator_id`、`operator_name`
  - `module_name`、`action_name`
  - `level`
  - `content`
  - `detail_json`
  - `create_time`
- 扩展字段：`request_id`、`ip`、`user_agent`、`biz_type`、`biz_id`、`duration_ms`、`result_status`
- 约束说明：
  - `operator_id -> sys_user.id`，`ON DELETE SET NULL`
  - 索引：`(log_time)`、`(level, log_time)`、`(operator_id, log_time)`、`(module_name, log_time)`、`(request_id)`、`(result_status, log_time)`
- 当前口径：
  - 该表只承载用户操作审计
  - 在 `log/list` 聚合查询中统一映射为 `type = system`

#### 6.4.2 `system_log`

- 作用：记录系统、采集、存储、告警运行日志
- 核心字段：
  - `id`
  - `log_time`
  - `level`
  - `log_type`
  - `source`
  - `device_id`、`device_code`
  - `content`
  - `detail_json`
  - `trace_id`
  - `create_time`
- 扩展字段：`point_id`、`host_name`、`service_name`、`exception_stack`、`elapsed_ms`
- 约束说明：
  - `device_id -> device.id`，`ON DELETE SET NULL`
  - `point_id -> device_variable.id`，`ON DELETE SET NULL`
  - 索引：`(log_time)`、`(level, log_time)`、`(log_type, log_time)`、`(device_id, log_time)`、`(trace_id)`、`(source, log_time)`、`(service_name, log_time)`、`(device_code, log_time)`
- 当前口径：
  - `log_type` 固定首轮枚举：`system / collect / storage / alarm`
  - 与 `operation_log` 一起支撑 `GET /api/device-monitor/log/list`

#### 6.4.3 `log_retention_policy`

- 作用：保存系统日志保留策略、容量上限、清理批大小和 DEBUG 落库开关
- 当前默认策略：保留 7 天、总容量 1GB、每天 03:00 清理、每 30 分钟检查容量、单批 5000 条、DEBUG 默认不落库
- 关键字段：`enabled`、`retention_days`、`max_total_mb`、`cleanup_time`、`capacity_check_interval_minutes`、`batch_size`、`debug_db_enabled`、`debug_enabled_until`、`debug_reason`、`last_cleanup_time`、`last_cleanup_result_json`
- 当前 SQL 基线：`docs/数据库/sql/system_log_optimization_2026_05_06.sql`
- 当前 verify 脚本：`docs/数据库/sql/system_log_optimization_verify_2026_05_06.sql`

#### 6.4.4 `plc_connection_log`

- 作用：记录 PLC / 设备连接状态变化的诊断日志
- 当前 live 字段：`id`、`device_id`、`event_type`、`status`、`messsage`、`create_time`
- 约束说明：
  - `id` 为自增主键
  - 索引：`device_id`、`create_time`
- 说明：
  - 字段名当前 live schema 为 `messsage`（三连 s），文档按实际库记录；如后续修正字段名，需要同步 migration 与代码

#### 6.4.5 当前日志样本策略

- 当前正式 SQL 基线与报警表共用以下脚本：
  - `docs/数据库/sql/alarm_log_schema_2026_04_20.sql`
  - `docs/数据库/sql/alarm_log_seed_2026_04_20.sql`
  - `docs/数据库/sql/alarm_log_verify_2026_04_20.sql`
  - `docs/数据库/sql/alarm_log_migration_2026_04_20.sql`
- 当前首轮联调样本策略：
  - `operation_log` 至少 10 条
  - `system_log` 至少 20 条
- 当前查询口径：
  - `operation_log + system_log` 联合查询
  - 筛选维度固定为 `keyword / startTime / endTime / level / type`
  - 排序固定按 `log_time DESC`
- 当前 seed 重复执行时，通过 `request_id` / `trace_id` 稳定键避免重复写入日志样本

## 九、关键结论

| 项目 | 当前结论 |
| :--- | :--- |
| MySQL 边界 | 当前承载配置、主数据、权限、报警事实、系统日志与日志策略 |
| TDengine 边界 | 当前承载历史时序宽表；实时数据由 Redis 承载 |

| 告警模型 | `alarm_record` 负责历史，`alarm_active` 负责当前活动告警快照 |
| 日志模型 | `operation_log` 负责操作审计，`system_log` 负责系统运行日志，`log_retention_policy` 负责清理与 DEBUG 落库策略 |
| 约束策略 | 已补齐主数据与权限域约束；报警 / 日志域已完成正式结构设计与 SQL 基线；日志策略、索引与权限已完成 2026-05-06 增量优化 |
