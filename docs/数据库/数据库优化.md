## 二、问题清单

### 2.1 MySQL 问题

#### 问题 M-001：device.status 字段语义模糊

| 项目 | 内容 |
|------|------|
| **问题描述** | `device` 表中 `enable` 和 `status` 两个字段职责重叠，`status` 语义不清晰 |
| **当前定义** | `enable TINYINT` - 是否启用；`status TINYINT` - 当前状态（无明确枚举） |
| **影响范围** | 前端设备状态展示、后端状态判断逻辑 |
| **置信度** | ⭐⭐⭐⭐⭐ 高（字段定义明确存在歧义） |
| **状态** | ⏸️ 未进行（通过设备连接判断即可，无需修改） |

**结论**：设备状态通过连接判断实现，`status` 字段由运行时从 TDengine 最新采集时间推断，无需在 MySQL 持久化。此问题暂不处理。

#### 问题 M-002：device_variable 缺少 unit 字段

| 项目 | 内容 |
|------|------|
| **问题描述** | 点位表缺少计量单位字段，前端展示数值时无单位信息 |
| **当前定义** | 无 `unit` 字段 |
| **影响范围** | 前端实时监控、历史数据展示、告警内容生成 |
| **置信度** | ⭐⭐⭐⭐⭐ 高（功能缺失明确） |
| **实施状态** | 🔄 已完成结构落地（`unit_dict` / `unit_id` 已入库，待查询链路补单位输出） |

**可实施计划（推荐）**

> 结论：不直接在现有点位表上增加自由文本 `unit`，而是统一落 `unit_dict`，并将 `unit_id` 作为公共字段同时增加到 `device_variable` 与 `template_variable`。`unit_id` 允许为空，不做必填。

**实施步骤：**

1. 新建 `unit_dict` 计量单位字典表，写入首批标准单位种子。
2. 在 M-006 模板化实施时，为 `device_variable` 与 `template_variable` 同步增加 `unit_id` 外键，不再使用字符串单位。
3. 迁移现有点位定义时，按 `var_seq / var_name / 业务分类` 回填单位映射；没有单位的点位直接保留 `NULL`。
4. 对外查询通过 JOIN 输出 `unit_symbol`，前端仍拿到简单的单位字符串，不增加接口复杂度。
5. `BOOL` 等开关量可映射到 `BOOL` 字典项，也可在业务表中保持 `unit_id=NULL`，两者都不影响保存。

**DDL 参考：**

```sql
-- 新增单位数据表
CREATE TABLE unit_dict (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT  COMMENT '主键ID',
    unit_code       VARCHAR(20) NOT NULL               COMMENT '单位编码，如 TEMP_C、SPEED_M_S、PRESSURE_MPA',
    unit_symbol     VARCHAR(20) NOT NULL               COMMENT '单位符号，如 ℃、m/s、MPa、rpm',
    unit_name       VARCHAR(50) NOT NULL               COMMENT '单位名称，如 摄氏度、米每秒、兆帕',
    unit_category   VARCHAR(20) DEFAULT ''             COMMENT '单位类别，如 温度、速度、压力',
    description     VARCHAR(255) DEFAULT ''            COMMENT '说明',
    create_time     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP  COMMENT '创建时间',
    
    UNIQUE KEY uk_unit_code (unit_code),
    UNIQUE KEY uk_unit_symbol (unit_symbol)
) COMMENT '计量单位字典表';

-- 初始数据
INSERT INTO unit_dict (unit_code, unit_symbol, unit_name, unit_category) VALUES
('TEMP_C', '℃', '摄氏度', '温度'),
('TEMP_K', 'K', '开尔文', '温度'),
('SPEED_M_S', 'm/s', '米每秒', '速度'),
('SPEED_RPM', 'rpm', '转每分钟', '速度'),
('PRESSURE_MPA', 'MPa', '兆帕', '压力'),
('PRESSURE_KPA', 'kPa', '千帕', '压力'),
('LENGTH_M', 'm', '米', '长度'),
('LENGTH_MM', 'mm', '毫米', '长度'),
('WEIGHT_T', 't', '吨', '重量'),
('WEIGHT_KG', 'kg', '千克', '重量'),
('PERCENT', '%', '百分比', '无量纲'),
('BOOL', '', '布尔值', '开关量');

-- 两张点位表同步增加单位关联（模板化方案实施时）
ALTER TABLE device_variable
ADD COLUMN unit_id BIGINT DEFAULT NULL COMMENT '关联单位ID，允许为空' AFTER var_bit;

ALTER TABLE device_variable
ADD CONSTRAINT fk_device_variable_unit FOREIGN KEY (unit_id) REFERENCES unit_dict(id);

ALTER TABLE template_variable
ADD COLUMN unit_id BIGINT DEFAULT NULL COMMENT '关联单位ID，允许为空' AFTER var_bit;

ALTER TABLE template_variable
ADD CONSTRAINT fk_template_variable_unit FOREIGN KEY (unit_id) REFERENCES unit_dict(id);
```

**方案影响分析：**

- **数据库影响**
  - 新增 `unit_dict` 表，低风险、无破坏性。
  - M-006 落地时需要在两张点位表同步增加 `unit_id` 外键。
- **后端影响**
  - 点位列表、实时值、历史值、告警文案需要补单位 JOIN 映射。
  - 不建议把单位解析逻辑放前端，统一由后端输出。
- **前端影响**
  - 页面字段基本不变，只是原来无单位的数值后面可追加标准单位。
- **数据迁移影响**
  - 需要一次性梳理首批模板点位的单位映射，工作量中低。
  - 没有单位的点位可直接保持 `NULL`，无需强行补齐。
  - 若历史告警内容已经固化文字，不需要回刷历史记录。

**方案置信度：⭐⭐⭐⭐⭐ 高**

- 原因 1：单位缺失是明确功能缺口，不是推测性优化。
- 原因 2：字典表方案与 M-006 模板化天然匹配，长期维护成本最低。
- 原因 3：对现有运行链路侵入小，优先级适合前置落地。

#### 问题 M-003：device_variable.var_address 冗余

| 项目 | 内容 |
|------|------|
| **问题描述** | `var_address` 与 `io_type + var_offset + var_bit` 存在推导关系，可能不一致 |
| **当前定义** | `io_type` + `var_offset` + `var_bit` + `var_address` 四字段并存 |
| **影响范围** | PLC 地址解析、采集配置生成 |
| **置信度** | ⭐⭐⭐ 中（推导关系取决于 PLC 协议类型） |
| **实施状态** | 📌 计划中（与 M-006 联动实施） |

**可实施计划（分阶段收口，推荐）**

> 结论：本轮不直接删除任何地址字段，而是先明确“单一真源”，再在模板化迁移中逐步收口。推荐将 `var_address` 保留为兼容展示字段，`io_type + var_offset + var_bit` 作为结构化解析字段。

**实施步骤：**

1. 在模板化迁移前，先写地址校验脚本，扫描现有 `device_variable` 中四字段是否一致。
2. 形成协议级地址解析规则：
   - `SNAP7 / GE SRTP / MODBUS` 等协议分别明确 `var_address -> io_type / offset / bit` 的解析方式。
3. 模板化后在 `template_variable` 与 `device_variable` 中继续保留结构化字段，并把 `var_address` 定义为兼容输出字段。
4. 对外统一由后端返回 `var_address`，避免前后端或采集脚本各自拼接地址。
5. 等 collector 和后台查询全部改为使用结构化字段后，再评估是否将 `var_address` 改为生成列或只读字段。

**推荐约束策略：**

- 短期：保留四字段，但增加校验脚本与导入校验，禁止新数据继续写出不一致记录。
- 中期：collector 内部地址构建只依赖结构化字段。
- 长期：`var_address` 仅作为展示/兼容字段，不再作为主配置输入。

**方案影响分析：**

- **数据库影响**
  - 首轮无需删除列，风险较低。
  - 需要补充校验脚本和后续模板表字段约束。
- **采集侧影响**
  - collector 的地址解析逻辑需要统一，不再允许不同模块各自拼接地址。
- **后端影响**
  - 查询层建议统一返回 `var_address`，减少前后端各自拼接。
- **数据迁移影响**
  - 需要对历史点位做一次地址一致性巡检，可能发现少量脏数据需要人工确认。

**方案置信度：⭐⭐⭐ 中**

- 原因 1：是否“完全冗余”高度依赖具体协议和地址语法。
- 原因 2：删除字段风险高，但“先校验、再收口”的分阶段实施可控。
- 原因 3：该项应作为 M-006 的配套治理，不建议单独激进推进。

| 项目 | 内容 |
|------|------|
| **问题描述** | 系统日志表无 TTL 策略，数据无限增长 |
| **当前定义** | 已新增 `log_retention_policy` 策略表，默认 7 天 + 1GB，DEBUG 默认不落库 |
| **影响范围** | 日志页面查询性能、磁盘空间 |
| **置信度** | ⭐⭐⭐⭐⭐ 高（日志增长是确定的） |

**当前落地状态（2026-05-06）：**

- 已执行 `docs/数据库/sql/system_log_optimization_2026_05_06.sql` 到本机 `device_watch`。
- 已新增 `log_retention_policy`，保存保留天数、容量上限、清理时间、检查间隔、批大小和 DEBUG 落库开关。
- 已补 `operation_log(request_id)`、`operation_log(result_status, log_time)`、`system_log(source, log_time)`、`system_log(service_name, log_time)`、`system_log(device_code, log_time)`。
- 已新增日志导出、清理、策略、DEBUG 权限，并按 `R_USER/R_ADMIN/R_SUPER` 完成数据库授权。
- 清理执行仍建议放在 backend 应用层调度，数据库负责保存策略和事实日志。

**历史建议方案：**

```sql
-- 方案 A：MySQL 事件调度器自动清理（推荐）
CREATE EVENT IF NOT EXISTS evt_cleanup_system_log
ON SCHEDULE EVERY 1 DAY
STARTS '2026-04-23 03:00:00'
DO 
  DELETE FROM system_log 
  WHERE log_time < NOW() - INTERVAL 30 DAY
  LIMIT 10000;  -- 分批删除，避免锁表

-- 方案 B：应用层定时任务清理
-- 在 backend 中增加定时任务，每天凌晨执行清理

-- 方案 C：表分区 + 删分区（性能最优）
ALTER TABLE system_log PARTITION BY RANGE (TO_DAYS(log_time)) (
    PARTITION p202604 VALUES LESS THAN (TO_DAYS('2026-05-01')),
    PARTITION pmax VALUES LESS THAN MAXVALUE
);
-- 清理时直接 DROP PARTITION p202604
```

**推荐方案**：方案 A，简单有效，对现有结构无侵入。

#### 问题 M-006：同类设备点位大量重复（重点）

| 项目 | 内容 |
|------|------|
| **问题描述** | 同类型设备（如 121 台 ASC）具有大量相同点位定义，每台设备独立存储造成冗余 |
| **当前结构** | 每个设备-点位组合一条记录，150 设备 × 100 点位 = 15,000 条记录 |
| **影响范围** | 存储空间、点位配置维护效率、一致性保证 |
| **置信度** | ⭐⭐⭐⭐⭐ 高（同类设备点位定义必然重复） |
| **实施状态** | 🔄 已完成 schema / migration 落地（待模板抽取与显式重同步验证） |

**场景分析：**

```
当前结构：
device_variable
├── qc100_30        (device_id=991001, var_seq=30, var_address=%I101.0)
├── qc101_30        (device_id=991002, var_seq=30, var_address=%I101.0)  ← 冗余
├── qc102_30        (device_id=991003, var_seq=30, var_address=%I101.0)  ← 冗余
└── ... 28 台 QC，相同点位定义重复 28 次

ASC 更严重：121 台设备，相同点位定义重复 121 次
```

**推荐方案：点位模板化（同构模板版）**

> **设计原则**：`template_variable` 与当前 `device_variable` 保持业务字段同构；运行时主表继续使用 `device_variable`，模板负责“标准定义 + 首次应用 + 显式重同步”。
>
> **首轮目标**：优先解决维护冗余，不在第一阶段重构成“设备差异表 + 运行时展开”。
>
> **性能判断**：`device_variable` 即使增长到约 100 万行，只要索引仍围绕 `device_id`、`id`、`(device_id, var_seq)`、`(device_id, var_address)` 设计，MySQL 配置表性能不是当前首要瓶颈。

**完整表结构设计：**

```sql
-- ============================================
-- 1. 点位模板主表
-- ============================================
CREATE TABLE variable_template (
    id                          BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '主键ID',
    template_code               VARCHAR(50) NOT NULL COMMENT '模板编码，如 QC_STD_V1',
    template_name               VARCHAR(100) NOT NULL COMMENT '模板名称',
    device_type_id              BIGINT NOT NULL COMMENT '设备类型ID，关联 device_type.id',
    version_no                  INT NOT NULL DEFAULT 1 COMMENT '模板版本号',
    enabled                     TINYINT NOT NULL DEFAULT 1 COMMENT '是否启用',
    description                 VARCHAR(255) NOT NULL DEFAULT '' COMMENT '模板说明',
    create_user                 VARCHAR(20) DEFAULT NULL COMMENT '创建人',
    create_time                 DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_user                 VARCHAR(20) DEFAULT NULL COMMENT '更新人',
    update_time                 DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',

    UNIQUE KEY uq_variable_template_template_code (template_code),
    KEY idx_variable_template_device_type_id (device_type_id),
    KEY idx_variable_template_enabled (enabled),
    CONSTRAINT fk_variable_template_device_type FOREIGN KEY (device_type_id) REFERENCES device_type(id)
) COMMENT '点位模板主表';

-- ============================================
-- 2. 模板点位表（与 device_variable 同构）
-- ============================================
CREATE TABLE template_variable (
    id                          BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '主键ID',
    template_id                 BIGINT NOT NULL COMMENT '模板ID，关联 variable_template.id',
    var_seq                     INT NOT NULL COMMENT '点位序号，纯序号；TDengine 子表名由 device_code + _ + var_seq 派生',
    var_name                    VARCHAR(50) NOT NULL COMMENT '变量名称',
    io_type                     VARCHAR(10) NOT NULL COMMENT '内存区域类型',
    var_type                    VARCHAR(20) NOT NULL COMMENT '数据类型',
    var_address                 VARCHAR(20) NOT NULL COMMENT '原始地址',
    var_offset                  INT DEFAULT NULL COMMENT '地址偏移',
    var_bit                     INT DEFAULT NULL COMMENT '位偏移',
    unit_id                     BIGINT DEFAULT NULL COMMENT '单位ID，允许为空',
    description                 VARCHAR(255) DEFAULT NULL COMMENT '描述',
    scan_rate                   INT DEFAULT NULL COMMENT '采集周期（ms）',
    is_alarm                    TINYINT NOT NULL COMMENT '是否报警',
    is_storage                  TINYINT NOT NULL COMMENT '是否存储历史',
    create_user                 VARCHAR(20) DEFAULT NULL COMMENT '创建人',
    create_time                 DATETIME DEFAULT NULL COMMENT '创建时间',
    update_user                 VARCHAR(20) DEFAULT NULL COMMENT '更新人',
    update_time                 DATETIME DEFAULT NULL COMMENT '更新时间',

    UNIQUE KEY uq_template_variable_template_var_seq (template_id, var_seq),
    UNIQUE KEY uq_template_variable_template_var_address (template_id, var_address),
    KEY idx_template_variable_template_id (template_id),
    KEY idx_template_variable_scan_rate (scan_rate),
    KEY idx_template_variable_is_alarm (is_alarm),
    KEY idx_template_variable_unit_id (unit_id),
    CONSTRAINT fk_template_variable_template FOREIGN KEY (template_id) REFERENCES variable_template(id) ON DELETE CASCADE,
    CONSTRAINT fk_template_variable_unit FOREIGN KEY (unit_id) REFERENCES unit_dict(id) ON DELETE SET NULL
) COMMENT '模板点位表（与 device_variable 业务字段同构）';

-- ============================================
-- 3. 设备表增加模板绑定元数据
-- ============================================
ALTER TABLE device
ADD COLUMN template_id BIGINT DEFAULT NULL COMMENT '当前绑定模板ID' AFTER type_id,
ADD COLUMN template_last_sync_version INT DEFAULT NULL COMMENT '最后处理过的模板版本号' AFTER scan_cycle,
ADD COLUMN template_sync_time DATETIME DEFAULT NULL COMMENT '最近一次模板同步时间' AFTER template_last_sync_version;

-- ============================================
-- 4. 设备点位表增加公共扩展字段
-- ============================================
ALTER TABLE device_variable
ADD COLUMN var_seq INT DEFAULT NULL COMMENT '点位序号，对应 TDengine var_seq' AFTER device_id,
ADD COLUMN unit_id BIGINT DEFAULT NULL COMMENT '单位ID，允许为空' AFTER var_bit;
```

**数据模型关系图：**

```text
device_type      1 ---- n  variable_template
variable_template 1 ---- n template_variable
device           n ---- 1  variable_template
device           1 ---- n  device_variable

说明：
- template_variable = 标准点位定义
- device_variable   = 设备实际运行点位快照
- 首轮运行查询继续读 device_variable
```

**模板生命周期（首轮固定口径）：**

1. **模板创建**
   - 默认推荐从 1 台“标准设备”的 `device_variable` 抽取模板
   - 也允许手工录入模板头和模板点位
2. **设备绑定模板**
   - 只记录 `device.template_id`
   - 不自动改写已有 `device_variable`
3. **首次应用模板**
   - 若设备暂无点位，则将 `template_variable` 批量复制到 `device_variable`
   - 复制时保留模板中的 `var_seq`、地址、采集参数、告警标记、`unit_id`
4. **显式重同步**
   - 模板变更后，不做自动跟随
   - 由后台显式触发“同步模板到设备”
5. **默认同步算法**
   - 匹配键：`var_seq`
   - 模板有、设备无：插入
   - 模板有、设备有：不覆盖
   - 设备有、模板无：不删除

**方案影响分析：**

- **数据库影响**
  - 新增 `unit_dict`、`variable_template`、`template_variable`、`cross_db_task`。
  - `device` 增加模板绑定字段，`device_variable` 增加公共扩展字段 `var_seq`、`unit_id`。
- **采集侧影响**
  - 首轮仍读取 `device_variable`，不需要切换到模板展开视图。
  - 后续只需逐步把 TDengine 点位标识统一到 `var_seq`。
- **后端影响**
  - 现有点位读取接口结构可保持不变。
  - 需新增模板抽取、模板首次应用、显式重同步等后台能力，但不是首轮联调阻塞项。
- **前端影响**
  - 点位管理、实时、历史页面首轮无需因为模板化改接口结构。
  - 模板管理 UI 可后续追加，不影响当前数据库基线落地。
- **数据迁移影响**
  - 首轮不追求物理去重，不会把 `device_variable` 改造成差异表。
  - 数据风险主要来自模板抽取是否准确，而不是运行时查询切换。

**方案置信度：⭐⭐⭐⭐⭐ 高**

- 原因 1：该方案保住了当前 `device_variable` 主链路，改造面最可控。
- 原因 2：它优先解决“维护冗余”，更符合当前项目阶段，而不是为极致去重过早重构。
- 原因 3：`unit_id`、`var_seq`、模板版本、显式同步都能在这套结构上平滑落地。

### 2.2 TDengine 问题

#### 问题 T-001：缺少数据质量标记

| 项目 | 内容 |
|------|------|
| **问题描述** | 当前 `value` 只有数值，无法区分正常值、采集失败、传感器异常等情况 |
| **当前定义** | `ts TIMESTAMP, value DOUBLE` |
| **影响范围** | 历史数据分析、告警判断、数据质量统计 |
| **置信度** | ⭐⭐⭐⭐⭐ 高（工业场景数据质量是核心关注点） |

**数据质量标记来源：**

| 质量码 | 名称 | 来源说明 |
|--------|------|----------|
| 0 | Good（正常） | PLC 通讯正常，值在有效范围内 |
| 1 | Bad（通讯失败） | PLC 连接断开、超时、协议错误 |
| 2 | Uncertain（可疑） | 值越界、传感器漂移、数据异常 |
| 3 | Timeout（超时） | 采集周期内未收到响应 |
| 4 | Overflow（越界） | 值超出预设的上下限范围 |

**数据质量判断时机：**

```
┌─────────────────────────────────────────────────────────────────┐
│                        采集服务流程                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   PLC 请求 ──► 连接成功？ ──否──► quality = 1 (Bad)            │
│                 │                                               │
│                 ▼ 是                                            │
│                                                                 │
│   读取数据 ──► 响应超时？ ──是──► quality = 3 (Timeout)        │
│                 │                                               │
│                 ▼ 否                                            │
│                                                                 │
│   解析数据 ──► 解析失败？ ──是──► quality = 1 (Bad)            │
│                 │                                               │
│                 ▼ 成功                                          │
│                                                                 │
│   值校验 ──► 越限？ ──是──► quality = 4 (Overflow)             │
│               │                                                 │
│               ▼ 正常                                            │
│                                                                 │
│   写入 TDengine ──► ts, value, quality = 0 (Good)              │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**建议方案：**

```sql
-- 方案 A：增加质量枚举字段（推荐）
CREATE STABLE qc.qc100_v2 (
    ts TIMESTAMP,
    value DOUBLE,
    quality TINYINT DEFAULT 0  -- 0=Good, 1=Bad, 2=Uncertain, 3=Timeout, 4=Overflow
) TAGS (var_seq INT);

-- 质量码定义（参考 OPC UA 标准）
-- 0x00 (0)  = Good - 正常
-- 0x01 (1)  = Bad - 通讯失败
-- 0x02 (2)  = Uncertain - 值可疑（如传感器漂移）
-- 0x04 (4)  = Timeout - 采集超时
-- 0x08 (8)  = Overflow - 值越界

-- 方案 B：利用 IEEE 754 NaN 表示异常
-- value = NaN 表示采集失败，无需额外字段
-- 优点：无存储开销
-- 缺点：无法区分失败原因
```

**推荐方案**：方案 A，增加 `quality` 字段，符合工业 OPC UA 标准。质量值由采集服务在数据采集过程中根据通讯状态和值校验结果生成。

#### 问题 T-002：子表命名依赖 device_code，编码变更风险

4. 将“设备改编码”定义为迁移型操作：新建设备、迁移配置、停用旧设备，而不是原地 UPDATE。

- **数据库影响**

- **后端影响**
  - 设备新增/编辑接口要区分“首次写入”和“后续修改”。

- **前端影响**
  - 设备编辑页中的 `device_code` 应显示为只读或禁用态。
  - 若保留“修改编码”入口，需改成引导式迁移而非原地编辑。
- **运维影响**
  - 历史 TDengine 表无需改名，避免批量重命名和停机风险。
  - 现场如果已形成“随手改编码”习惯，需要提前宣贯新规则。

**方案置信度：⭐⭐⭐⭐⭐ 高**

- 原因 1：当前项目里 `device_code` 已参与 TDengine 命名，改成不可变规则是最小代价方案。
- 原因 2：相比额外引入 `tdengine_stable_name`，实施复杂度和理解成本都更低。
- 原因 3：这项约束还能为 T-005/T-006 的 TAG 简化提供稳定前提。

**方案置信度：⭐⭐⭐⭐⭐ 高**

  - 该项依赖 M-006 模板化先明确模板点位主键体系。

**方案置信度：⭐⭐⭐⭐ 高**

- 原因 1：`variable_id` 与子表名不对应，确实增加了认知和排障成本。
- 原因 2：`var_seq` 与模板化方案天然耦合，长期一致性更好。
- 原因 3：主要风险不在方向，而在历史迁移和模板治理，需要按阶段推进。

### 2.3 跨库一致性问题

#### 问题 C-001：MySQL 与 TDengine 无事务保证

| 项目 | 内容 |
|------|------|
| **问题描述** | 双库操作无分布式事务，可能出现 MySQL 成功、TDengine 失败的数据不一致 |
| **影响范围** | 设备删除、设备编码变更、点位删除 |
| **置信度** | ⭐⭐⭐ 中（取决于操作频率和失败概率） |
| **实施状态** | 🔄 任务表已落地（待 worker / 重试链路接入） |

**可实施计划（最小补偿版，推荐）**

```python
# 决策：不做分布式事务，改为 MySQL 事务 + 补偿任务表 + 异步执行器

# Step 1: 业务事务内同时写 MySQL 数据和补偿任务
async def delete_device(device_id: int):
    async with mysql.transaction():
        await mysql.execute(
            "UPDATE device SET deleted=1, update_time=NOW() WHERE id=?",
            device_id,
        )
        task_id = await mysql.insert(
            """
            INSERT INTO cross_db_task
            (task_no, biz_type, biz_id, action_type, payload_json, status, retry_count, next_retry_time)
            VALUES (?, 'device', ?, 'cleanup_td_device', ?, 'pending', 0, NOW())
            """,
            gen_task_no(),
            device_id,
            json.dumps({"device_id": device_id}),
        )

    # 事务提交后异步触发执行
    await task_queue.enqueue("run_cross_db_task", task_id=task_id)


# Step 2: 异步执行器负责调用 TDengine
async def run_cross_db_task(task_id: int):
    task = await mysql.fetch_one("SELECT * FROM cross_db_task WHERE id=?", task_id)
    try:
        await tdengine.cleanup_device(task.payload_json["device_id"])
        await mysql.execute(
            "UPDATE cross_db_task SET status='success', update_time=NOW() WHERE id=?",
            task_id,
        )
    except Exception as exc:
        await mysql.execute(
            """
            UPDATE cross_db_task
            SET status='retry',
                retry_count = retry_count + 1,
                last_error = ?,
                next_retry_time = DATE_ADD(NOW(), INTERVAL 10 MINUTE),
                update_time = NOW()
            WHERE id = ?
            """,
            str(exc),
            task_id,
        )


# Step 3: 定时巡检补偿失败任务和孤儿数据
async def reconcile_cross_db_task():
    await task_queue.enqueue("scan_retry_tasks")
    await task_queue.enqueue("scan_orphan_td_tables")
```

**配套表建议：**

```sql
CREATE TABLE cross_db_task (
    id              BIGINT PRIMARY KEY AUTO_INCREMENT COMMENT '主键ID',
    task_no         VARCHAR(64) NOT NULL COMMENT '任务号',
    biz_type        VARCHAR(32) NOT NULL COMMENT '业务类型，如 device/variable/template',
    biz_id          BIGINT NOT NULL COMMENT '业务主键ID',
    action_type     VARCHAR(64) NOT NULL COMMENT '动作类型，如 cleanup_td_device/rebuild_td_point',
    payload_json    JSON NOT NULL COMMENT '执行参数',
    status          VARCHAR(20) NOT NULL DEFAULT 'pending' COMMENT '任务状态 pending/running/retry/success/failed',
    retry_count     INT NOT NULL DEFAULT 0 COMMENT '重试次数',
    next_retry_time DATETIME DEFAULT NULL COMMENT '下次重试时间',
    last_error      VARCHAR(1000) DEFAULT NULL COMMENT '最近一次错误信息',
    create_time     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    update_time     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',

    UNIQUE KEY uk_task_no (task_no),
    KEY idx_biz (biz_type, biz_id),
    KEY idx_status_retry (status, next_retry_time)
) COMMENT '跨库补偿任务表';
```

**实施步骤：**

1. 先覆盖三类高风险场景：设备删除、点位删除、TDengine 重建/补数。
2. 在 MySQL 业务事务中同步写入 `cross_db_task`，确保“要补偿什么”不会丢。
3. 事务提交后由异步 worker 执行 TDengine 动作，成功后回写任务状态。
4. 增加定时巡检任务，重试 `retry/failed` 状态任务，并补扫孤儿 TD 表。
5. 对管理后台补一个补偿任务查询页或日志入口，便于人工处理长期失败任务。

**方案影响分析：**

- **数据库影响**
  - MySQL 新增一张轻量任务表，改动集中且可控。
  - 不引入分布式事务组件，对现有数据库部署影响最小。
- **后端影响**
  - 删除设备、删除点位、重建点位等双库写操作要统一改走补偿框架。
  - 需要新增 worker、重试策略、失败告警或审计日志。
- **运维影响**
  - 运维可以通过任务表直接看到失败原因和重试状态，可观测性明显提升。
  - 需要约定失败任务的人工兜底流程，避免长期堆积。
- **一致性收益**
  - 无法做到强一致，但可把“不一致”从隐性问题变成显式、可追踪、可补偿的问题。
  - 对当前项目来说，这是比引入分布式事务更现实的实现路径。

**方案置信度：⭐⭐⭐⭐ 较高**

- 原因 1：双库场景下用补偿任务替代分布式事务，是成熟且符合当前体量的做法。
- 原因 2：最小补偿版先覆盖高风险操作，投入产出比高。
- 原因 3：真正的难点在工程落地和监控治理，而不是方案本身。
