# TDengine 写入压测优化建议

> 日期：2026-05-18  
> 范围：`collector/scripts/tdengine_write_benchmark.py` 对 `qc`、`asc`、`agv` 三库 304000 个子表的 100ms 写入压测  
> 当前结论：`stmt2-existing` 相比上一轮 `stmt2` 有小幅优化，但系统仍远未达到 304000 子表 100ms 全量写入目标。

---

## 一、两次压测对比

### 1. 压测对象

| 项目 | 数值 |
|------|------|
| 写入模式（上一轮） | `stmt2`，`INSERT INTO ? USING stable TAGS (?) VALUES ...` |
| 写入模式（本轮） | `stmt2-existing`，`INSERT INTO stable (tbname, ts, value, quality) VALUES ...` |
| 目标子表数 | 304000 |
| QC 子表数 | 28000 |
| ASC 子表数 | 121000 |
| AGV 子表数 | 155000 |
| 目标频率 | 每 100ms 一轮 |
| 理论目标吞吐 | 3040000 rows/s |

### 2. 结果汇总

| 指标 | 上一轮 `stmt2` | 本轮 `stmt2-existing` | 变化 |
|------|----------------|------------------------|------|
| 统计时长 | 约 61.4s | 约 61.7s | 基本一致 |
| 总 affected | 4471250 | 4925250 | +10.15% |
| 按总量折算平均 rows/s | 72822 | 79826 | +9.62% |
| 日志行平均 rows/s | 81225 | 86912 | +7.00% |
| 最高瞬时 rows/s | 254481 | 178428 | 下降 |
| 最大 max_lag_ms | 11877ms | 9294ms | -21.75% |
| 平均 max_lag_ms | 5307ms | 5131ms | -3.31% |
| errors | 0 | 0 | 无变化 |

### 3. 判断

`stmt2-existing` 有优化，主要体现在：

- 总写入量提升约 10%。
- 最大积压从约 11.9s 降到约 9.3s。
- 两轮均无写入错误，说明瓶颈不是失败重试或连接异常。

但优化幅度有限：

- 当前平均吞吐约 8 万 rows/s。
- 目标吞吐为 304 万 rows/s。
- 当前吞吐只有目标的约 2.6%。
- `max_lag_ms` 仍是秒级，说明无法稳定维持 100ms 周期。

结论：本轮代码层面的“预建表 + 不带 TAG 参数绑定”方向正确，但不是主瓶颈。主瓶颈更可能在 TDengine 数据库分片、写入内存、容器资源和压测目标规模本身。

置信度：高。

## 二、已确认的现状

### 1. TDengine 容器资源

当前 Docker 容器没有显式 CPU / 内存限制：

```text
NanoCpus=0
CpuQuota=0
Memory=0
```

但 Docker Desktop VM 可用资源约为：

```text
CPUs=16
TotalMemory≈7.6GiB
```

判断：

- 当前不是容器被 `--cpus` 限死。
- 但 Docker Desktop 总内存只有约 8GB，后续提高 `VGROUPS` 和 `BUFFER` 后会明显偏紧。

置信度：高。

### 2. 当前数据库参数

三个业务库当前均为：

```sql
BUFFER 16
PAGES 128
VGROUPS 2
WAL_LEVEL 1
WAL_FSYNC_PERIOD 3000
CACHEMODEL 'none'
STT_TRIGGER 2
```

当前每库表/vgroup 粗算：

| 库 | 子表数 | VGROUPS | 表/vgroup |
|----|--------|---------|-----------|
| qc | 28000 | 2 | 14000 |
| asc | 121000 | 2 | 60500 |
| agv | 155000 | 2 | 77500 |

官方高性能写入文档建议合理设置 `vgroups`，避免太少导致性能无法释放；在硬件充足时，每个 vgroup 的表数控制在 10000 以内效果更好。

本项目 ASC/AGV 当前明显超过该建议。

置信度：很高。

## 三、官方依据摘录

本节仅列本次判断直接用到的官方文档口径。

### 1. 参数绑定

官方说明参数绑定能减少 SQL 解析、复用预编译结果、降低网络开销，并推荐用于数据插入。

本地文档：

```text
docs/tdengine_docs_en/07-develop/05-stmt.md
```

关键点：

- 参数绑定减少语法解析。
- SQL 结构首次确定后，后续只替换参数。
- 对大量类似插入尤其有效。
- 子表已存在时，不带 TAG 的写法更有利于性能。

### 2. 批量写入与多线程

官方高性能写入文档建议：

- 尽量提高单次写入的数据量。
- 多线程写入在达到系统瓶颈前能提高吞吐。
- 每个写线程使用独立连接，减少连接资源竞争。
- 预创建子表，避免写入时检查或自动建表。
- 参数绑定比原始 SQL 写入更高效。
- 写入同一子表的数据应按时间戳升序提交。

本地文档：

```text
docs/tdengine_docs_en/07-develop/15-high.md
```

### 3. VGROUPS 与 BUFFER

官方高性能写入文档说明：

- `vgroups` 太少会无法充分释放系统性能。
- `vgroups` 太多会产生资源竞争。
- 建议根据磁盘 I/O、CPU 能力和表数合理设置。
- `buffer` 是 vnode 写入内存，适当增大可以缓存更多数据并提升批量刷盘效率。

本地文档：

```text
docs/tdengine_docs_en/07-develop/15-high.md
docs/tdengine_docs_en/08-operation/02-planning.md
```

### 4. WAL

官方灾备文档说明：

- `wal_level=1`：写 WAL，但不强制 fsync。
- `wal_level=2`：写 WAL 并执行 fsync。
- `wal_level=2` 且 `wal_fsync_period=0` 可保证更强数据完整性，但会降低写入速度。

本地文档：

```text
docs/tdengine_docs_en/08-operation/10-disaster.md
```

## 四、优化方案与置信度

### 方案 1：保留 `stmt2-existing` 作为压测默认写入模式

内容：

- 保持当前 `stmt2-existing`。
- 压测前确保子表全部预创建。
- 不再用 `USING stable TAGS (?)` 参与热路径写入。

收益：

- 本轮实测总吞吐提升约 9.6%。
- 最大积压下降约 21.8%。
- 符合官方“预创建子表、不带 TAG 可提升性能”的建议。

局限：

- 单独依靠该改动不足以解决 304000 子表 100ms 全量写入问题。

置信度：高。

### 方案 2：重建压测库，重点提高 `VGROUPS`

内容：

建议先在可清理的 benchmark 环境中重建三库，不直接动生产历史库：

```sql
CREATE DATABASE qc
PRECISION 'ms'
KEEP 365
DURATION 30d
VGROUPS 4
BUFFER 96
PAGES 256
WAL_LEVEL 1
WAL_FSYNC_PERIOD 3000
CACHEMODEL 'none'
STT_TRIGGER 2;

CREATE DATABASE asc
PRECISION 'ms'
KEEP 365
DURATION 30d
VGROUPS 12
BUFFER 96
PAGES 256
WAL_LEVEL 1
WAL_FSYNC_PERIOD 3000
CACHEMODEL 'none'
STT_TRIGGER 2;

CREATE DATABASE agv
PRECISION 'ms'
KEEP 365
DURATION 30d
VGROUPS 16
BUFFER 96
PAGES 256
WAL_LEVEL 1
WAL_FSYNC_PERIOD 3000
CACHEMODEL 'none'
STT_TRIGGER 2;
```

理由：

- 当前总计 6 个业务 vgroups 承担 304000 张子表。
- 建议配置后总计 32 个业务 vgroups，平均约 9500 表/vgroup。
- 更接近官方建议的“硬件充足时每 vgroup 控制在 10000 表以内”。

风险：

- `VGROUPS` 是建库级参数，通常需要新建库或迁移验证。
- vgroups 增加后会提高内存占用。

置信度：很高。

### 方案 3：提高 `BUFFER`，但配合 Docker 内存一起调整

内容：

- 从当前 `BUFFER 16` 提高到 `BUFFER 96`。
- `PAGES 128` 提高到 `PAGES 256`。
- 后续可测试 `BUFFER 128` 或 `BUFFER 256`。

理由：

- 官方说明 `buffer` 是 vnode 写入内存。
- 当前写入压力非常高，`BUFFER 16` 容易频繁触发刷盘。
- 增大 buffer 可以提高批量刷盘效率。

注意：

内存估算公式来自官方资源规划文档：

```text
vgroups × replica × (buffer + pages × pagesize + cachesize)
```

如果按 `qc=4`、`asc=12`、`agv=16`，`BUFFER=96`、`PAGES=256`、`PAGESIZE=4KB`、`CACHESIZE=1MB` 粗算，仅三库 vnode 写入相关内存约：

```text
32 × (96MB + 1MB + 1MB) ≈ 3136MB
```

再加 TDengine 进程、taosAdapter、元数据、大量子表、OS page cache，Docker Desktop 当前 8GB 会偏紧。

置信度：高。

### 方案 4：调整 Docker Desktop / 容器资源

内容：

当前容器没有显式限制，但 Docker Desktop VM 只有约 8GB。建议：

- Docker Desktop CPU：16
- Docker Desktop Memory：至少 16GB，条件允许 24GB
- 数据卷放 SSD
- TDengine 容器显式设置资源，便于复现

示例：

```powershell
docker run -d --name tdengine `
  --cpus=16 `
  --memory=16g `
  --memory-swap=16g `
  --ulimit nofile=1048576:1048576 `
  -e TZ=Asia/Shanghai `
  -v D:\tdengine\data:/var/lib/taos `
  -v D:\tdengine\log:/var/log/taos `
  -p 6030:6030 `
  -p 6041:6041 `
  -p 6043-6060:6043-6060 `
  -p 6043-6060:6043-6060/udp `
  tdengine/tsdb-amd64:3.4.0.9
```

说明：

- 当前不是 CPU quota 被限制。
- 显式资源参数的价值主要是避免部署环境不一致。
- 真正需要优先增大的是 Docker Desktop VM 总内存。

置信度：中高。

### 方案 5：压测并发矩阵测试

内容：

在重建库参数后，测试：

```text
workers-per-db = 2 / 4 / 8 / 12
bind-batch-size = 500 / 1000
```

说明：

- 当前每个超级表默认 1000 个子表。
- `bind-batch-size=1000` 已经能覆盖每个超级表的一轮写入。
- 如果 `subtables-per-stable=1000` 不变，继续把 `bind-batch-size` 调到 5000 或 10000 基本不会增加单次 statement 的行数。

验收指标：

- 不只看最高 rows/s。
- 更应看 `max_lag_ms` 是否能长期低于 100ms 到 200ms。
- 若 rows/s 提高但 lag 仍秒级，仍不满足 100ms 频率目标。

置信度：高。

### 方案 6：增加预热阶段，避免把 statement prepare 计入压测

内容：

- 压测脚本可增加 `--warmup-seconds`。
- 在正式计数前先让每个 worker 完成连接建立和每个 stable 的 statement prepare。

理由：

- 当前每个 worker 会按 stable 懒加载 prepare statement。
- 304 个超级表会产生 304 个 statement prepare。
- 第一阶段日志从 `t=5s` 左右开始，说明初始化和首次写入已有明显启动成本。

收益：

- 更准确区分“启动成本”和“稳定写入吞吐”。

置信度：中。

### 方案 7：用 taosBenchmark 做数据库基线压测

内容：

用 TDengine 官方 `taosBenchmark` 对同一容器、同一数据目录、类似表规模做基线测试。

目的：

- 如果 taosBenchmark 也只有几十万 rows/s，瓶颈主要在 TDengine / Docker / 磁盘。
- 如果 taosBenchmark 很高，而 Python 脚本低，瓶颈主要在 Python taosws 写入路径或脚本并发模型。

置信度：高。

### 方案 8：生产采集链路改造方向

内容：

生产链路后续建议逐步从普通 SQL 写入切到参数绑定：

- 子表初始化阶段统一预创建。
- 热路径写入不带 TAG。
- 按 `(database, stable)` 聚合。
- 每个 writer 线程独立 TDengine 连接。
- 每批尽量提交多行。
- 保证同一子表时间戳递增。

理由：

官方高性能写入建议与本轮压测结果方向一致。

注意：

生产真实目标是 `60 台 × 2 点位 × 10Hz = 1200 rows/s`，远低于本次 304000 子表压测目标。生产链路更需要保证：

- 不丢点。
- 队列有背压。
- 写入失败可观测。
- 批量写入稳定低延迟。

置信度：中高。

## 五、推荐执行顺序

### 第一步：确认 `stmt2-existing` 基线

继续使用当前脚本直接跑：

```powershell
collector\.venv\Scripts\python.exe collector\scripts\tdengine_write_benchmark.py
```

同时保留旧模式对照：

```powershell
collector\.venv\Scripts\python.exe collector\scripts\tdengine_write_benchmark.py --mode stmt2
```

目标：

- 确认 `stmt2-existing` 在多轮测试中是否稳定优于 `stmt2`。

### 第二步：重建 benchmark 库参数

在可清理环境执行：

- 提高 `VGROUPS`。
- 提高 `BUFFER`。
- 保持 `WAL_LEVEL 1`。
- 保持 `CACHEMODEL 'none'`。

然后重新创建超级表和 304000 个子表。

目标：

- 看吞吐是否从约 8 万 rows/s 提升到数十万或更高。
- 看 `max_lag_ms` 是否明显下降。

### 第三步：调整 Docker Desktop 内存

将 Docker Desktop Memory 调到 16GB 或更高。

目标：

- 避免提高 `VGROUPS` 和 `BUFFER` 后内存成为新瓶颈。

### 第四步：并发矩阵测试

建议测试：

```powershell
collector\.venv\Scripts\python.exe collector\scripts\tdengine_write_benchmark.py --workers-per-db 2
collector\.venv\Scripts\python.exe collector\scripts\tdengine_write_benchmark.py --workers-per-db 4
collector\.venv\Scripts\python.exe collector\scripts\tdengine_write_benchmark.py --workers-per-db 8
collector\.venv\Scripts\python.exe collector\scripts\tdengine_write_benchmark.py --workers-per-db 12
```

目标：

- 找到吞吐和 lag 的平衡点。
- 如果并发增加后 lag 变大，说明服务端或磁盘已经到瓶颈。

## 六、当前最终结论

1. 本轮 `stmt2-existing` 相比上一轮有优化，但幅度有限。
2. 当前主要瓶颈不是写入错误，而是吞吐不足导致调度积压。
3. 对 304000 子表每 100ms 全量写入，当前 `VGROUPS=2`、`BUFFER=16` 的库参数明显不足。
4. 下一步最值得做的是重建 benchmark 库，提高 `VGROUPS` 与 `BUFFER`，同时把 Docker Desktop 内存调到 16GB 以上。
5. 生产场景的真实目标约 1200 rows/s，本次压测远高于生产规模；生产优化应以稳定、背压、失败可观测和批量写入为主。
