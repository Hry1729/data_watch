# 历史数据查询指南 (初稿)

在时序数据服务中，历史数据的检索与分析面临“数据量大”、“采集频次不一致（非对齐）”以及“深分页查询缓慢”等挑战。本指南详细说明系统提供的 4 种历史查询路由机制、设计限制、降采样策略以及游标分页原理。

---

## 一、 四种历史查询路由机制对比

后端在 `backend/app/api/routes/history.py` 路由中向前端及第三方分析层暴露了 4 种不同维度的历史数据检索接口：

| 路由接口 | 核心职责 | 适用场景 | 分页与对齐特点 |
| :--- | :--- | :--- | :--- |
| `/history/query` | 合并多指标在同一条时间轴上的数值，缺失值以 `"-"` 占位 | 工业数据表格查看、基础透视分析，支持 Perspective 动态切片 | 不分页。多指标对齐于天然上报时间轴 |
| `/history/chart` | 批量获取多指标降采样聚合后的点位数值序列 | 趋势折线图、柱状图渲染，减少网络吞吐与渲染负载 | 不分页。按固定/自动计算步长（如 `5s`, `1m`）强制对齐时间 |
| `/history/raw` | 拉取**单个指标**无任何加工的毫秒级最原始物理时序流 | 故障根因精细化追溯，单点精确波形分析 | **时间戳游标分页**。单页容量上限高 (5000条)，不对齐时间 |
| `/history/raw-matrix` | 批量获取多个指标并在指定步长（如 100ms）下做对齐后的二维数据矩阵 | 多设备联动过程分析，工业机理建模多维数据导出 | **时间戳游标分页**。按对齐颗粒度（100ms / 500ms / 1s）强制整桶对齐 |

---

## 二、 路由入参限制与硬性约束

为了防止恶意或不当的大跨度数据拉取撑满系统内存并防范 SQL 注入风险，各接口在控制器层实施了严格的拦截校验：

1.  **`/history/query` 保护限制**：
    *   为了防止高频点位合并时造成堆溢出，系统设有一次查询总行数（全部点位的总数据行数之和）保护上限：`perspective_max_records_per_query`（由配置定义，通常为 50,000 ~ 100,000 行）。一旦超出，直接抛出 `400 ApiError`。
2.  **`/history/raw` 限制保护**：
    *   仅支持**单点位**查询（`varSeq` 仅能传入一个有效整数值）。
    *   单页大小 `pageSize` 进行了截断保护：最大不能超过 5000（后端使用 `min(pageSize, 5000)` 进行截断强制规整）。
3.  **`/history/raw-matrix` 限制保护**：
    *   时间跨度限制：查询的 `endTime - startTime` **严格禁止超过 24 小时**。
    *   指标点位限制：**一次最多仅允许传入 10 个 `varSeqs`**（多于 10 个报错 `400`）。
    *   对齐步长限制：`alignGranularity` 仅限 `100ms`, `500ms`, `1s` 三者之一，传入其他步长抛出 `400`。
    *   单页大小限制：`pageSize` 强制截断至最大 500（后端执行 `min(pageSize, 500)`）。

## 三、 时间戳游标分页 (Cursor Pagination) 原理

传统关系型数据库常采用 `LIMIT pageSize OFFSET offset` 进行分页。但在时序数据（如 TDengine/InfluxDB）的大数据量背景下，此方式具有重大弊端：
随着页数加深，`OFFSET` 会让数据库引擎在底层抛弃并扫描大量的历史索引记录，造成查询延迟呈指数级上升，严重时锁表卡死。

系统在 `/history/raw` 和 `/history/raw-matrix` 接口中全面引入了**时间戳游标 (Cursor) 分页**：

### 1. 游标流转设计
*   **第一页 (首页) 请求**：
    客户端不传 `cursorTs`。后端组装的 SQL 时间过滤为 `ts >= {startTime}`。
*   **后续页请求**：
    客户端在上一次接口返回结果中，取得最后一行的格式化时间戳 `ts`，作为 `cursorTs` 传回后端。
    后端将其安全规整后，组装的 SQL 时间过滤为 `ts > {cursorTs}`（在 raw-matrix 中为了防止同桶重读，采用严格大于 `aligned_cursor + 1 bucket_ms`）。
*   **翻页终点判定**：
    若接口查询返回的记录行数等于 `pageSize`，说明后续可能仍有数据，后端会将本页最后一行的 `ts` 作为 `nextCursor` 返回给前端；若数据少于 `pageSize`，代表后续无数据，`nextCursor` 返回 `None`，前端随即终止滚动加载。

### 2. 安全防注入规整
所有由客户端传入的 `cursorTs`（如 `2026-05-23 12:00:00.000`）必须经过服务层的 `parse_local_datetime` 转换和正则校验，在拼入 TDengine 语句前调用时间戳转换函数，确保不会引发 SQL 注入。

## 四、 趋势降采样 (Downsampling) 机制

在 `/history/chart` 查询中，系统调用 TDengine 的 `INTERVAL` 窗口切分来实现时序数据库内部的数据合并压缩。

### 1. `auto` 聚合周期自动计算
如果客户端将降采样步长 `interval` 指定为 `"auto"`，服务层会根据查询的时间窗总长度（`end_time - start_time`）进行自动计算，旨在把前端最终渲染的曲线点数控制在 **2000 个左右**：
*   跨度 $\le$ 2000 秒：聚合步长为 `500ms`。
*   跨度 $\le$ 10,000 秒：聚合步长为 `5s`。
*   跨度 $\le$ 60,000 秒：聚合步长为 `30s`。
*   跨度 $\le$ 120,000 秒：聚合步长为 `1m`。
*   跨度 $\le$ 600,000 秒：聚合步长为 `5m`。
*   跨度 $\le$ 7,200,000 秒（约 83.3 天）：聚合步长为 `30m`。
*   更长跨度（> 7,200,000 秒）：聚合步长为 `1h`。

### 2. 针对布尔型 (BOOL) 变量的聚合规整
*   **问题**：前端对图表聚合算法一般指定 `avg`（平均值）来进行趋势统计。但对于布尔类型数据（如故障信号 `0` 或 `1`），如果使用 `avg` 计算，就会在降采样后算出类似 `0.5` 的插值，这在物理上毫无业务意义（故障只有“有”和“无”）。
*   **解决方案**：服务层在下发降采样 SQL 前，会主动通过元数据检测该 `var_seq` 的 `var_type`。一旦检查为 `"BOOL"` 类型，**强制将该指标的聚合函数从 `AVG` (平均) 修正为 `LAST` (最新值)**。由此保证布尔指标在降采样后依然呈现干净的 `0` 或 `1` 数据点。

## 五、 时序数据桶对齐算法

在 `/history/raw-matrix` 矩阵对齐接口中，为了将时间戳错落不一的多设备/多指标数据规整到二维表格中，系统实施了“时间桶对齐”：

1.  **桶聚合查询**：
    对每一个指标，在 TDengine 侧发起带有 `INTERVAL({align_granularity})` 的分组查询，利用 `_wstart` 获取各时间桶的起点。由于数据库底层按时间片聚合，所以各指标拉出的时间轴必然是完全对齐的。
2.  **对齐填充 (`_align_to_bucket`)**：
    由于可能在某些时间桶内某个指标没有物理采集值，合并时，后端通过时间轴主键将各指标的桶结果映射回对应的单元格中，如果无值，默认使用 `None` 占位，避免出现时间线错位。
    `_align_to_bucket` 负责将用户的游标或者边界值规整到相应颗粒度的标准桶边界。

## 六、 多层级 Fallback 检索策略

由于历史系统经历了架构演进，新采集数据写入的是时序宽表，而老数据可能依然存放在旧的窄表和旧的超级表中。为了避免接口调用因历史表结构差异而失败，HistoryService 内部实现了**三层级 Fallback 容错检索链**（以 `get_raw_data` 为例）：

1.  **第一层（主路径 - 新宽表）**：
    查询 `device_data` 时序库下以设备编码命名的宽表子表 `{device_code}`，过滤特定列名 `td_column_name`（如 `v0001`）。
2.  **第二层（一级 Fallback - 旧窄表子表）**：
    如果第一层因宽表未就绪、或者该字段没有配置映射关系而失败，系统捕捉异常，转而查询旧窄表时序库下的单点子表 `{device_code_lower}_{var_seq_or_point_id}`（即不带 `t_` 前缀，且后缀优先选用点位的 `var_seq`，不存在时才使用 `point_id`）里的 `value` 字段。
3.  **第三层（二级 Fallback - 旧超级表）**：
    若子表丢失或不存在，系统会转向底层超级表，使用设备 Code 拼出的 STable 名称，在 SQL 中添加 `var_seq = {point.var_seq}` 进行过滤查询。

这种三层级 Fallback 检索策略，对上层应用完全透明，实现了新旧数据架构的无缝兼容。
