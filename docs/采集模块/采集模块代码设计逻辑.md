# 采集模块代码设计逻辑

> 本文档记录采集模块各组件的代码级设计逻辑，作为 `采集模块整体结构设计.md` 的补充。

------

# 一、总体数据流

```
PLC设备
  ↓ 驱动读取 (asyncio + run_in_executor)
DataPoint {device_id, variable_id, value, timestamp}
  ↓ TaskExecutor 按 group_code / scan_rate 分帧
RedisRealtimeWriter (最新值 + 短窗口 + Stream)
  ↓ XADD
Redis Stream
  ↓ 独立入库模块 (writer 模块) 批量消费 / ACK
TDengineBatchWriter (device_data -> 设备类型超级表 -> 设备子表 -> 点位宽列)
```

AGV 32 位 OPC DA 采用外部 sidecar 推送流：

```
ZPMC.OPCServer
  ↓ C# x86 sidecar 本机只读 OPC DA
TagBatch {device_id, group, tag, value, quality, timestamp}
  ↓ HTTP POST 到中心接收接口
中心映射 item_id -> variable_id / var_seq
  ↓ DataPoint
RedisRealtimeWriter -> Redis Stream -> 独立的 `writer` 模块 (入库模块)
```

说明：`collector/sidecars/opcda_push_service` 是 tag batch 推送服务基线。它不直接写 TDengine，也不要求本地 sidecar 知道中心 `variable_id`；中心侧通过 `OpcDaTagMapper` 使用 MySQL `device_variable.var_address` 将完整 `item_id` 映射到 `variable_id`，再直接写入 Redis latest/window/stream。`DataBuffer` / `DataAggregator` 保留为测试与旧调用兼容能力，不再作为生产 TDengine 写入路径。

# 二、分层设计逻辑

## 2.1 core/ - 核心模块

### config.py

使用 `dataclass` 定义配置层次：

- `TDengineConfig`：（已废弃，采集端不再加载）原数据库连接参数；现已转移至 `writer` 模块
- `DeviceConfig`：`DeviceConfig`：单个设备的连接信息（IP/端口/协议/采集周期）
- `VariableConfig`：变量定义（地址/数据类型/是否存储）
- `CollectorConfig`：顶层配置，聚合以上所有配置，加上批大小/刷新间隔/队列大小等运行时参数

设计意图：配置与逻辑解耦。当前运行时采用“**TOML 负责运行参数 + MySQL 负责设备/点位拓扑**”：
- `config/settings.toml` 提供 Redis、MySQL、接口与运行时策略等参数；TDengine 历史落库参数由独立 `writer/` 模块维护
  - 注：redis/mysql 的连接凭据（host/port/user/database/password）生产由 Agent 经 `DATAWATCH_<DB>_<FIELD>` 环境变量注入覆盖（单一来源 = Agent config.toml）；settings.toml 的连接段仅作 dev 回退
- 启动阶段通过 `core/config_db.py` 从 `device` / `device_variable` 表加载设备与点位，并覆盖 `CollectorConfig.devices/variables`
- 周期由数据库动态决定：`device.scan_cycle` 为设备默认周期，`device_variable.scan_rate` 为点位优先周期

### logger.py

创建统一的 `logging.Logger`，格式为 `时间 [级别] 模块名 - 消息`。所有模块通过 `get_logger(__name__)` 获取带前缀的日志记录器，便于排查问题时定位到具体模块。

### exceptions.py

定义层次化异常体系：
- `CollectorError` — 所有自定义异常的基类
- `DriverError` — 驱动层通用异常
- `DeviceConnectionError` — 设备连接失败；命名上避开 Python 内置 `ConnectionError`
- `ReadError` — 数据读取失败
- `StorageError` — 遗留的写入失败异常（采集模块只写 Redis，生产环境不抛出该异常）
- `ConfigError` — 配置加载异常
- `AggregatorError` — 数据聚合异常

## 2.2 drivers/ - 驱动接口层

自研驱动代码位于 `drivers/` 包（`base.py`、`s7_driver.py`、`ge_srtp_driver.py`、`opcua_driver.py`、`opcda_center_driver.py`）。业务侧通过 `from drivers.s7_driver import S7Driver` 等方式引用；包内模块之间使用相对导入（如 `from .base import BaseDriver`）。`ge_srtp_driver` 将 `drivers/gesrtp-py-main` 加入 `sys.path` 后使用 `from src.driver import GE_SRTP_Driver` 加载本地第三方库（与 `gesrtp-py-main` 官方示例一致），避免顶层模块名 `driver` 与项目或其它依赖冲突。

### base.py — 统一驱动接口

定义 `BaseDriver` 抽象基类，所有协议驱动必须实现四个方法；生产采集基线为只读采集，`write()` 仅保留接口占位，各内置 PLC 驱动默认直接拒绝写入：

```python
async def connect(config) -> None
async def disconnect() -> None
async def read(blocks: List[ReadBlock]) -> Dict[str, Any]
async def write(points: List[WritePoint]) -> None
```

`ReadBlock` 是批量读取的基本单位，包含地址、数量、数据类型。上层调度器不关心底层协议，只操作 `ReadBlock` 列表。

### s7_driver.py — 西门子 S7 驱动

核心设计：
1. **阻塞包装**：python-snap7 是同步库，通过 `loop.run_in_executor(None, ...)` 将其包装为异步调用，不阻塞事件循环
2. **地址解析**：支持标准 S7 DB 地址 `DB<num>.DBX<byte>.<bit>` / `DBB` / `DBW` / `DBD`，以及 `%I101.0`、`%Q101.0`、`%M101.0`、`%MB1304`、`%MW1304`、`%MD1304` 等 I/Q/M 区地址；支持 `%T<num>` Timer 和 `%C<num>` Counter；旧式 `DB100.0` 不再作为正式格式
3. **字节解析**：根据数据类型（BOOL/INT/REAL/DINT/WORD/BYTE）使用 `struct.unpack` 解析原始字节
4. **大端序**：S7 协议使用大端序，所有 struct 格式前缀为 `>`
5. **只读安全**：健康检查只确认连接状态，不调用 `plc_run` / `plc_stop`，写入接口直接抛出只读异常
6. **点位合并**：上层 `Device.build_scan_tasks()` 会将 S7 I/Q/M 区连续或重叠字节合并为 `%IB/%QB/%MB` BYTE 块；**同一 DB 号内连续/邻近的点位合并为 `DB<n>.DBB<start>` BYTE 块**（2026-06-18 新增，详见下文「S7 DB 连续合并」）；连续 `%T`、连续 `%C` 会按 Timer/Counter 编号合并为单个读取块；执行器再按 `result_map` 还原单点值

### ge_srtp_driver.py — GE SRTP 驱动

核心设计：
1. **路径注入**：将 `drivers/gesrtp-py-main/src` 动态加入 `sys.path`，避免改动第三方库源码
2. **阻塞包装**：同 S7 驱动，使用 `run_in_executor` 包装同步调用
3. **批量读取**：支持 `count > 1` 的批量读取，配合上层合并机制减少 PLC 请求次数
4. **地址映射**：将 `%R`、`%AI`、`%AQ`、`%I`、`%Q`、`%M` 等地址格式映射到对应的 gesrtp 方法
5. **地址基准**：
   - `%R/%AI/%AQ`：`protocol_offset = logical_number - 1`（需现场已知点校验）
   - `%I/%Q/%M`：保持库示例语义（需现场校验确认）
6. **只读设计**：gesrtp 驱动本身不支持写入，write 方法直接抛出异常

**批量合并机制（2026-05-14 新增）**：
- `%R/%AI/%AQ`：按 word 范围合并，最大 125 words，默认不跨空洞
- `%I/%Q/%M`：按 bit 范围合并（第一版只支持 BOOL），最大 512 bits
- 合并后读取块数量从约 4539 降到约 476（默认不跨空洞）
- `result_map` 记录变量到合并块的映射，执行器按映射还原单点值

## 2.3 device/ - 设备管理层

### device.py

三个核心类：

1. **Variable**：变量定义，记录地址、数据类型、采集周期、是否存储。包含 `last_value` 和 `last_storage_time` 用于后续去重判断

2. **ScanTask**：采集任务，同一个设备同一个周期（scan_rate）的所有变量归为一个任务。内部通过 `_build_read_blocks` 将变量列表转换为 `ReadBlock` 列表，并维护“变量 -> 读取块 -> 块内偏移”的映射元数据（用于结果还原）

3. **Device**：设备实例，维护一个驱动连接 + 变量列表。`build_scan_tasks()` 方法按 scan_rate 分组，将变量按周期分组到不同的 ScanTask 中

**设计意图**：将 N 个变量按设备和周期聚合，最终形成 `设备 × 周期数` 个采集任务，大幅减少调度粒度。

S7 协议在任务构建阶段还会进行读取块聚合：DB 区、I/Q/M 区点位均按字节区间合并为 BYTE 块，并在 `ScanTask.result_map` 记录变量相对偏移和 bit 信息；连续 `%T` / `%C` 按同一区域和同一数据类型分组合并，`result_map.value_offset` 记录变量在 Timer/Counter 批量返回列表中的位置。

#### S7 DB 连续合并（2026-06-18 新增）

**背景**：早期实现对 DB 地址「一点一块」（每个点 `count=1` 单独 `db_read`），导致单设备 800 个 DB 点 = 每轮 800 次 PLC 往返，采集周期被拖到 1~2 秒（远超设定的 100ms）。调度器是「读 → 解析 → 写 Redis 全部完成才进入下一轮」的串行模型，因此一轮实测耗时直接决定周期。

**合并规则**（`Device._build_s7_read_blocks` → `_create_s7_db_byte_block`）：
- 按 **DB 号分组**，不同 DB 号绝不合并（S7 每个 DB 是独立内存区，`db_read` 只能针对单个 DB 号）。
- 组内按起始字节排序，贪心合并：与当前段间隔 ≤ `S7_DB_MAX_GAP_BYTES`（默认 64，桥接小空洞）且并入后跨度 ≤ `S7_DB_MAX_BLOCK_BYTES`（默认 8192）即并入同一段。
- 每段生成 `DB<n>.DBB<start>` 的 BYTE 块（`count=跨度`），`result_map` 记录 `block_address`/`byte_offset`/`bit`/`data_type`，执行器 `_extract_mapped_s7_value` 按字节偏移还原（与 I/Q/M 同一条还原路径，executor 无需改动）。
- 字节宽度由访问类型决定：`DBX/DBB=1、DBW=2、DBD=4`。**访问宽度与数据类型解码宽度不一致（或类型不被还原逻辑支持）的点不并入合并块**，退回单点读，沿用驱动 `_read_db_block` 的既有校验（错配点会被如实报错并跳过，不影响同设备其他点）。

**效果**：连续点位场景下，单 DB 的读取块数从约 N 降到 1（snap7 `read_area`/`db_read` 对超过 PDU 的大段会在库内自动分帧，对调用方透明，仍只算一次调用）。

#### 已知限制：read_multi_vars 在当前 snap7 上无原生批量（第二层方案暂缓）

针对「点位散落在多个不同 DB、无法靠连续性合并」的场景，原本规划过「第二层」：用 `read_multi_vars` 把多个不相邻点（甚至跨 DB）压进**一次 PDU 往返**。

**经核查，当前依赖 `python-snap7==3.0.0` 无法兑现该收益**：
- 该版本的 `Client.read_multi_vars` 并非原生单报文批量，而是**在 Python 里 for 循环逐个调 `read_area`**（源码可证）——N 个点仍是 N 次 PLC 往返，与「逐点读」开销相同。
- 该 binding 未暴露底层 `_lib` 句柄，无法直接调用原生 `Cli_ReadMultiVars`。

**决策（2026-06-18）**：第二层暂缓。第一层 DB 连续合并 + `max_gap` 桥接已解决当前问题，并能廉价覆盖「同 DB 内中等稀疏」。**触发条件**：未来真出现「跨多 DB 散点」成为瓶颈时，需换用暴露原生 `Cli_ReadMultiVars` 的主流 ctypes 版 python-snap7，并**在真实 PLC 上验证报文正确性**（逻辑单测无法替代）后再实现第二层。

GE SRTP 协议（2026-05-14 新增）同样支持读取块聚合：
- `%R/%AI/%AQ`：按 word 区间合并，最大 125 words，默认不跨空洞
- `%I/%Q/%M`：按 bit 区间合并（第一版只支持 BOOL），最大 512 bits
- `result_map` 记录变量到合并块的映射，包含 `protocol`、`area`、`word_offset`/`bit_offset`、`word_length` 等元数据

> **GE 与 S7 的批量机制对比（2026-06-18 核查）**：GE **不存在** S7 早期那种「一点一请求」问题——构建层已按范围合并，且底层 `gesrtp-py-main` 每个合并块只发**一次** `_send_request_and_receive`（一次 SRTP 往返读连续范围），与 snap7 `read_multi_vars` 的「假批量」（Python 循环 `read_area`）截然不同。
>
> **已知优化空间**：GE 合并**不跨任何空洞**（`max_gap=0`，`_merge_ge_register_blocks`/`_merge_ge_discrete_blocks` 仅在 `start <= current_end` 时合并），而 S7 DB 已支持 `max_gap=64` 桥接。若某台 GE 设备点位**稀疏散布**导致请求次数偏高、采集变慢，根因即「不跨空洞」；对称优化是给 GE 合并加上与 S7 一致的 `max_gap` 跨空洞桥接（多读少量无用 word 换更少往返）。此为可选优化，非缺陷。

### manager.py

设备管理器的核心职责：
1. **批量注册**：遍历 `DeviceConfig` 创建设备，再将 `VariableConfig` 分配到对应设备
2. **并发连接**：`connect_all()` 使用 `asyncio.gather` 并发连接所有设备，而非逐个串行连接
3. **驱动工厂**：`_create_driver(protocol)` 根据协议名称创建对应驱动实例（如 `from drivers.s7_driver import S7Driver`），后续新增协议在 `drivers/` 中实现类并在此注册即可

## 2.4 collector/ - 采集任务层

### task.py

`CollectTask` 是调度器和执行器之间的桥梁，持有 `Device` 和 `ScanTask` 的引用，加上任务名、运行时间、错误计数等运行时状态。

### scheduler.py — 任务调度器

调度逻辑：
1. 为每个 `CollectTask` 创建独立的 `asyncio.Task` 循环
2. 每个循环按 `scan_rate` 间隔定时触发
3. 调用传入的 `execute_func(task)` 执行采集
4. 失败时累加 `error_count`，不中断循环（保证设备恢复后自动恢复采集）

**设计意图**：每个任务独立循环，不同周期的任务互不影响。1秒任务和5秒任务各自按自己的节奏运行。

### executor.py — 任务执行器

执行逻辑：
1. 检查设备连接状态，未连接则跳过并调度重连
2. 调用 `device.driver.read(scan_task.read_blocks)` 批量读取
3. 普通协议按原始地址解析结果；S7 I/Q/M 合并块通过 `scan_task.result_map` 从 BYTE 数组还原单变量值，S7 Timer/Counter 合并块通过 `value_offset` 从批量返回列表还原单变量值
4. GE SRTP 合并块通过 `_extract_mapped_ge_value()` 从 word/bit 数组还原单变量值
5. 调用 `buffer.put_batch(points)` 将数据点送入队列

**关键设计**：Executor 不关心数据怎么处理，只负责把读到的数据放入队列。实现了采集与处理的彻底解耦。

**GE SRTP 单点还原（2026-05-14 新增）**：
- 寄存器区域（%R/%AI/%AQ）：按 `word_offset` 定位，INT/WORD 取单 word，DINT/REAL/DWORD 取 2 words 组合
- 离散量区域（%I/%Q/%M）：按 `bit_offset` 从布尔列表取值（第一版只支持 BOOL）
- REAL/DINT 字序：当前默认使用 `low_high` word 序组合；现场必须用已知值校验。如现场 PLC 使用 `high_low`，需扩展 `word_order` 配置。

## 2.5 data_queue/ - 数据队列层

### buffer.py — 数据缓冲队列

基于 `asyncio.Queue`：
- `put()`：单条入队，队列满时丢弃数据（防止背压导致系统崩溃），记录丢弃计数
- `get_batch()`：非阻塞批量取出，尽可能多地取出，最多 `max_count` 个
- 统计指标：当前大小、总入队数、总丢弃数

**设计意图**：`put_batch` 使用非阻塞 `put_nowait`，即使队列满了也不会阻塞采集任务，保证采集的实时性。

### aggregator.py — 数据聚合器（核心组件）

三个核心功能：

1. **值变化去重**：`should_store()` 方法记录每个变量的上次 `value` 和时间。值未变化且在时间窗口内，跳过历史落库；实时最新值仍可进入 Redis
2. **批量缓存**：`add()` 将需要存储的数据点加入 `_cache` 列表，达到 `batch_size` 时触发 flush 条件
3. **时间窗口控制**：即使值未变化，超过 `max_window_seconds`（默认 10 分钟）也强制写入，确保数据连续性
4. **失败保护**：flush 后写入失败会将 batch 放回缓存头部并恢复 pending 状态；缓存有上限，连续失败超过阈值会暂停接收新数据，避免内存无限增长
5. **回调兼容**：输出回调使用 `inspect.iscoroutinefunction` 判断协程函数，避免 Python 3.16 对 `asyncio.iscoroutinefunction` 的弃用警告

**主循环 `run()`**：
- 非阻塞检查 buffer 是否有新数据
- 调用 `add_batch()` 聚合
- 达到条件（缓存满或定时刷新）时调用输出回调写入
- 休眠 50ms 避免空转

## 2.6 storage/ - 存储层

### tdengine.py — 遗留连接管理（已迁至 writer 模块）

说明：采集模块重构后不再直连 TDengine，此文件仅作为遗留代码或独立单元测试参考保留。实际运行中的连接由独立 `writer` 模块通过以下核心设计实现：
1. **仅 WebSocket**：统一使用 `taos-ws-py`（`taosws.connect`），经 **taosAdapter** 访问 TDengine，与官方推荐一致。
2. **DSN**：`ws://user:pass@host:port/database?...`；`timezone` 为可选参数。
3. **自动初始化**：连接后创建 `device_data` 数据库，按设备类型创建 `qc/asc/agv` 超级表，再按 MySQL `device` 创建设备子表。
4. **schema 兼容性**：超级表点位列由 MySQL `device_variable.var_seq` 动态映射，历史表不再存 `quality`。

### tdengine_ingestor.py / batch_writer.py — 遗留落库处理（已迁至 writer 模块）

说明：采集模块只负责写入 Redis，此组件已不再被采集主链路调用。其生产逻辑已转移至独立的 `writer` 模块：
1. **写入循环**：使用 Redis Stream Consumer Group 拉取待入库帧，按设备子表组装宽行后批量写入 TDengine。
2. **ACK 边界**：只有 TDengine 写入成功后才 ACK Redis Stream；失败保留 pending，后续重试或人工补偿。

当前目标主流程不再由采集聚合器直接触发 TDengine 写入。采集模块只写 Redis，TDengine 写入由独立 `writer` 模块完成。

### data_quality.py — 质量规则引擎

`core/data_quality.py` 已提供值域、变化率、缺失值、邻近点比较等规则能力，并有独立单元测试。后续异常、bad、缺失等语义建议进入实时态、告警或规则判断链路；TDengine 历史宽表只保存点位值，不再保存 `quality` 列。

## 2.7 monitor/ - 监控层

### metrics.py

## 2.8 utils/ - 工具类

### helpers.py

- `merge_continuous_blocks()`：将连续地址合并为更大的读取块（减少 PLC 请求次数），并生成映射所需的块起始地址与偏移信息
- `parse_address()`：解析地址字符串（如 `DB398.DBD0` → `{type: "DB", db: 398, access: "DBD", offset: 0}`，`%MD1304` → `{type: "M", width: "D", offset: 1304}`）

### 地址合并与结果还原机制（新增说明）

读取流程应遵循以下模型：

```text
变量列表（原始地址）
  -> merge_continuous_blocks
  -> ReadBlock 列表 + 变量映射表
  -> driver.read(ReadBlock[])
  -> executor 按映射表还原变量值
  -> DataPoint
```

建议映射结构：

```python
{
  "qc_motor_speed": {
    "block_addr": "DB398.DBD0",
    "value_index": 0
  },
  "qc_temperature": {
    "block_addr": "DB398.DBD4",
    "value_index": 1
  }
}
```

- `validate_value()`：值与数据类型匹配校验
- `validate_device_id()` / `validate_variable_id()`：ID 长度和格式校验

# 三、main.py 启动流程

```
main()
  1. load_collector_config_from_env()          # 读取 settings.toml
  2. ConfigDBManager.load_config(...)          # 从 MySQL 加载 device/point 并覆盖配置
  3. CollectorApp(config)                      # 组装组件
  4. app.start()                               # 进入采集主循环

CollectorApp.start()
  1. system_logger.start()                     # 启动系统日志异步写入器
  2. device_manager.register_devices()         # 注册设备+变量
  3. device_manager.connect_all()              # 并发连接所有设备
  4. scheduler.add_tasks(tasks)                # 构建采集任务并注册
  5. scheduler.start(execute_func)             # 启动异步调度循环，采集结果写 Redis
  6. ingest_server.start(...)                  # 启动外部 HTTP Push 接入，推送结果写 Redis
  7. health_checker.run()                      # 启动设备健康检查
  8. await _shutdown.wait()                    # 等待退出信号
  9. shutdown()                                # 停调度、接口服务与设备连接
```

当前运行时主要由以下后台逻辑协作：
- **调度循环**：按周期触发采集
- **Redis 写入执行**：轮询采集由 `TaskExecutor` 写 Redis latest/window/stream；HTTP Push / OPC DA 推送由 `InterfaceIngestServer` 映射后写 Redis
- **HTTP Push 接入**：接口类协议启用时接收外部推送并映射为采集点，生产路径不再进入 TDengine 直写
- **健康检查**：定期检查设备状态；TDengine 由独立 writer 模块自行负责

信号处理注册了 `SIGINT` 和 `SIGTERM`，Ctrl+C 或 kill 信号触发 `stop()` 方法，设置 `_shutdown` 事件，进入清理流程。

# 四、关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 采集模式 | asyncio + run_in_executor | PLC驱动都是同步库，不能改源码，用线程池包装 |
| 连接方式 | 长连接 + 自动重连 | 频繁连接PLC会导致PLC端资源耗尽 |
| 解耦方式 | Redis latest/window/stream | 采集进程和历史落库进程解耦，TDengine 抖动不拖慢采集 |
| 去重策略 | 由实时态/规则层和独立 writer 后续策略承接 | collector 负责按采集周期输出 Redis 帧，不再直写 TDengine |
| 批量写入 | Redis Stream + 独立的 `writer` 模块 + 设备子表宽行批量 INSERT / stmt2 | 采集与历史入库解耦；305 台设备级子表远少于旧点位子表模型，适合 500ms/1s 批量落库 |
| TDengine 连接 | 独立 `writer/` 模块负责 | collector 不再连接或初始化 TDengine |
| Redis 写入与 execute | run_in_executor 包装同步 Redis 调用 | redis-py 为同步 API，在线程池中调用以免阻塞事件循环 |
| 协议扩展 | 工厂模式 + 统一接口 | 新增协议在 `drivers/` 下实现 BaseDriver 子类，在 manager 的 `_create_driver` 中注册即可 |

# 五、设计原则与优化策略

## 5.1 架构设计原则
1. **分层解耦** — 各层（驱动、设备管理、调度、数据队列、存储、监控）职责清晰，通过统一接口与 `asyncio.Queue` 缓冲队列进行解耦，互不干扰。
2. **异步优先** — 全链路基于 `asyncio` 异步驱动，保证在高并发 PLC 并发连接与采集下系统响应敏捷。
3. **高可靠性与熔断** — 针对 PLC/数据库连接设计熔断与自动重连机制，通过指数退避策略确保在异常恢复后能自动重连并恢复采集。
4. **可观测性** — 内置轻量化性能指标收集器与统一日志管理，实现采集延迟、队列堆积与写入状态的全面追踪。

## 5.2 性能优化要点
1. **异步优化** — 使用 `loop.run_in_executor` 线程池包装 Snap7/GE SRTP 等同步 PLC 驱动库，避免阻塞主事件循环。
2. **批量合并** — 根据地址连续性将变量合并为 BYTE/Word 块读取，S7 和 GE 驱动均支持，可减少 PLC 请求次数 80% 以上。
3. **去重策略** — 在内存中过滤重复值，相同点位值在没有变化且未超时（默认 10 分钟最大时间窗口）时，不写入待入库队列，极大降低时序数据库的存储与 IO 压力。
4. **长连接与重连** — PLC 与数据库连接均采用长连接并由管理器常驻维护，避免频繁握手带来的网络与设备资源开销。

## 5.3 可扩展性设计
1. **统一驱动接口 (BaseDriver)** — 新增采集协议只需在 `drivers/` 目录下继承 `BaseDriver` 实现 `connect/disconnect/read/write` 接口，并在 `DeviceManager._create_driver` 工厂方法中注册即可。
2. **配置驱动设计** — 支持运行时从 MySQL 动态加载设备与点位关系。采集周期、是否存储等属性均由数据库配置驱动。
3. **插件化映射 (OpcDaTagMapper)** — 中心侧支持使用 Tag Mapper 实现 OPC DA 项标识符到点位 ID 的动态映射，sidecar 侧无需感知中心点位主键。

## 5.4 测试与质量保障
1. **单元测试** — `tests/` 目录下提供针对 S7 驱动解析、GE 驱动单点还原、去重算法和配置校验的完整测试用例。
2. **数据质量规则引擎** — 在 `core/data_quality.py` 中实现了独立的值域范围、变化率和趋势分析引擎，用作实时告警与质量判定。
