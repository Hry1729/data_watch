# 采集模块代码设计逻辑

> 本文档记录采集模块各组件的代码级设计逻辑，作为 `采集模块整体结构设计.md` 的补充。

------

# 一、总体数据流

```
PLC设备
  ↓ 驱动读取 (asyncio + run_in_executor)
DataPoint {device_id, variable_id, value, timestamp}
  ↓ put() / put_batch()
DataBuffer (asyncio.Queue)
  ↓ get_batch()
DataAggregator (去重/批量缓存/时间窗口)
  ↓ flush()
RedisRealtimeWriter (最新值 + 短窗口 + Stream)
  ↓ XADD
Redis Stream
  ↓ 入库模块批量消费 / ACK
TDengineBatchWriter (device_data -> 设备类型超级表 -> 设备子表 -> 点位宽列)
```

AGV 32 位 OPC DA 采用外部 sidecar 推送流：

```
ZPMC.OPCServer
  ↓ C# x86 sidecar 本机只读 OPC DA
TagBatch {device_id, group, tag, value, quality, timestamp}
  ↓ HTTP POST 到中心接收接口
中心映射 item_id -> variable_id / var_seq
  ↓ DataPoint
DataBuffer -> DataAggregator -> RedisRealtimeWriter -> Redis Stream -> TDengine 入库模块
```

说明：`collector/sidecars/opcda_push_service` 是 tag batch 推送服务基线。它不直接写 TDengine，也不要求本地 sidecar 知道中心 `variable_id`；中心侧通过 `OpcDaTagMapper` 使用 MySQL `device_variable.var_address` 将完整 `item_id` 映射到 `variable_id`，再进入既有 `DataPoint` 链路。

# 二、分层设计逻辑

## 2.1 core/ - 核心模块

### config.py

使用 `dataclass` 定义配置层次：

- `TDengineConfig`：数据库连接参数（host/port/user/password/database）；可选 `timezone`；**仅支持 WebSocket**（`use_ssl=True` 时为 `wss://`），经 taosAdapter，与官方推荐一致
- `DeviceConfig`：单个设备的连接信息（IP/端口/协议/采集周期）
- `VariableConfig`：变量定义（地址/数据类型/是否存储）
- `CollectorConfig`：顶层配置，聚合以上所有配置，加上批大小/刷新间隔/队列大小等运行时参数

设计意图：配置与逻辑解耦。当前运行时采用“**TOML 负责运行参数 + MySQL 负责设备/点位拓扑**”：
- `config/settings.toml` 提供 TDengine、MySQL、队列与批量策略等运行参数
- 启动阶段通过 `core/config_db.py` 从 `device` / `device_variable` 表加载设备与点位，并覆盖 `CollectorConfig.devices/variables`
- 周期由数据库动态决定：`device.scan_cycle` 为设备默认周期，`device_variable.scan_rate` 为点位优先周期

### logger.py

创建统一的 `logging.Logger`，格式为 `时间 [级别] 模块名 - 消息`。所有模块通过 `get_logger(__name__)` 获取带前缀的日志记录器，便于排查问题时定位到具体模块。

### exceptions.py

定义层次化异常体系：
- `CollectorError` — 所有自定义异常的基类
- `DriverError` — 驱动层通用异常
- `DeviceConnectionError` — 设备连接失败；命名上避开 Python 内置 `ConnectionError`
- `ReadError` — 数据读取失败
- `StorageError` — TDengine 写入失败
- `ConfigError` — 配置加载异常
- `AggregatorError` — 数据聚合异常

## 2.2 drivers/ - 驱动接口层

自研驱动代码位于 `drivers/` 包（`base.py`、`s7_driver.py`、`ge_srtp_driver.py`、`opcua_driver.py`、`opcda_center_driver.py`）。业务侧通过 `from drivers.s7_driver import S7Driver` 等方式引用；包内模块之间使用相对导入（如 `from .base import BaseDriver`）。`ge_srtp_driver` 将 `drivers/gesrtp-py-main` 加入 `sys.path` 后使用 `from src.driver import GE_SRTP_Driver` 加载本地第三方库（与 `gesrtp-py-main` 官方示例一致），避免顶层模块名 `driver` 与项目或其它依赖冲突。

### base.py — 统一驱动接口

定义 `BaseDriver` 抽象基类，所有协议驱动必须实现四个方法；生产采集基线为只读采集，`write()` 仅保留接口占位，各内置 PLC 驱动默认直接拒绝写入：

```python
async def connect(config) -> None
async def disconnect() -> None
async def read(blocks: List[ReadBlock]) -> Dict[str, Any]
async def write(points: List[WritePoint]) -> None
```

`ReadBlock` 是批量读取的基本单位，包含地址、数量、数据类型。上层调度器不关心底层协议，只操作 `ReadBlock` 列表。

### s7_driver.py — 西门子 S7 驱动

核心设计：
1. **阻塞包装**：python-snap7 是同步库，通过 `loop.run_in_executor(None, ...)` 将其包装为异步调用，不阻塞事件循环
2. **地址解析**：支持标准 S7 DB 地址 `DB<num>.DBX<byte>.<bit>` / `DBB` / `DBW` / `DBD`，以及 `%I101.0`、`%Q101.0`、`%M101.0`、`%MB1304`、`%MW1304`、`%MD1304` 等 I/Q/M 区地址；支持 `%T<num>` Timer 和 `%C<num>` Counter；旧式 `DB100.0` 不再作为正式格式
3. **字节解析**：根据数据类型（BOOL/INT/REAL/DINT/WORD/BYTE）使用 `struct.unpack` 解析原始字节
4. **大端序**：S7 协议使用大端序，所有 struct 格式前缀为 `>`
5. **只读安全**：健康检查只确认连接状态，不调用 `plc_run` / `plc_stop`，写入接口直接抛出只读异常
6. **点位合并**：上层 `Device.build_scan_tasks()` 会将 S7 I/Q/M 区连续或重叠字节合并为 `%IB/%QB/%MB` BYTE 块；连续 `%T`、连续 `%C` 会按 Timer/Counter 编号合并为单个读取块；执行器再按 `result_map` 还原单点值

### ge_srtp_driver.py — GE SRTP 驱动

核心设计：
1. **路径注入**：将 `drivers/gesrtp-py-main/src` 动态加入 `sys.path`，避免改动第三方库源码
2. **阻塞包装**：同 S7 驱动，使用 `run_in_executor` 包装同步调用
3. **批量读取**：支持 `count > 1` 的批量读取，配合上层合并机制减少 PLC 请求次数
4. **地址映射**：将 `%R`、`%AI`、`%AQ`、`%I`、`%Q`、`%M` 等地址格式映射到对应的 gesrtp 方法
5. **地址基准**：
   - `%R/%AI/%AQ`：`protocol_offset = logical_number - 1`（需现场已知点校验）
   - `%I/%Q/%M`：保持库示例语义（需现场校验确认）
6. **只读设计**：gesrtp 驱动本身不支持写入，write 方法直接抛出异常

**批量合并机制（2026-05-14 新增）**：
- `%R/%AI/%AQ`：按 word 范围合并，最大 125 words，默认不跨空洞
- `%I/%Q/%M`：按 bit 范围合并（第一版只支持 BOOL），最大 512 bits
- 合并后读取块数量从约 4539 降到约 476（默认不跨空洞）
- `result_map` 记录变量到合并块的映射，执行器按映射还原单点值

## 2.3 device/ - 设备管理层

### device.py

三个核心类：

1. **Variable**：变量定义，记录地址、数据类型、采集周期、是否存储。包含 `last_value` 和 `last_storage_time` 用于后续去重判断

2. **ScanTask**：采集任务，同一个设备同一个周期（scan_rate）的所有变量归为一个任务。内部通过 `_build_read_blocks` 将变量列表转换为 `ReadBlock` 列表，并维护“变量 -> 读取块 -> 块内偏移”的映射元数据（用于结果还原）

3. **Device**：设备实例，维护一个驱动连接 + 变量列表。`build_scan_tasks()` 方法按 scan_rate 分组，将变量按周期分组到不同的 ScanTask 中

**设计意图**：将 N 个变量按设备和周期聚合，最终形成 `设备 × 周期数` 个采集任务，大幅减少调度粒度。

S7 协议在任务构建阶段还会进行读取块聚合：DB 地址保持原始标准地址以保留 `DBX/DBB/DBW/DBD` 语义；I/Q/M 区点位按 area 和字节区间合并为 BYTE 块，并在 `ScanTask.result_map` 记录变量相对偏移和 bit 信息；连续 `%T` / `%C` 按同一区域和同一数据类型分组合并，`result_map.value_offset` 记录变量在 Timer/Counter 批量返回列表中的位置。

GE SRTP 协议（2026-05-14 新增）同样支持读取块聚合：
- `%R/%AI/%AQ`：按 word 区间合并，最大 125 words，默认不跨空洞
- `%I/%Q/%M`：按 bit 区间合并（第一版只支持 BOOL），最大 512 bits
- `result_map` 记录变量到合并块的映射，包含 `protocol`、`area`、`word_offset`/`bit_offset`、`word_length` 等元数据

### manager.py

设备管理器的核心职责：
1. **批量注册**：遍历 `DeviceConfig` 创建设备，再将 `VariableConfig` 分配到对应设备
2. **并发连接**：`connect_all()` 使用 `asyncio.gather` 并发连接所有设备，而非逐个串行连接
3. **驱动工厂**：`_create_driver(protocol)` 根据协议名称创建对应驱动实例（如 `from drivers.s7_driver import S7Driver`），后续新增协议在 `drivers/` 中实现类并在此注册即可

## 2.4 collector/ - 采集任务层

### task.py

`CollectTask` 是调度器和执行器之间的桥梁，持有 `Device` 和 `ScanTask` 的引用，加上任务名、运行时间、错误计数等运行时状态。

### scheduler.py — 任务调度器

调度逻辑：
1. 为每个 `CollectTask` 创建独立的 `asyncio.Task` 循环
2. 每个循环按 `scan_rate` 间隔定时触发
3. 调用传入的 `execute_func(task)` 执行采集
4. 失败时累加 `error_count`，不中断循环（保证设备恢复后自动恢复采集）

**设计意图**：每个任务独立循环，不同周期的任务互不影响。1秒任务和5秒任务各自按自己的节奏运行。

### executor.py — 任务执行器

执行逻辑：
1. 检查设备连接状态，未连接则跳过并调度重连
2. 调用 `device.driver.read(scan_task.read_blocks)` 批量读取
3. 普通协议按原始地址解析结果；S7 I/Q/M 合并块通过 `scan_task.result_map` 从 BYTE 数组还原单变量值，S7 Timer/Counter 合并块通过 `value_offset` 从批量返回列表还原单变量值
4. GE SRTP 合并块通过 `_extract_mapped_ge_value()` 从 word/bit 数组还原单变量值
5. 调用 `buffer.put_batch(points)` 将数据点送入队列

**关键设计**：Executor 不关心数据怎么处理，只负责把读到的数据放入队列。实现了采集与处理的彻底解耦。

**GE SRTP 单点还原（2026-05-14 新增）**：
- 寄存器区域（%R/%AI/%AQ）：按 `word_offset` 定位，INT/WORD 取单 word，DINT/REAL/DWORD 取 2 words 组合
- 离散量区域（%I/%Q/%M）：按 `bit_offset` 从布尔列表取值（第一版只支持 BOOL）
- REAL/DINT 字序：当前默认使用 `low_high` word 序组合；现场必须用已知值校验。如现场 PLC 使用 `high_low`，需扩展 `word_order` 配置。

## 2.5 data_queue/ - 数据队列层

### buffer.py — 数据缓冲队列

基于 `asyncio.Queue`：
- `put()`：单条入队，队列满时丢弃数据（防止背压导致系统崩溃），记录丢弃计数
- `get_batch()`：非阻塞批量取出，尽可能多地取出，最多 `max_count` 个
- 统计指标：当前大小、总入队数、总丢弃数

**设计意图**：`put_batch` 使用非阻塞 `put_nowait`，即使队列满了也不会阻塞采集任务，保证采集的实时性。

### aggregator.py — 数据聚合器（核心组件）

三个核心功能：

1. **值变化去重**：`should_store()` 方法记录每个变量的上次 `value` 和时间。值未变化且在时间窗口内，跳过历史落库；实时最新值仍可进入 Redis
2. **批量缓存**：`add()` 将需要存储的数据点加入 `_cache` 列表，达到 `batch_size` 时触发 flush 条件
3. **时间窗口控制**：即使值未变化，超过 `max_window_seconds`（默认 10 分钟）也强制写入，确保数据连续性
4. **失败保护**：flush 后写入失败会将 batch 放回缓存头部并恢复 pending 状态；缓存有上限，连续失败超过阈值会暂停接收新数据，避免内存无限增长
5. **回调兼容**：输出回调使用 `inspect.iscoroutinefunction` 判断协程函数，避免 Python 3.16 对 `asyncio.iscoroutinefunction` 的弃用警告

**主循环 `run()`**：
- 非阻塞检查 buffer 是否有新数据
- 调用 `add_batch()` 聚合
- 达到条件（缓存满或定时刷新）时调用输出回调写入
- 休眠 50ms 避免空转

## 2.6 storage/ - 存储层

### tdengine.py — 连接管理

核心设计：
1. **仅 WebSocket**：统一使用 `taos-ws-py`（`taosws.connect`），经 **taosAdapter** 访问 TDengine，**不使用**原生 `libtaos` / `taos.connect`，与官方对 Python 的推荐一致。
2. **DSN**：`ws://user:pass@host:port/database?...`；`timezone` 为可选参数。生产可配置 `use_ssl=True` 使用 `wss://`（仍为 WebSocket）。
3. **阻塞包装**：连接与 `execute` 通过 `run_in_executor` 包装，避免阻塞 asyncio 事件循环。
4. **自动初始化**：连接后创建 `device_data` 数据库，按设备类型创建 `qc/asc/agv` 超级表，再按 MySQL `device` 创建设备子表。
5. **schema 兼容性**：超级表点位列由 MySQL `device_variable.var_seq` 动态生成，缺失列通过 `ALTER STABLE ... ADD COLUMN` 增量补齐；TDengine 历史表不再存 `quality`。

依赖说明：存储层仅需 **`taos-ws-py`**，无需安装 `taospy` 做原生连接。

### tdengine_ingestor.py / batch_writer.py — TDengine 入库模块

核心设计：
1. **SQL 构建**：按“`device_data` + 设备类型超级表 + 设备子表”定位写入目标，每行包含 `ts` 与该设备类型的点位值宽列
2. **重试机制**：写入失败最多重试 `max_retries` 次，每次递增等待时间（1s, 2s, 3s...）
3. **写入循环**：入库模块使用 Redis Stream Consumer Group 拉取待入库帧，按设备子表组装宽行后批量写入 TDengine
4. **ACK 边界**：只有 TDengine 写入成功后才 ACK Redis Stream；失败保留 pending，后续重试或人工补偿

当前目标主流程不再由采集聚合器直接触发 TDengine 写入。采集模块只写 Redis，TDengine 写入由独立入库模块完成。

### data_quality.py — 质量规则引擎

`core/data_quality.py` 已提供值域、变化率、缺失值、邻近点比较等规则能力，并有独立单元测试。后续异常、bad、缺失等语义建议进入实时态、告警或规则判断链路；TDengine 历史宽表只保存点位值，不再保存 `quality` 列。

## 2.7 monitor/ - 监控层

### metrics.py

轻量指标收集器，支持计数器（increment）、仪表盘（gauge）、计时器（start/stop timer）。当前用于内部统计，后续可扩展为 Prometheus 格式暴露。

### health.py

定期检查：
- TDengine 连接状态
- 每个设备的连接状态
- 汇总在线设备数 / 总设备数

默认每 30 秒执行一次健康检查。

## 2.8 utils/ - 工具类

### helpers.py

- `merge_continuous_blocks()`：将连续地址合并为更大的读取块（减少 PLC 请求次数），并生成映射所需的块起始地址与偏移信息
- `parse_address()`：解析地址字符串（如 `DB398.DBD0` → `{type: "DB", db: 398, access: "DBD", offset: 0}`，`%MD1304` → `{type: "M", width: "D", offset: 1304}`）

### 地址合并与结果还原机制（新增说明）

读取流程应遵循以下模型：

```text
变量列表（原始地址）
  -> merge_continuous_blocks
  -> ReadBlock 列表 + 变量映射表
  -> driver.read(ReadBlock[])
  -> executor 按映射表还原变量值
  -> DataPoint
```

建议映射结构：

```python
{
  "qc_motor_speed": {
    "block_addr": "DB398.DBD0",
    "value_index": 0
  },
  "qc_temperature": {
    "block_addr": "DB398.DBD4",
    "value_index": 1
  }
}
```

### validators.py

数据验证：
- `validate_address()`：地址格式基本校验
- `validate_value()`：值与数据类型匹配校验
- `validate_device_id()` / `validate_variable_id()`：ID 长度和格式校验

# 三、main.py 启动流程

```
main()
  1. load_collector_config_from_env()          # 读取 settings.toml
  2. ConfigDBManager.load_config(...)          # 从 MySQL 加载 device/point 并覆盖配置
  3. CollectorApp(config)                      # 组装组件
  4. app.start()                               # 进入采集主循环

CollectorApp.start()
  1. system_logger.start()                     # 启动系统日志异步写入器
  2. device_manager.register_devices()         # 注册设备+变量
  3. tdengine.connect()                        # 连接 TDengine
  4. tdengine.init_storage_topology(...)        # 初始化 device_data、设备类型超级表、设备子表和点位宽列
  5. _write_fake_bootstrap_points()            # 假数据模式下写入示例点位
  6. device_manager.connect_all()              # 并发连接所有设备
  7. scheduler.add_tasks(tasks)                # 构建采集任务并注册
  8. scheduler.start(execute_func)             # 启动异步调度循环
  9. ingest_server.start(...)                  # 启动外部 HTTP Push 接入（如启用）
  10. aggregator.run()                         # 启动聚合循环，flush 后回调 BatchWriter 写入
  11. health_checker.run()                     # 启动健康检查
  12. await _shutdown.wait()                   # 等待退出信号
  13. shutdown()                               # 停调度、flush 聚合缓存、drain 写入、断开外部资源
```

当前运行时主要由以下后台逻辑协作：
- **调度循环**：按周期触发采集
- **聚合循环**：从 buffer 取数据、去重、缓存
- **写入执行**：聚合器 flush 后通过回调调用 `BatchWriter.write_sync` 批量写入 TDengine，不再单独启动 `batch_writer.run_writer_loop()`
- **HTTP Push 接入**：接口类协议启用时接收外部推送并映射为采集点
- **健康检查**：定期检查设备/数据库状态

信号处理注册了 `SIGINT` 和 `SIGTERM`，Ctrl+C 或 kill 信号触发 `stop()` 方法，设置 `_shutdown` 事件，进入清理流程。

# 四、关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 采集模式 | asyncio + run_in_executor | PLC驱动都是同步库，不能改源码，用线程池包装 |
| 连接方式 | 长连接 + 自动重连 | 频繁连接PLC会导致PLC端资源耗尽 |
| 解耦方式 | asyncio.Queue | 生产者和消费者完全独立，不会互相阻塞 |
| 去重策略 | 内存字典记录上次 value + 时间窗口 | 避免写入大量重复历史数据，实时最新值交给 Redis |
| 批量写入 | Redis Stream + 独立入库模块 + 设备子表宽行批量 INSERT / stmt2 | 采集与历史入库解耦；305 台设备级子表远少于旧点位子表模型，适合 500ms/1s 批量落库 |
| TDengine 连接 | 仅 WebSocket（taos-ws-py） | 官方推荐；经 taosAdapter，依赖小、易部署，避免原生客户端与 GIL 瓶颈 |
| 写入与 execute | run_in_executor 包装同步 API | taosws 的 connect/execute 为同步接口，在线程池中调用以免阻塞事件循环 |
| 协议扩展 | 工厂模式 + 统一接口 | 新增协议在 `drivers/` 下实现 BaseDriver 子类，在 manager 的 `_create_driver` 中注册即可 |
