## 一、采集模块整体结构设计（v2.3）

更新时间：2026-05-19

> 当前目标状态：采集主链路继续复用 MySQL 配置加载、协议适配、DataBuffer、DataAggregator 等基础能力；采集模块只写 Redis 最新值、短窗口和待入库 Stream。历史态由独立 TDengine 入库模块从 Redis Stream 批量消费后写入宽表。TDengine 目标模型为 `device_data` 单库、`qc/asc/agv` 三个超级表、每台设备一个子表、点位值按 MySQL `device_variable.var_seq` 动态映射为宽列；历史表不再存 `quality`。2026-05-14 的旧变量子表模型测试记录仅作为历史基线保留。

## 三、HTTP 端点

| 端点 | 方法 | 功能 | 说明 |
|------|------|------|------|
| `/ingest/health` | GET | 健康检查 | 返回队列状态和映射数量 |
| `/ingest` | POST | 通用点位接收 | 需要 `device_id` + `variable_id` |
| `/ingest/opcda-tags` | POST | OPC DA 专用 | schema: `opcda_tag_batch_v1` |

### /ingest/opcda-tags 请求格式

```json
{
  "source": "opcda_sidecar",
  "schema": "opcda_tag_batch_v1",
  "points": [
    {
      "device_id": "agv801",
      "item_id": "OPD_Server.AGV801.ViewMain.Tag30041800",
      "value": 123.45,
      "quality": 192,
      "timestamp": "2026-05-02T18:00:00+08:00"
    }
  ]
}
```

说明：OPC DA sidecar 可以继续上报原始 `quality`，中心侧仅将其用于实时态、告警或规则判断；TDengine 历史宽表不保存该字段。

### 响应格式

```json
{
  "accepted": 100,
  "unmapped": 2,
  "dropped": 0,
  "errors": []
}
```

## 四、MySQL 配置说明

### 设备表 (device)

| 字段 | 说明 | OPC DA 填写示例 |
|------|------|-----------------|
| device_code | 设备编码 | `agv801` |
| protocol_id | 协议ID | `opcda_sidecar` 协议的 ID |
| endpoint | 端点 | `127.0.0.1:8090` (collector 地址) |

### 点位表 (device_variable)

| 字段 | 说明 | OPC DA 填写示例 |
|------|------|-----------------|
| device_id | 设备ID外键 | 关联 agv801 |
| var_seq | 点位序号 | `1`, `2`, `3`... |
| var_address | 完整地址 | `OPD_Server.AGV801.ViewMain.Tag30041800` |
| var_type | 数据类型 | `REAL`, `BOOL`, `INT` |
| is_storage | 是否存储 | `1` |

**注意**: 当协议为 OPC DA Sidecar 时，`io_type`、`var_offset`、`var_bit` 字段忽略（已设为可空）。

## 五、启动流程

```python
# main.py 启动流程
CollectorApp.start():
  1. device_manager.register_devices()    # 注册设备+变量
  2. device_manager.connect_all()         # 连接 PLC 设备
  3. scheduler.add_tasks(tasks)           # 构建采集任务
  4. scheduler.start()                    # 启动调度循环，采集结果写 Redis
  5. ingest_server.start(opcda_mapper)    # 启动 HTTP 服务，推送结果写 Redis
  6. health_checker.run()                 # 启动设备健康检查
  7. await _shutdown.wait()               # 等待退出信号
  8. shutdown()                           # 清理调度、接口服务与设备连接
```

## 六、协议支持

| 协议 | 驱动文件 | 直连支持 | Sidecar |
|------|----------|----------|---------|
| S7 (Siemens) | `s7_driver.py` | ✅ | - |
| GE SRTP | `ge_srtp_driver.py` | ✅ | - |
| OPC UA | `opcua_driver.py` | ✅ | - |
| OPC DA center | `opcda_center_driver.py` | ✅ 通过本机 x86 代理 | - |
| OPC DA sidecar | - | ❌ 64 位 Python 不直连 COM | ✅ `opcda_push_service` -> `/ingest/opcda-tags` |
| HTTP Push | - | - | ✅ `/ingest` |

S7 额外能力：DB 地址保持 `DBX/DBB/DBW/DBD` 标准语义；I/Q/M 区连续或重叠字节会合并为 `%IB/%QB/%MB` BYTE 块读取，再由 `ScanTask.result_map` 和 `TaskExecutor` 还原到变量值。

GE SRTP 额外能力：`%R/%AI/%AQ` 按 word 区间合并，最大 125 words；`%I/%Q/%M` 第一版按 BOOL bit 区间合并，最大 512 bits。真实轨道吊 GE 点位表只读模拟验证为 4539 个可读变量合并成 476 个读取块。DINT/REAL/DWORD 当前默认 `low_high` word 序，现场必须用已知值校验。

## 八、关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| 采集模式 | asyncio + run_in_executor | PLC 驱动为同步库，用线程池包装 |
| 连接方式 | 长连接 + 自动重连 | 避免 PLC 端资源耗尽 |
| 去重策略 | collector 不再做 TDengine 落库去重 | collector 按采集周期输出 Redis 帧；异常状态由实时态、规则与告警链路承载 |
| 批量写入 | 采集模块写 Redis latest/window/stream，独立的 `writer` 模块 500ms/1s 批量写 TDengine `ts + 点位列` | 前端实时监控、可靠队列和历史落库解耦，避免 TDengine 抖动拖慢采集 |
| TDengine 连接 | 独立 `writer/` 模块负责 | collector 不连接、不建表、不直写 TDengine |
| OPC DA 接入 | C# x86 sidecar | 32 位 COM 无法被 64 位 Python 直连 |
| Tag 映射 | var_address → variable_id | 简单直接，无需解析 |
| GE SRTP 合并 | 默认连续合并，不跨空洞 | 降低 PLC 请求压力，同时保留现场字序/地址基准校验边界 |
