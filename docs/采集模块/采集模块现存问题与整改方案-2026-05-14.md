# 采集模块现存问题与整改方案

更新时间：2026-05-14

## 1. 结论摘要

当前采集主链路已经具备上线基础：GE SRTP 已支持按区域连续合并、批量读取、result_map 单点还原；Snap7、OPC DA、缓冲队列、聚合队列、批量写入链路保持可用。

本轮重点结论如下：

1. GE SRTP 的 32-bit 数据不应按大端 word 顺序还原。
2. 对 `%R/%AI/%AQ` 中的 `REAL/DINT/DWORD/UDINT`，当前 `word_order="low_high"` 与 GE PACSystems 文档和本地 `gesrtp-py` 实现基本一致。
3. 仍需用现场已知值校验 `REAL/DINT/DWORD` 字序和 `%I/%Q/%M` 地址基准，并将结果固化到文档和测试。
4. Snap7 `%T/%C` 时间/计数器采集已补齐，并支持连续 Timer/Counter 批量读取与单点还原。
5. 上线前还应补齐 dry-run 配置预检、采集指标告警、数据质量接入和长稳压测。

## 2. GE SRTP 字序结论

### 2.1 查阅资料

本次参考以下资料：

- `FST_DFS_GE_SRTP.pdf`
- `GFK2950D_PACSystemsCPU_ProgRefManual.pdf`
- `Leveraging_the_SRTP_protocol_for_over-the-network_.pdf`
- 本地 `gesrtp-py` 源码：`src/packet.py`、`src/driver.py`

### 2.2 资料证据

`GFK2950D_PACSystemsCPU_ProgRefManual.pdf` 中的 PACSystems 数据类型说明显示：

- `DINT` 使用两个连续 16-bit memory locations。
- `REAL` 使用两个连续 16-bit memory locations。
- `REAL` 的例子说明：如果浮点数占用 `R5` 和 `R6`，则 `R5` 是 least significant register，`R6` 是 most significant register。

这说明 GE PACSystems 中 32-bit 值的 word 顺序是：

```text
低地址寄存器 = 低 16 位
高地址寄存器 = 高 16 位
```

`Leveraging_the_SRTP_protocol_for_over-the-network_.pdf` 对 SRTP 请求包字段的描述显示：

- offset 和 length 字段是 least significant byte first。
- discrete byte 数据从 least significant bit 到 most significant bit 展开。
- `%R/%AI/%AQ` 以 word 方式访问，`%I/%Q/%M/%T` 等离散区可按 bit 或 byte 方式访问。

本地 `gesrtp-py` 的 `src/packet.py` 中：

```python
values = struct.unpack(f'<{word_count}h', self.payload)
```

即库已经把 SRTP payload 中的每个 16-bit word 按 little-endian signed short 解包为 Python `int`。

### 2.3 对当前代码的判断

当前 `collector/collector/executor.py` 中 GE 32-bit 还原逻辑为：

```python
low = values[word_offset] & 0xFFFF
high = values[word_offset + 1] & 0xFFFF
value = low | (high << 16)
```

`REAL/FLOAT` 使用：

```python
raw_bytes = struct.pack('<HH', low, high)
value = struct.unpack('<f', raw_bytes)[0]
```

这与上面的资料证据一致。因此：

| 问题 | 结论 |
| --- | --- |
| GE SRTP 32-bit 类型是大端还是小端？ | 对当前采集代码而言，应按 `low_high` 处理，等价于低地址 word 在前、高地址 word 在后。 |
| 当前 `word_order="low_high"` 是否合理？ | 合理。 |
| 是否可以完全不做现场校验？ | 不建议。不同 PLC 型号、点表定义、库版本或中间网关仍可能带来差异。 |

置信度：0.88

## 4. GE 现场校验建议

上线前建议执行一次小型校验，避免 32-bit 字序和离散地址基准在现场出现偏差。

### 4.1 字序校验

选择：

- 2 个已知 `REAL` 点。
- 2 个已知 `DINT` 或 `DWORD` 点。
- 每个点记录 HMI 显示值或 PLC 在线值。

对比：

1. 单点读取原始 word 列表。
2. 批量读取原始 word 列表。
3. `low_high` 还原值。
4. 如有必要，临时计算 `high_low` 还原值。

验收：

- 若 `low_high` 与 HMI/PLC 在线值一致，则固化当前策略。
- 若 `high_low` 才一致，则必须增加设备级 `word_order` 配置并修正映射。

### 4.2 离散地址基准校验

选择：

- 2 个 `%I` 已知点。
- 2 个 `%Q` 已知点。
- 2 个 `%M` 已知点。

对比：

1. 当前策略：`%I/%Q/%M` 不减 1。
2. 临时策略：`%I/%Q/%M` 减 1。
3. 与 HMI/PLC 在线状态比对。

验收：

- 若当前策略一致，则保留当前实现并写入文档。
- 若减 1 策略一致，则统一修改 `device.py` 和 `ge_srtp_driver.py`，并补回归测试。

## 5. 建议执行顺序

1. 先完成 GE 现场校验记录，特别是 `word_order` 和 `%I/%Q/%M` 地址基准。
2. 强化采集指标、告警和长稳压测。
3. 再考虑 GE 合并策略配置化和 AGV OPC DA 模板化导入增强。
