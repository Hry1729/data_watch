# 边缘运行时实现说明

> 对应《分布式部署架构方案》v14。本文记录已经进入代码的边缘运行契约，不替代总体架构文档。

## 1. 进程与依赖边界

分布式边缘包固定包含 Edge Agent、Edge Storage、Edge Collector、Uploader、SQLite 和边缘 App。

- Edge Storage 通过 `edge/storage_main.py` 启动，默认监听 `127.0.0.1:7073`，是 `edge.db` 的唯一写者。
- Edge Collector 通过 `edge/collector_main.py` 启动。
- Collector 拓扑只从本机配置快照读取，不连接中心 MySQL；配置、设备状态和采集帧通过 Storage IPC 读取或提交。
- `EdgeOutboxWriter` 保留 Collector sink 契约，但实际通过 `EdgeStorageClient` 把采集帧提交给 Storage，由 Storage 事务写入 local latest 与 outbox。
- Uploader 通过 `edge/uploader_main.py` 启动，经 Storage 领取批次和提交 ACK 状态；对中心只使用持久 HTTP 连接访问 Ingest，不直连中心 Redis。
- Edge Agent 负责按 `Storage -> Collector -> Uploader` 依赖顺序启动，并通过 Storage 或只读查询提供本机监控数据。

## 2. Storage 与 SQLite 原子边界

同一个 `edge.db` 保存：

- `edge_config_meta`：配置修订、checksum、可选 `read_timeout_ms`、应用时间。
- `edge_device`、`edge_variable`：本节点设备和点位快照。
- `device_assignment`：assignment epoch、有效采集周期和当前启停状态。
- `edge_assignment_schedule`：assignment epoch、原始 enabled、计划开始和计划停止时间。
- `outbox`、`metadata`、`local_latest_frame`：上传序列、会话、待上传数据和按设备/采集组保存的本机最新值；升级后的 Agent 仍可读取旧 `local_latest` 点位表。
- `edge_device_status`：Collector 本机连接状态。

配置快照先计算规范 JSON 的 SHA-256；checksum 不一致时拒绝应用。设备、点位、assignment 和修订号在一个 `BEGIN IMMEDIATE` 事务内切换，失败保留上一代完整快照。

Collector、Uploader 和 Agent 不再各自打开 SQLite 执行写事务。写命令进入 Storage 有界队列，由专用写线程串行执行；队列满、Storage 不可达或事务失败必须显式返回错误，不得把未持久化数据报告为成功。SQLite 继续使用 WAL，已提交事务在进程重启后保留。

每个采集帧只对 `local_latest_frame` 执行一次 JSON 快照 UPSERT，并在同一事务内写入 outbox，不再按点位逐行更新最新值。Collector 与 Uploader 各自复用一条串行的 HTTP/1.1 本机连接访问 Storage；请求体使用 `msgspec` 编解码，既保留 Storage 单写者约束，也避免反复建连和多线程共享连接池的竞争。

Storage 状态接口为 `GET http://127.0.0.1:7073/v1/status`，健康接口为 `GET /healthz`。关键指标包括：

- `writer_queue_depth / writer_queue_capacity`；
- `commit_p99_ms`、`errors_total`；其中提交延迟包含命令在 Storage 队列中的等待时间；
- `frames_per_second`、`points_per_second`；
- outbox 各状态数量、数据库总字节数、有效字节数、可回收字节数、空闲页比例、磁盘水位和累计丢弃数。

## 3. 采集与上传

Uploader 根据本节点已启用 assignment 的最小有效 `scan_rate_ms` 计算上传节拍，没有有效点位时休眠。每个节拍通过 Storage 快照 `target_seq=last_seq`，然后严格按序、单批次在途地上传至该水位；不发送空批次，离线恢复后连续追赶。

Uploader 到中心的网络请求使用 `httpx.AsyncClient`；对本机 Storage 的同步 IPC 调用通过 `asyncio.to_thread` 隔离，避免 Storage 超时阻塞上传事件循环。调用仍逐个等待完成，不增加并发批次，不改变严格按序和单批次在途契约。

Uploader 记录网络、认证、限流、服务端错误、ACK 异常和暂停原因，并每 10 秒输出批次、记录数、数据量、记录速率和批次 P99 摘要。Agent 的上行监控日志直接读取该模块日志文件，因此上传停滞时必须能够定位到具体响应语义。

Collector 每次加载 SQLite 快照时同步读取可空 `read_timeout_ms`。该值进入设备配置和热更新签名，因此仅修改节点读取超时也会重建本节点设备连接。未配置时保持各协议驱动原有默认；显式配置时同时下发到 S7 send/recv、GE socket、OPC UA client 和 OPC DA IPC request timeout。Executor 到达逻辑 deadline 后记录超时并拒绝迟到样本，但会等待底层调用实际退出后再释放同设备在途状态，避免下一周期与迟到调用并发。该设置不改变点位 `scan_rate`，允许大于点位周期。

网络错误、5xx 和限流保留原 `batch_id/upload_session_id/local_seq` 进入重试。401/403 暂停当前批次。ACK 的 `ack/duplicate/stale_config_warning` 进入 sent，`rejected_consumed` 进入 dead，`seq_reject/commit_unknown` 执行受控 session 切换。

`session_obsolete` 对账后若中心仍确认当前 session 有效，当前批次退回重试，避免记录永久停在 inflight 阻塞后续序号。

## 4. 本机运维 API

Edge Agent 仅在 `DATAWATCH_ROLE=edge` 时开放：

- `GET /local/devices`
- `GET /local/collector`
- `GET /local/storage`
- `GET /local/outbox`
- `GET /local/uploader`
- `GET /local/logs?module={collector|storage|uploader}`
- `GET /local/monitor/devices`、`GET /local/monitor/points`

非 edge 角色返回 404。接口默认跟随 Agent 监听 `127.0.0.1`，并沿用 Agent JWT 鉴权。

## 5. 边缘 App

edge 构建使用独立 Agent 端口和边缘导航。App 登录请求先到仅监听 localhost 的 Edge Agent，由 Agent 使用初始化时保存的中心 MySQL 连接校验中心 `sys_user/sys_role`；不再创建或维护本地用户密码。中心 Backend 不可达但中心 MySQL 可达时仍可登录；已登录期间中心网络中断时，现有 Agent 会话可继续访问本机运维和监控数据。完全断网且会话已失效时不能新登录，这是中心单一账号源的明确边界。首屏显示本机设备、配置修订、Collector/Storage/Uploader 进程、上传节拍、SQLite 大小、磁盘水位、累计丢弃数和离线积压，并提供管理员密钥轮换操作。

构建采用条件动态导入；中心工作台、Writer 和系统管理页面不会进入 edge 前端产物。edge 构建包含只读点位监控、实时监控和历史数据页面，只展示分配给本节点的设备。在线时业务数据经中心 Backend 读取；中心网络异常或 5xx 时自动回退到本机 SQLite 快照、`local_latest` 和保留期内 outbox 历史。401/403 不回退，避免绕过中心权限。

## 6. 节点身份、注册与配置同步

- 首次引导生成稳定的 `node_uuid` 和 Ed25519 密钥对；私钥经 Windows DPAPI 加密后写入本机 `config.toml`，公钥随一次性注册码提交中心。
- 身份在网络请求前持久化。中心注册接口对“同注册码 + 同 node_uuid + 同公钥”重试幂等，覆盖中心已提交但响应丢失的 `commit_unknown` 场景；注册码被其他节点使用或公钥不一致时拒绝。
- edge App 不保存本地用户密码。Edge Agent 直接校验中心 MySQL 的 PBKDF2-SHA256 密码哈希并读取启用角色，Agent JWT 携带同一组角色；账号、密码和角色只在中心维护。
- Edge Agent 后台发送签名心跳，携带本地 applied revision、outbox 积压、Collector/Storage/Uploader 状态、Storage 队列与提交指标和边缘时间。中心返回 desired revision；不一致时 Agent 拉取快照并通过 Storage 原子应用。
- 每次心跳都使用中心 `centerTimeMs` 推进计划启停；Collector 每轮配置轮询前再按受时钟偏差监控的本机时间刷新一次。开始/停止只改变 SQLite `enabled`，复用现有设备热增删，不改变设备独立调度、点位 `scan_rate` 或同设备串行约束。
- 控制面心跳周期与点位 `scan_rate`、Uploader 上传节拍相互独立。点位采集频率仍由业务配置决定，Uploader 仍只取本节点最小有效 `scan_rate_ms`。
- Storage 根据 Uploader 发起的维护命令清理终态记录：中心已接管的 sent 保留 60 秒，永久失败的 dead 保留 `max_offline_retention_days`；pending/retry_wait/inflight 不按终态保留期清理。维护执行 PASSIVE checkpoint，有删行时执行 TRUNCATE checkpoint。新建数据库启用 incremental auto-vacuum，删除终态记录后分批归还空闲页；既有数据库继续复用空闲页，切换 auto-vacuum 模式需要离线维护。磁盘达 70%/85%/95% 分别进入 warning/critical/overflow；95% 时先清理终态并重新测量，仍超限才放弃当前 session 全部未发送积压、累计丢弃数并受控切换 session。
- 身份轮换先以 DPAPI 保存 `pending_private_key_enc`，再提交中心。响应丢失时复用同一待提交密钥重试；成功后提升为当前私钥、清除 pending 并重启 Uploader。

三个固定角色分别使用独立 Agent 端口、ProgramData 数据根和 runtime 目录，避免并存安装时 PID、日志、SQLite 和配置互相覆盖。
## 7. 边缘初始化页面

edge 前端构建使用专用 EdgeBootstrapPage。用户先填写中心 HTTP(S) 地址，页面自动将 URL 主机同步到 MySQL、Redis、TDengine 三项中心连接配置，并保留端口、账号、密码和数据库名的独立修正能力。三项数据库必须分别测试成功后，页面才保存 Backend 与数据库配置、提交节点名称和一次性注册码，并完成初始化；页面不创建本地管理员账号。

节点身份在注册请求前落盘；中心已提交但响应丢失时，用户使用原注册码重试，仍沿用同一 node_uuid 和公钥。若注册已经成功但初始化完成步骤被中断，页面读取本地状态后只需完成初始化，不重新生成身份。

前端按 VITE_DATAWATCH_ROLE 条件动态导入初始化页。构建验证要求：edge 产物包含 EdgeBootstrapPage 且不包含中心 BootstrapPage；centralized 和 distributed-center 产物执行相反约束。
