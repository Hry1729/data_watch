## 四、方法库（避免后来人重犯）

1. **依赖探测必须设 `PYTHONUTF8=1`**：turboapi 导入时打印 emoji，GBK 控制台下抛 `UnicodeEncodeError`，会被 `$LASTEXITCODE` 误判为 "MISSING"（本步骤真实踩过）。
2. **不要用 PowerShell 管道做字节比对**：`git show HEAD:file | Set-Content | Get-FileHash` 会因换行改写得到**假不匹配**；用 `git hash-object` vs `git rev-parse HEAD:path`，或直接看 `git diff HEAD` 是否为空。
3. **PowerShell 去空白不要用 `-replace '\s',''`**：会删掉路径**中间**的空格（`D:\Program Files` → 无效路径）；用 `Trim()`。
4. **测真实入口不要绕过入口自身的 sys.path 处理**：`ingest/app/main.py` 依赖仓库根包，应从仓库根运行 `ingest.main`；用 `python -c "import app.main"` 从 `ingest/` 测会得到假失败。
5. **子进程不继承 pytest 插入的 sys.path**：需要导入本模块包时，用 `cwd=` 指向模块目录（模拟生产运行方式），不要依赖父进程的路径注入。
6. **venv 的 `Scripts\python.exe` 可能是转发器**：`kill()` 它不等于杀掉持锁/持资源的真实解释器进程；判断进程归属要看 PID 是否与子进程自报一致。

## 十、步骤 3 进行中：B33 取证完成，实现待续（**未修改代码**）

**已取证的三个事实（packages/ge_srtp/ge_srtp/driver.py）**：

1. `read()`（L147）持 `self._read_lock`（L158），内部用 `loop.run_in_executor(self._read_executor, ...)`
   执行**阻塞** socket I/O，共 **4 处**（L204、L290、L370，以及多通道的 `_read_parallel_blocks`）。
   线程**无法被取消**。
2. **取消会提前释放锁**：收到 `CancelledError` 时 `async with self._read_lock` 立即退出，而此时
   executor 线程仍在读写同一个 socket ⇒ 新代可拿到锁并在**同一 socket 上并发读**，协议帧交错。
   清单所述"不能以 await 已取消证明线程已停"成立。
3. **`disconnect()`（L132-145）不取 `_read_lock`**（已核对：该函数体内无 `_read_lock`）⇒ 它可以在
   在途读进行中关闭/替换连接，**"退出确认"完全缺失**。这是清单所说"尤其未配置逻辑 read_timeout
   的路径"之外、更直接的一处缺口。

**拟定修法（下轮实现并验证，不采用"只加协程锁又在取消时提前释放"）**：

- 新增 `_run_blocking(func, *args)` 包装全部 4 处 executor 调用：正常路径直接 await；
  `CancelledError` 时**先等待该 future 真正结束**（有界 drain 超时）再把异常抛出去，
  从而让 `_read_lock` 一直持有到底层 I/O 结束——即"取消后保留在途状态至真实读结束"。
- drain 超时仍不退出时，**强制关闭底层 socket**（`driver.sock.close()`）把线程逼出来，并把该连接
  标记为不可复用（下次连接重建）——即清单给出的"关闭/替换连接并隔离旧代"分支。
- `disconnect()` 与在途读建立明确串行（取同一把锁）或走显式 abort 路径，二者择一但必须**明确**。

**验收计划（下轮据此写回归）**：慢同步读期间同连接热重载；换连接配置；有/无 read_timeout；
停机。断言：同一 socket 不出现两个底层读；迟到结果不覆盖新代；取消后锁在真实读结束前不被释放。

**为什么本轮不改**：这类并发修复的完成判据是"慢读期间热重载"的注入验证，仅靠阅读无法证明；
按既定原则，未验证不写成完成，也不在半途改并发路径。

- 保持 `run_if_current_generation` 的 check→write 在锁内不变（原子性不动）；
- 把**事件循环侧**的失效入口改为不阻塞事件循环：`invalidate_device` / `swap_device` 的调用点

## 十四、步骤 3：B46 取证完成（两半均有确定机制与修法；**代码已回退，未半改**）

### B46.1 deadline 统计双计 —— 机制已确认（collector/collector/scheduler.py:189-209）

```python
for task in due:                                   # 逐 task
    lag_ms = max(0.0, (now - next_due[task.task_name]) * 1000)
    self._metrics.record_timing("deadline_lag_ms", lag_ms)
    if lag_ms > task.scan_rate * 1000 * ratio:
        self._metrics.increment("deadline_miss_count")      # ← 计数①（逐 task）
if not self._try_begin_device_execution(lead_task):          # 设备仍在执行上一周期
    self._metrics.increment("device_inflight_skip_count")    # ← 计数②（逐设备）
    await self._sleep(...); continue
```

**两个问题**：
1. **同一到期周期被计两次**：先记为"迟到"（deadline_miss_count），紧接着又记为"因在途跳过"
   （device_inflight_skip_count）⇒ 两计数器**语义重叠**，相加必然高估漏周期；
2. **粒度不一致**：miss 逐 task、skip 逐设备 ⇒ 一次跳过可把 miss 放大 N 倍（N=该设备到期 task 数），
   同一事件在不同计数器里以不同粒度出现，无法对账。

**建议的计数定义（互相排斥，可对账）**：
- `deadline_lag_ms`（timing）：到期 task 的实际滞后——保持；
- `deadline_miss_count`（逐 task）：**该 task 到期且确实开始了执行，但开始得晚**（滞后超阈值）；
- `device_inflight_skip_count`（逐设备尝试）：**该到期周期因设备仍在执行上一周期而未启动新执行**；
- 实现：把滞后/漏期记账**移到 `_try_begin_device_execution` 成功之后**，失败分支只计 skip。
  于是每个到期周期恰好落入 {准时开始, 迟到开始(miss), 因在途跳过(skip)} 三者之一。
- 验收：**可控时钟**验证每类计数（清单明确要求"可控时钟验证每类 deadline 计数"）——
  `ExecutionScheduler` 已有 `self._clock` 注入点（scheduler.py 使用 `self._clock`），可据此构造。

### B46.2 同地址合并丢失类型语义 —— 机制已确认，且**发现了更关键的下游阻塞**

事实链：
1. `executor.py:348-356` 合并键**只有 `block.address`**，冲突时 `block.count > existing.count`
   取胜 ⇒ 同地址不同 `data_type`（S7 同一字区按 INT 与 TIMER_MS/COUNTER 解码，或离散区按
   BYTE 成组）会被整块丢掉一套类型语义；清单所说"count 更大不证明可覆盖不同类型语义"成立。
2. **下游键控是地址级**：S7 驱动 `_read_blocks` 用 `result[block.address] = values`
   （packages/s7/s7/driver.py:137-142），且**解码在驱动内按 block.data_type 完成**（L353-381）。

**我尝试过的修法与为何回退**：把合并键改为 `(address, data_type)` 后会出现**同地址的两个块**，
它们在驱动返回的字典里**互相覆盖**，谁覆盖谁取决于顺序 ⇒ 由"确定性但类型错"变成
**不确定性**，更糟。**已完整回退**（工作区与 HEAD 一致，py_compile 通过），不留半成品。

**可行的修法（择一，均为采集器侧，不碰签名包）**：
- **A（推荐）冲突即不合并**：按 `(address, data_type)` 建表；若某地址出现**多于一种** data_type，
  则本次**放弃合并**，改为**逐 task 单独 `read()`**（即回到"未合并基线"的语义与结果）。
  满足验收"结果与未合并基线一致"，且不产生同地址块冲突、不引入不确定性；代价是这类设备失去
  合并收益（正确性优先）。需要核对 `execute_many` 的结果消费路径以支持"一趟多次 read"。
- **B 统一原始字节读后独立解码**（清单提到的另一条）：驱动只回原始字节、由采集器按点各自解码。
  语义最干净，但改动面大且可能触及驱动包 ⇒ 与 B33/B36-B 一样受签名打包约束。

## 二十、步骤 4：B29 取证完成（**代码未改**，方案与验证计划已定）

### 已核实的事实

- `writer/mysql_mapper.py`：`get_or_load` / `reload` / `load` 在**映射缺失时返回 `None`**，
  且**不缓存这次未命中**（`_cache` 只在成功时写入）⇒ 同一个 `(device_code, group_code)` 的未知
  var_id 会**每帧触发一次 MySQL 查询**（"重复 MySQL reload"成立）。
- `writer/consumer.py`：未知 var_id 的 reload 失败后日志为
  "mapping reload failed for device=... group=... unknown var_ids=..., **leaving entry pending**"
  ⇒ **不 ACK、原消息保留**（这一点实现已正确，符合"不因暂时缺映射 ACK 掉"）。
- 因此缺陷**只在请求放大**这一侧：高频缺映射时 MySQL 请求无界，且条目长期留在 PEL。

### 拟定修法（下轮实现）

- 在 `MysqlMapper` 增加**短期负缓存 + 退避**：`_negative_until: dict[key, monotonic_deadline]`，
  `negative_ttl_s` 默认取小值（秒级，可配置）；命中负窗口时 `get_or_load`/`reload` **直接返回
  `None` 不再查库**，从而把"每次请求 → 有界请求"。
- 同时提供 **`invalidate(device_code, group_code)`**（或 `invalidate_all()`）用于"**快速失效**"
  —— 收到失效事件（如控制面 `ingest:control:invalidate` 对应的事件、或配置版本变更）时立即清除
  负窗口，避免"新点被陈旧负缓存屏蔽"。
- **关键约束**：负缓存必须**只在缺失时**生效，成功加载后不得残留；TTL 必须足够短，使"补齐映射后
  及时恢复"即使没有失效事件也能在该窗口内自愈（验收"新点不被陈旧负缓存永久屏蔽"）。
- **不改** `_handle_entry` 的"不 ACK、保留 pending"语义。

### 前三次失败的结构性根因（本轮才诊断清楚）
`_delete_ids()` 是在 `_ack_ids()` 的**同一个 `try` 内、紧跟 `self._r.xack(...)` 之后**被调用的

2. 若该查询抛异常，会被 `_ack_ids` 的 `except` 捕获，条目被记进 **`_ack_retry`** 而不是 `_delete_retry`

## 三十二、本轮整改（工作单阶段一）：问题 1 —— B50/S3 秘密文件权限闭环

### 独立核实的结论（与审查描述**有出入**，如实记录）

审查称"`HardenDataPermissions()` 递归给 Users 授权后，`HardenTokenFile()` 可能保留显式 Users 读取"。
本轮用**隔离目录 + 真实 icacls** 做判别性实验，结果如下：

| 实验 | 观察 | 结论 |
|---|---|---|
| A 目录授 `Users:(OI)(CI)RX`，看文件 | 文件显示 `BUILTIN\Users:(I)(RX)`（**继承**）| 递归 `/T` 在**文件上不产生显式 Users ACE**（`OI/CI` 是目录专用标志）|
| B 再跑**旧形态** `/inheritance:r /grant:r 544/18` | Users **消失** | 对**继承**的 ACE，旧形态**已经足够** |
| C2 文件上先加**显式** `Users:(RX)`，再跑旧形态 | `BUILTIN\Users:(RX)` **仍在**（无 `(I)`）| **一般性弱点成立**：旧形态无法回收未列出 SID 的**显式** ACE |
| C3 追加 `/remove:g` 广域 SID | Users **被移除** | 加固有效 |

⇒ **审查描述的具体路径（经 HardenDataPermissions `/T`）未复现**；但**"白名单不成立"的一般性弱点成立**，
所以本轮按"**加固保证**"实施，而不是按"已复现的普通用户可读"实施。

**另发现（本轮记录，未改）**：递归 `/inheritance:r … /T` 之后，**文件上的 ACE 会全部消失**
（`OI/CI` 落到文件退化为 inherit-only，不作用于自身）⇒ 文件 DACL 实际为空。这会影响数据根下
**所有**文件，且是否影响功能取决于服务运行身份（管理员/SYSTEM 不受影响；专用低权账户可能读不到
自己的令牌文件）。**需目标机核实**，本轮不做该改动（属 `HardenDataPermissions` 的行为变更，超出最小修复范围）。
