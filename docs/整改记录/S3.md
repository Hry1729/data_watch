**对 W0-B 任务卡的一处修正（必须保留）**：W0-B §1 表格把 `storage_service.py:224-234` 的 `outbox.complete` 记为「**把任意行置 `sent`/`dead`**」。实测更精确：

1. **单发** `outbox.complete` **会被挡回**。`edge/app/outbox.py:428-468` 的 `complete_batch` 要求 `WHERE ... AND state='inflight' AND lease_owner=?`，行数不为 1 且状态不相等时抛 `RuntimeError("outbox terminal transition lost lease")` → HTTP **500**，行状态不变。实测输出：`[C] unauth outbox.complete(state=sent) -> HTTP 500 {"ok":false,"error":"outbox terminal transition lost lease"}`（改前第一次尝试即如此）。
2. 但**未认证进程可以先抢租约**，构成完整 3 步链（改前全部 HTTP 200）：
   - `outbox.recover {lease_owner:"attacker"}` —— `edge/app/outbox.py:331-343` 把 `lease_owner <> ?` 的 inflight 行重置为 `pending`，即**抢走合法 Uploader 的租约**；
   - `outbox.claim {lease_owner:"attacker"}` —— 以攻击者身份重新领取；
   - `outbox.complete {lease_owner:"attacker", state:"sent"}` —— 此时租约匹配，**成功**。
3. 因此「未确认数据被未授权 complete」结论**成立**，但必须按 **3 步链**描述，不能写成单发即成功。

### 最小修改（文件与行为差异）

#### 1. 信任边界选型

采用「**专用最小权限身份 + 受 ACL 保护的本机令牌文件**」：

- 令牌文件位于 **deployment 级**路径（`edge_database_path().parent / "storage-ipc-tokens.json"`，可用 `DATAWATCH_EDGE_STORAGE_TOKEN_FILE` 覆盖），**不是** per-database、也不是世界可读的临时目录。
- 服务端首次启动时生成每角色 32 字节随机令牌（`secrets.token_hex(32)`），并用 Windows 自带 `icacls /inheritance:r /grant:r <属主>:F *S-1-5-18:F *S-1-5-32-544:F` **尽力**收紧 ACL（失败只记 WARNING，不阻断启动）。
- **默认拒绝**：`/v1/command` 与 `GET /v1/status` 无有效 token → **401**；角色越权 → **403**；只有 `/healthz` 保持开放（仅返回 `{"status":"ok"}`，不读不写任何存储状态）。
- **角色 = 由 token 反查**（`hmac.compare_digest`），不接受客户端自报角色，避免角色伪造面。

**每角色命令白名单（依据真实调用点推导，非猜测）：**

### 被否掉的方案及原因

| 方案 | 否决原因 |
|---|---|
| **「无法识别调用方时回退到全量 `edge` 角色」** | 我曾短暂实现以保住既有零配置用例，**协调者与本 agent 一致否决**：这等于给任何未识别进程发一张全权限凭据，把本次修复作废。已**彻底删除**该角色，`resolve_client_role()` 现返回 `None` 并 fail-closed。 |
| 复用 `DATAWATCH_AGENT_SERVICE_TOKEN` / Agent service token | 清单原文明确禁止（「不要复用拥有广泛管理权的 Agent service token」），且会扩大 Agent 管理权限面。 |

| 命名管道 / 受 ACL 保护的本机传输（替代 HTTP） | 需同时重写服务端与全部调用方（含安装器内的进程间契约），远超「最小且可用」；且 `http.server` 在 Windows 上无对端身份（无 `SO_PEERCRED` 等价物）。列为跨模块候选。 |

### 5. 锁文件每次失败 append 1 字节（**本轮只登记，不修**）

**确实存在**，位置 `edge/app/uploader.py::SingleInstanceLock.__enter__:638-647`：文件以 `"a+b"` 打开后**无条件** `seek(0); write(b"0"); flush()`，而 write 在 append 模式下总是落在文件末尾 —— 且发生在 `msvcrt.locking(...LK_NBLCK)` **之前**，所以**每次加锁失败都 +1 字节**。

```text
after successful acquire: size=1
failed acquire #1 -> RuntimeError(another uploader instance is running); size now=2
failed acquire #2 -> ... size now=3
failed acquire #3 -> ... size now=4
failed acquire #4 -> ... size now=5
failed acquire #5 -> ... size now=6     bytes = b'000000'
```

对照：`collector/storage/collector_outbox.py::_acquire_owner:166-169` 有 `seek(0,2); if tell()==0:` 守卫，同样 5 次失败后 `size` 恒为 `1`（**不增长**）。

**影响评估**：单次 1 字节，只在「另一个 uploader 实例持锁」时发生；正常运维下可忽略，但若被守护进程/脚本以秒级频率反复重启，锁文件会无界增长（纯 `b"0"` 垃圾，无功能影响，只占磁盘且永不回收 —— 该文件设计上不删除）。**修复只需 1–2 行**（把 `write` 放进与 collector 相同的 `tell()==0` 守卫），但需要改 `edge/app/uploader.py`，**不在本轮允许清单内**，故只登记。建议协调者单独授权。

### 3. (C) bind 失败分类：从「只覆盖地址族」补齐到「覆盖全部 bind 失败」

**(ii) 复核结论：观察者判断正确，这是未满足的要求，不只是待验证项。** 本 agent 独立实测（改前）：

```text

   tail: OSError: [WinError 10049] ...
```

**根因（实读代码）**：`StorageEngine.__init__` 只赋值 `database_path`、**不建线程、不碰文件**
（DB 在 `_run` 中打开，`:275`）；`engine.start()` 才启动 **非守护** `edge-storage-writer` 线程
（`storage_service.py:194`）。异常发生在 `engine.start()` **之后**、`try/finally` **之前**，
线程无人收尾 ⇒ 进程挂死且无监听。此前本 agent 加在 `storage_main.py` 的 `_ipv4_resolution_error()`
只是 `getaddrinfo(AF_INET)` **预检**，覆盖不到端口占用/EADDRNOTAVAIL —— 观察者所述情况成立。

**修法（只在 `edge/storage_main.py`，最小改动）**：

1. 把 **bind（`StorageHttpServer(...)` 构造）移到 `engine.start()` 之前** —— 绑定失败时既没有
   非守护线程，也没有数据库写入（`database_path` 在 `__init__` 里不落盘）；
2. 新增 `_bind_error_message()`，按**真实异常**（`socket.gaierror` / `errno.EADDRNOTAVAIL` /

   **不得**出现 `Cannot bind Edge Storage IPC`。
