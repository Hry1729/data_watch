### 遗留问题（B41）

1. **R11（较重要）**：「崩溃后重启按状态文件恢复」在真实 CLI 入口**不可达**——崩于第 1 次移动后 `current` 缺失，`apply()`/`rollback()` 的前置检查都会拒绝，脚本永不再启动；且 CLI 自身就住在 `current` 内。建议后续把 reconcile 做成可从 CLI 侧显式触发的入口（例如不依赖 `current` 的 `data-watch update recover`），或让 `_require_windows_install` 在存在 `swap-state.txt` 时放行到 reconcile。
2. **R10（中）**：rollback 崩溃窗口 + `state=rollback:displaced` 重启会**永久删除被淘汰版本**并可能留下无 `current` 的目录（仅 `failed` 有副本）。可达性受 `rollback()` 前置检查限制，需人工触发。
3. **R9（中）**：阶段状态写入失败时 `current` 可能是**未经校验的新版本**，与 B41.md §5.1-2 的「任何失败路径下 current 一定是旧版本」表述矛盾（硬性验收要点仍满足）。建议把阶段状态改为「先写临时文件再原子改名」，或在 `Restore-*` 前用 `swap-state.txt` 内容与目录实际状态交叉判定。
4. 「完整性判据只有 `data-watch.exe` 是否存在」：**确认为残留风险，但非可触发缺陷**。我独立复核了修复者的边界分析：半截 `previous` 只出现在 `Remove-Item $previous` 阶段，而该阶段 `current` 必在，且随后 `Test-Path $previous` 守卫会 `throw`，`Restore-MissingCurrent`（要求 `previous` 含 exe 且 `current` 不存在）不会把它提升为 `current`；版本可用性实际由脚本运行 `data-watch.exe version` 自检兜底，比「仅存在性」更强。**残留**：`previous`/`failed` 的残留不做哈希级校验、`failed` 中的未验证版本无自动回收策略。
