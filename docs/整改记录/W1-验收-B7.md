## 3. 我构造的反例与结果

### 3.1 核心正向（清单验收要求：合法帧不得 `rejected_consumed`）
1. TTL=3600s 人为保留旧缓存（v1 / points={1}）→ 控制面已提交 `config_version=2` + 新点位 `2`，**全程不投递失效通知** → 送合法帧（point 2 / v2）：**`accept`**（HEAD 同场景为 `consume_reject/rejected_consumed`）。
2. 仅版本前移（点位不变）→ v2 帧：**`accept`**。
3. 多 worker（3 个独立缓存实例）：各自完成一次权威重读并 `accept`，**不依赖 pub/sub 送达**（实测每个 worker 各 +1 次 assignment / mapping 读）。
4. 服务层入口 `IngestService.ingest`（真实服务对象 + 最小 store 替身）：落后缓存下的合法帧返回 **`ack`**、store 收到 `accept`。

### 3.2 反向检查（本轮最关键）—— 非法/越权点**仍然被拒绝**
我在自己的夹具上**重新构造**了三条（未复用修复者的断言），并额外证明「拒绝前确实发生过权威重读」，即拒绝不是"没查库就拒"：

| 反例 | 结果 | 附加证明 |
|---|---|---|
| 映射外 `point_id=99`（缓存命中态） | `consume_reject` / `rejected_consumed` / `malformed_envelope:unknown_var_id` | `mapping_reads` **+1**（强制权威重读确实发生），`assignment_reads` **不变** |
| `config_version=99` 领先控制面 | `consume_reject` / `rejected_consumed` / `unknown_config_version` | `assignment_reads` **+1**，`mapping_reads` **不变** |
| `node_uuid` 不匹配（越权） | `consume_reject` / `rejected_consumed` / `stale_epoch` | 不属可重读集合，未触发放宽 |
| `device_type` 不匹配 | `consume_reject` / `rejected_consumed` / `malformed_envelope:device_type_mismatch` | 同上 |
| **服务层入口**送映射外帧 | `results = ["rejected_consumed"]`、store action = `consume_reject` | 反向结论穿过真实服务入口 |

**真实隔离 MySQL 上同样成立**（`test_adv_isolated_reverse_illegal_point_still_rejected_real_db`，3 passed 之一）：真实表 + 真实提交下，映射外点位、领先版本、节点不匹配三类**全部仍被 `rejected_consumed`**。

> **结论：不存在「为消除误拒而删除拒绝逻辑」的假修复。** 这是本轮最需要排除的风险，已排除，且证据等级为隔离集成。

### 3.3 并发 / 击穿
- **并发冷 miss 未被 single-flight 合并**：8 个并发冷 miss → `assignment_reads=8, mapping_reads=8`；**HEAD 改前完全相同（8/8）** → 属**既有**行为，非 B7 引入，B7 也未修（其「并发 miss」主张的准确含义是"不重读本次已由 miss 直接读到的 key"，这一点成立）。
- **并发非法帧的额外重读被合并**：8 个并发同 key 非法帧 → 只多 1 次 mapping 读（`_claim_reread` 在同一次事件循环内 check-then-set，无 await 间隙）。
- **读放大实测**：同一 key 连续 30 帧非法 → 仅 +1 次 mapping 读；50 个**不同** key × 每 key 10 帧非法 → `assignment_reads=50`（纯冷 miss）+ `mapping_reads=100`（50 冷 miss + 50 强制重读），`_reread_at` 条目 = **50**。
  即：**每个不同 key 每个 TTL 窗口最多 +1 次对应命名空间的强制读**，命名空间精确（非法点位帧不消耗版本帧的重读配额，实测 assignment 读数为 0 增量）；副作用是 `_reread_at` 随不同 key **无界增长**（修复者在 §10.7 已如实登记，我确认其线性增长）。

## 4. 残留问题（我独立验证的结论）

### 4.1 残留窗口（修复者 §10.4 自述）—— **真实存在，但上界被低估 5×**
确定性复现（单元 + **真实隔离 MySQL 各一次**）：
1. 同 key 先来一帧**同命名空间**的非法帧（映射外点位）→ 触发强制重读并写入 `_claim_reread` 冷却；
2. 控制面随后**真实提交**新点位 + `config_version=2`，通知丢失；
3. 冷却抑制重读 → **合法帧仍被 `rejected_consumed`**（`malformed_envelope:unknown_var_id`）；
4. **归因证明**：同样的旧缓存内容、但没有冷却记录（新进程/新实例）→ **同一帧 `accept`**。
   版本命名空间同样可复现（先 `config_version=99` 帧占冷却，再 v2 合法帧 → `rejected_consumed / unknown_config_version`）。

**我的判断**：该窗口**不是理论推测**，可在真实库上确定性复现；由于 `_claim_reread` 冷却窗口 = `_control_cache_ttl_seconds`，生产默认 TTL 是 **30s**（非报告所称 5s），窗口上界实测口径为 **≈30s**（缓存侧过期上界 ≈36s＝30s×1.2）。且**被判 `rejected_consumed` 的帧在 edge 侧直接记 `dead`、永不被 claim（我代码级复核：`edge/app/uploader.py:336-348` → `dead`；`edge/app/outbox.py:403/437/621` 的 `state IN ('pending','retry_wait','inflight')` 排除 `dead`）**，所以它是**有界但真实的数据丢失窗口**，不是"只是延迟"。彻底消除确如修复者所言需要把"缓存依赖型驳回"改为可重试状态 —— **属架构决策，本轮未做，我认同该定性**。

### 4.2 `device_type_mismatch` 缺口（修复者 §10.6 自述）—— 独立复现确认
缓存里旧 `device_type='qc'` + 控制面改成 `qc2` + 通知丢失 → 合法帧 `rejected_consumed / malformed_envelope:device_type_mismatch`，**未发生权威重读**（`assignment_reads` 增量 0）；补发 `{"scope":"assignments"}` 后**立即恢复 `accept`**。确认：**仅靠通知修复，通知丢失时永久拒收**（上界仍受 30s TTL 约束，非永久，但该帧已 dead）。

### 4.3 **修复者未披露的同类缺口：`unknown_device` 不可重读**（本轮新增发现）
`assignments.get(key)` 为 `None` 时会**负面缓存**（`_assignment_cache[key] = (expiry, None)`），而 `unknown_device` **不在** `_REREADABLE_REASONS` 内。确定性复现：
1. 点位/设备已存在但 `device_assignment` 尚未创建 → 帧被判 `unknown_device` / `rejected_consumed`，同时把 `None` 缓存一个 TTL；
2. 控制面**真实提交** assignment（同 node / 同 epoch），通知丢失；
3. 同 key 下一帧：**`assignment_reads` 增量 0（未重读）**，仍 `rejected_consumed / unknown_device`；
4. 补发 `{"scope":"assignments"}` → **`accept`**。
   单元 + **真实隔离 MySQL** 双复现通过。这与 B7 是**同一类缓存落后缺陷**，只是 reason 不同；修复者只登记了 `device_type_mismatch`，**漏登 `unknown_device`**。它同样受 TTL 约束（非永久），但同样会让该帧在 edge 侧变 `dead`。

### 4.4 其它（我核实）
- `_publish_control_invalidation` 仍吞噬异常（**既有行为，未改动**）：提交成功但发布失败时响应仍成功（其测试 + 源码双确认）。修复者已登记「未加发布失败可观测计数」→ **通知丢失率运行期不可度量**，我确认此缺口存在。
- 我只读复核了放大链：`rejected_consumed` → `dead` → 永不 retry（`uploader.py:336-348`、`outbox.py:403/437/621`），与修复者 §3 的代码级结论一致；**端到端故障注入（真实 edge 进程）我未执行**（修复者也未执行），故「一帧被误判后确实永久丢失」仍止于代码级 + 单元级。

## 9. 最终裁决

**证实**（核心主张），附 3 项必须结转的遗留问题。

- **修复确实成立**：`ingest/app/repository.py` 在永久拒绝前做**受控权威重读**，且受控性经我独立验证成立 —— ①按命名空间精确重读（非法点位帧不消耗版本帧配额，实测 assignment 读数为 0 增量）；②两轮固定顺序 `mapping → assignment`（映射补充后暴露版本落后的串行场景可恢复）；③**只重读「本次由缓存命中」的 key**（并发 miss 已权威读到，不重读，实测）；④同一 key 每 TTL 窗口至多强制重读一次（实测 30 帧非法 → +1 读；8 并发非法帧 → 合并为 1 次）。
- **控制面修复确实成立**：13 个变更路由在**服务层返回（事务已提交）之后、return 之前**各发布 `{"scope":"assignments"}` + `{"scope":"mappings"}` 两条；复用同一发布函数（频道/JSON 契约唯一）；发布异常被吞不影响已提交响应；覆盖完整性经我独立核对（两张表的**全部**写入点都在 `catalog.py:2128` 与 `device_point_group` 各 UPDATE/INSERT 处，其所属 6 个服务方法各自只有 1 个调用方，全部落在这 13 个路由内；`device_type` 表在 backend 无任何写入方）。
- **「判定/拒绝规则一字未改」经独立验证为真**：`_validate_item_row` 等 6 个关键函数与 HEAD **逐字节相同**；反向检查确认非法/越权点仍被 `rejected_consumed`（含真实库）。
- **清单验收要求逐条达成**：人为保留旧缓存并立即上传新点 ✓；修改后新版本 ✓；通知丢失 ✓；多 worker ✓；合法帧不得 `rejected_consumed` ✓（在清单列出的场景下）；真正越权/非法点仍拒绝 ✓；不可先通知后提交 ✓；并发 miss 未造成**新增**缓存击穿（既有 miss stampede 与 HEAD 完全相同，未被 B7 放大）。

**遗留问题（结转，不改变上述裁决）**
1. **残留窗口真实存在**（我确定性复现，单元 + 真实库）：同 key 同命名空间先有一次驳回、随后提交的新版本通知又丢失时，`_claim_reread` 冷却抑制重读 → 该合法帧仍 `rejected_consumed` → edge 记 `dead` 永久丢失。**上界应按生产默认 `control_cache_ttl_ms = 30000ms`（约 30s，缓存侧 ≈36s）计，而非报告所称 6s**。彻底消除需把缓存依赖型驳回改为可重试状态（改 ack 契约）→ 架构决策。
2. **`unknown_device` 缺口未登记**（我新增发现，单元 + 真实库复现）：assignment 负面缓存后控制面补建 assignment，通知丢失时不会重读，仍 `rejected_consumed`。与 B7 同类，建议按同一 TTL 窗口评估并补入重读集合或改契约（注意：`unknown_device` 也覆盖"设备确实不存在"的**真非法**情形，直接加入重读集合会把真非法帧变成每 TTL 一次额外查询，需与 1 一起设计）。
3. **`device_type_mismatch` 缺口**（修复者已自述，我复现确认）：仅靠通知修复，通知丢失时仍会 `rejected_consumed`（受 TTL 约束、非永久，但该帧已 dead）。
4. **可观测性缺口**：发布失败只有 `logger.exception`，无计数；通知丢失率运行期不可度量。
5. **`_reread_at` 无淘汰**（与既有 3 个缓存同性质）：我实测 50 个不同 key → 50 条目，线性增长。
6. **未覆盖的证据面**：HTTP 真实入口、目标机验收、真实 edge 进程的端到端故障注入（"误判 → dead → 永久丢失"仍为代码级 + 单元级）。
