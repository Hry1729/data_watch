## 5. 最小修改（文件与行为差异）

1. `security.py`：新增 `JWT_SECRET_MIN_LENGTH = 32`、`validate_jwt_secret()`、`_require_jwt_secret()`；`create_access_token` / `verify_token` 首行调用后者。**行为差异**：空/纯空白密钥不再能签出或校验出 subject（抛 `JWTError`，`deps` 映射为 401）。
2. `config.py`：`_load_config_unlocked` 对**既有配置**调用 `_ensure_jwt_secret_unlocked`。**行为差异**：合格密钥原样返回且不写盘；`bootstrap_done=true` 且密钥不合格 → `ValueError`（启动即失败、不会静默轮换、不改写文件）；`bootstrap_done=false`（明确首装）且不合格 → `secrets.token_hex(32)` + 原子落盘（`_save_config_unlocked` 的 tmp+fsync+`os.replace`）+ `logger.warning` 明示「旧令牌全部失效」。
3. `config.toml.example`：注释/取值与实现对齐。

**两处刻意的策略边界（诚实披露）**：

- 长度下限（>=32）只在**配置加载**处强制；签发/校验的加密闸门只拦**空值**。原因：既有测试 `agent/tests/test_admin_auth.py:32,42,53` 直接用 11 字符的 `"test-secret"` 调 `create_access_token` / `verify_token`，而该文件**不在本 agent 授权修改范围**。本轮先按 32 下限实现时实测这 3 个既有用例失败（`3 failed, 271 passed`），因此把长度策略固定在配置边界、加密边界只拦空值——**没有删除或放宽任何既有断言**，也没有降低对真实部署的要求（真实配置一律经 `load_config`）。
- 首装自动生成不是「静默轮换」：`bootstrap_done=false` 时 `login` 本身返回 503（`auth.py:35-36`），**不可能存在合法会话被失效**；且生成必有 `WARNING` 日志。已 bootstrap 的存量配置一律拒绝启动而非轮换。

## 7. 数据、权限、部署兼容影响

- **升级影响（重要，会改变既有部署的启动行为）**：若某台机器上 `config.toml` **已存在**且 `[agent].jwt_secret` 为空或短于 32 字符（典型来源：运维按 `config.toml.example` 手抄，或旧安装器留下了空值），升级后 Agent **拒绝启动**，`agent/main.py:43` 的 `load_config()` 抛 `ValueError`，进程退出并打印可执行的中文修复指引（含生成命令与「会话失效需重新登录」提示）。这是本条 P0 的**预期行为**——空密钥意味着任何本地进程都能伪造管理员令牌。
  - 修复动作：把 `[agent].jwt_secret` 改为 `python -c "import secrets;print(secrets.token_hex(32))"` 的输出（>=32 字符）。变更后所有已签发令牌失效，需重新登录（**必须明确告知用户**）。
  - 若该机器尚处首装（`bootstrap_done=false`）：不需要人工干预，首次加载会自动生成并写回，同时打印 WARNING。
  - **不会**出现「静默频繁轮换」：合格密钥永不改写；生成只发生在首装且不合格时，且落盘后稳定（并发/重启用例锁定）。
- 数据：无 schema、无数据迁移；只读校验 + 首装时写回同一个配置文件（原子替换，先写 `.<name>.tmp` 再 `os.replace`）。损坏的 `config.toml` 保持原样报错，**不会**被当作空密钥接受，也不会被重建覆盖。
- 权限：不新增文件与权限面。生成的密钥写入既有 `config.toml`（沿用既有 ACL/DPAPI 之外的明文约定，与改动前一致）。
- 部署兼容：`frozen` 与 `dev` 两种 `data_root()` 形态共用同一校验路径；`mutate_config`/`save_config` 走同一闸门（`admin.py:351-353` 会把该 `ValueError` 转成 HTTP 400）。

> 本节**只做记录**：未改动 §1-§12 的任何实现、测试或结论。

- **可达性核查（验收者已做）**：`create_access_token` / `verify_token` 的**全部 4 个调用点**
  （`deps.get_current_user:26`、`deps.get_current_admin:45-49`、`auth.login:40-45`、`viewer.tail_logs:160`）
  **都**从 `load_config()` 取密钥；grep 全 agent 代码，除 `config.py` 外**无处**读写 `jwt_secret`，
  也**没有第二处** `toml.load(CONFIG_PATH)`。因此「绕过 `load_config` 直接调 create/verify」在当前代码里
  **没有真实入口**，弱密钥无法经任何现有路径进入签发/校验。
- **判定**：32 字符下限**当前不可达**（不可绕过配置边界触发），故 **判定为可接受、非残留缺口**，
  不推翻本条的「已修并验证」结论。
- **仍需记账的部分**：加密层的契约只有「非空」，比配置层策略（`>=32`）**弱一档**，
  属**纵深防御缺口**：日后若新增任何密钥来源（环境变量、安装器写入、第二个配置文件），
  弱密钥口子会重新打开而现有测试不会告警。
- **验收者的记账建议**（供后续批次二选一）：(a) 把 `security._require_jwt_secret` 的 `min_length`
  提到 32；(b) 更省事——把 `agent/tests/test_admin_auth.py` 里的 `"test-secret"` 哨兵改成 >=32 字符
  （它只是夹具值，不是真实密钥），(a) 便自然成立。**本轮未执行**该改动：
  `test_admin_auth.py` 不在本 agent 的授权修改范围内（且 B15 实现已验收完毕）。
