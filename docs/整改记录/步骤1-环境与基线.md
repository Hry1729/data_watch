## 2. 三个环境问题的定位与修复

### 2.1 D35：`start-dev.ps1` 写死作者个人路径 —— 已修

- **原状**：`start-dev.ps1:68`（`C:\Users\Hry\.local\bin\python3.14t.exe`）、`:70`（`...pythoncore-3.14-64\python.exe`）、`:85`（`...pythoncore-3.14-64\Lib\site-packages`）。本机 `C:\Users\Hry` **不存在**，且 `backend\.venv-314t` 也不存在 ⇒ 原脚本在本机**选不到解释器**。
- **修法**：解析顺序改为
  1. `-PythonExe` 参数 / `DATAWATCH_PYTHON` 环境变量（显式优先）
  2. 仓库内 `.venv-314t`
  3. `py -3.14t`（由 py 启动器报告**真实**解释器路径，而不是猜路径）
  4. PATH 上的 `python3.14t`
  5. 标准安装根扫描（`$env:ProgramFiles` / `${env:ProgramFiles(x86)}` / `%LOCALAPPDATA%\Programs\Python` 下的 `Python3*`）—— **与会话用户名无关**
  - 新增 `Test-FreeThreadedPython`：选中的解释器**不是** free-threading(no-GIL) 构建时**显式告警**（后端依赖 TurboAPI 需要 3.14t），不静默降级。
  - `$backendPyPaths` 去掉写死的个人 site-packages，改为 `.py314t-site` + `DATAWATCH_BACKEND_PYTHONPATH`（分号分隔）追加。
- **实测**：脚本语法 **0 错误**；在作者路径不存在的本机上解析到 `D:\Program Files\python\python3.14.6\python3.14t.exe`，`free-threaded = True`。
- ⚠️ **协调者自查并修掉自己的一个缺陷**：初版用 `-replace '\s',''` 去空白，会**连路径中间的空格一起删掉**，把 `D:\Program Files\...` 变成无效的 `D:\ProgramFiles\...`（当时因后备候选恰好命中才没暴露）。已改为「取首行 + `Trim()`」。

### 2.2 collector 既有失败：不是产品缺陷，是测试的两层环境依赖 —— 已修

**现象**：`collector/tests/test_collector_receipt_v2.py::test_outbox_owner_lock_rejects_second_process_and_crash_releases` 报 `AssertionError: assert '' == 'ready'`（`:286`）。

- **第一层**：子进程执行 `from storage.collector_outbox import ...`。`collector/tests/` 是包，pytest 因此把 `collector/` 插入**父进程**的 `sys.path`；子进程**不继承** ⇒ `ModuleNotFoundError: No module named 'storage'` ⇒ 不打印 `ready` ⇒ 父进程读到空串。
- **第二层（修掉第一层后才暴露）**：`child.kill()` 后立即重开仍报 `RuntimeError: already owned by another process`（`collector_outbox.py:173` `msvcrt.locking` → `PermissionError`）。
  **根因已实测证明**：`collector\.venv-pack\Scripts\python.exe` 是**转发器（launcher）**——实测 launcher PID `33724` ≠ 子进程自报 PID `28952`。所以 `child.kill()` 杀掉的是转发器，**持锁的真实解释器进程仍然存活** ⇒ 锁未释放。
- **修法（最小、且不降低要求）**：
  1. 子进程以 `cwd = collector/` 运行 —— 按**生产运行方式**解析 `storage`（`python -c` 的 `sys.path[0]` 即 cwd），不再依赖继承 PYTHONPATH；
  2. 杀进程后**有界等待**锁可再取得（≤10s、50ms 轮询）再重开，并在注释里写明原因（venv 转发器导致 kill 不等于持锁进程已退出）。原断言「必须能重新取得锁」**未被放宽**，只是不再假定「立即」。
- **实测**：目标用例 **1 passed**；整个文件 **6 passed / 18 skipped**。

### 2.3 ingest 环境：是「本机未安装」，不是「不可安装」 —— 已修（并修正我先前的错误结论）

- ❌ **修正我先前的结论**：我此前说「`msgspec` 只有 cp314 轮子，与 TurboAPI 的 free-threading 需求**互斥**，故 ingest 全量跑不通」。**该结论不成立。** 实测：
  - `msgspec-0.21.1-cp314-cp314t-win_amd64.whl` **存在**
  - `psutil-7.2.2-cp314-cp314t-win_amd64.whl` **存在**
  - 真实情况是本机 **3.14t 环境里没有安装**它们。
- **修法（`--user`，不改系统目录、不动仓库、可逆）**：
  ```powershell
  & 'D:\Program Files\python\python3.14.6\python3.14t.exe' -m pip install --user --only-binary :all: msgspec==0.21.1 psutil==7.2.2
  ```
  两者都是 `ingest/requirements.txt` 已声明的版本，因此**无需改仓库声明**，只补本地安装。
- ⚠️ **另一个我自己踩的坑（写进方法库）**：**依赖探测必须设 `PYTHONUTF8=1`**。turboapi 在导入时会打印 emoji，GBK 控制台下抛 `UnicodeEncodeError`，会被 `$LASTEXITCODE` 误判为 `MISSING`（我第一次探测 turboapi 就是这么错的）。
- **实测**：3.14t + `PYTHONPATH=backend\.py314t-site` 下 `msgspec`/`psutil`/`aiomysql`/`turboapi` **全部 OK**；完整 ingest 套件 **73 passed / 6 skipped / 0 failed**（此前 cp314 下为 `1 failed / 62 passed / 6 skipped`，且 `test_http.py` 根本跑不了）。
