**超出的发现（W0-B 未点明）**：破坏 `current` 的**触发点不止 247 行**。原 catch 的第 257 行在**任何**异常下都会执行，因此「246 清理 `previous` 失败」这一路径同样会毁掉仍有效的 `current`——而且这一条能被**OS 级真实条件自然触发**（见 §4 场景③，无需任何注入），比 W0-B 只演示的 247 注入更贴近现实：

- 修复前：`current` 被删空（目录在、`data-watch.exe` 与 `keep.txt` 全没了），`previous` 被 `Remove-Item -Recurse` **部分删除**（`nested\` 丢失），catch 里 `Move-Item $previous -> $current` 又因文件被独占而失败 → **目录里没有任何可运行版本**。
- 这正是「恢复了一个不完整的版本 / 一个版本都不剩」的最坏情况。

**仍未确认（诚实标注）**：让 **247 行自身**（`Move-Item $current -> $previous`）自然失败的具体现实条件（跨卷、句柄占用）本轮**未**实测；本轮的 247 注入是**函数覆盖式注入**。但 §4 场景③证明「不需要 247 自然失败，B41 的破坏路径也能被真实条件触发」。

### 5.1 swap 脚本：显式阶段状态 + 只撤销已完成步骤

新增阶段状态文件 `<InstallRoot>\swap-state.txt`，取值 `<mode>:<phase>`：

| 阶段值 | 写入时机（已完成的事实） | 崩溃/失败时的处置 |
|---|---|---|
| `update:prepare` / `rollback:prepare` | `try` 之前，尚未搬动任何目录 | 什么都不做（`current` 若存在则原样保留） |
| `update:backed-up` | `Move-Item current -> previous` 成功之后 | 若 `current` 缺失 → 把 `previous` 搬回 `current` |
| `update:swapped` | `Move-Item staged -> current` 成功之后（**尚未校验**） | 先把未验证的 `current` 挪到 `failed`（**移动，不删除**），再把完整旧版本搬回 `current` |
| `rollback:displaced` | `Move-Item current -> failed` 成功之后 | 若 `current` 缺失 → 把 `previous` 搬回 `current` |
| `rollback:swapped` | `Move-Item previous -> current` 成功之后 | 不做破坏性动作（`failed` 保留被淘汰版本） |
| `<mode>:verified` | 版本自检通过 | 终态；`apply` 之外的独立确认依据 |
| `<mode>:failed` | 失败恢复已完成 | 终态 |

  「用户仍能启动 CLI」（例如从 `previous` 目录/副本启动、或在重新安装后 `current` 已存在）。
  一个**完全不依赖 `current` 的入口**（安装脚本在 `current` 外的 shim，或 `data-watch update recover`
  这类**命令层**子命令）才是彻底解法，但那是 CLI 命令层/安装脚本契约变更，超出 B41 授权文件范围
  （`cli/commands/update.py` 本轮不得改），**本轮未做，留给协调者决策**。

**R9（阶段状态写入本身失败）**

- 改前复现：

  ```text
  ### R9（before）：写 update:swapped 阶段状态失败
    exit=1  stderr=<空>
    终态： current='NEW' previous='OLD' failed=None  runnable={'current':'NEW','previous':'OLD'}  state='update:failed'
    结论：current 是否为「从未通过自检的新版本」= True
  ```

- 根因：`catch` 的判据只有阶段值 `update:swapped`。写该阶段失败时阶段值停在 `update:backed-up`，
  于是走了「只搬回缺失的 current」分支（`current` 存在 → 空操作），未自检的新版本被留在 `current`。
- 最小修改（两条）：
  1. `catch` 改为**阶段值 + 目录状态交叉判定**：`update` 模式下若 `StagedApp` 已被搬走而
     `current` 又存在，说明 `current` 就是那份未自检的新版本 ⇒ 走 `Restore-UnverifiedSwap`
     （`current -> failed`、`previous -> current`）。**没有**改用「与阶段值无关」的宽判据：
     那会在「手工/异常调用传入不存在的 `-StagedApp`」时把仍在运行的完整 `current` 换成更老的
     `previous`——正是 B41 修掉的 R3 类缺陷。
  2. `Set-SwapPhase` 改为**先写 `<state>.tmp` 再原子替换**（`File.WriteAllText` +
     `File.Replace`/`Move`），使「写入过程失败」不再产生空/半截阶段值（这是 R9 的根因侧加固；
     阶段值可信才使交叉判定可靠）。
- 改后复现：

  ```text
  ### R9（after）
    exit=1  stderr=<空>
    终态： current='OLD' previous=None failed='NEW'  runnable={'current':'OLD','failed':'NEW'}  state='update:failed'
    结论：current 是否为「从未通过自检的新版本」= False
  ```

- 不变量核对：至少一个可运行版本 ✓（`current=OLD`）；未报升级成功 ✓（`exit=1`、阶段非 `:verified`）；
  未把未自检版本提升为 `current` ✓；未删除仍有效的旧版本 ✓（旧版本回到 `current`，新版本停 `failed` 取证）。

**R10（rollback 崩溃窗口永久删除被淘汰版本）**

- 改前复现：

  ```text
  ### R10（before）：rollback 崩于第 2 次移动后，再以 rollback 模式重启
    第一次（崩溃）exit=97   current='OLDER' previous=None failed='OLD'  state='rollback:displaced'
    重启（rollback）exit=1
    重启后终态： current=None previous=None failed='OLDER'  state='rollback:failed'
    被淘汰版本 OLD 是否仍在目录中（任一槽位）？ False  markers={'OLDER'}
  ```

- 根因（确认独立验收的判断）：reconcile 的 `else` 分支**无条件** `Remove-Item $failed`；而
  `rollback:displaced` 不在「update 未校验」分支里，于是 `failed` 里**被淘汰的 OLD 被永久删除**；
  本次 rollback 又因 `previous` 已被上一次运行消耗而失败（`previous -> current` 抛错），
  兜底的 `Restore-MissingCurrent` 也无可搬之物 ⇒ `current` 消失。
- 最小修改（两条，都只改删除的**顺序/条件**）：
  1. reconcile 的 `else` 分支**不再删除** `failed`，只做 `Restore-MissingCurrent`；
  2. 把 `failed` 槽位的回收移进 `try`，且**先**加前置守卫「本次要装进去的版本
     （`$StagedApp`，update 时是 staging、rollback 时是 `previous`）必须完整」，**再**在
     `Test-CompleteVersion $current`（即目录里另有可运行版本）成立时才 `Remove-Item $failed`。
     守卫不成立就 `throw`，在动任何目录之前中止。
- 改后复现：

  ```text
  ### R10（after）
    第一次（崩溃）exit=97   current='OLDER' previous=None failed='OLD'  state='rollback:displaced'
    重启（rollback）exit=1
    重启后终态： current='OLDER' previous=None failed='OLD'  state='rollback:failed'
    被淘汰版本 OLD 是否仍在目录中（任一槽位）？ True  markers={'OLD', 'OLDER'}
  ```

- 可达性（沿用独立验收的诚实标注）：`rollback()` 自身要求 `previous\data-watch.exe`，所以正常 CLI
  路径**不会**再进入这次重启（`previous` 已被消耗 ⇒ 恢复后如实报「没有可回滚的上一版本」）；

  未新增任何 CLI 子命令。

## 9. 尚未覆盖的目标环境 / 故障场景

1. **目标机验收：未覆盖（本轮未授权）**。所有验证都在开发机的临时目录 + 真实 `powershell.exe` 下完成，没有在真实安装目录 / 真实 Windows 安装包链路上跑过。
2. **`apply()` → `_launch_swap` → `Popen(DETACHED_PROCESS)` 的完整调用链未端到端跑过**：`test_apply_reports_verification_pending` 在 `_launch_swap` 处做了 monkeypatch（单元级），脚本层测试是测试自己用与 `_launch_swap` **相同**的参数列表去调 `powershell.exe`。因此「`Popen` 的 `DETACHED_PROCESS` 行为、父进程退出时序、`Wait-Process` 语义」属**未覆盖**。
3. **247 行自然失败的真实成因未实测**（跨卷、被占用、权限、磁盘满）。本轮改用可确定复现的注入 + 一个自然的清理失败场景（③）。
4. **权限不足用的是注入而非真实 ACL**：我在临时目录实测过真实 ACL 拒绝（`icacls <dir> /deny "<user>:(D)"` 能让 `Move-Item`/`Remove-Item` 报 `Access to the path … is denied.`），但同一台机器上 `icacls /remove:d` **无法撤销该 DENY ACE**（`Successfully processed 0 files`，ACE 仍在，实测），在 pytest 里会给 `tmp_path` 留下删不掉的目录。因此用例退化为注入同形态错误。**真实 ACL 下的行为未覆盖**。
5. **残留边界（已观测，已分析，未修复）**：清理 `previous` 的 `Remove-Item -Recurse -Force` 在遇到独占文件时可能**部分删除**（场景③ 后 `previous\exe`+`keep.txt` 在、`previous\nested` 没了）。分析：这种「半截 `previous`」只可能出现在「`current` 仍然存在」的时刻（`Remove-Item` 与 `current` 无关），且脚本随即 `throw` 退出，`Restore-MissingCurrent` 因此是空操作；下一次运行也是重新 `Move-Item current -> previous`（完整覆盖）。所以半截 `previous` **不会被提升为 `current`**。但脚本的完整性判据只是 `data-watch.exe` 是否存在（`Test-CompleteVersion`），**没有做清单/哈希级完整性校验**——深度完整性未覆盖。
6. **崩溃点覆盖**：只注入了「第 1、2 次 `Move-Item` 之后硬崩」。~~`Set-Content` 写状态本身失败~~、`Remove-Item` 中途失败后再崩、掉电（非进程退出）等未覆盖。
   > **B41 后续更新**：「阶段状态写入本身失败」已由 R9 补齐并实测（§5.4-R9，注入方式改为对脚本自身 `Set-SwapPhase` 做同值代理，与写入实现无关；用例 `test_phase_write_failure_does_not_leave_unverified_version_in_current`）。**仍然未覆盖**：`Remove-Item` 中途失败后再崩、掉电（非进程退出）、磁盘真的写满。
7. **`failed` 目录的保留策略**：新版在「未验证新版本」时会保留 `failed` 作为取证，未来若引入自动清理，需要与「保留可运行版本」不冲突（本轮未设计自动清理）。
   > **B41 后续更新（R10）**：`failed` 槽位的回收已改为「**先确认 `$StagedApp` 完整、且 `current` 完整**（即目录里另有可运行版本）才删」，并在 `try` 内、动任何目录之前做前置守卫（§5.4-R10）。**残留**：一次**成功**的后续交换仍会回收（删除）上一次失败留下的 `failed`——这是原有设计（清单 §2 明令不得把失败路径的清理整体删掉），不是本轮引入。
8. **并发**：两个 update 进程同时跑同一安装根（例如用户连点两次）未覆盖；现有设计没有锁。
   > **B41 后续更新**：`apply()`/`rollback()` 现在会在前置校验前**同步**跑一次 reconcile-only，于是「上一次 updater 仍在运行时的第二次 CLI 调用」这条竞态多了一个进入点（脚本里已加「阶段值未被改动过才落 `:recovered`」的乐观检查，避免覆盖在跑的 updater 进度，但**没有加锁**）。**仍属未覆盖**，且是本轮新增的已知窗口。
9. **真实 CLI 安装根的默认值**：生产默认安装根是 `%LOCALAPPDATA%\DataWatch\CLI`（`cli/update_manager.py:199-201`）。我自己**未**探测它在本机是否存在；**协调者已独立只读探测**：`C:\Users\myrh\AppData\Local\DataWatch\CLI` **不存在**、`C:\Users\myrh\.data-watch\cli-install` **不存在**。因此「不传 `install_root` 会作用到真实安装」这一风险在本机**当前未实际成立**，仅为**部署期潜在风险**（真实用户机上该目录可能存在）。任何不传 `install_root` 就调用 `apply()/rollback()` 的代码都会作用于它——本轮用例与取证脚本全部显式传 `install_root`，但**未**对生产调用方做该保护（见 §4.4(4)，按协调者指示只报告）。（**B41 后续**：新增的 `_recover_interrupted_swap()` 只接受调用方传入的 `install_root`，未引入任何新的默认路径探测；本 agent 同样**未**探测上述真实路径。）
10. **`C:\ProgramData\DataWatch Edge`**：本轮**零读写**（见 §4.4），但也因此**没有**用它做任何「已存在安装/配置」类场景的夹具（符合 `隔离测试环境.md` §1.1 的要求）。（**B41 后续**同样零读写：所有实验根为 `%TEMP%\b41b-*` 与 pytest `tmp_path`；未对 `C:\ProgramData\DataWatch Edge`、`%LOCALAPPDATA%\DataWatch\CLI` 做任何读/写/`resolve()`。）
11. **（B41 后续新增）R11 修复的可达性前提**：`current` 同时是 CLI 自身的安装位置。崩在「`current` 已搬走、`staged` 未搬入」窗口时，安装根里能运行的 CLI 只剩 `previous\data-watch.exe`。本轮的恢复入口挂在 `apply()`/`rollback()` 上，因此**只有在用户还能启动 CLI 时才可达**（从 `previous`/副本启动，或重新安装后 `current` 已存在）。彻底解法是安装脚本在 `current` 之外放一个 shim，或加 `data-watch update recover` 这类命令层子命令——**均超出 B41 授权文件范围，未做**（见 §5.4-R11 残留）。
12. **（B41 后续新增）原子阶段写 `File.Replace` 的适用面**：阶段状态改为「临时文件 + `File.Replace`/`File.Move`」。**未实测**不支持 `ReplaceFile` 的安装根（例如某些网络共享/UNC 路径）：那种环境下阶段写入会失败，脚本会在动目录之前 `throw`（不丢版本、退出非 0），但**自动更新无法完成**。本轮只在本地 NTFS 的 `%TEMP%` 上验证。
13. **（B41 后续新增）阶段写入失败后的 `.tmp` 残留**：`File.WriteAllText` 成功而 `File.Replace` 失败时，安装根会留下 `<InstallRoot>\swap-state.txt.tmp`（下一次写入会覆盖它，无任何读取方）。**未加清理逻辑**（保持最小改动），已知且无害。
14. **（B41 后续新增）一次未解释的间歇失败**：见 §6 末条诚实披露——某次全量套件里既有崩溃注入用例的退出码不是 97，之后 **12 次全量 + 10 次 `-k crash` + 160 次脚本级压力均未复现**。**根因未定位**，不排除是阶段写入在瞬时占用/并行负载下失败（早于注入点退出）；未观测到任何版本丢失。**仍属未覆盖**：并发/高负载下阶段写入的失败率。
