## 3. 各项修复说明

### 3.1 B10：实时卡片把正常数据标红（前端）

- **根因**：`frontend/src/views/device_monitor/realtime/index.vue` 用 `q === 0` 判红色，注释写“q=0 表示数据无效”。
  平台约定恰好相反：`0 = GOOD`，非 0（2 UNCERTAIN、5 BAD、6 STALE、7 NOT_CONNECTED、8 解码错误、255 等）才是异常。
- **改动**：
  - 新增 `frontend/src/utils/realtime-quality.ts`，导出 `isQualityAbnormal(q)`：`0`、`null`、`undefined` 返回 false，其余数字返回 true。
  - 实时页卡片颜色改用该函数，注释同步更正。
  - 新增测试 `frontend/tests/realtime-quality.test.ts`。
- **验证**：新测试在修复前失败；`npm test` 29/29 通过；`npm run build`（含 `vue-tsc`）通过。

### 3.2 B2：Perspective 历史快照推不到 WebSocket 会话（后端）

- **根因**：HTTP 历史查询用 `Authorization` 头生成 owner_key（`backend/app/services/history.py`），
  WebSocket 用 `user_id` 生成（`backend/app/api/routes/perspective.py`），两边永远对不上，快照存进了另一个会话。
- **改动**：
  - `backend/app/api/routes/history.py`：保留 `require_permissions` 返回的 principal，传 `owner_identity=str(principal["user_id"])`。
  - `backend/app/services/history.py`：`query_history` / `_store_perspective_snapshot` 的参数 `authorization` 改名为 `owner_identity`，用它生成 owner_key。
  - 新增测试 `backend/app/tests/test_perspective_owner_key.py`（2 条：HTTP 快照能推到同一用户的 WS 会话；路由传的是 user_id）。
- **验证**：新测试在修复前失败；backend 281 passed / 1 skipped。

### 3.3 B9：TDengine 端口对所有网卡开放（部署）

- **根因**：`deploy/docker-compose.yml` 把 6030 / 6041 / 6043 / 6060（映射为 6062）发布到所有网卡，而 MySQL / Redis 早已只绑 `127.0.0.1`。
- **核实的部署事实**：
  - 所有客户端都只用 6041（taosAdapter，WebSocket/REST），6030/6043/6060 无人使用。
  - 两种部署形态下 TDengine 只被中心机连接：中心式的 Writer/Agent；分布式中心的 Writer/Agent（与 Ingest 同机，nginx 把 `/ingest` 转发到 `host.docker.internal:8010`）；backend 容器走 compose 内部网络（实测容器内 `TDENGINE_HOST=tdengine`）。
  - 分布式边缘只经 nginx `8080` → Ingest 上传，代码里没有任何 TDengine 连接；B12 已让边缘拒绝保存中心 TDengine 凭据。
- **最终改动（方案 A）**：
  - `deploy/docker-compose.yml`：TDengine 只发布 `"127.0.0.1:6041:6041"`。
  - `docs/04-运维部署/README.md` §4.1 / §10、`docs/01-总体设计/系统架构总览.md` 同步更新端口说明。
- **验证**：`docker compose config` 解析结果只有一条映射（`127.0.0.1:6041`）。

### 3.4 B8：Writer 遇到永久错误无限重试（Writer）

- **根因**：单个逻辑帧的 SQL 超出语句上限（原因 `size`）时被当作普通 RETRY，进入隔离区后永远重试。这类帧越积越多会占满隔离区，触发背压，拖住整条流。
- **策略（已确认）**：按**错误类别**判定永久错误，写入 DLQ 后 ACK；**不按次数**终结。
- **改动**：
  - `writer/consumer.py`：新增 `_PERMANENT_RETRY_REASONS = frozenset({"size"})`。命中的行附上分段证据后推入 DLQ，**DLQ 写入被 Redis 接受后才 XACK**；推送失败就不 ACK，留在主缓冲和 PEL 里。
  - `connection` / `unknown` / `schema` / `bisect_depth` 行为不变：继续重试、隔离和背压，不进 DLQ。
  - `writer/tdengine_writer.py`：状态说明注释补充 size 例外。
  - 终结策略契约写入 `docs/03-数据与契约/数据库/Redis结构与字段.md` §8（判定依据、归档位置、ACK 时机、恢复方式、容量告警）；`docs/02-模块设计/writer/README.md` 的状态表与流程说明同步更新。
  - DLQ 记录：`rt:dlq:{device_type}:{group_code}`，`last_error` 以 `permanent size:` 开头，`segment_evidence.overall_status = permanent_size`。
  - 新增测试 `writer/tests/test_b8_permanent_retry_dlq.py`（7 条）。
- **验证**：其中 2 条在修复前失败；writer 251 passed。
