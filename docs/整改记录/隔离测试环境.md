## 3. 已知能力缺口（后续批次需要时再补）

- 本隔离 Redis 是 **7.4.11**。条目 **B30**（Redis 6.2 的 `XAUTOCLAIM` 两元素响应不兼容三元素解包）在 7.4 上无法复现，批次 D 处理该条时需另起一个 `redis:6.2` 容器（例如 `127.0.0.1:16380`）。
- 批次 A 不涉及 TDengine，故隔离环境未提供 TDengine。批次 D 处理 Writer 相关条目时再补。
- 本机 Python 为 3.14.6，**是 free-threading 构建**（GIL 关闭）。`py -0p` 显示 `-V:3.14t`（默认，`python3.14t.exe`）与 `-V:3.14`（`python.exe`）并列。

### 3.2 两个硬坑（照抄，别自己试）

1. **backend 的 `PYTHONPATH` 必须让 `backend\.py314t-site` 排在最前**，否则系统 cp314 的 cryptography 会触发 `Windows fatal exception: access violation` 硬崩。
2. **backend 必须加 `-Xgil=0`**，否则 `test_free_threading` 失败（sqlalchemy 的 cyextension 会回退并打开 GIL）。

### 3.3 关于 `.venv-pack` 的准确结论（W0-A 实测）

`.venv-pack` **不是"纯打包 venv"**，两个模块的性质还不一样：

- `collector\.venv-pack`：由 `python3.14t -m venv` 创建（见 `collector/README.md:53`），实测 `SOABI=cp314t-win_amd64`、GIL 关闭、**装有 pytest 9.1.1**，且 `collector/tests/README.md:8` 就登记它为测试解释器。**collector 必须用它** —— `packages\*\driver.toml` 声明 `python_abi='cp314t'`，用 cp314 跑会出现 81 failed。
- `agent\.venv-pack` / `writer\.venv-pack`：是 **cp314** 的打包 venv（含 PyInstaller，**无 pytest**），**不可**作为测试解释器；但 `agent\.venv-pack\Lib\site-packages` 可作为**依赖目录**经 `PYTHONPATH` 注入（已实测：`jose 3.5.0` 由此解析成功，`import app.core.security` 通过）。
- `backend\.py314t-site`：是**依赖目录，不是解释器**。

### 3.4 已确认的环境阻塞（不属整改范围，需用户决策）

**`ingest` 全量测试跑不通**，根因是依赖互斥：TurboAPI 要求 free-threading 构建，而 `msgspec` 本机只有 cp314 轮子；两个解释器各缺一半，无法同时满足。因此：
- `ingest/tests/test_http.py`、`ingest/tests/test_repository.py::test_parent_schema_preflight_marks_workers_ready` **当前无法运行**，任何涉及它们的结论必须标「未覆盖」。
- 另：`ingest/Dockerfile:1` 基于 `python:3.14-slim`（带 GIL），但依赖需要 free-threading 的 TurboAPI —— 容器内能否正常启动**未确认**（禁止重建业务容器，故未验证）。

**不要把"装依赖/建 venv"当作整改动作自行执行** —— 那属于环境建设，超出本轮只读与最小修复授权，需用户决定。

### 3.5 控制台编码坑（协调者实测，导入 turboapi/dhi 必踩）

本机控制台代码页是 **GBK**。`turboapi` 的依赖 `dhi` 在导入时会打印一个 emoji（`ℹ️`，`dhi/validator.py:186`），在 GBK 控制台下直接抛：

```
UnicodeEncodeError: 'gbk' codec can't encode character '\u2139' in position 0: illegal multibyte sequence
```

这会伪装成"依赖缺失/导入失败"，实际与依赖无关。**跑任何 backend/ingest 代码前先设**：

```powershell
$env:PYTHONUTF8='1'
$env:PYTHONIOENCODING='utf-8'
```

### 3.6 另一个独立确认：`turboapi` 要求 free-threading

实测 `python3.14.6\python.exe`（带 GIL）导入 `turboapi` 直接 `ImportError`，明确要求 no-GIL 构建；而 `python3.14t.exe` 可正常导入并注册路由。这与 §3.4 的 ingest 阻塞是同一根因的两个侧面。

## 5. 已确认的安全风险（Agent 必须遵守）

### 5.1 Redis 测试守卫保护 DB 0，但不阻止连到现场实例

`ingest/tests/redis_test_guard.py:20-31` 的守卫只要求「回环 + 非零 DB + 无 query 覆盖」。实测现场 `data-watch-redis` 有 **16 个 DB**，因此 `redis://127.0.0.1:6379/15` 能通过守卫，却仍然是现场实例。**集成测试必须使用 16379；不得因为"守卫通过了"就认为已经隔离。**

### 5.2 全仓库没有 MySQL 侧的测试守卫

grep 未发现任何 MySQL 隔离守卫，而 `ingest/app/config.py` 与 `backend/app/core/config.py` 的默认值都指向 `127.0.0.1:3306` 的 `device_watch` 库（root + 空密码）。**任何新建的 MySQL 集成测试必须显式指向 13306 / `device_watch_test`，并自行加守卫。**

### 5.3 backend 现有测试全部是 mock 级，只能给「单元」证据

`backend/app/tests/` 下 39 个测试文件通篇使用 `AsyncMock` / `FakeSession` / `monkeypatch`，不连接 MySQL、Redis、TDengine。**B7 这类需要真实授权重读路径的条目，隔离集成证据必须新建测试才能获得，不得用现有 mock 测试冒充集成验收。**

### 5.4 ingest 集成测试只构造 MySQL 设置、不连接

`ingest/tests/test_redis_store_integration.py:34-38` 硬编码 `mysql_port=3306`（现场端口），但该文件仅用它构造 `IngestSettings`，`IngestRedisStore` 不使用 MySQL；`ingest/tests/test_repository.py:32` 用 monkeypatch 替换了 `aiomysql.create_pool`。**现有 ingest 测试暂不触发现场 MySQL，但改动这两处时必须保持这一性质。**

## 7. 隔离 MySQL 已预置完整 schema（零业务数据）

**已就绪，直接用，不必自己建表。** 库 `device_watch_test`（`127.0.0.1:13306`）现含 **35 张表**，包括 B7 需要的 `device`、`device_variable`、`point_storage_mapping`、`point_storage_mapping_staging`、`sys_node`、`device_assignment`。

**来源与做法（可复现）：**
- 表结构的权威来源是 `backend/app/services/auth_bootstrap.py:392`（SQLAlchemy `Base.metadata.create_all`），仓库内另有一份发布期完整转储 `outputs/DataWatch-release-20260929/database/device_watch.sql`。
- 该转储 **20.66 MB、含 113,686 条 INSERT**，即**含真实业务数据**。按执行纪律「禁止读真实业务数据用于测试」，**没有**整份导入。
- 实际做法：只抽取其中的 `CREATE TABLE` 语句（35 条 → 50.5 KB，`INSERT` 计数为 0），落到仓库外的 `D:\python\device_alarm\dw-test-env\schema_ddl.sql`，再导入隔离库。**隔离库内不含任何业务数据行。**
- 随后按序应用仓库的 `scripts/sql/db1..db6` 增量脚本。其中：
  - `db2_device_variable_fields.sql`、`db4_device_config_version.sql` 报 `ERROR 1060 Duplicate column name` —— **这是预期的**，说明发布转储已包含这两处新增列，补丁已无副作用。
  - `db6_distributed_core.sql` 首次单独执行时曾因缺 `device` 表而在第 49 行失败（FK 依赖）；预置完整基础结构后已成功。

**给 W1-I1 的提醒：** 若你的测试需要更接近当前 HEAD 的列（发布转储可能落后于 HEAD），不要改现场库，也不要改仓库里的补丁脚本；在隔离库里用 `ALTER TABLE` 临时补列即可，并在任务卡里注明该列是测试脚手架而非仓库事实。
