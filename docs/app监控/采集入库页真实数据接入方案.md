## 二、数据源结论（已核实）

**A. 即时类，可直接读、准确、零改 collector/writer：**

| 指标 | 来源 | 说明 |
|---|---|---|
| 在线 / 总设备数 | MySQL `device` + Redis `rt:latest` | 后端 `DashboardService.get_overview` 已现成计算（在线判定阈值 120s） |
| 点位总数 | MySQL `COUNT(*) device_variable` | 同上，`get_overview` 已返回 |
| 协议 | MySQL `comm_protocol.protocol`（`device.protocol_id` join） | `MonitorService._fetch_target_device` 已用此 join |
| 采集周期 | MySQL `device_variable.scan_rate` | `MonitorService._fetch_min_scan_rate` 已用此查询 |
| 每设备最新时间 / 质量 / 连接状态 | Redis Hash `rt:latest:{device_code}:{group_code}`（字段 `t`/`q`） | `MonitorService._get_device_latest_from_redis` 已用 |
| Stream Lag | Redis `XINFO GROUPS rt:stream:{type}:{group}:{shard}` 的 `lag` | 新增读取 |
| PEL Pending | Redis `XPENDING`（或 `XINFO GROUPS` 的 `pending`） | 新增读取 |
| DLQ 数量 | Redis `LLEN rt:dlq:{type}:{group}` | 新增读取 |

后端三库客户端齐备：`backend/app/db/{mysql,redis,tdengine}.py`。

**B. 速率类，需"计数器 + 采样"（二期）：**
- Redis 写入 **pts/min**、批量写入 **rows/min**：Redis/TDengine 无现成速率，需进程自报累计计数或读端按增量/时间差采样。
- 两类趋势图（时间序列）：需历史采样点。

## 四、一期设计（架构 B：后端扩展）

职责切分：**Agent = 进程/OS 指标（现状不变），后端 = 业务/数据指标（新增）**。

### 4.1 后端新增 2 个只读接口

路径前缀 `/api/device-monitor/`。新增 `backend/app/api/routes/module_monitor.py` + `backend/app/services/module_monitor.py`，并在 `api/router.py` 注册。

**响应包裹**：两个接口都走后端统一格式，用 `success_response(data=...)` 返回 `{ "code": 200, "msg": "success", "data": { ... } }`；下文 JSON 示例均为 `data` 内部结构。前端 `backendFetch` 已只取 `json.data`，无需特殊处理。

**权限**：与现有 `monitor.py` 一致，用 `require_permissions(credentials, {"device_monitor:monitor:view", "device_monitor:realtime:view"})`（**任一权限即可**）。避免"有 realtime:view 能看旧实时页、却看不了新模块指标"的 403 不一致。

#### ① `GET /module-monitor/collector`

返回：
```json
{
  "scanRateMs": 100,
  "onlineDevices": 18,
  "totalDevices": 18,
  "pointTotal": 3264,
  "tasks": [
    {
      "deviceCode": "AGV-01",
      "deviceName": "AGV 01",
      "groupName": "main",
      "protocol": "OPC DA",
      "scanRateMs": 100,
      "pointCount": 384,
      "lastCollectTime": "2026-06-01 14:26:08",
      "connectStatus": "online"
    }
  ]
}
```
数据来源与定义：
- `onlineDevices` / `totalDevices` / `pointTotal`：**不整段复用 `DashboardService.get_overview`**——它还会查 `system_log` / `operation_log` 告警统计，与本指标无关、会拖慢接口。改为抽轻量方法或单独 SQL，只查 `deviceTotal` / `onlineDeviceTotal` / `pointTotal`。
  - `onlineDevices` **只算连接状态 `online`（最新采集时间 ≤120s）**；`unstable`（120~900s）**不计入连接数**（只在任务表行状态展示），避免卡片过于乐观。
  - `totalDevices` 为全部设备。
- `scanRateMs`（头部单值）：取全部启用变量的 **MIN(scan_rate)**，表达系统最紧的采集压力。**UI 卡片标题改为"最短周期"**（不叫"采集周期"，避免被误解为平均/统一周期）；逐设备周期已在任务表呈现。
- `tasks`：一条聚合 SQL（`device` join `comm_protocol`/`device_type`/`device_group`，`device_variable` 求 `MIN(scan_rate)` 与 `COUNT` 点位）+ 逐设备读 Redis `rt:latest:{device_code}:g001` 求最新时间戳与质量；`connectStatus` 复用 `MonitorService._build_connect_status`（120s/900s 阈值）。
  - `groupName` = `device_group.group_name`（业务分组，展示用）；Redis latest key 固定用点位组 `g001`。
  - ⚠️ **一期默认点位组为 `g001`**：当前所有设备点位组均为 g001。若后续一个设备出现多个 point group，固定读 `rt:latest:{device}:g001` 会漏掉其他组——多点位组聚合留待后续，本期不处理。

#### ② `GET /module-monitor/writer`

返回：
```json
{
  "streamLagTotal": 24,
  "pelPendingTotal": 3,
  "dlqTotal": 0,
  "streams": [
    { "streamKey": "rt:stream:agv:main:0", "lag": 12, "pel": 1, "length": 1500, "status": "backlog" }
  ]
}
```
数据来源与定义：
- `SCAN rt:stream:*` → 每 key `XINFO GROUPS`（取各组 `lag`、`pending`）、`XLEN`（取 `length`）。
- `streamLagTotal` / `pelPendingTotal` = 所有 stream / 组的 `lag` / `pending` 求和。
- `SCAN rt:dlq:*` → 每 key `LLEN` 求和 = `dlqTotal`。
- `status`：派生展示状态——`lag == 0` → `"normal"`，否则 `"backlog"`（替换原 mock 的假 `ACK=OK` 列）。
- 纯只读，**零改 writer**；消费组名由 `XINFO GROUPS` 读出，后端无需知道 writer 配置。

## 五、Agent 内存"改全"——❌ 经验证不实施

**原方案设想**：`agent/app/services/process_manager.py::_info_running` 改为
`memory_mb = 主进程 rss + Σ proc.children(recursive=True) 各子进程 rss`，
以为内存"偏小像假的"是漏算了 OPC DA sidecar 子进程。

**2026-06-01 运行态验证结论：不实施。** 用 `Win32_Process` 递归查进程树实测：
- `data-watch-collector`(79.8MB) / `data-watch-writer`(57.3MB) 各自**唯一的子进程是 `conhost.exe`**（Windows 控制台宿主，约 7.6MB 系统开销），**没有应用级子进程**；当前系统无独立 OPC DA sidecar 进程。
- OPC DA sidecar（中心驱动）是经 **TCP/IPC 通信的外部进程，不在 collector 的进程树里**，`children(recursive=True)` 根本抓不到它。

因此该改法 ① 抓不到 sidecar；② 反而把 `conhost.exe` 的系统噪声并入采集内存，让数字**更不准**。collector 当前 rss 即单进程真实工作集，并非"假"。**保持现状，不改 `process_manager`。**

> 后续若真需并入外部 sidecar 内存：用"按已知进程名 / 端口匹配外部进程"的显式机制，而非 `children()`。

## 六、二期（仅记录，不实施）

2 张速率卡 + 3 张趋势图。届时在以下之间决策：
- **读端采样**：后端定时采 Redis（`XLEN`/latest 更新）或 TDengine 行数增量，按时间差算速率，趋势点存滚动缓冲（重启即丢，~10min 窗口够用）。
- **进程自报**：collector/writer 每 N 秒向 Redis 写累计计数（`stats:collector` / `stats:writer`），读端算增量。最精确，但需改并重新打包 exe。

## 七、验证标准（一期）

1. 启动 collector + writer + 后端 + app，登录超管。
2. Collector 页：设备连接数分子 = 最新采集时间 ≤120s 的设备数（`online`，不含 `unstable`），分母 = 全部设备；采集点位 = `COUNT(*) device_variable`；"最短周期"卡 = `MIN(scan_rate)`；任务表每行协议/周期/点位/最新时间与库一致；停掉某设备数据后该行 120s 后转 `unstable`、900s 后转 `offline`，且该设备不再计入连接数分子。
3. Writer 页：Stream Lag / PEL / DLQ 与直接 `redis-cli`（`XINFO GROUPS` / `XPENDING` / `LLEN rt:dlq:*`）核对一致；制造积压后 Lag 上升、对应 stream 行 status 转 `backlog`。
4. 2 张速率卡显示"待接入"，无假数字。
5. 内存：Agent 报的 collector 内存 ≈ 任务管理器中主 exe + 全部 sidecar 子进程之和。
6. 401 时前端走 logout；后端不可达时卡片/表显示错误态而非崩溃。
