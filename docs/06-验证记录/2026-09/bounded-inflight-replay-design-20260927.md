# 有界多批在途：最小设计与故障测试方案（2026-09-27，**未启用**）

状态：**设计 + 验证条件，不改生产默认回放方式**。
依据：本轮诊断实测（`outputs/diag-20260927-latestcost/latest-cost-500pt.json`、
`ab-*.json`）与源码 `collector/storage/durable_redis_writer.py`、`collector/storage/collector_outbox.py`。

## 1. 串行确认到底卡在哪（先看值不值得做）

现状：`_replay_loop` 串行执行 领取 → 组包 → pipeline(EVALSHA…) → **同连接 WAITAOF** → SQLite 清理提交 → 再领取。

* 500 点档 30 分钟长测：批次周期 p50 2000ms，确认往返 p50 1845ms，`claim_gap_ms` p50 93ms，
  批内最老帧在队列里已等 p50 1986ms；Redis 单线程忙碌比 **0.93**。
* 200 点档 30 分钟长测：周期 1001ms，往返 967ms，`claim_gap` 23ms，Redis 忙碌比 **0.28**。
* 单因素对照（`appendfsync everysec` vs `always`）：`always` 把中位往返从 959ms 压到 347ms
  （−64%，说明这段主要是**等落盘**），但把周期 p95 抬到 8.15s、持续速率压到 134–187 帧/秒
  → `always` 不可用；不过它证明"等待"与"执行"是两回事。

结论：**等待占多少，决定了多批在途有没有用**。

| 档位 | 一次往返 | 其中 Lua 执行（本轮实测） | 其中等待 | 2 批在途的理论上限 |
| --- | ---: | ---: | ---: | --- |
| 200 点/帧 | 967ms | 0.20s/200 帧 ≈ 0.2s | ≈ 0.75s（fsync 节奏） | 可接近 2×（Lua 远小于 1s 节拍） |
| 500 点/帧 | 1845ms | ≈ 1.7s/400 帧 | ≈ 0.15s | **几乎无收益**（Redis 单线程已 93% 忙，瓶颈是执行不是等待） |

**边界（不得越界表述）**：多批在途**不能**提高 Redis 执行 Lua 的硬上限，
只能在"等待占主导"的档位填补流水线空档；也不能预先承诺把 P99 降到某个值。

## 2. 最小设计（最多 2 批在途）

### 2.1 谁领取、如何避免重复领取
* 保留 `CollectorRetryOutbox._replay_lock` 作为**唯一领取者**：仍由回放线程同步领取（`SELECT … ORDER BY rowid LIMIT`），
  领取后立刻把该批 id 标记为"在途"（进程内集合 `_in_flight: dict[batch_id, set[row_id]]`）。
* 领取即从"可领取窗口"移除：下一次领取从**当前最小未领取 rowid** 继续，不重复选中同一行。
  （实现上等价于给进程内游标 + 在途集合；不新增表、不新增持久状态。）

### 2.2 批次与连接如何绑定
* 每个在途批次独占一条 Redis 连接（`redis.Redis(connection_pool=…, single_connection_client=True)`）。
* 原因：`WAITAOF numlocal` 确认的是**执行该命令的连接自己**写下的内容。
  若两条批次共用一条连接，第二条的 pipeline 会排在第一条的 `WAITAOF` 之后，
  既拿不到并行，又让"确认覆盖了哪些写"变得不可解释。
* **明确不假设**：同一连接在 `WAITAOF` 阻塞期间还能执行排在它后面的下一批命令——设计上按"不能"处理。

### 2.3 未确认的行如何留在 Outbox
* 与现状一致：`DELETE` 只在**该批的 WAITAOF 返回并确认 numlocal ≥ 1** 之后、与
  `history_frames_confirmed += n` 在**同一事务**内提交。任何一条在途批次未确认，其行就还在 SQLite 里。
* 在途批次失败/超时：只把该批的 id 从在途集合移除并**保留行**，等待下一轮按 rowid 顺序重试。

### 2.4 顺序清理与"已确认但未清理"
* 允许批次 B 的清理先于 A 提交（两批独立事务）。计数不依赖顺序：
  每行最多被 `history_frames_confirmed` 计一次（计数与删除同事务）。
* 维护 `_confirmed_not_cleaned` 仅用于观测：正常情况下它在一次事务内从有到无；
  若事务失败则整批回滚（行与计数一起回退），不会出现"计数已加、行还在"的偏态。

### 2.5 在途预算（硬上限）
* 批大小上限从一次 `max_batch` 收敛为 **每批 ≤ 256 帧**，在途批数 ≤ 2
  → **在途帧数 ≤ 512**、在途字节 ≤ 2 × 现有窗口上限（`_MAX_REDIS_WINDOW_BYTES`）。
* 预算与 `--redis-memory-guard-mb` 联动：在途字节 + 队列字节 + Redis 已用内存不得超过护栏的 80%。

### 2.6 receipt 连续序号与 1024 gap 上限（**关键约束**）
现状（`FRAME_LUA_V2`）：每个 session 一个 receipt hash，维护 `high`（已连续确认的最大 seq）
与最多 1024 个 `g:<seq>` 乱序字段；`seq > high+1` 时记 gap，`gaps >= 1024` 直接报错
`collector receipt gap limit reached`。

* 单连接顺序投递时 `seq == high+1`，**从不产生 gap**。
* 两批并发后，后一批可能先到：`gaps` 最多等于**先到批次的帧数**（另一批尚未到齐）。
  因此设计上把每批限制在 **≤ 256 帧** ⇒ 并发 gap ≤ 256 < 1024，**不会触发上限**。
  若沿用当前 4096 帧/批，两批在途最坏可产生 >1024 个 gap → 会触发拒绝，故必须收敛批大小。
* 还要保证每批内部**串行**（批内多个 window 顺序执行），只有批与批之间并行。

### 2.7 超时与未知结果
* `WAITAOF 1 0 2000` 的超时只在极端情况下触发；触发即视为**未确认**：保留行、释放该批的连接、下轮重试。
* 响应丢失（Redis 已执行但客户端没收到回复）：重试时该批 `seq <= high` → 判为 duplicate →
  **不再 XADD**（不重复入库），但仍 `HINCRBY fence` 推进写偏移以参与 `WAITAOF`（现有语义，已由测试固定）。
* 进程重启：SQLite 里未确认的行本来就是唯一权威，直接从头重放；receipt 去重保证不重复 append。
* Redis 重启：receipt 可能丢失 → `high=0` 且 `gaps=0`，重放的帧会被记为 gap **但仍会 XADD**（不丢数据）；
  gap 数受 §2.6 的 256 上限约束，不会触发 1024 拒绝。

## 3. 故障测试方案（必须在独立实例做）

| # | 故障 | 期望 |
| --- | --- | --- |
| 1 | 批次 A 的 WAITAOF 响应丢失，批次 B 正常确认 | A 的行仍在库、B 的行已删；重试 A 不产生重复 XADD（stream 长度 == 帧数） |
| 2 | A 慢、B 快（顺序颠倒） | receipt `high` 单调；`gaps ≤ 256`；最终 `high == 总帧数` |
| 3 | 进程在 2 批在途时被强杀 | 重启后重放：帧不丢、不重（守恒 `A−D == 队列条数`，残差 0） |
| 4 | 隔离 Redis 重启（receipt 丢失） | 不触发 gap 上限；帧全部入库；重放后 `high` 恢复连续 |
| 5 | 单批 WAITAOF 超时 | 该批保留、连接释放、下轮重试成功；无重复 |
| 6 | shutdown/pause 时有 1 批在途 | `pause_replay` 仍等**所有**在途批次结束才置 idle（现在的同步语义要扩展到多批） |
| 7 | 在途预算被突破 | 拒绝领取新批次（不扩容），已有批次不受影响 |

统一判据：`queue_conservation` 残差逐样本为 0；stream `XLEN` 恰等于唯一帧数；
`duplicate_frames == 0`；receipt `gaps` 峰值 < 1024；排空后 `outbox == 0`。

## 4. 本轮不建议直接开发的理由

1. 只有在"等待占主导"的档位才有收益（200 点档），而 500 点档几乎无收益——
   **真实部署的帧宽未定**，先做会押错方向。
2. 它把"单连接顺序"这一隐含前提改成"多连接乱序"，直接触碰 receipt/gap 与暂停语义，
   需要上面 7 项故障测试与一条新的守恒判据都通过才谈得上落地。
3. 更便宜的替代顺序：先把**每帧 Lua 成本**降下来（本轮已落地两项低风险改动），
   再考虑协议层（预编码载荷）与时间戳索引；这些都是"降低单批时间"，与在途解耦互补。

**结论**：值得进入下一轮开发，但**前置条件是先确定目标帧宽**，并按 §3 的 7 项故障测试与
守恒判据验收；本轮不改生产默认行为。
