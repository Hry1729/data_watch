## 1. 主导成本实际在哪里？原先哪些归因被支持或推翻？

### 1.1 微基准（隔离 Redis，500 点/帧，200 次调用；**26/26 档自证通过**）

`scripts/diagnose_latest_duplication.py` → **`latest-cost-500pt-v3.json`**（当前有效）。
自证期望值 = latest 写入（按档位与变体）+ **每帧 2 次回执 HSET**
（`durable_redis_writer.py:105-106`，实测见 `receipt-hset-probe.json`）。
v1（冒烟取整假象）、v2（自证公式漏算回执 HSET）标 superseded，数字保留：

| 组件 | 不写 v2 → v3 | 全写 v2 → v3 |
| --- | ---: | ---: |
| 历史帧整帧（`FRAME_LUA_V2`） | 1.360 → 1.361 | 2.541 → 2.583 |
| 历史帧去掉 latest 补偿段（diagnostic_only） | 0.541 → 0.579 | 0.565 → 0.595 |
| **历史 latest 补偿段（差值）** | **0.819 → 0.782** | **1.976 → 1.988** |
| 快车道 `LATEST_LUA`（生产 `eval`） | 1.195 → 1.218 | 2.379 → 2.398 |
| 快车道 `evalsha`（脚本缓存） | 1.194 → 1.215 | 2.422 → 2.489 |
| 快车道 + 256 分块 HMGET | 1.207 → 1.228 | 2.395 → 2.438 |
| 快车道 + 客户端预编码载荷 | 1.281 → 1.311 | 2.129 → 2.194 |

**结论（主导成本）**：同一批点位的 latest 更新在一帧里做了**两遍**——
历史 Lua 的补偿段（≈0.78–1.99ms）与独立快车道（≈1.22–2.49ms）。
整帧合计 ≈2.6ms（无写入）～5.1ms（全写）。以 500 点/帧 × 200 帧/秒计约 **1.0 CPU 秒/秒**，
与 09-26 那次 30 分钟长测独立测到的 Redis 单线程忙碌比 **0.93** 一致 `[真实服务实测 vs 微基准互证]`。

快车道内部再拆：读取+解码+比较 ≈1.24ms，编码+写入 ≈1.31ms，
其中**逐点 `cjson.encode` 只占 0.06–0.33ms**（编码不是大头，读+比与写各占一半）`[离线/微基准实测]`。
这两条在 v1/v2/v3 三次运行中方向一致（补偿段占比大、编码占比小），可以采信。

### 1.2 被推翻 / 被更正的归因

1. **"500 点每帧两次 HMGET ⇒ 每点写了两遍"——不成立。**
   两次 HMGET 只是 256 点分块遍历同一批 500 点；逐点 HGET vs 分块 HMGET 实测差 **−0.04～−0.06ms（2–5%）**，
   在噪声边缘。真正重复的是**跨路径**：历史补偿 + 快车道各更新一遍 `rt:latest`。
2. **我自己的第一版诊断场景是错的**：`stored_ts` 按帧重算，导致"应当不写"的档位后半段照样写，
   实测 `hset_calls=50000`（应为 0）。修正为"相对整段帧范围取新/取旧"，并给每个场景加了
   `expected_hset_calls` 自证断言。相关过程留在 `explain_no_write.py`。
3. **`appendfsync always` 的证据被支持但结论被限制**：它把中位确认往返 959→347ms（−64%），
   说明窄帧的 ~1s 主要是**等落盘**；但周期 p95 涨到 8.15s、持续速率掉到 134–187 帧/秒
   → 不可作为解法（本轮未改任何业务持久化配置）。
4. **本轮两项快车道优化在 200 帧/秒的端到端负载下低于测量分辨率**（见 §3）：
   微基准里 B1（脚本摘要）**跨次变号**（−0.100 → +0.043 → +0.091ms）⇒ 无收益证据；
   B2（分块 HMGET）方向一致但差值（−0.027…−0.051ms）**小于基线自身散布**（0.05–0.16ms）⇒ 不可辨。
   所以既不能说它们解决了延迟，也不能说它们带来了可测的改进——保留理由是语义等价与去掉冗余工作量。

## 2. 修改了什么，为什么安全？

只改了快车道的两处，均在 `collector/storage/durable_redis_writer.py`：

| # | 改动 | 为什么安全 |
| --- | --- | --- |
| B1 | 快车道由 `client.eval(LATEST_LUA, …)`（每次重传 462 字节脚本源码）改为 `script_load` + `evalsha`，`NOSCRIPT` 时重载一次再重试 | 只换传输方式；失败仍走原有"重排队 + 退避 + 重建连接"路径（异常不吞）。新增用例钉住 NOSCRIPT 重载语义 |

| 指标 | baseline（2 次均值） | 优化后（2 次均值） | 判断 |
| --- | ---: | ---: | --- |
| Redis 忙碌比（进程 CPU/墙钟） | 0.2271 | **0.2232** | −1.7%；组内散布 0.7% → **贴噪声边** |
| `latest_fastlane_redis_ms` p50 / p95 / p99 | 1.0 / 2.0 / 2.0–5.0 | 1.0 / 2.0 / 5.0 | 直方图桶分辨率（1/2/5ms）→ **不可分辨** |
| 稳态确认帧率 | 200.69 / 199.48 | 200.86 / 199.32 | 无差异 |
| 队列守恒 | pass（残差 0） | pass（残差 0） | 无退化 |
| 生产期最老积压 | 2014 / 1917 ms | 2015 / 2119 ms | 无差异 |
| 传输生效证据 | `eval` 24,000 次 / `evalsha` 24,000 次 | `eval` **0** 次 / `evalsha` 48,000 次 | ✅ 改动确实生效 |
| Redis 内存峰值 | 119.9 / 120.2 MB | 118.3 / 119.8 MB | 无差异 |
| **AOF 成本** | — | — | **未测**：4 次运行共享同一实例且期间发生 AOF 重写，字节数不可比 |

微基准层面两次运行的差值**会变号**（见 §3.2），端到端则被 22% 的低 Redis 占用稀释到 <1%。
**诚实结论**：两项改动是"严格减少工作量、语义不变"（少传 462 字节/次、少 498 次 redis.call/次），
但**没有任何一层（微基准或端到端）能证明它们带来可测量的性能收益**；
保留它们的理由是"语义等价 + 去掉冗余工作量 + 评审侧 400 组差分 0 不一致"，
**不是**"更快了"。

### 3.2 候选差值 vs **基线自身重复散布**：B1/B2 都不可辨（`verify_microbench_deltas.py` 可复算）

差值 = 候选 − 基线（负数 = 候选更快）。"散布"= 同一档位内 `fastlane_full` 各次运行
`per_call_ms.mean_ms` 的 max − min，即基线自身的抖动。**差值小于散布 = 不可辨。**

全写档（生产代表性最高）：

| 候选 | v1 | v2 | v3 | 该档散布(v1/v2/v3) | 判定 |
| --- | ---: | ---: | ---: | --- | --- |
| B2 分块 HMGET − 逐点 HGET | −0.037 | −0.027 | −0.051 | 0.051 / 0.084 / 0.156 | **不可辨**（每次 \|差值\| 都 ≤ 散布） |
| B1 `evalsha` − `eval` | −0.100 | +0.043 | +0.091 | 同上 | **不可辨且变号** → 无收益证据 |
| 预编码载荷 − 现状（未采纳） | −0.156 | −0.293 | −0.295 | 同上 | **可辨**（三次都超出散布、同号） |

* 不写档：B2 的差值 **变号**（v1 −0.062 / v2 +0.013 / v3 +0.012），B1 也都在散布内；
* 预编码在不写档反而**更慢**（+0.117 / +0.087 / +0.096ms）——载荷变大而没有可写内容，符合预期；
* v3 的散布本身比 v2 大（0.156 vs 0.084ms），说明"散布"也只能按当次运行估计。

**因此**：B1 与 B2 都**不能**声称有收益（B1 变号，B2 差值小于基线抖动）；
预编码载荷是三项里唯一"三次都超出散布、方向一致"的候选（全写档 −0.16…−0.30ms，约 6–12%），
但**每档只跑 1 次**、且不写档更慢，因此只写成**下一轮候选**，不构成结论。
这些判断只用两次以上的重复测量，不含未测推断。

### 3.1 这组 A/B 的 pass/fail 本身不可用（必须交代）

四次运行的判定是**翻转**的，**基线自己也会 fail**（`verify_reviewer_claims.py` 可复现）：

| 运行 | overall | sustained_replay | steady_state | 生产期最大积压 | trend |
| --- | --- | --- | --- | ---: | --- |
| a1-baseline | not_tested | pass（200.69，比值 1.003） | pass | 420 | flat |
| b1-optimized | **fail** | pass（200.86，比值 1.004） | **fail** | 420 | growing |
| b2-optimized | **fail** | **fail**（199.32，比值 0.997） | pass | 440 | shrinking |
| a2-baseline | **fail** | **fail**（199.48，比值 0.997） | pass | 400 | flat |

原因（源码确认）：`sustained_replay` 是 `PASS if ratio >= 1.0 else FAIL`
（`validate_collector_ingest_capacity.py:436`），**没有容差**，199.32/200=0.997 即判失败；
`steady_state` 的趋势判据是"尾段比前段高 5% 且差值 > 设备数"（`acceptance.py:658`），
b1 与 a1 的**最大积压同为 420 帧**，却被判成 `growing`。

**因此**：这组 120 秒 A/B **只能看连续数值（忙碌比、commandstats、帧率、内存），
不能拿 pass/fail 当证据**，也不能因为 b1/b2 出现 fail 就认为改动有害。
§3 表格里的"无差异/贴噪声边"结论只依赖连续量，不受此影响。
（更长窗口下判据更稳：09-26 的 30 分钟长测里同一档位给出 `flat` + 守恒残差 0。）

## 4. Writer 是否存在独立瓶颈？

`scripts/diagnose_writer_tdengine_capability.py`：生产入口 `writer/main.py`（配置发现 + 多 consumer 分区 + TDengine 连接 +
`shutdown_flag` 停机）消费独立构造的、与生产同形的 Stream 积压。
**持续喂入用 XADD-only**（字段与生产逐字段一致，但不产生 receipt/latest/window 副作用）——
这是刻意的：历史 Lua 每帧约 2.4ms Redis 主线程，若用它喂入会**自己打满 Redis 并掩盖 Writer 能力**。
因此下表是 **Writer 侧上限**，不是端到端上限。1 个 consumer worker。

| offered | 点/秒 | 点/帧 | 跟得上？ | 喂入期最大积压 | 停喂后排空 | 实测质量行/秒 | 结果 |
| ---: | ---: | ---: | :---: | ---: | ---: | ---: | --- |
| 200 帧/秒 | 100k | 500 | ✅ | 59 帧 | 0.50s | 99,360 | 通过 |
| 400 帧/秒 | 200k | 500 | ✅ | 120 帧 | 0.50s | 198,720 | 通过 |
| **800 帧/秒** | **400k** | 500 | ✅ | 1,290 帧 | 0.50s | 397,440 | 通过 |
| 1000 帧/秒 | 500k | 500 | ❌ **积压增长** | 5,646 帧 | 5.51s | 496,614 | 未跟上 |
| 200 帧/秒 | 200k | 1000 | ✅ | 60 帧 | 0.50s | 199,360 | 通过 |
| 1000 帧/秒（喂入端只到 620） | 620k | 1000 | ❌ **积压增长** | 6,757 帧 | 13.53s | 618,228 | 未跟上 |

**结论**：Writer→TDengine 在单 consumer 下能稳定跟上 **≈400k 点/秒**（800 帧/秒 × 500 点），
在 **≈500k 点/秒** 明显掉队 → 能力边界在 400k～500k 点/秒之间。
**质量窄表不是当前的下一处瓶颈**：它在 618k 行/秒下仍被写入，未先于帧率掉队。
每条探针都通过了行数与抽样全字段对账（抽样比例写在结果里；不是全量点值正确）。

**覆盖差异（必须声明）**：自建最小同构 MySQL schema + 空 TDengine 库；输入不经
`collector.executor`；只有 1 个 consumer worker；持续探针 30–60 秒，不含长时间稳定性与故障注入。

## 5. 哪些内容可保留，哪些实验应撤销？

**保留**
* B1（脚本摘要）+ B2（分块 HMGET）：严格减少工作量、语义不变、回归全绿（附"端到端收益不可辨"的说明）。
* 两个诊断工具 + 证据：`scripts/diagnose_latest_duplication.py`、`scripts/diagnose_writer_tdengine_capability.py`。
* 设计文档 `docs/06-验证记录/2026-09/bounded-inflight-replay-design-20260927.md`（仅设计，未启用）。
* 新增回归用例：`collector/tests/test_collector_outbox.py` 的 NOSCRIPT 重载用例。

**撤销 / 更正（都在工具内，不涉及生产行为）**
* 第一版"消融场景"（按帧重算 stored_ts）→ 已改为整段取新/取旧 + 每档 HSET 次数自证。
* 持续模式 `keys` 未去重 → 积压被按设备数重复累加（20 设备 5×、100 设备 25×）→ 已去重，
  并用"同一 (device_type, group) 的设备共享 shard 键"的原因写在代码注释里。
* 持续模式的期望值沿用了固定积压模式的 `ticks` → 已改为按实际喂入量计算。
* 第一版"排空即通过"的判定在持续模式下会把"没跟上"报成 pass → 已加
  `kept_up_under_load` 判定（800 → pass，1000 → fail，已验证两种方向）。
* 固定积压阶梯（`writer-cap-t1..t4`）**不作为能力结论**：排空时间被 Writer 固定的
  ack/pending 周期（≈0.5–2s）主导，600 帧与 1200 帧都"2 秒排空"——这正是不能用排空时间当能力的原因。

判断依据（本轮实测）：

| 档位 | 一次确认往返 | 其中 Lua 执行 | 其中等待 | 2 批在途的理论空间 |
| --- | ---: | ---: | ---: | --- |
| 200 点/帧 | 967ms | ≈0.20s | ≈0.75s（等落盘） | 可接近 2× |
| 500 点/帧 | 1845ms | ≈1.70s | ≈0.15s | **几乎没有**（Redis 单线程 93% 忙，瓶颈是执行） |

设计要点（每条都在文档里给出理由）：唯一领取者 + 在途集合避免重复领取；
**每批独占一条连接**（`WAITAOF` 只确认执行它的那条连接写下的内容，不能假设被阻塞的连接还能执行后面的批次）；
未确认行继续留在 Outbox；允许批次间乱序清理但计数与删除同事务；
在途预算硬上限（**每批 ≤256 帧、在途 ≤2 批 ⇒ 并发 receipt gap ≤256 < 现有 1024 上限**，
这是把批大小从 4096 收敛的直接原因）；响应丢失/进程重启/Redis 重启/暂停关闭的超时与重试路径；
并列出 7 项故障测试与统一守恒判据。
**明确不承诺**：它不会提高 Redis 执行 Lua 的硬上限，也不预设 P99 目标。
前置条件：**先定目标帧宽**——帧宽未定就做，很可能押错方向。

## 7. 距离原目标还缺哪些证据？

目标：100 台 × 1000 点 × 100ms ≈ **1000 帧/秒、1M 点值/秒**（质量另算）。

1. **该规模从未被测过**：本轮 1000 点/帧的喂入端只到 **620 帧/秒**（620k 点/秒）——
   喂入端自身就受限，Write 侧边界也只测到 ~620k 点/秒。1M 点/秒需要更大的喂入能力
   （例如多进程喂入）或先解决上游 Redis 侧成本。
2. **多 consumer worker 扩展性未测**（本轮有效数据只有 1 worker）。
3. **"Redis 历史路径比 Writer 更早成为瓶颈"——较强假设（不再是纯推断），但仍需联合测量确认**：
   依据：同一帧宽（500 点/帧）下，Redis 侧在 200 帧/秒（=100k 点/秒）时单线程已 **93% 忙**、
   批次周期被拉到约 2 秒；而 Writer→TDengine 在 1 consumer 下能稳定跟上 **400k 点/秒**
   （800 帧/秒 × 500 点）且积压不增长，到 500k 点/秒才掉队 `[真实服务实测]`。
   即该负载只约等于 Writer 实测上限的 **1/4**。
   **两个保留项**：(a) 两侧不是同一次运行测的，Redis 侧数据来自 30 分钟长测、Writer 侧来自 30–60 秒探针；
   (b) 联合运行时 Writer 的读（XREADGROUP/Lua 内的映射读取）会给**同一个 Redis** 加负载，
   其实测上限会低于单独测量的 400k 点/秒。
   因此结论只能是"**很可能** Redis 先到瓶颈"，需一次"同一隔离环境同时跑采集回放 + Writer"的联合测量证实。
4. 额定规模长测（含 30% 余量）、故障矩阵（可靠移交/响应丢失/重启）、
   浏览器可见延迟、现场硬件验收：仍全部未完成。
5. AOF 成本在 A/B 中**未隔离测量**（共享实例 + 期间重写）。
6. 抽样范围：Task C 的逐列全字段核对只覆盖每设备 3 帧（其余只核对行数与身份），
   不得表述为"全部点值正确"；Task A 的微基准是单实例单键，未覆盖多设备并发竞争。
