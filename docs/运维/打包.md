**总体方案**

```
Docker 继续负责： MySQL / Redis / TDengine / Backend Windows 安装包负责： Data Watch Console app DataWatch Agent collector writer OPC DA proxy
```

**成功标准**
安装后应满足：

1. 桌面有 Data Watch Console。
2. Agent 作为 Windows 服务开机自启。
3. app 只调用 Agent，不直接启动任何进程。
4. app 点“启动 collector”时：
   - Agent 检测是否存在 opcda_center 设备；
   - 有则先启动 OpcDaProxyService.exe；
   - proxy 端口就绪后再启动 collector；
   - 无 OPC DA 则直接启动 collector。
5. app 点“启动 writer”时，Agent 启动 writer。
6. app 能看到 collector / writer 状态、日志、健康检查。

```
C:\Program Files\DataWatch\ ├─ app\ ├─ agent\ ├─ collector\ ├─ writer\ └─ sidecars\opcda_proxy_service\ C:\ProgramData\DataWatch\ ├─ agent\config.toml ├─ collector\config\settings.toml ├─ writer\config\settings.toml ├─ logs\ ├─ pids\ └─ runtime\
```

这一阶段只更新文档和配置约定。

------

**Phase 1：Agent 作为中枢补能力（修订版）**

这是整个方案的核心阶段，安装包只是把这里的能力打包起来。以下为最终施工依据。

**核心原则**

- app 只调用 Agent，不直接启动任何进程。
- Agent 用现有 `ProcessManager` 管 collector / writer（公开 `/admin/processes/{name}`）。
- Agent 新增 `SidecarManager` 管动态的 proxy（`proxy_9090` / `proxy_9091` …），**不暴露到公开 admin modules**。
- `ProcessManager` 与 `SidecarManager` 共用一个底层 `ManagedProcessRunner`（或同类工具类），复用进程监管内核：stdout/stderr 重定向到日志文件、PID 记录、存活/状态判断、terminate/kill 兜底、日志路径管理。**不要为 proxy 复刻一套裸 `subprocess.Popen`。**
- endpoint → port **粘性分配**，不轻易回收端口。
- proxy **差量**启动/停止，不无条件重建。

> 背景约束（务必牢记）：proxy 是 32 位 .NET 程序，建立 OPC DA 的 DCOM 连接是**最脆弱、最昂贵**的环节（Session 0 / 服务账户 / Identity 问题都卡在这里）。因此凡是"反复重连 OPC"的设计都要避免——能保持 proxy 在线就不要重启它。

**端口粘性分配规则**

- 已存在 endpoint：沿用旧端口（从旧 `port_mapping.json` 读）。
- 新增 endpoint：追加下一个可用端口（9090 起递增）。
- 已删除 endpoint：标记 stale，可停掉对应 proxy；**短期不回收其端口**，避免端口来回漂移。端口回收留到后续真有需要再单独做。
- 注意：现有 `collector/check_protocols.py` 每次从 9090 按 DB 查询顺序**重新分配**（line 123），是**不粘**的——Agent 重写映射生成时必须改为粘性，否则差量重启不成立。
  > **（002 已落地）** 粘性分配在 Agent 侧由 `agent/app/services/opcda_detect.py:assign_sticky_ports` 实现：已存在 endpoint 沿用旧端口、新端点取 `max(现有∪历史)+1`、stale 端点保留在 `port_mapping.json` 不回收。详见下方「002 实现落点」。

**Agent 启动时（认领已存活 proxy）**

Agent 自身是 Windows 服务，重启后内存态会丢，但 proxy 进程可能还活着。SidecarManager 启动时必须从 PID 文件重建注册表，否则会重复拉起、造成端口冲突：

```
1. 读取旧 port_mapping.json
2. 扫描 runtime pid 目录下的 proxy_*.pid
3. 用 pid + create_time 校验进程是否仍是原 proxy
4. 仍存活的 proxy → 加回 SidecarManager 注册表
5. 已死亡的 proxy → 清理 pid/state
（动态实例，靠枚举 pid 目录认领，不依赖硬编码模块名）
```

**启动 collector**

```
1. 检测当前 opcda_center endpoint 集合
2. 粘性更新 endpoint -> port 映射
3. 写 port_mapping.json
4. 对比现有 proxy 集合，只差量启动缺失 endpoint 的 proxy
   （并按需停止已删除 endpoint 的 proxy）
5. 等所有必需 proxy 的 TCP 端口 ready（见"两道 ready 闸门"），超时即失败
6. ready 全部通过后才启动 collector，显式传 --config / --port-mapping
7. collector 连接 OPC 失败时，日志/Agent 状态必须能定位 endpoint / proxy / serverProgId
```

> collector 当前从 `os.path.dirname(__file__)/../port_mapping.json`（`device/manager.py:22`）硬编码读映射，frozen 打包后该路径不可靠。**需给 collector 增加 `--port-mapping` / `COLLECTOR_PORT_MAPPING`**，由 Agent 显式传 `C:\ProgramData\DataWatch\runtime\opcda_proxy\port_mapping.json`。配置同理用 `--config` 显式传 `C:\ProgramData\DataWatch\collector\config\settings.toml`，不依赖工作目录。
> **（002 已落地）** `collector/main.py` 已加 `--port-mapping`（回退 env `COLLECTOR_PORT_MAPPING`）；`collector/device/manager.py:EndpointPortMapper(mapping_file=)` 为**权威只读模式**——只对自己拥有的 endpoint 查端口、缺失 fail-fast、忽略文件中多余 stale 项、绝不探测/分配/写回。Agent 经 extra_args 通道自动拼 `--config`/`--port-mapping`（见下方「002 实现落点」）。

**重启 collector（差量、幂等）**

只要 endpoint 集合没变，就保持 proxy 在线，只 bounce collector（重连一个已活着、DCOM 已建好的 proxy，更快更稳）：

```
1. 停 collector
2. 重新检测 endpoint 集合
3. 粘性更新 mapping
4. proxy 差量调整（仅对变化的 endpoint 动 proxy）
5. 等新增/仍需的 proxy ready
6. 启 collector
```

**停止 collector**

```
1. 停 collector
2. 按策略决定是否停 proxy：
   - 用户明确"停止模块" → 可以停 proxy
   - 仅"重启 collector" → 不无条件停 proxy
```

**两道 ready 错误闸门**

`127.0.0.1:{port}` 可连接只证明 proxy 的 TCP 监听起来了，**不代表 OPC DA/DCOM 已连通**（OPC 连接是 collector 发 `connect` 时才懒建立）。因此错误路径必须分两道：

- **Proxy 端口闸门**（proxy 启动后）：检查 proxy 是否监听本地端口；超时（如 10s）未 ready 则**不启动 collector**；错误带 `endpoint`、`port`、proxy 日志路径。
- **Collector 连接闸门**（collector 启动后）：真正连 OPC 时才暴露 DCOM / OPCEnum / ProgID / Identity 问题；这类错误必须在 collector 日志和 Agent 返回状态里可见，至少带 `endpoint`、`port`、`serverProgId`、`channel`、proxy 日志路径、collector 日志路径。

**待定项（非阻塞）**

- proxy **运行期崩溃**（非启动期）策略：暂定"仅上报、不自动重启"，是否让 SidecarManager 复用 health loop 做自动重启，留到 Phase 1.5 再定。

**Phase 1 硬验收**

1. Agent 检测 opcda_center → 生成粘性 mapping → 差量启动 proxy → 等端口 ready → 才起 collector，启动顺序不可颠倒。
2. Agent 服务重启后能认领仍存活的 proxy，不重复拉起、不端口冲突。
3. **在目标 Windows 服务账户上下文下，验证 proxy 能连通远程 OPC DA/DCOM**（成败级风险，必须本阶段验，不能等安装包做完）。
4. 安装包携带**已编译**的 `OpcDaProxyService.exe`，目标机只检查 .NET Framework 4.8 运行时（不依赖 csc.exe / .NET SDK）。

**002 实现落点与交叉引用（Phase 1 中枢能力已完成）**

特性分支 `002-agent-opcda-proxy`，权威文档 `specs/002-agent-opcda-proxy/`（spec/plan/tasks）。上面 Phase 1 描述的能力已实现，对应落点如下（设计→代码→测试）：

- **SidecarManager**（`agent/app/services/sidecar_manager.py`）—— 动态 proxy 编排核心，**不**进公开 `/admin/processes` modules：
  - `resolve_proxy_executable()`：按部署约定解析 `OpcDaProxyService.exe`（`sidecars/opcda_proxy_service/bin/` 优先，回退 `collector/sidecars/...`），缺失抛 `ProxyExecutableNotFound` 含全部候选路径。
  - `generate_proxy_config(port, vm_host)`：写 `runtime/opcda_proxy/proxy_{port}.json`（serverProgId/channel 由 factory 从 config 注入，默认 `ZPMC.OPCServer`/`OPD_Server`）。
  - `prepare_for_collector_start()`：检测→（有端点才）一致性校验→差量停删→粘性映射→差量起缺失 proxy→端口闸门，返回 `CollectorStartPlan(port_mapping_path, proxies)`；无 OPC DA 返回 `port_mapping_path=None`。
  - `claim_existing_proxies()`：Agent 重启认领仍存活 proxy（扫 `pids/proxy_*.pid` + pid/create_time 校验），死亡/stale 清记录、活着不可映射保留不杀。
  - `on_collector_stop()` / `_stop_removed()`：停止策略与差量删。
  - `proxy_log_snapshot()`：供 status 暴露日志路径。
  - 测试：`agent/tests/test_sidecar_manager.py`。

- **粘性 mapping + 检测 + 一致性**（`agent/app/services/opcda_detect.py`）：`detect_center_endpoints`（pymysql+DPAPI，与 health_checker 一致）、`assign_sticky_ports`（粘性、stale 保留不回收）、`load/save_port_mapping`（坏文件 fail-fast）、`verify_mysql_consistency`+`MysqlConsistencyError`（FR-P13）。测试：`agent/tests/test_opcda_detect.py`。

- **端口闸门（三条件）**：`SidecarManager.start_proxy()` —— spawn 后轮询直至①`127.0.0.1:{port}` 可连接 ②该端口 LISTEN 属主在 proxy 子树内 ③proxy 进程存活；超时/进程先退→整树回收+抛 `ProxyStartError`（含 endpoint/port/日志路径），**不启动 collector**、不漂移端口。admin 层 `prepare` 失败→`HTTPException(400)` 不启动。

- **collector 消费（权威只读端口映射）**：`collector/main.py --port-mapping`（回退 `COLLECTOR_PORT_MAPPING`）；`collector/device/manager.py:EndpointPortMapper(mapping_file=)` 权威只读。测试：`collector/tests/test_device_manager.py`。

- **连接可观测（非阻断）**：
  - collector 侧失败补定位字段：`collector/drivers/opcda_center_driver.py`（ConnectionError 含 serverProgId/endpoint/proxy_port）、`collector/core/opcda_ipc_client.py`（connect_opc_server 失败日志同字段）。channel 暂不塞（点位 ID 前缀、不在 connect 上下文）。测试：`collector/tests/test_opcda_center_driver.py`。
  - Agent status 暴露日志路径：`agent/app/schemas/models.py:ProxyLogItem` + `ModuleStatusResponse.log_path/proxy_logs`；`agent/app/routers/viewer.py` `GET /viewer/processes/{name}/metrics` 组合（仅 collector 有 proxy_logs）。只给路径、不读日志内容。测试：`agent/tests/test_viewer.py`。

- **停止策略（FR-P17）**：`SidecarManager.on_collector_stop()` 停全部 proxy+清表；`agent/app/routers/admin.py:stop_process` collector 分支接入（pm.stop→detach→on_collector_stop）；**重启不调用**（proxy 由 prepare 差量保留）。测试：`agent/tests/test_admin.py`。

- **编排接线**：`agent/app/routers/admin.py` `start_process`/`restart_process` 经 `_collector_extra_args` 共用 prepare+拼参（`--config`/`--port-mapping`，writer 不碰 sidecar）；`agent/app/services/process_manager.py` `start/restart(name, extra_args=)` 通道（不写回 config）；`agent/app/factory.py` lifespan `build_sidecar_manager` 挂 `app.state.sidecar_manager` + 启动认领。底层监管内核 `agent/app/services/managed_process_runner.py`（PID 读写/校验、spawn+日志重定向、terminate→kill）由 ProcessManager 与 SidecarManager 共用。

- **端到端验收**：`agent/tests/test_collector_start_e2e.py`（真实 admin→prepare→proxy 闸门→collector，验证 proxy 先 ready、--config/--port-mapping 透传）。
