## 2. 四问结论

1. **最高已验证可持续负载 = 30 设备 × 500 点 × 100ms = 300 帧/秒 = 150,000 点/秒**，
   已用 **30 分钟联合长测**验证（输入全程达标、0 拒收、积压不增长、Redis 主线程稳定 0.93）。
2. **第一档越界出现在 40 台（200k 点/秒）**，位置是**采集侧本地持久队列 + 历史交付路径**，
   不是 Writer/TDengine（其积压峰值仅 225 帧、CPU 0.376、0 失败）：
   40 台档 13 次提交失败 / 13 帧拒收、`OperationalError: database or disk is full`、
   排空 3.0s→62.8s、Redis 可见 p50 1.86s→50.1s。
   注：前三档"持续积压"判据（后半窗 > 前半窗×1.2 且 >200 帧）**均未触发**，积压均值全程持平。
3. **延迟在吞吐饱和之前很久就已超标**。历史路径 p50：753 → 1465 → 1861 →（长测）23,701 → 50,068 ms；
   TD 确认 1058 → 1669 → 2083 → 9155 → 41,862 ms；而 **latest 快车道全程 104–185 ms**。
   按"采样到 TD 完整确认 ≤ 1 个采样周期（100ms）"，**第一档就超标约 10 倍**；
   即使在"可持续"的 30 台档，历史路径也常年落后 ~24 s（p95 46 s）、排空 35.6 s。
   → **"吞吐可持续"不等于"延迟可接受"**：本次最高可持续档的 duable 路径延迟约为采样周期的 240 倍。
4. **下一步优先：Redis 单位成本 + 批次调度；Writer/TDengine 最后。**
   唯一线性逼近 1.0 的资源是 Redis 主线程（0.743/0.840/0.923/0.930/0.945）；
   Writer 侧在所有档位宽裕（CPU ≤0.38 核、0 失败、缓冲峰值 ≤225 行）；TD 确认延迟是**跟随**历史路径排队。
   历史路径成本集中在：每帧 2 次回执 HSET、**每点两遍 latest 读/解码/比较（写入只有一遍）**、
   每档 AOF 写入量大（40 台档 423 MB/250s）、批大小偏小（均值 13.6–15.6 帧）且每批都要 `WAITAOF`。〔⚠️ 适用路径：本条「每批都要 `WAITAOF`」指**已撤销的中心 Durable 方案**（`DurableRedisWriter`，`collector/storage/durable_redis_writer.py:467`）。现行中心式**不逐批 `WAITAOF`**；现行仅分布式 Ingest 保留同连接 `WAITAOF 1 0 2000` 门禁（`ingest/app/redis_store.py:365`）。本阶梯结论不得当作现行中心式性能结论。〕

## 3. 未测 / 边界（不得当作已完成）

* **40 台档的停止直接触发是采集侧本地队列写满（ENOSPC），同刻 Redis 主线程 0.945**。
  两者叠加，因此**不能**声称"Redis 单独在 200k 点/秒精确封顶"；ENOSPC 根因**未确认**
  （容器 `/tmp` 在 overlay 上、Docker VM 显示 899 GB 可用）。
* 40 台以上未测（按要求发现边界后不再加压）。上限位于 **150k–200k 点/秒之间**。
* 只有 1 个 consumer worker；单 Redis/TD/MySQL 实例；输入不经 `collector.executor` 的过滤；
  MySQL 为最小同构 schema（无 `system_log` 表，Writer 记一条无害告警）。
* 第 1–3 档缺 `fastlane_merge_ratio` / `batch_frames_mean` / AOF 窗口字节（补丁在其后加入），
  长测与基线档齐全。
* 本次**没有**测：30% 余量长测、故障矩阵、浏览器可见延迟、现场硬件。

## 4. 本轮修掉的测量缺陷（含我自己引入的一个）

1. **CPU 窗口错位**：`cpu_after` 原取在排空之后（分子含排空、分母只算喂入）→ 40 台档量出 >1 的 1.101；
   已改为**喂入结束**取样，`commandstats`/AOF 同理。
2. **`commandstats` 跨档累计**（`FLUSHDB` 不重置统计）→ 改为窗口内差值，否则每档数字不可比。
3. **异常打断整条阶梯**：提交失败（本地队列满）与对账异常（缺失子表）原本会让整轮/整条阶梯崩掉 →
   现在提交失败被**记录成边界**、对账缺失子表被**记录成 problem**，阶梯继续。
4. **我自己引入又撤回的**：〔适用路径：本条的 `outbox` 属**已撤销的中心 Durable 方案**；该条已自述「撤回」，仅作历史记录。〕为规避 40 台档 ENOSPC，把 outbox 改到**宿主 Windows 绑定挂载**，
   结果 SQLite 在 virtiofs 上把驱动拖到 46 fps（Redis 仅 0.19 忙）→ 那次长测与基线**全部作废并重跑**。
5. **对账期望基线取错字段**：原用"喂入结束"的确认数（525,069），应为"排空结束"（540,000），
   导致全部档被判 fail。**数据本身正确**（值行 = 排空后确认数、质量行 = 逐 tick 期望值），
   已修代码；但**无法事后复算**——每档测完即删库（保护 vnode）、Redis 逐档 flush，
   故更正只能由当时记录的原始数字推出，不是重跑结果。
